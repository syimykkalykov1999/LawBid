## Что это и зачем

Миграция — это небольшой файл с командами, который меняет устройство базы данных при выпуске новой версии (добавляет таблицу, колонку, индекс). При выкладке (Deploy в GitHub) миграции идут первым шагом. Если файл оборвался на середине — кончилось время (лимит 30 минут), не хватило места или задачу остановили руками, — база помечает его как «упавший» и **не пускает следующие миграции**, пока человек не скажет, что с ним делать. Это защита, а не поломка.

Важно: приложение в этот момент **продолжает работать на старой версии**. Новые сервисы выкатываются только после зелёной миграции. Паниковать не нужно.

Как узнать: в GitHub шаг «Migrations» красный, а в его логе есть `P3009`, `migrate found failed migrations` или `the migration ran longer than 1800s`.

## Что понадобится

- Доступ к GitHub (репозиторий LawBid → Actions) и к консоли AWS.
- Mac с проектом и входом в AWS, если вы делаете шаги сами. Обычно это делает Claude по просьбе «миграция упала», а вы только подтверждаете код 2FA.
- Денег не стоит.

## Шаги

1. **Не нажимайте Re-run** сразу. Сначала убедитесь, что задача остановлена: AWS Console → **ECS** → cluster `lawbid-prod` → вкладка **Tasks** → фильтр `lawbid-prod-migrate`. Если есть задача со статусом RUNNING — нажмите **Stop**. (Скрипт деплоя сам останавливает задачу через 30 минут и не запускает вторую, пока первая жива.)
2. Посмотрите состояние миграций (только чтение, ничего не меняет): в Терминале в папке проекта `scripts/deploy/prod-run.sh <тег> migrate-status`. Тег — это номер выпуска из названия запуска Deploy в GitHub. Команда покажет, какие миграции применены, какая упала и какие ждут.
3. Решите, что произошло с упавшей миграцией. Обычный файл выполняется «всё или ничего»: если оборвался — ничего не применилось, выбираем вариант «откатилась» (`rolled-back`). Файлы из папки `prisma/concurrent` (строят индексы на ходу) работают иначе: там недостроенный индекс нужно удалить и собрать заново — это делает Claude.
4. Пометьте миграцию одной из двух команд (скрипт попросит набрать имя миграции ещё раз для защиты от опечатки):
   - откатилась целиком: `scripts/deploy/prod-run.sh <тег> migrate-resolve <имя_миграции> rolled-back`
   - на самом деле применилась (все изменения уже видны в базе): `scripts/deploy/prod-run.sh <тег> migrate-resolve <имя_миграции> applied`
5. Запустите Deploy заново: GitHub → **Actions** → Deploy → **Run workflow** с тем же тегом. Миграция выполнится с нуля (если `rolled-back`) или будет пропущена (если `applied`), затем выкатятся сервисы.

## Если миграция просто долгая

Индекс на большой таблице строится минутами. Это не падение. Ждите до 30 минут — потом задача остановится сама. Если она не укладывается в 30 минут, такую операцию программисты должны переписать (порциями или через `prisma/concurrent`); напишите Claude.

## Если красный шаг пишет «schema check: the database differs»

С 27 октября 2026 после миграций база сверяется с ожидаемой схемой. Если они расходятся, выкладка останавливается до запуска новой версии, старая работает дальше. Чаще всего какая-то защищённая миграция пропустила работу, потому что таблица была занята. Это разбирает Claude: обычно нужно в тихое время выполнить одну команду в базе и перезапустить Deploy. В виде исключения проверку можно один раз ослабить переменной GitHub `SCHEMA_DRIFT_CHECK=warn` (**Settings → Secrets and variables → Actions → Variables**), после выкладки её удалить. Значение `off` не использовать.

## Как проверить

- В GitHub → Actions новый запуск Deploy зелёный целиком, шаг «Migrations» прошёл.
- В админке **Система → Здоровье системы** всё зелёное, в **Система → Запуск** строка о выкладке (пункт про Deploy) показывает свежую дату.
- Перед любым ручным вмешательством убедитесь, что есть свежий снимок базы: AWS → **RDS → Databases** → `lawbid-prod-postgres` → **Maintenance & backups** → Latest restore time должно быть недавним. Деплой с «сжимающими» миграциями делает снимок сам.

## Частые ошибки

- Нажали Re-run, не остановив задачу: две миграции одновременно. Скрипт не даст запустить вторую, пока первая жива, но лучше сначала проверить ECS.
- Пометили `applied`, хотя изменения в базе нет: следующая версия упадёт уже на реальной ошибке. Если не уверены, что успело примениться — всегда `rolled-back` для обычных миграций.
- Перепутали тег: берите его из названия того запуска Deploy, который упал.
- Долго не разбираетесь — приложение продолжает работать на старой версии, срочности нет. Но пока миграция не разобрана, ни одна новая версия не выкатится.
