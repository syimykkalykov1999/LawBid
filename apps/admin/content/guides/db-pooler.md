## Что это и зачем

База данных может держать ограниченное число одновременных соединений (у нашей сейчас 99). Каждый сервер приложения открывает свои, и когда серверов становится много под нагрузкой, база просто перестаёт пускать новых. Пулер — это два «диспетчера» между серверами и базой: сервера подключаются к ним, а они держат к базе не больше 69 соединений, сколько бы серверов ни было. Остальные 30 соединений зарезервированы под миграции, очистку по срокам хранения и демо-мир — им пулер не подходит.

В админке это карточка **«Пулер соединений (PgBouncer)»** на странице **Система → Масштаб**, а облачный выключатель `db_pooler_enabled` виден на **Система → Расходы**. Сам выключатель — строка `db_pooler_enabled` в файле настроек Terraform; применяет его Claude, вы решаете когда.

## Что понадобится

- Решение по времени: **после** перевода базы в Multi-AZ (воскресенье), отдельным вечером вне часов пик — не меняем два больших узла за раз.
- Один нагрузочный тест с включённым пулом перед продом (в тестовом окружении он включён по умолчанию).
- Claude с Mac и доступом к AWS, доступ в GitHub → Actions.

## Шаги

1. Код, Terraform и воркфлоу уже влиты в `main`: новый образ приложения без настройки пулера работает как раньше.
2. **Репозиторий образов.** Claude в папке `infra/bootstrap`: `terraform plan`, затем `terraform apply`. В плане должен быть только новый репозиторий `lawbid-pgbouncer` и его правило очистки.
3. **Собрать образ.** GitHub → **Actions → Build PgBouncer → Run workflow** (тег по умолчанию `1.24.0-1`). Внизу страницы запуска — строка `pgbouncer_image = "...lawbid-pgbouncer:1.24.0-1"` и подтверждение, что есть сборки для двух типов процессоров.
4. **Настройки прода.** Claude добавляет в `infra/envs/prod/terraform.tfvars`: `db_pooler_enabled = true`, `pgbouncer_image` (строка из шага 3), `pgbouncer_max_tasks = 3`.
5. **Посмотреть план** (`terraform plan`). Ожидается: проверка бюджета соединений проходит; создаются внутреннее имя `lawbid-prod.internal`, сервис пула, правила доступа, 5 тревог, автомасштабирование; у серверов api и worker меняются настройки (добавлен адрес пула). **Ничего не удаляется.** Если план другой — не применять.
6. **Сначала только пул:** `terraform apply -target='module.stack.module.pgbouncer'`. Подождать 3-5 минут, проверить пункты 1-3 раздела «Как проверить».
7. **Потом всё остальное:** `terraform apply`. Сервера api и worker перезапустятся по очереди уже через пул.
8. 30 минут наблюдения, затем ночь без вмешательства.

## Как проверить

1. AWS → **ECS** → кластер `lawbid-prod` → сервис `pgbouncer`: 2 из 2 задач Running.
2. AWS → **Cloud Map → Namespaces** → `lawbid-prod.internal` → сервис `pgbouncer`: 2 экземпляра Healthy.
3. **CloudWatch → Log groups** → `/lawbid/lawbid-prod/pgbouncer`: строка `process up: PgBouncer 1.24.0` и раз в 30 секунд строка с числами соединений.
4. **Главное.** AWS → **RDS** → база → **Monitoring** → `DatabaseConnections`: не больше ~69 и ровнее, чем раньше. В **CloudWatch → Metrics → LawBid/lawbid-prod/PgBouncer**: `ServerConnections` ≤ 23 на задачу, `ClientsWaiting` и `MaxWaitSeconds` около нуля.
5. В админке **Система → Здоровье системы** всё зелёное; на **Система → Масштаб** карточка «Пулер соединений (PgBouncer)» показывает две живые задачи; пробный вход пользователя проходит.
6. В логах api нет ошибок `prepared statement ... does not exist`, `query_wait_timeout`, `P1017`.

## Частые ошибки

- Тревога `pgbouncer-waiting` или `pgbouncer-max-wait`: запросы стоят в очереди за соединением — нагрузка или медленная база. Решение: база на размер больше (через админку), смотреть медленные запросы.
- Тревога `pgbouncer-server-connections`: пул у предела. Не поднимать `pgbouncer_max_tasks` без понимания — он делит общий бюджет базы.
- Тревога `pgbouncer-no-healthy` (нет живых задач пула, приложение без базы): **аварийный откат за 2 минуты** — AWS Console → **ECS** → сервис `api` (и `worker`) → **Update service** → предыдущая ревизия задачи (без адреса пула) → **Force new deployment**. Потом разбор по логу.
- Тревога `pgbouncer-unhealthy` (одна из двух задач 10 минут не работает): подождать, ECS пересоздаст сам; если повторяется — смотреть лог.
- Ошибки Prisma `P1017` или `prepared statement`: Claude ставит переменную `DB_POOLER_QUERY=pgbouncer=true` для api/worker и повторяет.
- Обычный откат (5-10 минут): `db_pooler_enabled = false` и одновременно понизить потолки `api_max_tasks = 10`, `worker_max_tasks = 4` (иначе проверка бюджета соединений не пройдёт), затем `terraform plan` и `apply`. Расходы на пул прекращаются.
- Короткие (10-30 секунд) ошибки подключения в момент пересоздания или масштабирования пула допустимы — это цена внутреннего имени вместо балансировщика. Если их много — обсудить переход на балансировщик.
