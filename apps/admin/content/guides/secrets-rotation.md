## Что это и зачем

У приложения есть несколько «паролей»: пароль к базе данных, токен к быстрой памяти Redis и три списка ключей шифрования (для входов в приложение, для чатов и для хранилища «Ключи и сервисы»). Если такой пароль утечёт, им можно пользоваться годами, пока его не сменят. Ротация это регулярная замена: пароль базы раз в 30 дней, остальное раз в 90.

Замена безопасная: новый секрет сначала добавляется рядом со старым, старый ещё работает. Приложение перезапускается по одному серверу (как при обычной выкладке), пользователи ничего не замечают. Новый ключ шифрования начинает работать через 6 часов после добавления, старые остаются, пока нужны: ключи входов 2 дня, ключи чатов и сервисов до перешифровки.

По умолчанию всё выключено. Включается по частям, в порядке от самой безопасной к самой сложной: ключи приложения, потом Redis, потом база.

## Что понадобится

- Claude готовит изменения Terraform, вы подтверждаете `apply` (инструкция «Terraform plan и apply через наши скрипты»).
- Для части «База»: мастер-пароль базы в Secrets Manager. Проще всего в AWS Console → RDS → база → **Modify** → включить **Manage master credentials in AWS Secrets Manager** (без остановки).
- Между частями пауза: убедитесь, что сайт и приложение живы, прежде чем включать следующую.

## Шаги

1. **Ключи приложения** (самое безопасное). Claude ставит `secret_rotation = { keys_enabled = true }` в настройках прода. В плане: 3 новых секрета `*_ACTIVE_KID`, две функции (rotator и ops), расписание, 2 тревоги. Серверы перезапустятся один раз при apply. Первая замена через 90 дней.
2. Проверьте, что сайт работает, подождите хотя бы день.
3. **Redis**. Claude добавляет `redis_enabled = true`. План не должен менять сам Redis, только отдать управление токеном функции ротации. Через 24 часа после каждой замены приходит письмо «старый токен отключён».
4. **База**. Сначала мастер-пароль в Secrets Manager (см. выше). Claude добавляет `db_enabled = true` и ссылку на мастер-секрет. После apply один раз заполняется стартовый пароль командой `aws lambda invoke --function-name lawbid-prod-secret-rotation-ops --payload '{"mode":"bootstrap-db"}' --cli-binary-format raw-in-base64-out /dev/stdout` (пароль в чат и на экран не попадает).
5. Принудительная проверка любой части, не дожидаясь расписания: `aws secretsmanager rotate-secret --secret-id lawbid-prod/JWT_KEYS`, затем `aws secretsmanager describe-secret --secret-id lawbid-prod/JWT_KEYS --query '{last:LastRotatedDate,next:NextRotationDate}'`. Во время замены адрес `/health/ready` должен оставаться зелёным.
6. Старые ключи чатов и «Ключей и сервисов» убираются только когда **Здоровье системы → Ключи сообщений** пишет, что старые ключи больше не нужны, а в «Ключах и сервисах» нажата **Перешифровать**. Команду удаления готовит Claude; активный и самый новый ключ функция удалить откажется.

## Как проверить

- **Система → Здоровье системы** → строка «Смена паролей и ключей» зелёная, в ней дата последней и следующей замены.
- У секрета в AWS появилась дата `LastRotatedDate`.
- Нет писем с тревогой `lawbid-prod-secret-rotation-problems`.
- Пользователи не разлогинились, чаты открываются, вход работает.

## Частые ошибки

- Пришло письмо `secret-rotation-problems`: замена сорвалась или просрочена. Приложение продолжает работать на текущих секретах: замена ничего не ломает, пока не завершена. Напишите Claude, он посмотрит журнал функции и повторит шаг.
- Выключили `keys_enabled` после первой замены: так нельзя без разбора, серверы могут не запуститься (старые номера ключей вернутся в настройки). Сначала Claude приводит номера активных ключей к текущим.
- Включили «База» на проде, не проверив на копии: второй пользователь базы `lawbid_app_clone` создаётся при первой замене; проверка на staging обязательна.
- Redis «modifying» в момент замены: функция повторит сама, писать никому не нужно.
- Ротация не касается пользователей миграций и хранения (`MIGRATOR_DATABASE_URL`, `RETENTION_DATABASE_URL`): их меняют руками по отдельной инструкции.
