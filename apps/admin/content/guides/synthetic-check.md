## Что это и зачем

Робот-пользователь - скрипт `scripts/ops/synthetic-check.mjs`, который ходит на боевой сервер как человек: после каждой выкладки и каждые 5 минут (чаще GitHub не умеет). Он проверяет:

- сервер отвечает и показывает правильную версию (`/health/ready`);
- настройки приложения отдаются (`/api/v1/config/bootstrap`);
- вход с заведомо неверным номером возвращает аккуратную ошибку 400, а не 5xx (сбой сервера);
- если заведён тестовый аккаунт: вход, запрос под токеном, рукопожатие Socket.IO (живые события чатов) на `/realtime`, выход.

Так вы узнаёте о поломке раньше пользователей, даже если тревоги AWS молчат. Чего пока нет: создание тестового дела и сообщение «эхо» - для этого нужна тестовая организация, невидимая настоящим пользователям.

## Что понадобится

- Доступ к репозиторию GitHub (вкладка **Actions**).
- Для полной проверки: отдельный тестовый аккаунт с паролем (не живой человек). Его логин и пароль кладутся в секреты репозитория `SYNTHETIC_IDENTIFIER` и `SYNTHETIC_PASSWORD` (**Settings → Secrets and variables → Actions → New repository secret**). Пароль в чат и в файлы не писать.

## Шаги

**Включить полную проверку (один раз)**

1. Создайте в приложении тестовый аккаунт с паролем. Не используйте свой личный.
2. GitHub → репозиторий → **Settings → Secrets and variables → Actions → New repository secret**: `SYNTHETIC_IDENTIFIER` и `SYNTHETIC_PASSWORD`.
3. Запустите проверку руками: **Actions → Synthetic check → Run workflow**. Через 1-2 минуты запуск должен быть зелёным.

**Пришла тревога**

4. Тревога приходит как issue с заголовком `[ci-alert:synthetic]` и письмом (если настроен `AWS_NOTIFY_ROLE`).
5. Откройте **Actions → Synthetic check** → последний запуск и посмотрите, какой шаг красный:
   - версия не та - выкладка ещё не закончилась (Deploy / ECS); подождите 10 минут и проверьте снова;
   - 5xx - сбой сервера, смотрите **Здоровье системы** и инструкцию по проверке после выкладки, при повторе откат;
   - сокет - проблема с живыми событиями (Redis, воркер); **Здоровье системы** → строки Redis и очереди;
   - вход тестовым аккаунтом - проверьте, что аккаунт не удалён и пароль в секретах актуален.
6. Если один запуск красный, а следующий через 5 минут зелёный - это был короткий перебой, записывать не нужно.

**Следующий уровень (по желанию)**

7. CloudWatch Synthetics canary в AWS (≈ $1-3 в месяц) делает то же изнутри AWS и шлёт тревогу в `lawbid-prod-alerts`. Включается в tfvars (инструкция slo-alarms, раздел про uptime canary).

## Как проверить

- **Actions → Synthetic check**: последние запуски зелёные, идут каждые 5 минут.
- Открытых issue `[ci-alert:synthetic]` нет.
- На **Здоровье системы** строка состояния сервера зелёная и версия совпадает с последней выкладкой.

## Частые ошибки

- Тестовый аккаунт удалён или заблокирован модерацией: проверка краснеет на входе, хотя сервер здоров. Заведите аккаунт заново и обновите секреты.
- Положили в секреты свой личный пароль: робот входит под вами каждые 5 минут и сбивает устройство. Только отдельный аккаунт.
- Тревога пришла сразу после выкладки: почти всегда «версия не та», подождите окончания Deploy.
- Ждёте проверку чаще 5 минут: GitHub не умеет; для минутной частоты нужен CloudWatch canary.
