# Новые кейсы адвокатам: волны, порядок, честность (2026-10-25)

## Коротко для владельца (5 строк)

1. Пуш о новом кейсе теперь идёт не «всем подряд без порядка», а по оценке: подходящая практика и штат, уровень доверия, рейтинг, скорость и доля принятых предложений, и меньше тем, кто уже получил много пушей сегодня.
2. Пуши можно слать волнами: первые N лучших сразу, дальше каждые X минут, пока не наберётся K предложений или не охвачены все. Часть мест в каждой волне (до 20 %) занимают новые адвокаты.
3. Можно ограничить число пушей одному адвокату в сутки: остальное сворачивается в одну итоговую строку в уведомлениях, без нового пуша.
4. Кейс клиента «на проверке» или с ограничениями: пуши не идут вообще или идёт малая отложенная волна (настройка). Сейчас по умолчанию: «на проверке» — как обычно, «ограничен» — без пушей.
5. Все настройки в админке (`case_fanout.*`). По умолчанию охват как сегодня: одна волна на 5000 человек, без суточного лимита; включать волны и лимит вы решаете сами. Рекомендуемый старт: первая волна 100, потом по 100 каждые 10 минут, стоп на 8 предложениях, лимит 5 пушей в сутки.

## Как это устроено

- `SubscriptionAlertsService.attorneysForCase` → `CaseFanoutService.start(caseId)` ставит задачу BullMQ в очередь `case-fanout` (волна 1; для «малой» волны подозрительного клиента — с задержкой).
- Каждая волна — отдельная задача `casefanout-<caseId>-w<N>` (идемпотентно по id). Воркер (API при `JOBS_ENABLED` и процесс worker) запускает её в шард-контексте кейса (`shardKeyOf.case`, то есть `forCase`).
- Волна: кейс ещё открыт и не на паузе → проверка антифрода клиента → стоп, если предложений уже `stop_at_bids` → аудитория (`CaseAudienceService`: тот же отбор, что был: выбранные практики, проверенная лицензия в штате кейса, «Новые кейсы» включены, не заблокированные, «только срочные») → убрать уже оповещённых (строка уведомления с ключом `case_fanout:<caseId>`) → оценка → выбор волны с квотой для новых → `emitMany` пачками по 500 → следующая волна через `wave_interval_minutes`.
- Повтор задачи ничего не шлёт дважды: у строки уведомления уникальный ключ (user, `case_fanout:<caseId>`), уже оповещённые отфильтровываются.
- Без Redis (тесты, dev) все получают пуш сразу (волны невозможны).

## Оценка (`case-fanout.scoring.ts`)

Веса, сумма 1: практика кейса 0.22, штат кейса 0.10, уровень доверия 0.14, рейтинг со сглаживанием (байес) 0.16, скорость ответа 0.14 (среднее время от кейса до предложения за 180 дней), доля принятых предложений 0.10 (со сглаживанием), нагрузка 0.14 (чем больше пушей о кейсах за 24 часа, тем ниже).
Расстояние: в данных нет координат адвоката, поэтому «штат кейса» = лицензия именно в основном штате. Равные оценки разбираются стабильным хешем кейса, чтобы одни и те же люди не были всегда первыми.

## Новые адвокаты

Новый = получил меньше `new_max_alerts` пушей о кейсах за 30 дней и сделал меньше `new_max_bids` предложений. В каждой волне до `new_quota_percent` % мест отдано новым, сначала тем, кто получил меньше всего пушей (бонус убывает с числом полученных пушей, а не со временем). Если новых меньше, места получают лучшие из остальных.

## Суточный лимит

`daily_cap` пушей о новых кейсах за скользящие 24 часа. Сверх лимита человек получает одну итоговую строку в сутки (`aggregate_count` растёт, пуш был только один), в первой волне. Кейс остаётся в его ленте и поиске.

## Антифрод клиента

Статус из `client_fraud_profiles`: `review` → `fraud_review_action`, `restricted` → `fraud_restricted_action`, `banned` → без пушей. Значения: `normal` / `small` (одна малая волна `fraud_small_wave_size` через `fraud_delay_minutes`, без продолжения; статус перечитывается при запуске) / `none`.

## Метрики (структурные логи, поле `metric`)

- `case_fanout_wave`: кейс, волна, размер аудитории, отправлено, свёрнуто, `newReached`, `newShare` (доля новых среди охваченных), осталось.
- `case_first_bid`: секунды от публикации кейса до первого предложения (пишется волной, которая увидела первое предложение; после последней волны не пишется).
- Очередь `case-fanout` входит в `OBSERVED_QUEUES` (глубина и возраст самой старой задачи).

## Эксперименты (ALG-A)

Ветка `claude/experiments` на момент PR не влита. Хук готов: провайдер `CASE_FANOUT_IMPRESSIONS` (интерфейс `CaseFanoutImpressionSink`) получает `caseId`, номер волны, адвокатов и их оценки в каждой волне. Когда API экспериментов будет в main, достаточно привязать реализацию.

## Настройки (`case_fanout.*`, по умолчанию охват как сегодня)

`enabled` false (выключено по умолчанию: пуш всем сразу и синхронно, как раньше); `first_wave_size` 5000; `wave_size` 5000; `wave_interval_minutes` 10; `max_waves` 20; `stop_at_bids` 0 (выкл.); `new_quota_percent` 20; `new_max_alerts` 20; `new_max_bids` 3; `daily_cap` 0 (выкл.); `fraud_review_action` normal; `fraud_restricted_action` none; `fraud_small_wave_size` 10; `fraud_delay_minutes` 60. `enabled=false` возвращает старое поведение (всем сразу, без лимитов и антифрода). Волна 1 при этом идёт сразу в самом запросе API (не через очередь `case-fanout`), только без ранжирования и запросов статистики (проверка 2026-10-26, R-32); без Redis (тесты, разработка) — так же сразу в запросе. Очередь используется только при `enabled=true`.
