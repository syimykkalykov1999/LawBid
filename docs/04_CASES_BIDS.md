## 1. Обзор процесса

```
Клиент создает кейс ──► кейс виден адвокатам с лицензией в штате кейса и подходящей практикой
        │
        ▼
Адвокаты (верифицированы + активная подписка/триал) отправляют биды (неограниченно)
        │
        ▼
Клиент смотрит биды: принять / отклонить / встречное предложение (торг, до 5 раундов)
        │
        ▼
Клиент принимает один бид ──► остальные биды автоматически отклоняются
        │                       кейс: in_progress, открывается чат, адвокату выдаются контакты клиента
        ▼
Клиент нажимает «Выполнено» ──► адвокат подтверждает (или оспаривает) ──► кейс closed
```

Ключевые принципы:
- Платформа не участвует в оплате гонорара и не берёт комиссию. Гонорар клиент платит адвокату вне приложения.
- Адвокат до принятия бида не видит имя и контакты клиента. Контакты выдаются автоматически только после принятия бида этого адвоката и только при активной подписке/триале.
- Каждое значимое действие по кейсу пишется в неизменяемый журнал `case_journal` (хранение 5 лет).

## 2. Доступ к действиям (матрица прав)

| Действие | Кто | Условия |
|---|---|---|
| Создать кейс | клиент | подтверждены телефон и email (`CLIENT_CONTACTS_INCOMPLETE`), онбординг завершён, аккаунт `active` |
| Видеть открытые кейсы (список, детали) | адвокат | `verification_status = verified`, есть лицензия `verified` в штате кейса, практика кейса выбрана адвокатом |
| Отправить бид | адвокат | те же + **активная подписка или триал** (`SUBSCRIPTION_REQUIRED`) |
| Написать клиенту по кейсу (открыть чат) | адвокат | те же + **активная подписка или триал** |
| Видеть контакты клиента | адвокат | бид принят **и** подписка/триал активны на момент выдачи |
| Принять/отклонить/встречное по биду | клиент | владелец кейса, кейс `open`, бид `active`, его ход |
| Ответить на встречное предложение | адвокат | автор бида, бид `active`, его ход |
| Отозвать бид | адвокат | автор бида, бид `active` |

Без активной подписки/триала верифицированный адвокат видит список и детали кейсов (тема, штат, город, описание, бюджет, счётчики), но кнопка «Сделать бид» и «Написать клиенту» ведёт на экран подписки (файл 6).

**Если подписка адвоката перестала быть активной** (не оплачена, отменена, истёк триал), сервис подписок (файл 6) вызывает `BidsService.withdrawActiveBidsForAttorney(attorneyId)`: все его бид в статусе `active` переходят в `withdrawn`, клиенты получают уведомление. Кейсы в работе (`in_progress`) остаются, а контакты клиента для этого адвоката блокируются до возобновления подписки (раздел 8.3).

## 3. Создание кейса (клиент)

### 3.1 Шаги мастера (Flutter, экран открывается с «+»)
1. **Практика:** выбор категории → специализации (поиск по названию, справочник из файла 2). Если клиент не знает, выбирает `General Practice → Not Sure or Other`.
2. **Суть:** заголовок и описание.
3. **Место:** основной штат (по умолчанию штат из профиля клиента), город (текст), до 2 дополнительных штатов («Добавить ещё штат»).
4. **Бюджет:** переключатель «Указать сумму» или «Уточню позже» (`clarify_later`). Сумма вводится в долларах.
5. **Проверка и публикация:** сводка, дисклеймер «LawBid не является юридической фирмой и не оказывает юридических услуг», для первого кейса отдельная галочка согласия `client_contact_sharing` («Я согласен, что мои контакты будут переданы адвокату, чей бид я приму»). Кнопка «Опубликовать».

Черновик хранится только локально (drift) до публикации; серверных черновиков нет (в `case_status` нет статуса `draft`). При закрытии мастера приложение предлагает сохранить черновик.

### 3.2 Поля и валидация
| Поле | Правила |
|---|---|
| title | 10-120 символов |
| description | 30-5000 символов |
| practice_area_id | активная специализация (лист дерева) |
| primary_state_code | штат из справочника (50 + DC) |
| additional states | 0-2 других штата, без повторов; итого не более 3 штатов на кейс |
| city | до 80 символов, необязательно |
| budget | `amount`: целое число долларов, от $1 до $10 000 000, хранится в центах; либо `clarify_later` |

### 3.3 Защита от обхода платформы
Сервер проверяет `title`, `description` и `city` на телефоны, email и ссылки (регулярные выражения + нормализация цифр и слов, например «пять пять пять»). При обнаружении возвращается ошибка `CASE_CONTAINS_CONTACT_INFO` с текстом «Не указывайте контакты в описании: они автоматически передаются выбранному адвокату». Кейс не сохраняется.

### 3.4 Публикация
`POST /cases` (с `Idempotency-Key`) в одной транзакции: создаёт `cases` (`status = open`, `last_activity_at = now()`), `case_states` (основной + дополнительные), запись `case_journal` (`created`), записывает согласие `client_contact_sharing` при необходимости. Push-уведомлений адвокатам о новых кейсах нет: кейсы просто появляются в их вкладке «Кейсы».

### 3.5 Редактирование и удаление клиентом
- Клиент может менять `title`, `description`, `city`, `budget` пока кейс `open` (с той же валидацией 3.2 и 3.3).
- `practice_area_id` и штаты можно менять только если `bids_count = 0`.
- Если у кейса уже есть биды, после изменения все адвокаты с активными бидами получают уведомление «Кейс обновлён» (тип `case_updated`, добавляется в enum `notification_type`, раздел 14).
- Каждое изменение пишется в `case_journal` (`updated`, в `payload` старое и новое значение изменённых полей).
- **Закрыть кейс** (клиент решил не продолжать без выбора бида): статус `closed`, все `active` биды → `rejected_auto`, событие `closed`. Открыть заново нельзя.
- **Удалить кейс:** только пока статус `open` или `archived`; `deleted_at = now()`, активные биды → `rejected_auto`, адвокаты получают уведомление `bid_rejected`. Событие `deleted` в журнале, физически данные остаются. Кейсы `in_progress`, `pending_completion`, `disputed`, `closed` удалить нельзя.

## 4. Показ кейсов адвокатам

### 4.1 Правило видимости
Кейс попадает в список адвоката, если одновременно:
1. `cases.status = 'open'` и `deleted_at IS NULL`;
2. у адвоката есть `attorney_licenses` со `license_status = 'verified'` хотя бы в одном штате из `case_states` кейса;
3. `practice_area_id` кейса входит в `attorney_practice_areas` адвоката;
   - исключение для кейсов с `general_practice.not_sure_or_other`: их видят адвокаты с лицензией в штате кейса, выбравшие специализацию `General Practice` (`general_practice.general_practice`) либо `Not Sure or Other`.

Запрос должен использовать индексы из файла 2 (раздел 5.2 и 5.4), полный скан `cases` не допускается (проверяется `EXPLAIN` в тесте).

### 4.2 Вкладка «Кейсы» (Лента → Кейсы, только адвокат)
- Список карточек от новых к старым, cursor-пагинация (`?cursor=&limit=`).
- Фильтры: практика (из своих выбранных), штат (из своих лицензий). Сортировка: сначала новые.
- **Карточка кейса:** цветная шапка с названием категории, метка **NEW** (кейс младше 24 часов), заголовок, «город, штат» (если штатов несколько, основной + «+N»), статус «Open», просмотры, число бидов, бюджет (`$600`) или «Clarify Later». Если адвокат уже сделал бид: метка «Вы сделали бид».
- Тап открывает детали кейса.
- Состояния: loading (skeleton), empty («Пока нет подходящих кейсов»; если у адвоката не выбраны практики: призыв выбрать практики; если нет подтверждённых лицензий: призыв пройти верификацию), error, offline, pagination.

### 4.3 Детали кейса для адвоката
Показывается: категория и специализация, заголовок, описание, штат(ы) и город, бюджет, дата публикации, число просмотров и бидов, кнопки «Сохранить» (в «Сохранённое», `saved_items` тип `case`), «Сделать бид», «Написать клиенту». **Не показывается:** имя, фото, телефон, email клиента (ни до, ни после отправки бида; только после принятия бида, раздел 8).
- Счётчик просмотров: +1 не чаще раза на пару (адвокат, кейс), дедупликация в Redis, запись в БД пакетно воркером.
- Если адвокат уже сделал бид на этот кейс, вместо кнопки «Сделать бид» показывается карточка его бида со статусом и действиями.

## 5. Бид

### 5.1 Поля бида (адвокат выбирает сам, что отправить)
| Поле | Правила |
|---|---|
| fee_type | `fixed` (фиксированная сумма), `hourly` (почасовая ставка), `free_consultation` (бесплатная консультация) |
| amount | для `fixed` и `hourly`: > 0, до $10 000 000 (в центах); для `free_consultation`: 0, поле скрыто |
| message | обязательно, 20-2000 символов |
| start_availability | `immediately` («Могу начать сразу»), `within_week`, `custom_date` (+ `start_date`, не в прошлом) |
| estimated_duration_days | необязательно, 1-3650 |

- Один бид от одного адвоката на один кейс (UQ `case_id + attorney_id`). После `withdrawn` повторный бид на этот же кейс невозможен.
- Количество бидов на кейс не ограничено.
- Создание: `POST /cases/:caseId/bids` (`Idempotency-Key`). В одной транзакции: проверка прав (раздел 2), `bids` (`status = active`, `round_count = 0`, `turn = client`), `bid_offers` (`round_no = 0`, `from_role = attorney`, `status = pending`), `cases.bids_count + 1`, `cases.last_activity_at = now()`, журнал `bid_placed`. После коммита: уведомление клиенту `bid_received`.

### 5.2 Что видит клиент
На экране кейса (в «Моё») список бидов: карточка = фото, имя, синяя галочка, рейтинг и число отзывов, тип и сумма (или «Бесплатная консультация»), начало работы, первые строки сообщения, статус торга («Ваш ход» / «Ожидает адвоката»), счётчик раундов. Сортировка: новые / самая низкая цена / высший рейтинг. Тап на фото или имя открывает публичный профиль адвоката (файл 3). Тап на карточку открывает детали бида: полное сообщение и **история торга** (все предложения по раундам).

### 5.3 Отзыв предложения адвокатом (withdraw)
`POST /bids/:id/withdraw`: доступен, пока бид `active`. Статус `withdrawn`, событие `bid_withdrawn`, `bids_count` не уменьшается (счётчик считает все поданные биды), клиент получает уведомление.

## 6. Торг (встречные предложения)

### 6.1 Правила
- Исходное предложение адвоката = раунд 0. Далее стороны обмениваются **встречными предложениями**; каждое встречное предложение увеличивает `round_count` на 1. Максимум **5** встречных предложений на один бид (`round_count ≤ 5`).
- Ходят по очереди, поле `bids.turn` показывает, чья очередь. Действия доступны только стороне, чей ход.
- **Клиент** на предложение адвоката может: принять, отклонить, сделать встречное предложение (новая сумма, сообщение до 500 символов необязательно).
- **Адвокат** на встречное предложение клиента может: принять, сделать своё встречное (новая сумма), отозвать бид.
- Тип оплаты в торге не меняется, торгуется сумма. Для `free_consultation` встречные предложения недоступны (только принять или отклонить).
- Встречное предложение клиента **обязывающее**: если адвокат его примет, бид принят и кейс переходит в работу. Перед отправкой клиент видит предупреждение «Если адвокат согласится, кейс перейдёт в работу, остальные предложения будут отклонены».
- Клиент может торговаться с несколькими адвокатами одновременно, по каждому биду отдельно. Как только принят любой бид, все остальные автоматически отклоняются (раздел 7).
- Текущие условия бида (`bids.amount_cents`, `bids.fee_type`) всегда равны последнему предложению; вся история в `bid_offers`.

### 6.2 Завершение торга без согласия
После **5-го встречного предложения** сторона, получившая его, может только принять или отклонить. Если она **отклоняет** (клиент «Отклонить» или адвокат «Отозвать»), бид переходит в `failed_negotiation`. Обе стороны получают уведомление `negotiation_failed` и системную запись в истории бида: **«Стороны не договорились»**. Клиент может продолжать работу с другими бидами, новый бид от этого адвоката на этот кейс невозможен.
Если на предыдущих раундах клиент отклоняет бид: `rejected_by_client`; адвокат отзывает: `withdrawn` (уведомление «Клиент отклонил предложение» / «Адвокат отозвал предложение»).

### 6.3 Операции и переходы
| Операция | Кто | Из состояния | Результат |
|---|---|---|---|
| `POST /bids/:id/counter` `{amountCents, message?}` | клиент или адвокат (чей ход) | `active`, `round_count < 5` | новая запись `bid_offers`, `round_count + 1`, `turn` переключается, предыдущее pending-предложение → `countered`, уведомление `offer_countered`, журнал `offer_made` |
| `POST /bids/:id/accept` | клиент (принять предложение адвоката) или адвокат (принять встречное клиента) | `active`, его ход | принятие (раздел 7) |
| `POST /bids/:id/decline` | клиент | `active` | `rejected_by_client` (или `failed_negotiation`, если `round_count = 5` и его ход) |
| `POST /bids/:id/withdraw` | адвокат | `active` | `withdrawn` (или `failed_negotiation`, если `round_count = 5` и его ход) |

Все операции идемпотентны (`Idempotency-Key`), выполняются в транзакции с `SELECT ... FOR UPDATE` по бид-строке; повторный запрос после смены хода возвращает `BID_NOT_YOUR_TURN` (`409`), недопустимое состояние: `BID_INVALID_STATE` (`409`).

## 7. Принятие бида (критичная транзакция)

`POST /bids/:id/accept` выполняется **одной транзакцией** через `withTxRetry()`:

1. `SELECT ... FOR UPDATE` строки `cases` и строки `bids`.
2. Проверки: кейс `open` и не удалён; бид `active`; вызывающий имеет право принять (раздел 6.3, его ход); адвокат бида `verified`, его лицензия в штате кейса всё ещё `verified`, подписка/триал активны на момент принятия (иначе `BID_ATTORNEY_INACTIVE`, бид переводится в `withdrawn`, клиенту показывается «Этот адвокат недоступен, выберите другой бид»).
3. Текущее pending-предложение → `accepted`. `bids.status = accepted`, `decided_at = now()`.
4. `cases.status = in_progress`, `accepted_bid_id = bid.id`, `last_activity_at = now()`.
5. Все остальные биды кейса со статусом `active` → `rejected_auto`, их pending-предложения → `superseded`.
6. Создаётся или обновляется `conversations` (`case_id`, `attorney_id`): `status = active`, `contacts_unlocked = true`, `bid_id` заполняется (раздел 9).
7. Выдача контактов (раздел 8): запись `contact_disclosures`.
8. Записи `case_journal`: `bid_accepted` (в `payload` итоговая сумма, тип оплаты, раунд, кто принял), `contacts_disclosed`, по каждому отклонённому биду `bid_rejected` (причина `another_bid_accepted`).
9. После коммита воркер отправляет уведомления: принявшему/принятому адвокату `bid_accepted` (или клиенту `offer_accepted`, если адвокат принял встречное), остальным адвокатам `bid_rejected`; кейс пропадает из списка кейсов адвокатов (статус не `open`).

Если условия не выполняются, транзакция откатывается и клиент получает понятную ошибку (`CASE_INVALID_STATE`, `BID_INVALID_STATE`, `BID_ATTORNEY_INACTIVE`). Параллельное принятие двух бидов одним клиентом невозможно (блокировка строки кейса): победит первый, второй получит `CASE_INVALID_STATE`.

## 8. Контакты клиента

### 8.1 Что выдаётся
После принятия бида адвокат видит: имя и фамилию, телефон, email, предпочитаемый способ связи и заметку о времени (из профиля клиента, файл 1 и 3). Экран «Контакты клиента» в разделе «В работе» с кнопками «Позвонить», «SMS», «Email», «Чат».

### 8.2 Журнал выдачи
Запись `contact_disclosures` (кто, когда, какие поля, IP и устройство) создаётся в транзакции принятия и не изменяется. По запросу поддержки и госорганов (файл 6) выдаётся из неё.

### 8.3 Подписка адвоката неактивна после принятия
Контакты в этом случае скрыты за экраном «Продлите подписку, чтобы увидеть контакты клиента» (файл 6, экран подписки). После возобновления подписки контакты открываются сразу, повторная запись `contact_disclosures` не создаётся (используется существующая). Чат остаётся доступен.

### 8.4 «Не могу связаться»
- Кнопка в «В работе» у карточки кейса, доступна после выдачи контактов. Адвокат выбирает причину (`phone_invalid`, `no_answer`, `email_bounce`, `wrong_person`, `other`) и добавляет комментарий. Создаётся `contact_issue_reports` (`open`).
- Проверяет админ/поддержка (очередь в админке, файл 6): решение `confirmed` или `rejected` с комментарием.
- При `confirmed`: клиенту приходит предупреждение (уведомление `moderation_notice`), после **3 подтверждённых обращений** аккаунт клиента приостанавливается (порог в `app_config`, ключ `contacts.suspend_after_confirmed_reports`, по умолчанию 3). Компенсация адвокату (например, продление подписки) решается администратором вручную в админ-панели (файл 6).
- Обе стороны получают уведомление `contact_issue_update` о результате.

## 9. Чат по кейсу (правила создания; интерфейс в файле 5)

- Чат создаётся только из кейса:
  1. **после принятия бида** (раздел 7, шаг 6) между клиентом и этим адвокатом, `status = active`, `contacts_unlocked = true`;
  2. **когда адвокат пишет клиенту по открытому кейсу** («Написать клиенту» в деталях кейса, при активной подписке/триале): `status = pre_acceptance`, `contacts_unlocked = false`.
- Клиент сам первым чат по кейсу не открывает; он отвечает в чате, инициированном адвокатом, или пользуется бидами.
- Одна беседа на пару (`case_id`, `attorney_id`).
- Пока `contacts_unlocked = false`: телефоны, email и ссылки в сообщениях автоматически маскируются (`body_display`), исходный текст хранится в `body_original`; собеседник-адвокат видит клиента как «Клиент по кейсу «заголовок»» без имени и фото.
- После принятия бида этого адвоката маскировка для этой беседы отключается, показывается имя клиента.
- Если кейс принят другим адвокатом или закрыт/удалён/архивирован, беседы `pre_acceptance` переводятся в `closed` (только чтение), отправка сообщений блокируется.
- Механика сообщений, realtime, непрочитанные: файл 5.

## 10. Жизненный цикл кейса

### 10.1 Статусы и переходы
| Из | В | Кто/что | Условие |
|---|---|---|---|
| `open` | `in_progress` | принятие бида | раздел 7 |
| `open` | `closed` | клиент «Закрыть кейс» | без выбора бида |
| `open` | `archived` | система | автоархив (10.2) |
| `archived` | `open` | клиент «Вернуть» | `last_activity_at = now()`, `archived_at = null` |
| `in_progress` | `pending_completion` | клиент «Выполнено» | `client_completed_at = now()`, `auto_close_at = now() + 7 дней`, адвокату уведомление `completion_requested` |
| `pending_completion` | `closed` | адвокат «Подтвердить» | `attorney_confirmed_at`, `closed_at`, событие `completion_confirmed` |
| `pending_completion` | `closed` | система | `auto_close_at` наступил, адвокат не ответил (событие `auto_closed`) |
| `pending_completion` | `disputed` | адвокат «Оспорить» | создаётся `case_disputes` (причина обязательна), событие `disputed` |
| `disputed` | `closed` или `in_progress` | админ | решение по спору (файл 6), событие `dispute_resolved`; при `closed` ставится `closed_at` |

Удаление (`deleted_at`) допускается только из `open` и `archived` (раздел 3.5). Любой переход вне таблицы: `CASE_INVALID_STATE` (`409`). Все переходы выполняет единый `CaseStateMachine`, а не разрозненные обновления в сервисах.

После `closed` (кроме закрытия клиентом без бида) клиенту приходит `case_closed` с предложением оставить отзыв (файл 3, раздел 7).

### 10.2 Автоматические задачи (BullMQ repeatable jobs)
| Задача | Расписание | Действие |
|---|---|---|
| Напоминание об актуальности | каждый час | `open` кейсы с `last_activity_at < now() - 30 дней` и `stale_prompt_sent_at IS NULL`: push и уведомление клиенту `case_stale_prompt` («Кейс ещё актуален?», действия «Да, актуален» → `last_activity_at = now()`, `stale_prompt_sent_at = null` / «Закрыть кейс»), `stale_prompt_sent_at = now()` |
| Автоархивация | каждый час | `open` кейсы с `stale_prompt_sent_at < now() - 14 дней` и без активности после него: `archived`, `archived_at`, уведомление `case_archived`, активные биды → `rejected_auto` (причина `case_archived`), событие `archived` |
| Автозакрытие | каждый час | `pending_completion` с `auto_close_at <= now()`: `closed`, событие `auto_closed` |
| Напоминание адвокату | каждый час | `pending_completion`, до `auto_close_at` остаётся ≤ 24 часа и напоминание не отправлялось: уведомление `completion_reminder` |
- **Что считается активностью** (обновляет `last_activity_at`): новый бид, встречное предложение, любое действие клиента по кейсу (просмотр бидов не считается), редактирование кейса, сообщение в чате по кейсу, ответ «Да, актуален».
- Задачи идемпотентны, работают батчами (500 кейсов за прогон), используют индексы из файла 2 (`cases(last_activity_at) WHERE status='open'`, `cases(auto_close_at) WHERE status='pending_completion'`), защищены от параллельного запуска блокировкой в Redis.

## 12. История кейсов (Настройки → «История кейсов»)

- Доступна клиенту и адвокату. **Вход только после повторной аутентификации** (биометрия или код на телефон/email, файл 1, `POST /auth/reauth`, `reauthToken` 5 минут). Каждый вход пишется в `auth_events` (`history_viewed`).
- **Содержимое:** список кейсов пользователя, включая закрытые, архивные и удалённые из ленты. Клиент видит кейсы, где он `client_id`; адвокат видит кейсы, где он подавал бид или работал. Для каждого кейса: заголовок, практика, штат, даты, итоговый статус, принятый бид (сумма, тип оплаты) и подробная **хронология событий** из `case_journal` (создание, биды, раунды торга, принятие, выдача контактов, завершение, споры).
- Адвокат видит имя клиента в хронологии только если ему были выданы контакты по этому кейсу, иначе «Клиент».
- **Неизменяемость:** записи нельзя удалить или изменить ни из приложения, ни через API. Кнопки удаления в этом разделе нет. Удаление кейса из ленты не удаляет запись из журнала.
- **Скачать PDF:** `POST /users/me/case-history/export` создаёт фоновую задачу, PDF (со списком кейсов и хронологией) кладётся в приватный S3, пользователь получает уведомление и ссылку на скачивание (действует 10 минут, при повторном скачивании нужен новый reauth).
- **Срок хранения:** 5 лет (`retain_until`, файл 2). При удалении аккаунта данные пользователя обезличиваются, а журнал остаётся до окончания срока.
- **Госорганы** прямого доступа в приложение не получают: данные выдаются только по официальному запросу (subpoena или court order) через админку с записью в `data_access_requests` и `data_access_log` (файл 6).
- **Целостность:** каждая запись журнала содержит `prev_hash` и `row_hash`; запись выполняется только через `CaseJournalService.append()` внутри той же транзакции, что и основное изменение; ежедневный воркер проверяет цепочку и при нарушении отправляет алерт (файл 6).

## 16. ЭТАПЫ РЕАЛИЗАЦИИ ФАЙЛА 4

> Порядок обязателен. После каждого этапа: `flutter analyze`, `flutter test`, `npm run lint`, `npm run test`, приложение запускается.

### Этап 4.1: Миграция, машина состояний, журнал
- Миграция раздела 14. Модули `cases`, `bids`, `negotiations`, `journal`. `CaseStateMachine` (таблица переходов 10.1), `BidStateMachine` (6.3), `CaseJournalService.append()` с хэш-цепочкой в общей транзакции.
- **Приёмка:** юнит-тесты на все допустимые и недопустимые переходы; журнал: цепочка валидна, изменение записи ломает проверку; UPDATE/DELETE журнала под ролью приложения запрещены.

### Этап 4.2: Создание и управление кейсом (API)
- Разделы 3.1-3.5 (валидация, `CASE_CONTAINS_CONTACT_INFO`, согласие `client_contact_sharing`, редактирование, закрытие, удаление, возврат из архива, keep-alive), `GET /users/me/cases`.
- **Приёмка:** кейс не создаётся без подтверждённых контактов; более 3 штатов, отсутствие основного штата, короткое описание, контакты в тексте отклоняются; смена практики/штатов при наличии бидов запрещена; удаление `in_progress` запрещено.

### Этап 4.3: Показ кейсов адвокатам (API)
- Раздел 4: видимость по лицензии и практике (включая правило для `not_sure_or_other`), список с cursor-пагинацией и фильтрами, детали без данных клиента, просмотры с дедупликацией, «Сохранить».
- **Приёмка:** адвокат без лицензии в штате кейса не видит кейс и получает `CASE_NOT_AVAILABLE` по прямому id; в ответах нет имени/контактов клиента; `EXPLAIN` списка использует индексы, без seq scan.

### Этап 4.4: Биды и торг (API)
- Разделы 5 и 6: создание бида, отзыв, встречные предложения, ходы, лимит 5 раундов, `failed_negotiation`, гейты подписки (используется интерфейс `SubscriptionAccessService.isActive(attorneyId)`, реализация-заглушка на этапе, боевая подключается в файле 6), автоотзыв бидов при потере подписки.
- **Приёмка:** второй бид того же адвоката отклоняется; бид без активной подписки даёт `SUBSCRIPTION_REQUIRED`; ход вне очереди даёт `BID_NOT_YOUR_TURN`; 6-е встречное невозможно; отклонение на 5-м раунде приводит к `failed_negotiation` и уведомлению «Стороны не договорились»; встречное недоступно для `free_consultation`.

### Этап 4.5: Принятие бида и выдача контактов
- Раздел 7 и 8: транзакция принятия, автоотклонение остальных, создание беседы с `contacts_unlocked`, `contact_disclosures`, `GET /cases/:id/contacts` с проверкой подписки, «Не могу связаться» и порог блокировки клиента.
- **Приёмка (интеграционные и конкурентные тесты):** два параллельных `accept` по разным бидам одного кейса: успешен ровно один; после принятия остальные биды `rejected_auto`, кейс `in_progress`, кейс исчезает из списка адвокатов; контакты не выдаются без активной подписки, выдаются после её возобновления; в журнале есть `bid_accepted`, `contacts_disclosed` и отклонённые биды.

### Этап 4.6: Жизненный цикл и задачи
- Раздел 10: «Выполнено», подтверждение, оспаривание, автозакрытие, напоминания, автоархивация, спор (`case_disputes`, решение админом реализуется API-заглушкой с ролью, полноценный экран в файле 6). Repeatable jobs с блокировкой в Redis.
