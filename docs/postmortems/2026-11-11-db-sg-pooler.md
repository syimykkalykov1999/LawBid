# Разбор: API не достучался до базы (правило доступа пула снято) — SEV1 — 11.11.2026

Шаблон: `docs/runbooks/INCIDENT.md` §5 (Google SRE Book гл. 15 «Postmortem Culture», SRE Workbook гл. 10). Без поиска виноватых: ищем, что в системе позволило этому случиться. Источник фактов: `docs/dev/KNOWN_ERRORS.md` №99, CloudTrail, журнал помощников (`perf-detective`, 7 дней прода). Личных данных и секретов здесь нет.

**Коротко (3 строки).** Применение облака (копия базы) переписало группу доступа базы. Terraform при этом снял отдельное правило «пул PgBouncer → база». Через 23 минуты истекли старые соединения пула, и API 50 минут не мог открыть новые: «database unreachable», админка не грузилась. Тревога не позвонила, нашли случайно.

## Влияние
- **Когда:** 11.11.2026 20:25–21:15 UTC (12:25–13:15 по Тихоокеанскому времени, 13:25–14:15 по горному). ALB видел 5xx 20:28–21:17 UTC.
- **Кто:** все, кто открывал приложение, сайт или админку. По журналу помощников задача API была одна (`api desired = 1`), запасной не было.
- **Сколько запросов:** Logs Insights (`docs/dev/PERF_DETECTIVE_2026-11-13.md`, S1): задача `ip-10-30-128-177` ответила `/health/ready` 503 «database unreachable» **1 549 раз** с 20:28 до 21:17 UTC. Сама база была здорова (CPU 5 %), отрезана была задача. За 7 дней вокруг двух простоев (11.11 и 13.11) ALB насчитал 5 199 ответов 5xx цели из ~406 000 запросов. Число 5xx ALB именно за это окно можно получить командой из раздела «Как проверить цифры».
- **Деньги и данные:** денег не списано, данных не потеряно (запись не доходила до базы, ничего не записалось наполовину).

## Обнаружение
- **Как нашли:** ручной проверкой скорости веба, **не тревогой**. Поэтому разбор обязателен по самому шаблону («тревога, которая должна была сработать и не сработала»).
- **Почему тревога не дошла до телефона:**
  1. Проверки здоровья ALB и ECS смотрят `/health/live`, а он базу не трогает. Задача считалась здоровой, тревоги `unhealthy-hosts` / `no-running-tasks` молчали.
  2. Внешняя проверка `/health/ready` (`uptime-canary`, Route 53) и `api-5xx-ratio` идут в тему `critical`, но звонок PagerDuty работает только со вставленным ключом. Ключа нет (`ARCHITECTURE_VS_BIG_PLATFORMS_2026-11-25.md`, O2), поэтому пришло только письмо.
  3. Сама причина, снятое правило группы безопасности в 13:02 MST, ни на какую тревогу не была заведена. А у нас было 23 минуты до падения.
- **Время до обнаружения:** около 50 минут.

## Хронология (UTC)
- 20:02 — infra-apply (копия базы). В плане строка `~ aws_security_group.db`. CloudTrail: `RevokeSecurityGroupIngress` от роли GitHubActions в 20:02:27 снимает правило `db_from_pooler`.
- 20:02–20:25 — открытые соединения пула живут дальше, всё работает.
- 20:25 — соединения истекают, новые не открываются. `/health/ready` 503, API «database unreachable».
- до 21:15 — проблему видит ручная проверка скорости веба (точная минута не записана; это тоже пункт действий: время обнаружения писать сразу).
- 21:15 — владелец вручную возвращает правило. Подключения восстанавливаются.
- 21:17 — последние 5xx на ALB.

## Причина и способствующие факторы
- **Причина:** у группы `aws_security_group.db` правила были записаны внутри (`ingress {}`), а доступ пула был отдельным ресурсом `aws_vpc_security_group_ingress_rule.db_from_pooler`. При таком смешении Terraform считает отдельное правило лишним и снимает его при любом изменении группы (документация провайдера AWS, `aws_security_group`: «do not use in-line rules together with separate rule resources»).
- **Способствовало:** план читали, но строка «~ aws_security_group» не была помечена как опасная; после применения не проверяли `/health/ready`; одна задача API; проверки здоровья балансировщика не смотрят базу; нет ключа PagerDuty.

## Что прошло хорошо, что плохо, где повезло
- **Хорошо:** CloudTrail сразу показал, какой вызов и кто снял правило. Возврат правила вылечил всё за минуты, данных не потеряли.
- **Плохо:** 50 минут простоя без звонка; нашли случайно.
- **Повезло:** простой был днём (по Тихоокеанскому), и ручная проверка шла как раз в это время. Ночью без звонка он длился бы до утра.

## Смягчение
Правило вернули вручную (владелец, 21:15 UTC). Быстро, потому что CloudTrail назвал точный вызов. Медленно было только обнаружение.
