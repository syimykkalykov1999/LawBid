# Разбор: «Авто» сам выключил PgBouncer, через который шли серверы — SEV1 — 13.11.2026

Шаблон: `docs/runbooks/INCIDENT.md` §5 (Google SRE Book гл. 15 «Postmortem Culture», SRE Workbook гл. 10). Без поиска виноватых. Источник фактов: `docs/dev/KNOWN_ERRORS.md` №144, `docs/dev/DETECTIVE_prod-errors_2026-11-14.md`, `docs/dev/PERF_DETECTIVE_2026-11-13.md`, PR #1026. Личных данных и секретов здесь нет.

**Коротко (3 строки).** Автоматика «Авто» решила, что пул соединений PgBouncer не нужен, и сама удалила его через infra-apply. Задачи API при этом всё ещё ходили в базу через пул (`DB_POOLER_HOST`). 55 минут API, админка и воркер не могли работать с базой.

## Влияние
- **Когда:** 13.11.2026 21:58–22:53 UTC (13:58–14:53 по Тихоокеанскому времени).
- **Кто:** все пользователи приложения, сайта и админки. Фоновые задачи (cron) тоже стояли.
- **Сколько:** за этот час ALB насчитал 5xx цели: api **1 748**, api-admin 205, admin 205. В логах 1 997 «failed with status code 503», 1 722 «Health Check has failed», 286 упавших запусков cron, 1 680 ответов `/health/ready` 503 «database unreachable» с задачи `ip-10-30-128-177`. Прокси админки за оба простоя (11.11 и 13.11) ответил 503 1 156 раз.
- **Деньги и данные:** денег не списано, данные не потеряны (до базы ничего не доходило, транзакции не начинались).

## Обнаружение
- **Как нашли:** время и способ обнаружения в журнале не записаны (это тоже пункт действий ниже). Причину нашли по запросу `f758b39f` в журнале InfraAutoService (`aws.pgbouncer on -> off`) и прогону infra-apply 43511676199.
- **Почему тревога не помогла:**
  1. Проверки здоровья ALB и ECS смотрят `/health/live`, без базы, поэтому задачи «здоровы» и не заменялись (`PERF_DETECTIVE_2026-11-13.md`, S1).
  2. Сам хук «тревога → строка аварии» `/internal/alarm-events` в это время получил 50 ответов 503: он работает через тот же API и ту же базу.
  3. Звонок PagerDuty без ключа не работает (O2), осталась только почта.

## Хронология (UTC)
- до 21:58 — «Авто» (InfraAutoService) видит сигнал `poolSmall = false` дольше `infra.auto_off_hours` и ставит запрос `aws.pgbouncer on -> off`. План проходит сам: `autoApplyOk('off')` пропускал любой план без новых ресурсов, кроме замены task definition.
- 21:58 — infra-apply 43511676199 удаляет сервис пула. Замена task definition не выполняется, потому что в другом шаге 403 на `ResetDBParameterGroup` и DependencyViolation на группе пула. Задачи остаются с `DB_POOLER_HOST`.
- 21:58–22:53 — API, админка и воркер не достают базу.
- 22:53 — работа восстановлена (последние 503 в логах). Каким шагом, в журнале не записано; это пункт действий ниже.

## Причина и способствующие факторы
- **Причина 1:** сигнал «пул нужен» (`poolSmall` в `infra-auto.service.ts`) был `!pooler && …`, то есть всегда false, пока пул работает. Пул сам гасил свой сигнал, и правило KEEP_ON через `infra.auto_off_hours` считало его лишним.
- **Причина 2:** Terraform удаляет старую зависимость, не дожидаясь, пока ECS перекатит задачи (UpdateService возвращается сразу). При ошибке в другом шаге замена task definition не выполнялась совсем.
- **Способствовало:** выключение того, через что идут запросы, проходило без подтверждения владельца; тот же самогасящийся сигнал был у потока Kinesis.

## Что прошло хорошо, что плохо, где повезло
- **Хорошо:** журнал InfraAutoService и номер прогона infra-apply сразу показали, кто и что удалил. Исправление (#1026) вышло в тот же день.
- **Плохо:** автоматика удалила живую зависимость сама; хук аварий упал вместе с API; время обнаружения не записано.
- **Повезло:** база сама не пострадала (CPU 5 %), откат был только в облаке.
