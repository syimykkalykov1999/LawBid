## P0 before release

### 1. Phone paging for critical alarms
**Practice.** Big shops page a human by phone from an alert router (PagerDuty, Opsgenie-class) with escalation. Options today:
- **AWS Incident Manager: do not use.** Closed to new customers on 2025-11-07, no new features ([AWS docs](https://docs.aws.amazon.com/incident-manager/latest/userguide/incident-manager-availability-change.html), seen 2026-10-24).
- **AWS Chatbot is now Amazon Q Developer in chat applications** (renamed 2025-02-19, no extra cost) ([AWS docs](https://docs.aws.amazon.com/chatbot/latest/adminguide/service-rename.html)). It posts to Slack/Teams; it does not ring a phone. Good as a second channel, not a pager.
- **PagerDuty Free**: $0, up to 5 users, 1 schedule, 1 escalation policy; unlimited push/email, but only **100 phone+SMS notifications per month** ([PagerDuty pricing](https://www.pagerduty.com/pricing/incident-management/), 2026). CloudWatch/SNS connects through an HTTPS SNS subscription to an Events API integration URL ([PagerDuty guide](https://support.pagerduty.com/docs/aws-cloudwatch-integration-guide), 2026). 100 calls/month is enough if only critical composites page.
- **Better Stack**: free tier is Slack/email only; phone calls need a paid responder, from about $29/month ([Better Stack pricing](https://betterstack.com/uptime/pricing), 2026, price unverified).
- **Grafana OnCall OSS: dead.** Archived 2026-03-24 ([Grafana](https://grafana.com/blog/grafana-oncall-maintenance-mode/)); successor is Grafana Cloud IRM (free for 3 users, $20 per paid user per month, unverified).
- **SMS to the owner by SNS** (no vendor): needs a US origination identity (10DLC registration or toll-free verification, takes days) ([AWS SNS SMS pricing](https://aws.amazon.com/sns/sms-pricing/)). Cheap, but no acknowledge or escalation.

**Reuse.** PagerDuty Free as primary (phone, app push), the existing e-mail and Slack subscriptions as backup. Cost $0.
**Design.** `infra/modules/monitoring/main.tf:91` already has a `aws_sns_topic_subscription.slack` (var `slack_webhook_url`). Add a variable `pagerduty_https_endpoint` (sensitive, default null) and a subscription with `protocol = "https"`, `raw_message_delivery = false`. Plumb it through `modules/stack/main.tf:1226`, `envs/prod/variables.tf`+`main.tf`, `launch.tfvars.example`. Route only critical composites: the 6 composite alarms from `slo.tf` plus RDS/Redis/ALB-5xx. Today the whole topic `lawbid-prod-alerts` is one stream, so first add a second SNS topic `lawbid-prod-critical` (the 6 composites only) and subscribe PagerDuty to that; otherwise a noisy alarm burns the 100 calls. Runbook `docs/runbooks/paging.md`. The owner creates the PagerDuty account and phone verification (manual, outside agent scope).
**Effort.** 3 ah. **Test.** `aws sns publish` a test message to the critical topic; phone rings; acknowledge; check the incident closes on OK action. **Rollback.** set the variable to null (subscription destroyed), alarms still e-mail. **Safe before release: yes** (additive).

### 2. Restore drill and RDS Multi-AZ failover test; why the vault has 0 recovery points
**Finding (live).** Plan `lawbid-prod-db-daily` was created today 04:54 PDT (11:54 UTC), schedule `cron(0 6 * * ? *)`, **LastExecutionDate None**, zero jobs. The selection and role exist. The DB uses our CMK `alias/lawbid-prod` (so cross-region copy works), is `available`, and Multi-AZ is pending. So the vault is empty only because the first scheduled run (2026-10-25 06:00 UTC, start window 60 min) has not happened yet. It is not a selection bug. Risks for that run: Multi-AZ conversion lands in the Sunday window 04:30-05:30 UTC, 30 min before the job, and a still-modifying instance can fail the job.
**Do now (no code):** `aws backup start-backup-job --backup-vault-name lawbid-prod-db --resource-arn arn:aws:rds:us-east-1:047754151252:db:lawbid-prod-postgres --iam-role-arn arn:aws:iam::047754151252:role/lawbid-prod-backup`; confirm a recovery point and the copy into `lawbid-prod-db-dr` (us-west-2). The existing alarm `…-db-backup-age` treats missing data as breaching, so expect one false alarm tonight if the first job is late.
**Practice.** AWS Well-Architected REL09 BP4 (periodic restore test); Netflix/Stripe-style game days.
**Drill.** `scripts/ops/restore-drill.sh` restores the newest RDS snapshot to a temp `db.t4g.micro`, runs a smoke query through an ECS `migrate` one-off task, deletes the copy; about $0.05. Gaps to fix: (a) add `MODE=backup-vault` that restores from the AWS Backup recovery point (`aws backup start-restore-job`) and from the DR-region copy, because that is what we claim to have; (b) log RTO/RPO to `docs/runbooks/restore-drill.md`; (c) a `FAILOVER=1` step: `aws rds reboot-db-instance --db-instance-identifier lawbid-prod-postgres --force-failover`, then poll `/health` and count 5xx for the outage. AWS says reboot-with-failover simulates a failure, DNS flips, connections must reconnect, and an outage still happens; AWS advises stopping transactions first ([RDS docs](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_RebootInstance.html), 2026). Typical 60-120 s is a third-party figure.
**Order.** Multi-AZ converts Sunday 2026-10-25; first backup 06:00 UTC; drill and failover test Monday off-peak, with Prisma/pgbouncer reconnection watched (pool settings in `modules/pgbouncer`).
**Effort.** 3 ah (script + runbook) plus owner approval for the failover. **Rollback:** drill deletes its own copy (`KEEP=1` off); a failed failover test self-heals through RDS. **Safe before release:** yes, and required before launch.

### 4. Bot protection on signup and OTP
**Today.** Server `modules/auth/app-check/app-check.guard.ts` with modes off/monitor/enforce (`security.app_check.mode`, default **monitor**), client `core/security/app_check.dart` + `network/app_check_interceptor.dart`, runbook `docs/runbooks/APP_CHECK.md`. Mobile uses App Attest (iOS) and Play Integrity (Android); web is planned on reCAPTCHA Enterprise. There is no Turnstile code anywhere.
**Facts.**
- Turnstile is **free**: unlimited challenges, 20 widgets, 10 hostnames per widget, 7-day analytics; Enterprise raises limits ([Cloudflare Turnstile plans](https://developers.cloudflare.com/turnstile/plans/), updated 2026-08-24). Terms of service not re-read: owner/legal should skim them before use.
- There is **no native mobile SDK**; Cloudflare documents a WebView approach ([mobile implementation](https://developers.cloudflare.com/turnstile/get-started/mobile-implementation/)). iOS WKWebView problems are reported in the community, so on mobile Turnstile is the worse tool.
- Play Integrity Standard API quota is **10,000 requests per day** by default, raisable by request once the app is on Google Play ([Firebase docs](https://firebase.google.com/docs/app-check/android/play-integrity-provider), 2026); App Check tokens live 1 h by default, so quota is fine with the SDK's own caching. App Attest has Apple-side limits; no numbers published. A FlutterFire issue notes Standard-request support was missing in the plugin ([#17190](https://github.com/firebase/flutterfire/issues/17190)); check the installed `firebase_app_check` version.
**Recommendation.** Mobile: App Check alone (already built), switch to `enforce` after the monitor week shows `missing` near zero. Web (Flutter web at `apps/mobile/web`): Turnstile, server verified, replacing reCAPTCHA Enterprise (cost and Google dependency). Rooted or de-Googled Android fails Play Integrity: keep the existing WAF OTP rate rule, per-number and daily SMS caps as the second layer.
**Design.** New `modules/auth/turnstile/turnstile.service.ts` (POST `https://challenges.cloudflare.com/turnstile/v0/siteverify`, secret from provider-registry `common/secrets/provider-registry.ts`, check `success`, `hostname`, `action`). In `app-check.guard.ts`, when the request carries `X-Turnstile-Token` and no App Check token, accept it for web only. Web client: JS widget in `apps/mobile/web/index.html` and a small Dart interop; for mobile fallback `webview_flutter` is optional, not recommended. Add a `security.turnstile.mode` setting next to `security.app_check.mode` in `app-settings.defaults.ts` and `admin-config/config-schema.ts`.
**Effort.** 6 ah server+web; App Check enforce flip 0.5 ah after the monitor week. **Test.** unit tests with a mocked siteverify (Turnstile publishes always-pass/always-fail test keys); Playwright against web. **Rollback.** mode `off`/`monitor` from the admin config, no deploy. **Safe before release:** enforce flip only after the monitor week (needs the signed builds); the Turnstile code is additive.
