# Рекомендации по вопросам (R-401, владелец 04.11.2026)

Коротко: адвокат, который отвечает на вопросы клиентов в разделе «Вопрос юристу», поднимается в рекомендациях. Считаем это **раз в ночь**, страницы читают **готовый список**. Своих формул нет — взяты открытые проверенные схемы.

## Как сейчас

- Сетка «Люди» (Поиск → Люди, для клиента и адвоката) и «возможно знакомы»: `RecommendationsService.peopleFor` — взвешенная сумма из 10 признаков (контакты, штат, тема, общие подписки, рейтинг, активность в постах, Identity, подписчики). Ответы на вопросы **не учитываются**. Список считается по запросу зрителя и кэшируется на 10 минут; при малой базе клиенту досыпают популярных адвокатов штата (`FollowsService.suggestionPool`, PR #739).
- Кейсы адвокату (Поиск → Кейсы, «для вас»): `casesFor` — 11 признаков (тема, штат, свежесть, бюджет, конкуренция…). Темы, в которых адвокат отвечает на вопросы, не учитываются.
- «Вопрос юристу» (`legal_qa`): вопросы клиентов, ответы только проверенных адвокатов, лайки на ответах, «лучший ответ» от автора. Ни на что в рекомендациях не влияет.

## Как будет

1. **Ночная задача** `reco.qa-snapshot` (05:20 UTC, BullMQ, тяжёлая полоса — останавливается «Паузой тяжёлых задач») один раз читает все опубликованные ответы за **90 дней** и считает:
   - **балл адвоката** 0…1 и **его темы** (доли тем, на которые он отвечал);
   - **топ-списки по темам**: лучшие адвокаты темы, открытые вопросы темы (60 дней, меньше 10 ответов), открытые кейсы темы (30 дней, статус open).
2. Результат пишется в таблицу `reco_qa_snapshots` (kind, key, payload) и в **Redis** (один hash на вид, живёт 2 ночи). Старый снимок заменяется целиком.
3. **Чтение** (никаких подсчётов при открытии экрана):
   - `peopleFor` / `peopleAffinity`: к обычной оценке адвоката **прибавляется** `reco.people.qa × балл` + `reco.people.qaTopic × совпадение тем адвоката с интересами зрителя`. Старые веса не меняются (их сумма остаётся 1).
   - `casesFor`: к оценке кейса прибавляется `reco.case.qaTopic × доля темы кейса среди тем ответов адвоката`.
   - Новый `GET /questions/recommended` (адвокат): открытые вопросы его тем (его практики + темы его ответов) из топ-списков, лучшие первыми, одна страница. В приложении — раздел «Рекомендуемые вопросы» над кейсами в Поиске → Кейсы (те же карточки вопросов).
   - Нет снимка (первая ночь, Redis и таблица пусты) или флаг выключен → **ничего не прибавляется**, список вопросов = неотвеченные вопросы моей практики, то есть сегодняшнее поведение.
4. **Подсказка адвокату** — одна маленькая строка «Ответы поднимают вас в рекомендациях» под существующей карточкой «Новые вопросы по вашей практике» в ленте и под строкой «Отвечайте на вопросы…» в своём профиле. Клиенты её не видят. Новых виджетов нет.

## Формула (откуда взята)

- **Затухание по времени — «гравитация» Hacker News**: `вес = 1 / (возраст + 2)^1.8` (news.arc; разбор «How Hacker News ranking algorithm works», 2010). У нас возраст в неделях (окно 90 дней): свежий ответ = 1, через месяц ≈ 0.2, через три ≈ 0.03.
- **Польза ответов — нижняя граница Уилсона** (Evan Miller, «How Not To Sort By Average Rating», 2009; так же Reddit сортирует «best»): испытание = ответ, успех = ответ с хотя бы одним лайком, z = 1.96. Один ответ с одним лайком не обгонит восемь из десяти.
- **Объём — логарифм** (как `log10(голоса)` в Reddit «hot»).

Балл адвоката = `0.5·ответы + 0.3·лайки + 0.2·лучшие`, где
`ответы = saturate(Σ затухших ответов, 6)`, `лайки = ½·Уилсон(ответов с лайком, ответов) + ½·log(затухших лайков, 50)`, `лучшие = saturate(Σ затухших лучших, 3)`.
Темы: доля затухшего веса ответов по категориям практики, сильнейшая = 1 (та же форма, что интересы зрителя).
Открытый вопрос / кейс для адвоката: `гравитация(возраст) × (½ + ½·свободного места)` — свежие и ещё не заваленные ответами/откликами первыми.

Код: `apps/api/src/modules/recommendations/qa-ranking.ts` (формулы), `qa-snapshot.service.ts` (ночная сборка и чтение), тесты `qa-ranking.spec.ts`, `qa-snapshot.service.spec.ts`, e2e в `test/owner-qa-scope-limits.e2e-spec.ts`.

## Что настраивает админ

Система → Настройки, карточка «Рекомендации по вопросам (ответы адвокатов)»:

| ключ | что это | по умолчанию |
|---|---|---|
| `reco.qa.answers` | вес «ответов за 90 дней» | 0.5 |
| `reco.qa.likes` | вес «лайков на ответах» | 0.3 |
| `reco.qa.best` | вес «лучший ответ» | 0.2 |
| `reco.qa.gravity` | затухание свежести (как HN) | 1.8 |
| `reco.people.qa` | вклад балла в сетку «Люди» | 0.1 |
| `reco.people.qaTopic` | совпадение тем (люди) | 0.08 |
| `reco.case.qaTopic` | совпадение тем (кейсы адвокату) | 0.08 |

Там же — время последнего расчёта с числами (адвокатов, вопросов, кейсов) и кнопка **«Пересчитать сейчас»** (ставит задачу в очередь BullMQ; нужен свежий код 2FA, второго админа нет). Веса `reco.qa.*` применяются при следующем расчёте, `reco.people.*` / `reco.case.*` — сразу (при следующей пересборке списка зрителя, ≤10 минут).

Флаг **`recommendations_qa_ranking`** (Функции): включён по умолчанию — пустой снимок ничего не меняет. Выключен = снимок не читается вообще (сегодняшняя выдача), ночная задача продолжает считать.

## Помощники адвоката (дополнение владельца 04.11 13:05)

Новый доступ помощника **«Отвечать на вопросы»** (`qa_answers`) в том же списке доступов, что «Ставки» и «Публикации» (экран «Команда» → доступы помощника, с подтверждением ответственности, как у остальных). С этим доступом помощник отвечает на вопросы **от имени адвоката**: ответ выходит под профилем адвоката, лайки и балл в рекомендациях идут адвокату; в строке ответа хранится, кто набрал текст (`legal_answers.authored_by_user_id` = помощник; правка самим адвокатом сбрасывает в пусто). Действие попадает в ленту действий помощника («ответил(а) на вопрос клиента»). Без доступа — как сегодня: вопросы только читать, кнопки ответа нет (сервер отвечает 403 `ASSISTANT_NOT_ALLOWED`). Доступы хранятся как список строк — миграции под сам доступ нет; одна «расширяющая» миграция добавляет колонку автора.

### Предел ролей у одного помощника (владелец 04.11 13:15)

Откуда «3»: настройка `assistants.max_duties` (владелец 22.10), по умолчанию 3, уже редактируется в админке; сервер проверяет её в `AssistantsService.assertDutyCount` (409 `ASSISTANT_TOO_MANY_DUTIES`), приложение получает число в ответе `GET /team` (`maxDuties`) и не делает лишних запросов. Теперь: ярлык в админке «Макс. ролей у одного помощника», значение 1…11 или **0 = все** (без ограничения); ответ `/team` несёт ещё `maxDutiesUnlimited`. В выборе ролей под заголовком «Обязанности» строка «Можно ещё N»; при «все» строки нет, и все готовые роли (включая «Всё») доступны. По умолчанию ничего не меняется (3).

## Нагрузка

Ночью: три запроса (ответы за 90 дней, открытые вопросы, открытые кейсы, с LIMIT) и одна запись. Днём: HMGET в Redis по id кандидатов (уже выбранных старым путём) — никаких новых соединений таблиц при открытии. Телефон: один дополнительный запрос `GET /questions/recommended` при открытии Поиска → Кейсы адвокатом, ответ держится 10 минут.
