# Свой пул соединений с базой (PgBouncer): исследование и проект

Владелец решил 2026-10-24: **никаких платных посредников (RDS Proxy)**, делаем
свой пул соединений, как Instagram. Реализация: `infra/modules/pgbouncer`,
образ `infra/pgbouncer`, пошаговая инструкция `docs/runbooks/DB_POOLER.md`.

---

## Коротко по-русски (для владельца)

**Проблема.** База (RDS db.t4g.micro) принимает не больше 99 соединений.
Каждая копия сервера (api или worker) держит свои соединения с базой. Когда
копий станет 70 (а при выкладке до 140), нужно 140 x 3 = 420 соединений, база
столько не примет. Сейчас проверка Terraform (`db_connection_budget`) честно
падает именно из-за этого.

**Решение.** Между серверами и базой ставим «диспетчера» (PgBouncer). Серверы
открывают сколько угодно дешёвых соединений к диспетчеру (до 5000 на штуку), а
диспетчер держит к базе **фиксированное малое число** соединений (всего 69 из
99) и раздаёт их запросам по очереди, на время одной операции. Сколько бы ни
было серверов, база увидит не больше 69 соединений. Остальные 30 остаются
для миграций, служебных задач и администратора.

**Как устроено.**
- 2 диспетчера в двух зонах AWS; при нагрузке на процессор добавляется третий.
- Серверы находят диспетчеров по внутреннему имени `pgbouncer.lawbid-prod.internal`
  (AWS Cloud Map: частный DNS, виден только внутри нашей сети; дешевле
  балансировщика).
- Доступ: к диспетчерам ходят только серверы api/worker; к базе ходят
  диспетчеры (и миграции, и служебные задачи, как раньше).
- Пароль диспетчер берёт из Secrets Manager (тот же секрет `DATABASE_URL`),
  связь и с серверами, и с базой зашифрована (TLS).
- Миграции базы, очистка по срокам хранения и «демо-мир» **не** идут через
  диспетчера, они остаются на прямом подключении.
- Образ собираем сами из официального Alpine (amd64 и arm64), кладём в свой
  ECR; чужих образов не тянем.

**Выключатель.** Одна строка `db_pooler_enabled = false` в tfvars + `apply`
возвращает прямое подключение, как было. По умолчанию выключено. На
нагрузочных тестах (`loadtest`) пул **включён**, чтобы следующий тест
доказал, что всё работает.

**Сколько стоит.** Около **32 долларов в месяц** (2 диспетчера ~29, частное имя
в Cloud Map ~0.5, метрики и тревоги ~2). Если третий диспетчер включился, +14 на
время нагрузки. Раньше было 49 с балансировщиком; по решению владельца (экономия)
вместо него Cloud Map. Подробнее в разделе «Стоимость».

**Что проверено уже сейчас (на моём компьютере).** Настоящий PgBouncer 1.24 +
PostgreSQL 16 + тот же Prisma 6.19, что в приложении: 500 запросов, в том числе
транзакции, 100 одновременно, через 6 соединений с базой, 0 ошибок; после
перезапуска базы пул сам восстановился. **Не проверено**: работа внутри AWS и
под реальной нагрузкой. Это и есть задача ближайшего нагрузочного теста.

**Главные риски.** (1) Если диспетчеры недоступны, приложение остаётся без базы;
на это есть тревога «нет живых серверов пула» и выключатель. (1а) Без
балансировщика сервер может на несколько секунд помнить адрес только что
остановленного диспетчера: он просто переподключится (подробно в 2.1). (2) Одна
находка: тест `pgbench -M prepared` с большим числом клиентов подвисает на
PgBouncer 1.24 (это нагрузочная утилита, не Prisma, но нагрузочный тест должен
это подтвердить). (3) Прямые подключения (миграции, очистка, демо) всё ещё
используют часть базы, под них зарезервировано 30 соединений.

## 1. Исследование (что узнали)

### 1.1. Центральный пул или «спутник» в каждой задаче

| | Спутник (sidecar) в каждой задаче | Центральный сервис |
|---|---|---|
| Соединений к базе в сумме | растёт с числом задач: каждая задача держит хотя бы свой минимум | **фиксировано**: `задач пула x размер пула` |
| 70 задач (140 при выкладке), минимум по 2 к базе | 140 x 2 = 280 > 99 | 3 x 23 = 69 |
| Что даёт | убирает только «толстый» пул Prisma внутри задачи | реально защищает базу |
| Плюс | нет сетевого прыжка, нет общей точки отказа | 1 место для настроек, метрик, тревог |
| Минус | **не уменьшает число соединений к базе** при росте числа задач | общая точка отказа (лечится 2 штуки в 2 зонах + выключатель) |

Вывод: sidecar не решает задачу (общая сумма соединений всё равно растёт
вместе с числом задач), нужен **центральный** пул. Так делают GitLab (отдельные
узлы PgBouncer) и Heroku (Connection Pooling = PgBouncer в режиме transaction
рядом с базой).

### 1.2. Образ

| Вариант | Итог |
|---|---|
| `bitnami/pgbouncer` | Список тегов на Docker Hub пуст («Secure Image», состояние поддержки неясно). Не берём. |
| `edoburu/pgbouncer` (v1.25.1-p0) | Есть amd64 и arm64, поддерживается. Но его скрипт запуска разбирает `DATABASE_URL` простыми `cut`/`sed`: не понимает `?sslmode=...` в конце (имя базы получится `lawbid?sslmode=require`) и ломается на спецсимволах пароля. В нашем секрете именно такой URL. Не берём как есть. |
| `pgbouncer/pgbouncer` | Отдельного официального образа на Docker Hub не нашли. |
| **Свой тонкий образ: `alpine:3.22` (официальный, закреплён по digest) + пакет `pgbouncer` из Alpine** | **Выбрали.** amd64 и arm64, подписанные пакеты Alpine, работает от непривилегированного пользователя, версия 1.24.0 (нужна >= 1.21 для prepared statements). Свой запуск (`infra/pgbouncer/entrypoint.sh`) разбирает URL надёжно (в том числе пароль с `@ : / "`), включает TLS. Собирается и проверяется сканером ECR и воркфлоу `build-pgbouncer.yml` для обеих архитектур. |

### 1.3. Prisma за PgBouncer

- Нужен режим **transaction** (соединение с базой привязано к клиенту только на
  время транзакции).
- Документация Prisma: `?pgbouncer=true` нужен только для PgBouncer **ниже 1.21**.
  Начиная с 1.21 надо не ставить флаг и включить `max_prepared_statements` > 0
  (PgBouncer сам запоминает именованные prepared statements на любом соединении
  с базой). У нас 1.24 и `max_prepared_statements = 200`: флаг не нужен.
  Запасной выход: переменная `DB_POOLER_QUERY=pgbouncer=true` (Prisma перестанет
  использовать prepared statements).
- Миграции (`prisma migrate deploy`) не работают через пул («prepared statement
  s0 already exists»). Нужна прямая ссылка. У нас migrate-задача **и так** берёт
  отдельный секрет `MIGRATOR_DATABASE_URL`, а в её окружение пулерные переменные
  не попадают (фильтр в `modules/ecs`). Поэтому `directUrl` в `schema.prisma`
  **не добавляли**: он потребовал бы новую переменную при каждом
  `prisma generate`/CI без выгоды. Prisma 6 в этом репозитории читает URL только
  из `DATABASE_URL`.
- В коде нет session-level конструкций, ломающих transaction-режим:
  `pg_advisory_lock`, `LISTEN/NOTIFY`, `SET` вне транзакции не найдены; есть только
  `SET LOCAL statement_timeout` внутри транзакции (это безопасно).

### 1.4. Instagram, GitLab, Heroku

Поиск в этой сессии дал данные только про GitLab (PgBouncer однопоточный, при
сильной нагрузке упирается в одно ядро, поэтому GitLab ставит несколько
процессов/узлов). Про Instagram и Heroku из поиска ничего не вернулось, ниже
общеизвестное, **в этой сессии не перепроверено**: Instagram в ранних инженерных
статьях описывал PgBouncer перед PostgreSQL, чтобы тысячи соединений сервера
приложений превращались в десятки соединений с базой; Heroku Postgres даёт
«Connection Pooling» на базе PgBouncer в режиме transaction. Общая схема у всех
одна: много дешёвых клиентских соединений -> мало дорогих серверных.
Следствие для нас: PgBouncer однопоточный, масштабируем **числом задач**, а не
размером одной (поэтому CPU у задачи 0.5-1 vCPU, а не больше).

## 2. Проект

```
api / worker (до 70 задач, Prisma pool 10 к пулу)
        |  имя pgbouncer.<имя стека>.internal  (Cloud Map, A-записи, TTL 10 с)
        |  TLS, :5432, SG tasks -> SG pgbouncer
        v
PgBouncer x2..3 (Fargate, 2 зоны, transaction mode)
        |  TLS, SG pgbouncer -> RDS
        v
RDS PostgreSQL (Multi-AZ позже)

Мимо пула: migrate-задача (MIGRATOR_DATABASE_URL), RETENTION_DATABASE_URL, DEMO_DATABASE_URL
```

### 2.1. Как приложение находит пул

| Вариант | Цена | Вывод |
|---|---|---|
| **Cloud Map: частный DNS** (`pgbouncer.lawbid-prod.internal`, A-записи, TTL 10 с, ECS `service_registries`) | ~0.5 $/мес (частная зона Route 53, которую создаёт Cloud Map; запросы копейки) | **Выбрали (решение владельца: экономия).** |
| Внутренний NLB | ~18 $/мес | Был в первой версии. Фиксированное имя и проверка здоровья, но дороже на ~17 $. Запасной вариант. |
| ECS Service Connect | 0 $ + нагрузка | Ставит прокси-сайдкар Envoy в каждую из 140 задач (память, CPU), лишний прыжок. Нет. |

Как работает: ECS сам добавляет IP задачи в DNS-имя, когда задача стартует, и
убирает его **до** сигнала остановки. Ответ DNS «мультизначный»: отдаёт адреса
обеих задач (до 8) в случайном порядке, поэтому новые соединения грубо
делятся между диспетчерами. Prisma заново ищет адрес при каждом новом
соединении, готового кеша адреса у неё нет.

**Компромисс (честно).** У Cloud Map нет проверяющего балансировщика:
- Задачу, которая «умерла» без предупреждения (сбой), DNS убирает по статусу
  задачи в ECS: это секунды, но не мгновенно. Новое соединение за это время
  может попасть на мёртвый адрес и получить ошибку подключения; Prisma
  пробует заново (следующая попытка берёт другой адрес из ответа), и через
  ~10 с (TTL) адреса уже нет.
- При плановой остановке (деплой, масштабирование) адрес убирается из DNS
  раньше сигнала остановки, а `stopTimeout = 30 с` больше TTL 10 с: диспетчер
  ещё принимает работу и корректно завершает транзакции (SIGINT).
- Уже открытые соединения к остановленной задаче рвутся, Prisma открывает новые.
- Деление нагрузки случайное, а не по числу соединений: перекос возможен,
  но каждый диспетчер ограничен своим пулом, а при CPU > 50 % добавляется третий.
- Нет простоя NLB-таймаута 350 с (прямые соединения), поэтому
  `tcp_idle_timeout` больше не нужен.
Если на нагрузочном тесте ошибок подключения при деплое пула будет заметно,
вернуть NLB (+17 $/мес): изменение локальное, в модуле `infra/modules/pgbouncer`.

### 2.2. Сеть и права

- SG PgBouncer: вход 5432 только от SG задач (api, worker, а также admin и
  migrate, они делят тот же SG `tasks`); выход 5432 (база) и 443 (ECR,
  Secrets Manager, логи).
- SG базы: добавлено правило «вход 5432 от SG PgBouncer».
- Роль выполнения PgBouncer читает **один** секрет (`DATABASE_URL`) и ключ KMS.
  Роль самой задачи без прав (метрики идут строками в лог).

**Что осталось не так строго, как просилось (честно):** SG `tasks` по-прежнему
допущен к базе, потому что через него работают прямые подключения очистки
(`RETENTION_DATABASE_URL`), «демо-мира» и migrate-задача, а они живут в тех же
задачах api/worker. Полное «только PgBouncer и migrate» требует отдельных SG для
migrate и перевода очистки через пул или отдельную задачу. Это следующий шаг,
сейчас он дал бы риск без выигрыша для проблемы соединений.

### 2.3. Пароль и TLS

- PgBouncer получает **тот же прямой `DATABASE_URL`** (ECS кладёт его из Secrets
  Manager в переменную окружения), на старте собирает `userlist.txt` (права 0600,
  в `/tmp`), конфиг и самоподписанный сертификат. Пароль нигде не печатается.
  Отдельного секрета и ручной работы нет.
- Приложение секрет **не меняет**: код (`src/prisma/pooler-url.ts`) при заданном
  `DB_POOLER_HOST` подменяет только хост/порт и ставит `sslmode=require` +
  `sslaccept=accept_invalid_certs` (шифруется, но самоподписанный сертификат
  внутри VPC не проверяется цепочкой). Это нужно, потому что в секрете
  `sslmode=verify-full` для хоста базы, а у пула имя другое. Проверка
  `env.schema.ts` (обязателен sslmode) остаётся довольна.
- К базе: `server_tls_sslmode = require` (шифрование; `verify-full` включается
  позже, если положить в образ CA RDS).

### 2.4. Настройки пула (`entrypoint.sh`)

Бюджет: 70 % от `max_connections` базы отдаём пулу (для db.t4g.micro 99: 69),
30 % остаются прямым пользователям (миграции, очистка, демо, админ, служебное,
резерв суперпользователя).

| Параметр | Значение | Почему |
|---|---|---|
| `pool_mode` | transaction | требование Prisma/масштаба |
| `default_pool_size` | `floor(69 / 3) - 3 = 20` на задачу | 3 = потолок автомасштабирования; формула в Terraform |
| `reserve_pool_size` | 3 (`reserve_pool_timeout` 3 с) | запас для ждущих |
| `max_db_connections` | 23 на задачу | жёсткий предел; 3 x 23 = **69** |
| `max_client_conn` | 5000 | у нас <= 1400 при 140 задачах x 10 |
| `max_prepared_statements` | 200 | prepared statements Prisma |
| `query_wait_timeout` | 30 с | не копить очередь вечно |
| `idle_transaction_timeout` | 120 с | зависшая транзакция не держит соединение |
| `server_lifetime` / `server_idle_timeout` | 1800 / 300 с | ротация |
| TCP keepalive | idle 30, interval 10, count 3, user_timeout 30 с | быстро заметить мёртвое соединение |

Prisma-пул внутри задачи при включённом пуле: `DB_POOL_SIZE = 10` (раньше 3 при
такой нагрузке), потому что он теперь держит только дешёвые соединения к
диспетчеру.

### 2.5. Проверка здоровья, метрики, тревоги

- ECS-проверка в контейнере: `pg_isready`; здоровье для DNS ведёт сам ECS (задача
  без прохождения проверки выпадает из имени).
- Метрики: каждые 30 с контейнер печатает строку CloudWatch EMF (из
  `SHOW POOLS`): `ClientsActive`, `ClientsWaiting`, `ServerConnections`,
  `ServerActive`, `MaxWaitSeconds`; CloudWatch сам превращает их в метрики
  (пространство `LawBid/<имя>/PgBouncer`), права IAM не нужны.
- Тревоги (в SNS «alerts», как остальные):
  1. `pgbouncer-waiting`: ждут больше 20 клиентов 3 минуты;
  2. `pgbouncer-max-wait`: самое долгое ожидание больше 5 с (2 минуты);
  3. `pgbouncer-server-connections`: >90 % лимита одной задачи 10 минут;
  4. `pgbouncer-no-healthy`: метрик от пула нет 3 минуты (ни одной работающей задачи);
  5. `pgbouncer-unhealthy`: метрик меньше, чем даёт `min_tasks` задач, 10 минут
     (одна задача не работает).
  Существующая тревога `db-connections` (80 % от max_connections базы) остаётся.

### 2.6. Автомасштабирование самого пула

Минимум 2 (в двух зонах), максимум 3 (`pgbouncer_max_tasks`), цель CPU 50 %, наружу быстро
(60 с), внутрь очень медленно (15 мин). Размер пула на задачу делится на
**максимум**, поэтому даже при 3 задачах база не увидит больше 69. Обновление
пула идёт «одна задача за раз» (min healthy 50 %, max 100 %), чтобы никогда не
превысить число задач; делать вне пика.

### 2.7. Переключение Multi-AZ RDS (failover)

Имя базы остаётся тем же, при failover DNS-запись указывает на новый узел за
60-120 с. PgBouncer: `dns_max_ttl = 15` (быстро видит новый IP), `server_check_query =
select 1` с `server_check_delay = 10` (мёртвое соединение выявляется до выдачи
клиенту), keepalive 30/10/3. Ожидаемое поведение: запросы в полёте получают
ошибку, новые ждут до `query_wait_timeout` (30 с), потом тоже ошибка, после
переключения всё работает без перезапуска приложения. Проверить на
запланированном failover в воскресенье или на тесте (`reboot-db-instance
--force-failover`).

### 2.8. Откат

`db_pooler_enabled = false` -> `terraform apply`. Что происходит: убирается
`DB_POOLER_HOST` из окружения api/worker (rolling deploy), код возвращается к
прямому `DATABASE_URL` (секрет не менялся), потом удаляются сервис, имя Cloud Map, SG
пула. Проверка бюджета при выключенном пуле снова упадёт (140 x 3 > 99), пока
`api_max_tasks`/`worker_max_tasks` не понижены или база не больше: откатывать
вместе с потолком задач (см. runbook).
Аварийный откат без Terraform: в консоли ECS у сервисов api и worker новая
ревизия без `DB_POOLER_HOST`/`DB_POOLER_PORT`.

### 2.9. Стоимость (us-east-1, цены 2026-10, ARM64)

| Статья | $/мес |
|---|---|
| 2 задачи PgBouncer x 0.5 vCPU / 1 GB (ARM64) | ~29 |
| Cloud Map: частная зона Route 53 + запросы DNS | ~0.5 |
| 5 пользовательских метрик + 5 тревог | ~2 |
| Логи | <1 |
| **Итого** | **~32** (x86: ~43) |
| (было с внутренним NLB: ~49) | -17 |
| Третий диспетчер при нагрузке | +14 на время нагрузки |

Для сравнения (из памяти, не перепроверено): RDS Proxy на db.t4g.micro стоил бы
порядка 22 $/мес (минимум 2 vCPU x 0.015 $/ч). Решение владельца «без платного
посредника» оставляет нас с нашей ценой и нашей ответственностью за работу пула.

## 4. Риски и открытое

1. **Не проверено в AWS.** Проверено локально (Docker, Postgres 16, PgBouncer 1.24,
   Prisma 6.19.3 с `sslmode=require&sslaccept=accept_invalid_certs`): prepared
   statements, интерактивные транзакции, 100 параллельных, перезапуск базы.
   Остальное докажет loadtest.
2. `pgbench -M prepared` (много клиентов, транзакции из нескольких запросов)
   зависает на PgBouncer 1.24 при клиентов больше, чем соединений с базой;
   `-M simple` и Prisma работают. Если нагрузочный тест (k6) покажет похожее,
   включить `DB_POOLER_QUERY=pgbouncer=true`.
3. Самоподписанный сертификат + `accept_invalid_certs`: шифрование есть, защиты от
   подмены хоста нет, защита только SG внутри VPC.
4. Прямые пользователи (30 соединений): `DEMO_DATABASE_URL` создаёт клиентов
   Prisma с пулом до `DB_POOL_SIZE` напрямую, в каждой задаче, где включён
   демо-режим; следить за `db-connections`.
5. Пул это новая точка отказа. Смягчение: 2 задачи в 2 зонах, тревоги, выключатель.
6. Сквозная нагрузка по CPU PgBouncer с TLS не измерена. Начальный размер 0.5 vCPU,
   автомасштабирование до 3; нагрузочный тест решит, нужно ли 1 vCPU.
7. ECR-репозиторий `lawbid-pgbouncer` создаётся в `infra/bootstrap`: сначала
   `apply` там, потом воркфлоу сборки, потом `apply` в prod.
8. Нагрузочный тест создаёт Cloud Map-имя и частную зону Route 53 от имени роли
   `lawbid-loadtest-*`. Права добавлены в `infra/bootstrap-loadtest` (политика
   `dns`): Cloud Map по тегу `Project=lawbid-loadtest`; зона Route 53 без
   ограничения по тегу (AWS такого не даёт), но записи только под
   `lawbid-loadtest.internal`. **Нужно выполнить `apply` в `infra/bootstrap-loadtest`
   до следующего теста.** Условие по именам записей не проверялось в AWS: если
   первый запуск упадёт на `route53:ChangeResourceRecordSets`, это место ослабить.
   Прод-DNS не в Route 53 (`hosted_zone_id = null`), вредить нечему; Cloud Map на
   prod создаёт ту же зону (+0.5 $).
9. Новая ловушка: если api стартует раньше, чем имя пула появилось в DNS, первые
   запросы получают ошибку подключения (Prisma повторяет). Поэтому порядок
   включения в runbook: сначала только пул (`-target`), потом остальное.
