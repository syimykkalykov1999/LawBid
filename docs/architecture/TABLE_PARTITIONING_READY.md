# Разделение больших таблиц по месяцам (partitioning)

## Для владельца (5 строк)

1. Журнал админов (`audit_log`) и события входа (`auth_events`) уже делятся по месяцам: миграция `20261026095000_partition_audit_auth`, пока таблицы крошечные, блокировка длится миллисекунды.
2. Сообщения (`messages`) и уведомления (`notifications`) пока НЕ делятся: на сообщения ссылаются 6 таблиц и есть защита от двойной отправки, у уведомлений уникальный ключ дедупликации. База не умеет держать такие правила на разделённой таблице (причины ниже).
3. Новые месяцы создаёт ночная задача `partition.maintain`; старые месяцы не удаляются (срок хранения не задан, включается одной строкой).
4. На «Масштаб» у каждой таблицы карточка: строки, размер, «по месяцам: да/нет», кнопка «Запустить» (2FA + второй админ), прогресс, пауза, «Вернуть как было» (быстро, пока старая копия не удалена). Сигнал «таблица перешла 50 млн строк» виден в «Здоровье системы».
5. Проверено на локальной базе с 1,5 млн строк: глубокие страницы журнала в 16 раз быстрее, первые страницы в пределах шума (цифры ниже); Prisma, внешние ключи и откат работают.

## Что и почему

| Таблица | Решение | Причина |
|---|---|---|
| `audit_log` | разделена по `created_at`, месяц | только добавление, нет ссылок на неё, чтение «новые сверху» |
| `auth_events` | разделена по `created_at`, месяц | то же |
| `search_query_log` | пока нет | в базе ничего не мешает, но третий составной ключ в `schema.prisma` ломает типы Prisma-клиента (TS2589 в `prisma.service.ts`, клиент уже на пределе глубины типов TypeScript). Вернуться после упрощения типов |
| `data_access_log` | кандидат для кнопки | ключ `accessed_at`, мало строк |
| `notifications` | нет | частичный уникальный индекс `(user_id, dedupe_key)` без `created_at`: PostgreSQL не может держать уникальность поперёк кусков. Менять правило дедупликации нельзя |
| `messages` | нет | 6 внешних ключей на `messages(id)` (ответы, скрытые, реакции, правки, закрепы, сохранённые) и уникальный `(conversation_id, sender_id, client_message_id)` против повторной отправки: оба правила нельзя сохранить без `created_at` |

Для `messages` и `notifications` скорость не причина отказа, а целостность данных. Когда придёт время, путь такой: добавить `created_at` в дочерние таблицы и переписать правила (отдельный проект с изменением кода), либо уходить на шардирование (`SHARDING_READY.md`).

## Как это делают другие (источники, 2026)

- Первичный и уникальные ключи разделённой таблицы обязаны включать ключ раздела; внешний ключ ссылаться только на такой составной ключ: [oneuptime, 2026-08-13](https://oneuptime.com/blog/post/2026-08-13-postgresql-mysql-unique-keys-include-partition-key/markdown), документация PostgreSQL (CREATE TABLE, раздел Partitioning).
- Prisma не создаёт разделённые таблицы; DDL пишут руками в миграции `--create-only`, а `schema.prisma` описывает составной ключ, иначе `prisma migrate diff` видит расхождение: [Spur, dev.to](https://dev.to/shivsarthak/surviving-the-scale-inside-spurs-database-partitioning-makeover-with-postgresql-5c9h), [prisma/prisma#1708](https://github.com/prisma/prisma/issues/1708). У нас: `@@id([id, created_at])`, проверка «нет расхождений» в CI проходит.
- Живое превращение большой таблицы без простоя: новая разделённая таблица + триггер копирования + пакетное копирование + короткая смена имён: [oneuptime, 2026-08-13](https://oneuptime.com/blog/post/2026-08-13-live-postgresql-table-declarative-partitioning-minimal-downtime/markdown). Именно так устроен наш ранер (`apps/api/src/partitioning/partition-runner.ts`). `pg_partman.partition_data_proc` делает то же копирование, но не даёт обратного триггера, поэтому «Вернуть как было» там быстрым не бывает.

### Почему не pg_partman

`pg_partman` на RDS доступен, но для месячных кусков нужны только две вещи: заранее создавать будущие месяцы и (по желанию) отцеплять старые. Это 40 строк SQL (`lawbid_ensure_month_partitions`, `lawbid_detach_old_partitions` в миграции) и ночная задача, без расширения, без прав `CREATE EXTENSION` для роли миграций и без фонового воркера `pg_partman_bgw` (он требует `shared_preload_libraries` и перезагрузки базы). Имена кусков `таблица_pГГГГ_ММ` совпадают с форматом pg_partman: если когда-нибудь понадобится его retention, его можно подключить поверх (`create_parent` на уже разделённой таблице), это не проверено локально, расширения в образе нет.

## Замеры (локальный PostgreSQL 16, 1,5 млн строк за 24 месяца, prepared statements, pgbench)

Запросы те, что шлёт `GET /admin/audit-log` (Prisma: `ORDER BY created_at DESC, id DESC LIMIT 51`, курсор `(created_at < X OR (created_at = X AND id < Y))`, фильтры admin_id / target / action). «Плоская» = та же таблица без разделения, те же индексы.

| Запрос | плоская | по месяцам, 29 кусков (24 мес. истории) | по месяцам, старт (7 кусков, 123 тыс. строк) плоская → по месяцам |
|---|---|---|---|
| первая страница | 0,085 мс | 0,136 мс | 0,083 / 0,106 → 0,123 / 0,124 |
| страница по курсору (глубоко) | 91,3 мс | 5,7 мс | 1,0 / 1,3 → 0,65 / 1,0 |
| по админу | 0,164 мс | 0,210 мс | 0,138 / 0,161 → 0,177 / 0,149 |
| диапазон 30 дней | 0,086 мс | 0,122 мс | 0,090 / 0,134 → 0,120 / 0,094 |
| по цели | 0,074 мс | 0,099 мс | 0,072 / 0,076 → 0,090 / 0,068 |
| по действию (префикс) | 0,267 мс | 0,416 мс | 0,177 / 0,243 → 0,202 / 0,153 |
| вставка одной строки | 0,016 мс | 0,010 мс | |

Честно: при двух годах истории и 29 кусках короткие запросы медленнее на 0,02-0,15 мс (это время планирования по числу кусков); два повторных прогона на старте (7 кусков) дают разброс ±0,03 мс, то есть различий не видно. Глубокие страницы (самый дорогой запрос журнала) быстрее в 16 раз, потому что планировщик отбрасывает куски по `created_at`. Проверено, что узкое место не в самом разделении: с нижней границей `created_at >= now() - 35 дней` запрос с 29 кусками идёт за 0,094 мс против 0,085 плоской. При росте истории: окно «последние N дней, потом шире» в сервисе журнала, и более крупные куски (квартал) - не дали стабильного выигрыша в замерах, поэтому не внедрены.

Что НЕ измерялось: чат (`messages`) и уведомления остались неразделёнными, их запросы не менялись.

## Prisma, ключи, проверки

- `schema.prisma`: `@@id([id, created_at])` у `AuditLog` и `AuthEvent`. Нигде в коде нет `findUnique`/`update`/`delete` по одному `id` для этих моделей (`tsc` чистый). Поиск по `id` в БД проходит индекс первичного ключа по всем кускам.
- Внешние ключи наружу (`admin_id` и `user_id` на `users`) сохранены на разделённой таблице и проверены: неверный `admin_id` отвергается.
- Права сохраняются точно (у `lawbid_app` остаются только INSERT/SELECT на журнал).
- `prisma migrate diff` — «No difference detected»; `scripts/migrate-from-previous.mjs` — OK (обновление поверх предыдущего набора миграций).
- Шарды: у этих таблиц нет триггера `shard_fill`, они в манифесте как «глобальные»; тесты `src/sharding` проходят. Перенос шарда логической репликацией: публикация должна быть с `publish_via_partition_root = true`.
- Блокировка при миграции: функция берёт `ACCESS EXCLUSIVE` с `lock_timeout 5s`; 20 000 строк целиком за 342 мс, пустые таблицы за миллисекунды. Больше 2 млн строк миграция откажется (`RAISE EXCEPTION`) и ничего не изменит: для таких таблиц ранер.

## Онлайн-ранер для будущих таблиц (кнопка и CLI)

`apps/api/src/partitioning/partition-runner.ts`: проверки (`precheck`), сухой прогон (`plan`), шаги `prepare → backfill → verify → swap → swapped → done`, пауза, возобновление, `abort` (до переключения), `undo` (после, быстрым переименованием), `finalize` (через 7 дней, удаляет старую копию). Состояние в таблице `_partition_job` (создаётся ранером, не миграцией). Роль с правами владельца таблицы: `PARTITION_DATABASE_URL` (секрет, не `lawbid_app`). Задача `partition.tick` двигает работу раз в минуту, 40 секунд за раз. Сквозной тест: `sh scripts/ops/partition-selftest.sh` (docker, 7 проверок: запись во время копирования не теряется, имена индексов, ключ `(id, created_at)`, обратная синхронизация, undo, пауза, abort).

Ограничения ранера (проверяются, иначе кнопка недоступна и карточка пишет причину): нет внешних ключей на таблицу, уникальные индексы содержат ключ раздела, нет serial/identity, нет своих триггеров, есть индекс с `created_at` первой колонкой.

«Вернуть как было»: безопасный путь есть, пока жива старая копия (обратный триггер держит её полной). После «Завершить» отката кнопкой нет, только отдельная медленная работа обратного копирования.

## Сигнал роста

Элемент `table_growth` в «Здоровье системы»: жёлтый, если неразделённая таблица перешла 50 млн строк (оценка из `pg_class`, бесплатно). Разделённые таблицы сигнала не дают: это и есть лекарство.
