# Разделение больших таблиц (partitioning): по месяцам и по хешу

## Для владельца

1. Журнал админов (`audit_log`) и события входа (`auth_events`) делятся по месяцам онлайн-ранером, когда админ нажмёт «Запустить». Миграция `20261107114000_partition_audit_auth` только добавляет функции обслуживания месяцев: она ничего не копирует, не блокирует таблицы и не может сорвать выкладку (разбор 2026-10-26, R-20).
2. Сообщения чатов (`messages`), сообщения групп (`chat_group_messages`) и уведомления (`notifications`): разделение по ХЕШУ (16 кусков: по чату, по группе, по человеку) сделано, но ВЫКЛЮЧЕНО. На малых объёмах обычные таблицы быстрее (замеры ниже: список чатов с кусками медленнее в 7 раз). Включается кнопкой на «Масштаб»: «Выкл / Вкл / Авто», «Авто» начинает само, когда в таблице станет 50 млн строк (порог меняется в админке, `partition.auto_rows`).
3. Миграция `20261107114400_partition_messages_notifications` только готовит почву (составные ключи, колонка чата у дочерних таблиц), таблицы остаются обычными и не медленнее (замеры ниже). Она только расширяет схему: уникальные индексы строятся `CONCURRENTLY` (три отдельные миграции 20261107114100/220000/230000), ключи переставляются на готовый индекс, внешние ключи добавляются `NOT VALID` и потом проверяются, таблицы не переписываются. Если какая-то из таблиц уже больше 2 млн строк (по статистике, без подсчёта) или занята дольше 5 с, миграция пишет NOTICE и пропускает шаг, выкладка не падает; шаг потом запускают вручную (инструкция). Само превращение делает только онлайн-ранер в фоне, без остановки приложения, и только когда его включили.
4. Новые месяцы (для месячных таблиц) создаёт ночная задача `partition.maintain`; старые месяцы не удаляются (срок хранения не задан, включается одной строкой).
5. На «Масштаб» у каждой таблицы карточка: строки, размер, «по месяцам/по хешу: да/нет», переключатель «Выкл / Вкл / Авто» (для хеш-таблиц), кнопка «Запустить» (код 2FA), прогресс, пауза, «Вернуть как было» (быстро, пока старая копия не удалена). Сигнал «таблица перешла 50 млн строк» виден в «Здоровье системы».
6. Проверено на локальной базе с 1,5 млн строк: глубокие страницы журнала в 16 раз быстрее, первые страницы в пределах шума (цифры ниже); Prisma, внешние ключи и откат работают.

## Что и почему

| Таблица | Решение | Причина |
|---|---|---|
| `audit_log` | делит ранер по `created_at`, месяц | только добавление, нет ссылок на неё, чтение «новые сверху» |
| `auth_events` | делит ранер по `created_at`, месяц | то же |
| `search_query_log` | пока нет | в базе ничего не мешает, но третий составной ключ в `schema.prisma` ломает типы Prisma-клиента (TS2589 в `prisma.service.ts`, клиент уже на пределе глубины типов TypeScript). Вернуться после упрощения типов |
| `data_access_log` | кандидат для кнопки | ключ `accessed_at`, мало строк |
| `notifications` | хеш по `user_id`, 16 кусков, ВЫКЛ по умолчанию | ключ `(id, user_id)` готовит миграция; частичный уникальный `(user_id, dedupe_key)` содержит ключ раздела и остаётся; превращает ранер (Вкл / Авто на 50 млн) |
| `messages` | хеш по `conversation_id`, 16 кусков, ВЫКЛ по умолчанию | ключ `(id, conversation_id)`; защита от двойной отправки остаётся; дочерние таблицы (реакции, правки, скрытые, закрепы, сохранённые, ответ внутри `messages`) получили колонку `conversation_id` и составной внешний ключ; ранер перевешивает эти ключи на новую таблицу при переключении |
| `chat_group_messages` | хеш по `group_id`, 16 кусков, ВЫКЛ по умолчанию | то же: ключ `(id, group_id)`, опросы и ответы ссылаются на `(group_id, id)` |

Хеш-разделение — по желанию (opt-in): на малых объёмах обычные таблицы быстрее, ранер превращает таблицу при ~50 млн строк (или когда вы нажали «Вкл»). Хеш-куски не нужно ни создавать, ни удалять: ночная задача их не трогает. Три режима на карточке: «Выкл» (по умолчанию), «Вкл» (начать в ближайшую минуту), «Авто» (начать, когда строк станет `partition.auto_rows`, по умолчанию 50 млн). После «Вернуть как было» или «Остановить» режим сам возвращается в «Выкл», чтобы таблицу не превращали снова. Ответ может ссылаться только на сообщение своего же чата (в коде так всегда было; миграция обнуляет чужие ссылки, если они вдруг есть). Если в какой-то из таблиц уже больше 2 млн строк (оценка по статистике) или таблица занята, миграция НЕ падает: пишет NOTICE и пропускает перестройку ключа; тогда её запускают руками в тихий час: `SELECT lawbid_messages_composite_keys(<лимит строк>);` (инструкция).

## Как это делают другие (источники, 2026)

- Первичный и уникальные ключи разделённой таблицы обязаны включать ключ раздела; внешний ключ ссылаться только на такой составной ключ: [oneuptime, 2026-08-13](https://oneuptime.com/blog/post/2026-08-13-postgresql-mysql-unique-keys-include-partition-key/markdown), документация PostgreSQL (CREATE TABLE, раздел Partitioning).
- Prisma не создаёт разделённые таблицы; DDL пишут руками в миграции `--create-only`, а `schema.prisma` описывает составной ключ, иначе `prisma migrate diff` видит расхождение: [Spur, dev.to](https://dev.to/shivsarthak/surviving-the-scale-inside-spurs-database-partitioning-makeover-with-postgresql-5c9h), [prisma/prisma#1708](https://github.com/prisma/prisma/issues/1708). У нас схема оставляет `@id id` (как для `data_access_log`): ключ в базе расширяет только ранер при переключении.
- Живое превращение большой таблицы без простоя: новая разделённая таблица + триггер копирования + пакетное копирование + короткая смена имён: [oneuptime, 2026-08-13](https://oneuptime.com/blog/post/2026-08-13-live-postgresql-table-declarative-partitioning-minimal-downtime/markdown). Именно так устроен наш ранер (`apps/api/src/partitioning/partition-runner.ts`). `pg_partman.partition_data_proc` делает то же копирование, но не даёт обратного триггера, поэтому «Вернуть как было» там быстрым не бывает.

### Почему не pg_partman

`pg_partman` на RDS доступен, но для месячных кусков нужны только две вещи: заранее создавать будущие месяцы и (по желанию) отцеплять старые. Это 40 строк SQL (`lawbid_ensure_month_partitions`, `lawbid_detach_old_partitions` в миграции) и ночная задача, без расширения, без прав `CREATE EXTENSION` для роли миграций и без фонового воркера `pg_partman_bgw` (он требует `shared_preload_libraries` и перезагрузки базы). Имена кусков `таблица_pГГГГ_ММ` совпадают с форматом pg_partman: если когда-нибудь понадобится его retention, его можно подключить поверх (`create_parent` на уже разделённой таблице), это не проверено локально, расширения в образе нет.

## Замеры (локальный PostgreSQL 16, 1,5 млн строк за 24 месяца, prepared statements, pgbench)

Запросы те, что шлёт `GET /admin/audit-log` (Prisma: `ORDER BY created_at DESC, id DESC LIMIT 51`, курсор `(created_at < X OR (created_at = X AND id < Y))`, фильтры admin_id / target / action). «Плоская» = та же таблица без разделения, те же индексы.

| Запрос | плоская | по месяцам, 29 кусков (24 мес. истории) | по месяцам, старт (7 кусков, 123 тыс. строк) плоская → по месяцам |
|---|---|---|---|
| первая страница | 0,085 мс | 0,136 мс | 0,083 / 0,106 → 0,123 / 0,124 |
| страница по курсору (глубоко) | 91,3 мс | 5,7 мс | 1,0 / 1,3 → 0,65 / 1,0 |
| по админу | 0,164 мс | 0,210 мс | 0,138 / 0,161 → 0,177 / 0,149 |
| диапазон 30 дней | 0,086 мс | 0,122 мс | 0,090 / 0,134 → 0,120 / 0,094 |
| по цели | 0,074 мс | 0,099 мс | 0,072 / 0,076 → 0,090 / 0,068 |
| по действию (префикс) | 0,267 мс | 0,416 мс | 0,177 / 0,243 → 0,202 / 0,153 |
| вставка одной строки | 0,016 мс | 0,010 мс | |

Честно: при двух годах истории и 29 кусках короткие запросы медленнее на 0,02-0,15 мс (это время планирования по числу кусков); два повторных прогона на старте (7 кусков) дают разброс ±0,03 мс, то есть различий не видно. Глубокие страницы (самый дорогой запрос журнала) быстрее в 16 раз, потому что планировщик отбрасывает куски по `created_at`. Проверено, что узкое место не в самом разделении: с нижней границей `created_at >= now() - 35 дней` запрос с 29 кусками идёт за 0,094 мс против 0,085 плоской. При росте истории: окно «последние N дней, потом шире» в сервисе журнала, и более крупные куски (квартал) - не дали стабильного выигрыша в замерах, поэтому не внедрены.

## Замеры по хешу (локальный PostgreSQL 16, 1 млн сообщений, 20 тыс. чатов, 1 млн уведомлений, 4 тыс. людей)

Скрипт `scripts/perf/hash-partition-bench.sh` (`BENCH_SCALE=2`), pgbench, 1 клиент, prepared; время самого запроса в мс. Три состояния одной и той же базы: обычная таблица, обычная таблица после миграции-подготовки, разделённая по хешу (16 кусков).

| Запрос | обычная | после миграции (ключ `(id, чат)`, всё ещё обычная) | разделённая по хешу |
|---|---|---|---|
| история чата (50 сообщений) | 0,27 | 0,32 | 0,31 |
| последнее сообщение по каждому чату (список чатов) | 0,33 | 0,43 | 2,54 |
| непрочитанные по чатам | 0,50 | 0,78 | 3,55 |
| сообщение по одному `id` (без чата) | 0,18 | 0,17 | 0,79 |
| сообщение по `(чат, id)` | 0,16 | 0,23 | 0,15 |
| список уведомлений | 0,22 | 0,17 | 0,22 |
| бейдж непрочитанных | 0,18 | 0,16 | 0,17 |
| дедуп-вставка уведомления | 0,22 | 0,17 | 0,19 |
| закреплённые | 0,26 | 0,26 | 0,27 |
| ответы на сообщение | 0,14 | 0,16 | 0,16 |

Честно: (1) миграция-подготовка не замедляет: планы те же (EXPLAIN «непрочитанные»: 0,106 -> 0,128 мс при одинаковом плане), разброс между прогонами на этой машине около 20-30%. (2) Разделение по хешу на 1 млн строк МЕДЛЕННЕЕ на запросах «по многим чатам сразу»: само выполнение около 0,1 мс, остальное — планирование по 16 кускам (Planning Time 0,6 мс). Поэтому разделение выключено по умолчанию и включается на объёмах, где оно окупается (сотни миллионов строк: меньше индексы, быстрее обслуживание, готовность к шардированию), по умолчанию с 50 млн. (3) Колонка «разделённая» сделана прямой конверсией той же базы, в рабочем режиме её делает ранер (проверен тестом `hash-partition.int.spec.ts` на реальной базе: записи во время копирования не теряются, ответы и внешние ключи работают, откат переименованием).

## Онлайн-превращение в хеш (ранер)

Те же шаги, что у месячного (новая таблица, триггер копирования, пакеты, сверка, смена имён, обратный триггер, «Вернуть как было» до «Завершить» через 7 дней), плюс: копируются целые группы по ключу (все сообщения 100 чатов за раз, чтобы ответ и его родитель попали в один запрос); внешний ключ ответов на новой таблице создаётся пустым и `DEFERRABLE INITIALLY DEFERRED`, триггер копирования подтягивает цепочку «на что ответили»; в момент переключения триггеры (`shard_fill`) переносятся на новую таблицу, а внешние ключи других таблиц (реакции, правки и т.д.) перевешиваются на неё (добавляются `NOT VALID` и сразу проверяются без блокировки записи); при откате всё возвращается обратно. Нужна та же роль-владелец (`PARTITION_DATABASE_URL`): она должна владеть и дочерними таблицами.

## Research → choice → why

- Хеш, а не месяц: уникальность «защита от двойной отправки» и `(user_id, dedupe_key)` не содержат даты, а ключ раздела обязан быть в каждом уникальном правиле ([oneuptime, 2026-08-13](https://oneuptime.com/blog/post/2026-08-13-postgresql-mysql-unique-keys-include-partition-key/markdown), документация PostgreSQL). Хеш-ключ (чат, группа, человек) уже есть во всех правилах.
- Не разделять сразу, а по порогу: у разделённых таблиц цена планирования растёт с числом кусков; выигрыш — на больших объёмах (измерено выше). Поэтому «Выкл / Вкл / Авто на 50 млн».
- Свой ранер, а не `pg_partman`: нужен обратный триггер для быстрого «Вернуть как было», а `pg_partman.partition_data_proc` его не даёт; для хеша месячные задачи не нужны вовсе.

## Prisma, ключи, проверки

- `schema.prisma`: `@@id([id, created_at])` у `AuditLog` и `AuthEvent`. Нигде в коде нет `findUnique`/`update`/`delete` по одному `id` для этих моделей (`tsc` чистый). Поиск по `id` в БД проходит индекс первичного ключа по всем кускам.
- Внешние ключи наружу (`admin_id` и `user_id` на `users`) сохранены на разделённой таблице и проверены: неверный `admin_id` отвергается.
- Права сохраняются точно (у `lawbid_app` остаются только INSERT/SELECT на журнал).
- `prisma migrate diff` — «No difference detected»; `scripts/migrate-from-previous.mjs` — OK (обновление поверх предыдущего набора миграций).
- Шарды: у этих таблиц нет триггера `shard_fill`, они в манифесте как «глобальные»; тесты `src/sharding` проходят. Перенос шарда логической репликацией: публикация должна быть с `publish_via_partition_root = true`.
- Блокировка при миграции: нет. Миграция только создаёт функции; таблицы делит онлайн-ранер (копия в фоне, короткое переключение с `lock_timeout`), поэтому выкладка не зависит от размера таблиц.

## Онлайн-ранер для будущих таблиц (кнопка и CLI)

`apps/api/src/partitioning/partition-runner.ts`: проверки (`precheck`), сухой прогон (`plan`), шаги `prepare → backfill → verify → swap → swapped → done`, пауза, возобновление, `abort` (до переключения), `undo` (после, быстрым переименованием), `finalize` (через 7 дней, удаляет старую копию). Состояние в таблице `_partition_job` (создаётся ранером, не миграцией). Роль с правами владельца таблицы: `PARTITION_DATABASE_URL` (секрет, не `lawbid_app`). Задача `partition.tick` двигает работу раз в минуту, 40 секунд за раз. Сквозной тест: `sh scripts/ops/partition-selftest.sh` (docker, 7 проверок: запись во время копирования не теряется, имена индексов, ключ `(id, created_at)`, обратная синхронизация, undo, пауза, abort).

Ограничения ранера (проверяются, иначе кнопка недоступна и карточка пишет причину): нет внешних ключей на таблицу, уникальные индексы содержат ключ раздела, нет serial/identity, нет своих триггеров, есть индекс с `created_at` первой колонкой.

«Вернуть как было»: безопасный путь есть, пока жива старая копия (обратный триггер держит её полной). После «Завершить» отката кнопкой нет, только отдельная медленная работа обратного копирования.

## Сигнал роста

Элемент `table_growth` в «Здоровье системы»: жёлтый, если неразделённая таблица перешла 50 млн строк (оценка из `pg_class`, бесплатно). Разделённые таблицы сигнала не дают: это и есть лекарство.
