# Эксперименты и журнал показов (A/B)

## Для владельца (5 строк)

1. Новая формула ленты (дел, людей, поиска) сначала проверяется на 5-10% людей: «Система → Эксперименты» → «Новый тест» → «Запустить на 5%» (нужен код 2FA, второй админ не нужен).
2. Каждую ночь считается отчёт простыми словами: клики по верхним местам, дело → отклик → принят, часы до первого отклика, дела без откликов за сутки, получили ли новые адвокаты хотя бы одно дело, пустые поиски, жалобы на 1000 показов; у каждого числа указан диапазон, и сказано «лучше / хуже / разницы не видно / мало данных».
3. Если жалобы или ошибки растут сильнее порога (по умолчанию +25%), тест останавливается сам и в карточке написано почему. Если люди поделились между вариантами не так, как задумано (проверка SRM), страница прямо говорит не верить цифрам.
4. «Остановить» возвращает всем прежнюю работу за секунды. Доля «Функций» (rollout_percent) теперь тоже работает: 30% значит 30% людей, одни и те же каждый раз; приложение читает свои флаги с `GET /config/flags`, а публичный bootstrap показывает частично включённый флаг как выключенный.
5. Журнал показов (`ranking_events`) режется по неделям, хранится 90 дней, старые недели удаляются сами; показы и клики пишутся только для 10% людей (потолок, настройка «Настройки → ranking.impression_sample_percent») и только пока идёт хоть один тест (переключатель «Выкл / Вкл / Авто» — `ranking.events_mode`, по умолчанию Авто), поэтому база почти не растёт. Новые веса формулы можно проверить на сохранённых показах заранее: `node dist/src/cli/ranking-replay.js`. Приложение внешне не менялось: тесты включают только серверное поведение, пока разработчик не подключит конкретный экран.

## Что выбрали и почему (исследование, 2025-2026)

Решение: **собственный маленький модуль без внешнего сервиса**, устроенный так же, как SDK GrowthBook (хеш от «человек + ключ теста» → 0..1 → доли вариантов), а статистика считается в нашем коде по нашим таблицам. Цена: 0 долларов, ничего нового не нужно запускать и оплачивать.

| Вариант | Что нашли | Почему не взяли |
|---|---|---|
| GrowthBook (MIT, самохостинг) | Есть последовательные тесты, CUPED, SRM, защитные метрики ([документация статистики](https://docs.growthbook.io/statistics/overview), без даты). Самохостинг: образ Docker + обязательная MongoDB ([self-host](https://docs.growthbook.io/self-host), без даты, стабильный тег 4.1.0 в примере) и источник данных для анализа. | Отдельный сервер + MongoDB ≈ ещё одно платное приложение, которое надо обновлять и защищать. Его SDK умеет только назначать вариант, а это у нас 20 строк (`assignVariant`). Остальное он считает по SQL-запросам к нашей же базе, то есть те же самые запросы нам пришлось бы писать и ему. Подключить его позже можно: наши таблицы `ranking_events` и `experiment_exposures` читаются как обычный источник данных Postgres. |
| Statsig | Бесплатный тариф, CUPED, последовательные тесты, SRM ([Best Open Source Experimentation Tools, Statsig, 2025-08-02](https://statsig.com/comparison/best-open-source-experimentation-tools), страница вендора); в сентябре 2025 Statsig купил OpenAI (по сравнительным страницам, не проверено независимо). | Облако вендора, события уходят наружу, условия тарифа меняются; страницы сравнений написаны самими вендорами, цифры тарифов в источниках противоречат друг другу. |
| Eppo | Расширенная статистика поверх склада данных, цена «по запросу» ([Best A/B Testing Tools for Product Experiments in 2026, Listen Labs](https://blog.listenlabs.ai/?p=257), 2026, без точной даты). | Нужен склад данных (Snowflake / BigQuery) и договор. |
| PostHog experiments | Байесовский расчёт, SRM, защитные метрики; без CUPED и без последовательных тестов в частотном смысле ([Top 7 alternatives to PostHog, Spotify Confidence](https://confidence.spotify.com/comparisons/alternatives-to-posthog.md), страница конкурента, без даты; то же про CUPED в Statsig, 2025-08-02). Самохостинг: Kafka + ClickHouse ([Statsig, 2025-08-02](https://statsig.com/comparison/best-open-source-experimentation-tools)). | Тяжёлая инфраструктура или отправка событий в облако. |

Оговорка по источникам: почти всё найденное написано вендорами или их конкурентами, точных дат у документации нет. Поэтому в код взяты только общепринятые методы, их можно проверить по учебникам: хеш-назначение, критерий хи-квадрат для SRM, интервал Уилсона для долей, дельта-метод для отношений «клики / показы» (учитывает, что один человек даёт много показов), NDCG@k для оффлайн-проверки.

Что сознательно НЕ сделано:

- **CUPED** (снижение разброса по данным «до теста»). На маленьком рынке адвокатов данных «до» мало, выигрыш небольшой. Поле `experiment_exposures.first_at` и журнал позволяют добавить позже.
- **Формальные последовательные тесты (mSPRT)**. Вместо них: решение «лучше / хуже» принимается по обычному 95% интервалу и только как подсказка (в карточке есть «мало данных» до 100 людей в варианте), а автоостановка по защитным метрикам использует строгий порог (z = 3,09, то есть 99,9% с одной стороны), чтобы ежедневные просмотры не давали ложных срабатываний. Это не математически безупречный последовательный тест; для остановки «на всякий случай» достаточно.
- Автоматическое «выиграл, включить всем»: включает человек (кнопка «Увеличить долю» с 2FA, и то, что победитель станет формулой по умолчанию, делает разработчик).

## Как это устроено

### Назначение варианта
`apps/api/src/modules/experiments/experiments.service.ts`

```ts
const v = await this.experiments.variant(user.id, 'case_feed_v2');
// null = не в тесте или тест остановлен: работать как раньше
// 'control' | 'new_formula': применить вариант
```

- Хеш: тот же `hash01()` из `recommendations/ranking.math.ts` (FNV-1a). Сначала «ворота доли» (`ключ:traffic:человек`), потом вариант по накопленным весам (`ключ:variant:человек`). Повышение доли 5% → 50% не выбрасывает уже попавших.
- Единица назначения — любая стабильная строка (id человека, а для тестов на делах id дела).
- Определения читаются из базы раз в 15 секунд на каждый сервер; остановка действует на этом сервере сразу, на остальных до 15 секунд. Ошибка базы = «не в тесте» (ничего не ломается).
- Первое попадание записывается в `experiment_exposures` пачкой (`ON CONFLICT DO NOTHING`); по этой таблице считается SRM.
- `assign()` отдаёт `{experimentKey, variant}`, чтобы передать в журнал.

### Журнал показов и действий
`ranking-events.service.ts`: `logImpression(...)` и `logAction(kind, ...)`. Не бросают ошибок и не ждут базу: строки копятся в памяти и пишутся одной пачкой (раз в 2 секунды или по 200 штук; при перегрузке старые отбрасываются). Виды: `impression, click, bid, accept, reply, report, error, search, case_posted`.

```ts
await this.rankingEvents.logImpression({
  userId, surface: 'case_feed', itemId: caseId, listId, position: 3,
  formulaVersion: 'cases-2026-10', experimentKey, variant,
  features: { urgency: 0.8, practice: 1 },   // 0..1, для оффлайн-проверки
});
await this.rankingEvents.logAction('bid', { userId, surface: 'case_feed', itemId: caseId, experimentKey, variant });
```

- Выборка: показы и клики пишутся только для `ranking.impression_sample_percent` % людей (по хешу человека, одни и те же люди), остальное (отклики, принятия, жалобы, ошибки, поиски, новые дела) пишется всегда.
- Таблица `ranking_events`: только добавление (у роли приложения отозваны UPDATE / DELETE / TRUNCATE), ключ `(id, created_at)`.
- **Разделы по неделям** (схема как в `TABLE_PARTITIONING_READY.md`, PR #334: декларативное `PARTITION BY RANGE (created_at)`, ключ раздела входит в первичный ключ, раздел `DEFAULT` ловит опоздавшие строки, функции `SECURITY DEFINER` для создания разделов, потому что роль приложения таблицы создавать не может). Выбрана неделя, а не месяц, потому что срок хранения 90 дней: месячный раздел удалялся бы с запасом до месяца. Названия `ranking_events_pГГГГММДД` (понедельник). Функции `lawbid_ranking_ensure_partitions(недель_вперёд)` и `lawbid_ranking_drop_old_partitions(дней)` называются отдельно от функций #334, чтобы два PR не конфликтовали. Их вызывает ночная задача `experiments.metrics`; удаление недели = `DROP TABLE` раздела, без тяжёлого `DELETE`.
- На таблицу никто не ссылается, поэтому проблем с внешними ключами нет. Данные удалённого пользователя уходят сами через 90 дней (в журнале только id, без имён и текстов).
- В манифесте шардов все 4 модели — `global` (`apps/api/src/sharding/shard-manifest.ts`). Перед «предстартовой очисткой» эти таблицы в списке «стереть»; разделы журнала считаются той же таблицей.

### Ночной отчёт (`experiments.metrics`, 02:20 UTC)
`experiment-metrics.service.ts`, `experiments-nightly.job.ts`. Для каждого идущего теста: интервалы по вариантам и сравнение с `control`, проверка SRM, защитные метрики, запись в `experiment_results` (последние 30 отчётов на тест), остановка по сроку (`end_at`) или по защите.

| Показатель | Как считается | Метод интервала |
|---|---|---|
| CTR@k (k=5, настройка `experiments.ctr_k`) | клики на местах 1..k / показы на местах 1..k | дельта-метод по людям |
| дело → отклик | отклики / показанные дела | дельта-метод |
| отклик → принят | принятия / отклики | дельта-метод |
| часы до первого отклика (до 24) | по делам старше суток | среднее, нормальный интервал |
| дела без откликов за 24 ч | доля дел | Уилсон |
| новые адвокаты получили хотя бы одно дело | зарегистрированы за 30 дней до входа в тест; доля с показом | Уилсон |
| поиски без результата | поиски с 0 результатов / поиски | дельта-метод |
| жалобы на 1000 показов, ошибки на 1000 показов | событие / показы × 1000 | дельта-метод |

В отношения «событие / показы» входят только люди, у которых есть показы (то есть попавшие в выборку), так что выборка не искажает доли. Справедливость для новых адвокатов считается тоже только по людям из выборки показов.

Защита: для жалоб и ошибок вариант хуже `control` больше чем на порог (в процентах, по умолчанию 25) и при этом нижняя граница интервала разницы выше нуля (z = 3,09) и показов не меньше минимума (по умолчанию 1000 на вариант) → тест остановлен, `stopped_by_system = true`, причина в карточке. Второго админа не нужно, а остановленный тест заново не запускают (создают новый).

SRM: критерий хи-квадрат по числу попавших людей против заданных долей, тревога при p < 0,001.

### Оффлайн-проверка новых весов
`ranking-replay.ts` и `apps/api/src/cli/ranking-replay.ts`:

```
node dist/src/cli/ranking-replay.js --surface=people --days=14 --k=10 \
  --weights='{"contact":0.3,"state":0.1,"practice":0.2,...}'
```

Берёт сохранённые показы (с признаками `features`), заново считает оценку новыми весами, переставляет списки и сравнивает NDCG@10 порядка, который видели люди, и нового (оценка: клик 1, отклик 2, принят 3, в пределах 24 часов), с интервалом по спискам. Ограничение: можно оценить только то, что людям уже показали; формула, которая вытащила бы то, чего никто не видел, оффлайн не проверяется. Поэтому оффлайн-проверка отсекает плохие изменения, а хорошие подтверждаются тестом на 5-10%.

### Доля флага (`rollout_percent`)
`feature-flags.service.ts`: `isEnabledFor(key, default, userId)` и `getFlagsFor(userId)`. Включённый флаг с долей меньше 100 включён для этой доли людей (хеш `flag:<ключ>:<человек>`), 0 = выключен. Публичный `GET /config/bootstrap` (кешируется на CDN, человека не знает) показывает такой флаг выключенным; приложение может прочитать свои флаги после входа на `GET /config/flags` (без кеша). Подключение этого запроса в приложении — отдельная задача и внешний вид не меняет.

### Админка
`Система → Эксперименты` (только владелец). Все запуски, повышения доли и остановки пишутся в журнал аудита (`experiment.create / start / traffic / stop`).

## Проверено

- Юнит-тесты: назначение (равномерность, независимость тестов, повышение доли не выбрасывает попавших), SRM, интервалы, NDCG, отчёт на подставных данных (находит рост CTR, срабатывает защита по жалобам, не срабатывает на малом объёме), журнал (выборка по человеку, пачка, отказ базы), сервис админки (лимит старта, переходы состояний), доля флагов.
- Миграция и функции разделов прогнаны на чистом PostgreSQL 16 (см. описание PR).
