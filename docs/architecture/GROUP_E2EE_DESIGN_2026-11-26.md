# Сквозное шифрование групп (как группы WhatsApp)

Статус: проект, фаза 1 (исследование и решение, кода нет). Дата: 2026-11-26. Приказ владельца: «лечи» — группы должны шифроваться от телефона до телефона, как группы WhatsApp. Продолжение плана [`E2EE_MLS_PLAN_2026-11-25.md`](E2EE_MLS_PLAN_2026-11-25.md) (пункт 25), где группы были отложены отдельным PR.

## Коротко для владельца

- Сейчас личные чаты и чаты дел (с помощниками) уже шифруются на телефоне по стандарту MLS. Группы (`chat_groups`) нет: текст и файлы группы сервер видит.
- Делаем группы на том же MLS, той же библиотекой, которая уже стоит в приложении и вебе. Второй механизм шифрования не нужен.
- Как у WhatsApp: сообщение шифрует телефон отправителя, сервер хранит только «кашу». Новый участник видит сообщения с момента вступления; отправитель может сам переслать ему последние 25–100 сообщений (WhatsApp ввёл это 19.02.2026), группа видит строку об этом.
- Убрали человека из группы — ключ группы сразу меняется, старыми ключами он новые сообщения не прочитает.
- Старые сообщения групп остаются как есть (их видит сервер), в группе появляется системная строка «С этого момента сообщения защищены сквозным шифрованием».
- Выключатель в админке `groups.e2ee_mode` (Выкл / Вкл / Авто), сначала Выкл. После проверки на телефонах ставим Авто.
- Чем платим (так же, как WhatsApp): серверный поиск по тексту группы, антивирус файлов на сервере и пересылка сервером уходят на телефон. Публичные группы (вход по @имени для всех) по умолчанию не шифруем: туда может войти любой, шифрование там ничего не защищает (у Telegram публичные группы тоже без шифрования, у WhatsApp публичных групп нет).
- Работа: около 20–24 рабочих дней одного исполнителя, с помощниками параллельно около 2 недель. Внешний вид не меняется, кроме жёлтой плашки и строк, которые уже есть в личных чатах.

Группы (`apps/api/src/modules/groups`, `prisma` модели `ChatGroup*`):

- Роли `owner / admin / member`, права админа (`admin_rights`), `who_can_post/add/media/poll/pin/call/edit_info`.
- Типы `public` (вход по @имени, поиск, «Найти группы»), `closed` (по ссылке, может быть одобрение), `private` (добавляют люди).
- Приглашения (`chat_group_invites`), заявки (`chat_group_join_requests`), ссылка `invite_code`.
- Темы (форум), опросы (подсчёт голосов на сервере), реакции, закрепы, ответы, упоминания (`mention_ids`), медленный режим, исчезающие сообщения, «запрет копирования», пересылка (`forwardSource` читает текст на сервере), голосовые, вложения (`group_media_outbox.dart`: файл и подпись уходят как есть).
- Размер: `groups.max_members` = 1024 (как WhatsApp). С лимитом устройств 5 это до 5120 листьев MLS.
- Сообщения `chat_group_messages` разбиты по хэшу `group_id` на 16 частей; доставка через очередь `groups.fanout_partitions` = 64.
- Каналы (`modules/channels`) — отдельная вещь (вещание, как каналы WhatsApp и Telegram). WhatsApp каналы не шифрует сквозным шифрованием; мы тоже не трогаем. Сообщества по решению владельца 17.11 — следующее обновление, не трогаем.
- Жалобы на сообщения групп сейчас нет (в `ReportTargetType` нет цели для группы), админка групп (`admin-groups.service.ts`) показывает только счётчики, не текст. Значит, шифрование здесь ничего не отнимает у модерации.

## 3. Выбор подхода

| Критерий | A. Sender Keys (модель WhatsApp) | B. MLS (уже стоит у нас) | C. Megolm (Matrix, `vodozemac`, Apache-2.0) |
|---|---|---|---|
| Что нужно ещё | Парные каналы между всеми участниками. У нас парных сессий Signal нет: 1:1 сделан на MLS. Пришлось бы держать по MLS-группе на каждую пару: для группы 1024 — до 523 тыс. пар | Ничего нового в криптографии: тот же движок, та же служба доставки, обобщить ключ `conversation` → `conversation | group` | Второй протокол (Olm для пар + Megolm для групп) рядом с MLS |
| Лицензия | libsignal — AGPL, только идея. Готовой MIT-реализации Sender Keys на Dart и TS нет → своя криптография (запрещено правилом №1) | `openmls` MIT, `ts-mls` 1.6.4 MIT — уже в `apps/mobile/THIRD_PARTY_NOTICES.md` | `vodozemac` Apache-2.0 (Rust), под Flutter и веб — своя обвязка |
| Убрали участника | Каждый оставшийся заново раздаёт свой ключ всем: O(n²) сообщений на группу | Один коммит: O(log n) | Как Sender Keys |
| Безопасность после взлома (PCS) | Только после смены ключа | Есть: каждый коммит с путём обновляет ключи | Слабее |
| Состав группы | Сервер может «подбросить» участника (KCL 2025) | Добавить устройство может только устройство-участник своей подписью; сервер подделать не может | Как Sender Keys |
| Веб `--wasm` | Своя библиотека | Уже работает (`ts-mls`) | Своя обвязка WASM |
| Отправка | Одно сообщение на всех | Одно сообщение на всех | Одно сообщение на всех |
| Отраслевое направление 2025–2026 | Signal/WhatsApp | IETF стандарт, Google/Apple RCS, Wire, Webex, Discord DAVE (звонки) | Matrix сам изучает переход на MLS |

**Решение: B — MLS на том же движке.** Это и «как большие» (Google и Apple для RCS, Wire, Webex), и единственный вариант без своей криптографии: всё, что нужно, уже есть в `openmls` 4.0.0 (`joinGroupExternalCommit`, `exportGroupInfo`, `exportRatchetTree`, `exportSecret` — проверено в пакете) и в `ts-mls` (документация «07 External join», «02 Ratchet tree extension»). У WhatsApp берём не протокол, а поведение: тексты строк, историю для новых, жалобу, пуш с текстом, превью ссылок у отправителя.

Скорость при наших размерах (до 1024 человек × до 5 устройств = до 5120 листьев):

- Отправка сообщения: одно шифрование AES-GCM, один шифр на всех; сервер раздаёт тем же `group-fanout`. Не зависит от размера.
- Коммит (добавить/убрать/обновить ключ): ≈ log2(5120) ≈ 13 шифрований HPKE у того, кто коммитит, одна расшифровка у каждого остальных. У WhatsApp удаление участника из группы 1024 стоит ≈ 1023 × 1023 парных отправок.
- Дорогое место MLS — дерево целиком: вход нового устройства тянет дерево (≈ 200–300 байт на лист → до ≈ 1–1,5 МБ для 5120 листьев, оценка, проверить замером), проверка хэшей дерева O(n). Это мера для нагрузочного теста (раздел 10) и причина держать GroupInfo на сервере (раздел 4.3).

## 4. Устройство

### 4.1 Общая служба доставки

Служба доставки (DS) одна для чатов и групп. Ключ группы MLS: `(scope, id)`, где `scope` = `conversation` или `group`. Идентификатор MLS группы: `lawbid:g:<groupId>` (у чатов `lawbid:<conversationId>`), поэтому шифр одной группы нельзя подложить в другую: сервер сверяет `group_id` в заголовке.

Эндпоинты — те же, что у чатов, с префиксом группы (одна реализация, параметр `scope`):

| Чат (есть) | Группа (новое) |
|---|---|
| `GET /e2ee/conversations/:id` | `GET /e2ee/groups/:id` — состояние `off / pending / on`, эпоха, устройства, `removeDevices`, ключи превью |
| `POST /e2ee/conversations/:id/group` | `POST /e2ee/groups/:id/group` — первое устройство создаёт группу MLS (эпоха 0) |
| `POST …/key-packages/claim` | то же — только для добавления людей тем, кто их добавляет (4.2) |
| `POST …/commits`, `GET …/commits?after=` | то же + в теле коммита `groupInfo` (новое, 4.3) |
| — | `GET /e2ee/groups/:id/group-info` — последний GroupInfo с деревом для внешнего входа |
| — | `POST /e2ee/groups/:id/external-commit` — вход своего устройства внешним коммитом |
| — | `POST /e2ee/groups/:id/lease` — право на коммит на короткое время (4.4) |
| `POST …/rejoin` | заменяется внешним коммитом с удалением своего старого листа (RFC 9420 §12.4.3.2, «resync») |
| `POST …/reports` | `POST /e2ee/groups/:id/reports` — только если владелец решит добавить жалобу на группы (сейчас её нет, новую функцию здесь не вводим) |

Сообщения: `POST /groups/:id/messages` принимает `type = mls` с `ciphertext`, `epoch`, `frankingTag`, `sealedPreviews`; проверка та же `assertMlsSend` (устройство моё и в группе, шифр этой группы и этой эпохи, все `removeDevices` уже убраны).

### 4.2 Кто что коммитит (главное отличие от чатов на 2–3 человека)

В чатах дел сейчас каждое устройство при синхронизации само добавляет недостающих и само убирает лишних. В группе на 1024 человека это значит: появилось новое устройство — до 5000 устройств одновременно берут для него KeyPackage и спорят за эпоху; все, кроме одного, получают 409, а его 100 одноразовых KeyPackage сгорают. Поэтому для групп правила как у Wire:

| Событие | Кто коммитит | Как |
|---|---|---|
| Создание группы | Устройство создателя | `createGroup` + коммит Add для устройств участников (KeyPackage) + Welcome |
| Админ добавил людей | Устройство того, кто добавил | Берёт KeyPackage всех устройств добавленных, один коммит Add, один Welcome на всех |
| Человек вошёл по ссылке / заявку одобрили / принял приглашение | Само устройство вошедшего | Внешний коммит (External Commit) по GroupInfo с сервера. Сервер пускает только устройство человека, который уже в `chat_group_members` и `left_at IS NULL` |
| Новое устройство участника | Само новое устройство | Внешний коммит в каждую свою зашифрованную группу (как Wire). Остальным ничего делать не надо |
| Убрали / вышел / забанили / админ площадки убрал (`adminRemoveMember`) | Устройство того, кто убрал; если он не в сети или это сервер — первое устройство, которое пишет следующим | Сервер кладёт устройства человека в `removeDevices`; `assertMlsSend` не пропускает новое сообщение, пока их не убрали (как в чатах сейчас). Короткое право на коммит (4.4) не даёт всем делать это разом |
| Устройство отключено (`revokeDevice`) | То же | То же |
| Плановая смена ключей (PCS) | Каждое устройство своё | Коммит «обновить свой лист» раз в `groups.e2ee_update_days` (по умолчанию 7) дней, если писало в группу |

Сервер (DS) сверяет каждый коммит с `chat_group_members` так же, как сейчас с участниками чата: добавить можно только устройства действующих участников, убрать — только тех, кого убрали, или отключённые устройства. Права группы (`who_can_add`) проверяет обычный `groups.service` до коммита: коммит Add принимается, только если на сервере уже есть строка участника (добавил тот, кому можно).

Защита от «призрака» (слабое место WhatsApp по исследованию KCL 2025): сервер не может сам добавить устройство, у него нет ключа подписи ни одного участника. Каждый лист виден всем; при новом листе человека в группе появляется строка «Код безопасности {имя} изменился» (как в чатах), при новом человеке — строка «{кто} добавил(а) {кого}», которую телефон строит из коммита (кто подписал), а не из слов сервера.

### 4.3 GroupInfo на сервере

Каждый коммит в группе идёт «пакетом», как у Wire: сам коммит + Welcome (если добавляли по KeyPackage) + новый GroupInfo с деревом (`exportGroupInfo` с расширением `ratchet_tree`). Сервер хранит последний GroupInfo группы (сжатый gzip; больше `groups.e2ee_group_info_inline_kb` = 256 КиБ — в хранилище файлов, в базе ссылка). Внешний вход и восстановление после сбоя читают его. Тогда Welcome не обязан тащить дерево, а вход нового устройства не требует ничьего присутствия в сети.

Шаг 2 (если нагрузочный тест покажет, что загрузка GroupInfo после каждого коммита тяжела для больших групп): сервер сам ведёт открытое дерево по открытым коммитам (в OpenMLS для этого есть `PublicGroup`, в ts-mls — разбор состояния «14 Group state inspection»), и коммитящий GroupInfo не грузит.

### 4.4 Право на коммит (lease)

`POST /e2ee/groups/:id/lease` → сервер одной строкой в Redis (`SET NX PX`) выдаёт право одному устройству на `groups.e2ee_lease_ms` = 15000 мс. Пока право у кого-то, остальные устройства не берут KeyPackage и не коммитят, а ждут коммит (он придёт по сокету) или конца срока. Сервер отвергает выдачу KeyPackage для группы без права. Без права можно только отправить сообщение, если `removeDevices` пуст.

### 4.5 Отправка и приём

1. Телефон: `E2eePayload` (тот же формат v1, добавляются поля групп: `tp` тема, `m` упоминания, `poll`, `vote`, `react`, `edit`, `del`, `hist`) → `engine.encrypt(gid, bytes)`.
2. Сервер: в `chat_group_messages` строка `type = mls`, `ciphertext`, `mls_epoch`, `sender_device_id`, `franking_tag`; `body = ''`. Открытыми остаются только данные для доставки: `group_id`, `sender_id`, `topic_id`, `mention_ids` (нужны для пушей «вас упомянули» сквозь выключенный звук и для непрочитанных по темам), `reply_to_id`, `expires_at`, `client_message_id`.
3. Раздача — существующий `group-fanout` (одна копия шифра на группу).
4. Приём: `engine.decrypt` → открытый текст в локальную базу (`E2eePlaintexts`, как в чатах). Сообщение можно расшифровать один раз (прямая секретность), поэтому расшифрованное хранится локально, а не берётся с сервера повторно.

Что из функций групп переезжает внутрь шифра (как у WhatsApp, где опросы, реакции и правки зашифрованы):

| Функция | Сейчас | В зашифрованной группе |
|---|---|---|
| Текст, подпись к файлу, голосовое | `body`, `file_id` открыто | Внутри MLS; файл — зашифрованный (`e2ee_file`) |
| Правка | Сервер меняет `body` | Новое MLS-сообщение `edit` со ссылкой на id; сервер ставит `edited_at` |
| Удалить у всех | Сервер очищает | Сервер удаляет шифр, ставит `deleted_at` + MLS `del` (телефоны стирают у себя) |
| Реакции | `chat_group_message_reactions` | MLS `react`; таблица не пишется (сервер не знает, кто чем отреагировал) |
| Опросы | Варианты и голоса на сервере, подсчёт на сервере | Вопрос и варианты в MLS `poll`, голос — MLS `vote`, подсчёт на телефоне (как WhatsApp). Таблицы опросов не пишутся |
| Пересылка | `forwardSource` читает текст на сервере | Телефон расшифровывает у себя и отправляет новым сообщением; файл — тот же `fileId` и ключ без повторной загрузки (как в чатах) |
| Закреп | `pinned_message_id` | Остаётся открытым (только id) |
| Темы | `topic_id` открыто | Остаётся открытым (название темы — `chat_group_topics.title` — метаданные группы, как название группы; шифровать название группы и тем WhatsApp тоже не шифрует от сервера) |
| Медленный режим, исчезающие, «запрет копирования», права | Сервер | Без изменений (это метаданные; «запрет копирования» и сейчас исполняет приложение) |
| Системные строки (добавил, вышел, переименовал) | `system` открыто | Остаются открытыми (сервер и так знает состав) + строки из коммитов |
| Звонки группы | K3 | Не трогаем (закреплено). Позже ключ звонка из `exportSecret` эпохи, как Discord DAVE |

### 4.6 История для новых участников (копия WhatsApp, 19.02.2026)

- При добавлении человека у добавляющего переключатель «Отправить последние сообщения» (25 / 50 / 100, по умолчанию 25, максимум `groups.e2ee_history_max` = 100).
- Телефон собирает последние сообщения из своей локальной базы в файл, шифрует как вложение (`e2ee_file`), отправляет MLS-сообщение `hist` уже в новой эпохе (в ней новый участник есть).
- В группе строка «{кто} отправил(а) {кому} историю: N сообщений»; у нового участника эти сообщения отделены и помечены «Из истории группы».
- Админ может выключить в настройках группы (новое поле `chat_groups.history_sharing`, по умолчанию да, менять по `who_can_edit_info`).
- Без отправки истории новый видит сообщения с момента входа (как WhatsApp и Wire).

### 4.7 Вложения и медиа

Как в зашифрованных чатах (план 25.11, §5): ключ на файл, AES-256-GCM кусками по 64 КиБ (Tink Streaming AEAD), прямая загрузка `purpose = chat_attachment_e2ee`, `scan_status = skipped_e2ee`, ключ и хэши внутри MLS. Путь отправки медиа групп (`group_media_outbox.dart`) после PR другого помощника, который его сейчас меняет, получает ветку «группа зашифрована → `e2ee_file` → `type = mls`», как уже сделано для чатов. Превью картинки (blurhash и маленькая миниатюра) — внутри сообщения. Видео: те же правила, что для зашифрованных чатов (лёгкая обработка на телефоне, без перекодирования на сервере).

### 4.8 Пуш с текстом (M12)

- До `MAX_PUSH_PREVIEWS` = 32 устройств-получателей — M12 как есть: отправитель запечатывает превью HPKE каждому устройству, сервер раскладывает по пушам. Ключи превью приходят в `GET /e2ee/groups/:id` (как в чатах). `info` HPKE = метка + id группы, превью нельзя перенести в другой чат.
- Больше 32 устройств — шаг 2 (G4): один ключ превью на эпоху из MLS-экспортёра (`exportSecret("lawbid push preview", groupId, 32)`, RFC 9420 §8.5, так же ключи выводят SFrame RFC 9605 и Discord DAVE). Отправитель запечатывает превью один раз (ChaCha20-Poly1305, AAD = id группы ‖ эпоха ‖ устройство), в пуше один блок на всех. Приложение кладёт ключи последних эпох в общее с расширением уведомлений хранилище (там же, где ключ M12). Нет ключа эпохи в расширении — «Новое сообщение в {группа}».
- Выключатель `push.chat_preview` (есть) действует и на группы.

### 4.9 Несколько устройств, веб, копия

- Устройство = лист MLS; лимит `chat.e2ee_max_devices` общий.
- Веб — тот же `ts-mls`; вход в группы внешним коммитом при первом входе в веб.
- Копия с 64-значным кодом уже сохраняет все расшифрованные строки (`E2eePlaintexts`), группы входят в неё без изменений. После восстановления устройство входит в группы внешним коммитом.

## 5. Включение и переход старых групп

Настройка `groups.e2ee_mode` (Выкл / Вкл / Авто), **по умолчанию Выкл** до проверки на телефонах владельца, потом Авто.

| Режим | Что происходит |
|---|---|
| Выкл | Группы пишут как сейчас. Уже зашифрованные группы остаются зашифрованными (их нельзя «расшифровать» назад); новые MLS-группы не создаются |
| Вкл | Каждая непубличная группа шифруется; участник со старым приложением видит «Обновите приложение» |
| Авто | Группа шифруется, когда у всех действующих участников есть устройство с ключами MLS (как чаты в Авто) |

Где не шифруем никогда: демо-мир, группы с `deleted_at`, каналы. Публичные группы — по настройке `groups.e2ee_public` (по умолчанию нет, причина в «Коротко»). Группы больше `chat.e2ee_max_group_members` (1024) — нет.

Переход группы: первое устройство участника создаёт группу MLS и добавляет остальных по KeyPackage (по праву 4.4), сервер ставит `chat_groups.e2ee_since` и пишет системную строку «С этого момента сообщения и звонки в группе защищены сквозным шифрованием…» (текст плашки как в чатах). Старые сообщения (`type ≠ mls`) остаются на сервере как есть и показываются как сейчас; поиск по ним на сервере продолжает работать. Сообщения после `e2ee_since` — только `mls` (сервер отвергает `text`, `attachment`, `voice`, `poll` в зашифрованной группе, как `E2EE_PLAIN_REFUSED` в чатах).

## 6. Серверные функции, которые меняются

| Функция (файл) | Что ломает шифрование | Как держим (как у кого) |
|---|---|---|
| Поиск внутри группы (`groups.service.ts messages`, слова в `body`) | Сервер не видит слов | Поиск по локальной базе на телефоне (WhatsApp, Signal); для старых сообщений — серверный, как сейчас |
| Поиск публичных групп, «Найти группы» (`searchPublic`, `discover`, `previews`) | Ничего: ищется по названию и @имени | Без изменений |
| Ссылки-превью | Сервер не видит ссылку | Карточку строит телефон отправителя (`SealedLinkCard`, уже есть в чатах) |
| Пересылка (`forwardSource`, `sendForwarded`) | Сервер не видит текста | Пересылает телефон (4.5) |
| Антивирус (M3, `markScanWait`, `fileScanEnded`) | Сервер видит только шифр | `skipped_e2ee`; файл открывается только по нажатию с типом и размером; при жалобе — проверка тем же ClamAV (как в чатах, 4.1 плана 25.11) |
| Пуш (`push-dispatcher.ts dispatchGroupMessage`) | Текста нет | M12 / ключ эпохи (4.8); без ключа — «Новое сообщение в {группа}» |
| Модерация и админка групп (`admin-groups.service.ts`) | Сейчас текста не показывает — ничего не теряем | Метаданные, счётчики, удаление группы и участника остаются |
| Жалоба на сообщения группы | Сейчас нет | Новую функцию не вводим. Если владелец решит — путь как в чатах (`e2ee_report_evidence`, franking, 5 сообщений) |
| Выгрузка своих данных (`data-export.service.ts`) | Сервер не может расшифровать | Метаданные + пометка «зашифровано»; переписка — «Экспорт чата» с телефона (как WhatsApp) |
| Юридическая выгрузка и хранение (`legal-export.builder.ts`, `legal-retention.service.ts`) | Содержимого нет | Метаданные и шифр, пометка «сквозное шифрование» |
| Исчезающие сообщения (`disappearing-sweep.service.ts`) | Ничего | Сервер удаляет шифр по `expires_at`, телефон — свою расшифрованную копию |
| Обезличивание аккаунта (`account-anonymization.service.ts`) | Ничего | Шифр остаётся, автор обезличен, как сейчас |
| Очистка хранилища и освобождение файлов (`storage-cleanup`, `file-release`) | Ничего | `file_id` у `mls`-строки — колонка вне шифра (как в чатах) |
| Опросы (`group-polls.service.ts`) | Сервер не знает голосов | Подсчёт на телефоне (4.5) |
| Непрочитанные (`group-unread.sql.ts`) | Ничего (по id и времени) | Без изменений |

## 7. Изменения базы и API (расширение без поломки, `MIGRATIONS_EXPAND_CONTRACT.md`)

1. `mls_groups`, `mls_commits`, `mls_group_devices`, `mls_welcomes`: новая колонка `scope` (`conversation` по умолчанию / `group`). Первичные ключи на `conversation_id` остаются: id чатов и групп — UUID, не пересекаются; колонку логически читаем как `chat_id`, переименование — отдельным шагом «contract» позже. Индексы `(scope, conversation_id)`.
2. `mls_groups`: `group_info` (bytea, gzip, ≤ 256 КиБ) и `group_info_file_id` (UUID, если больше).
3. `chat_group_messages` (разбита на 16 частей): `ciphertext bytea`, `mls_epoch int`, `sender_device_id uuid`, `franking_tag bytea` — все NULL, добавление без перезаписи таблицы (PostgreSQL добавляет NULL-колонку мгновенно). В `GroupMessageType` значение `mls`.
4. `chat_groups`: `e2ee_since timestamptz`, `history_sharing boolean default true`.
5. Настройки (все в админке, правило 11): `groups.e2ee_mode` = off, `groups.e2ee_public` = false, `groups.e2ee_lease_ms` = 15000, `groups.e2ee_update_days` = 7, `groups.e2ee_history_max` = 100, `groups.e2ee_group_info_inline_kb` = 256. Общие с чатами: `chat.e2ee_max_devices`, `chat.e2ee_max_group_members`, `chat.e2ee_key_packages_target`, `chat.e2ee_welcome_keep_days`, `chat.e2ee_file_max_mb`, `push.chat_preview`.
6. Контракт API: эндпоинты 4.1, `SendGroupMessageDto` + `ciphertext/epoch/frankingTag/sealedPreviews`, `GroupMessageDto` + `ciphertext/mlsEpoch/senderDeviceId`, `GroupDetailDto.e2ee` (`off | pending | on`). Регенерация контракта и ERD (KNOWN_ERRORS A.3).
7. Движок в приложении (`MlsEngine`): новые методы `exportGroupInfo`, `joinExternal(groupInfo, {resyncOldLeaf})`, `exportSecret(label, context, length)`, `selfUpdate`. Все есть в `openmls` 4.0.0 и `ts-mls`; своего кода в криптографии нет. `E2eeService` получает `scope`, ключи хранилища `p:g:<id>` и т. п.

## 9. Проверки

- Векторы MLS: официальные тестовые векторы IETF (`mlswg/mls-implementations`, `test-vectors/*.json`: tree-math, crypto-basics, secret-tree, key-schedule, tree-validation, welcome, messages) — прогон в CI для обеих библиотек (OpenMLS их уже проходит, мы проверяем свою связку и версию; для ts-mls — тот же набор). Отдельно: перекрёстный тест «телефон (openmls) ↔ веб (ts-mls)» в одной группе.
- HPKE превью: вектор RFC 9180 A.2.1 (уже есть, `push_preview_test.dart`) + новый известный ответ для превью по ключу эпохи (фиксированный секрет эпохи → фиксированный шифр).
- Файлы: известные ответы Tink Streaming AEAD (уже есть для чатов) — те же для групп.
- Сервер (e2e с `ts-mls` в роли клиентов): создать группу 3 человека × 2 устройства; отправить/прочитать; добавить человека → новая эпоха, новый видит только новое; убрать → убранный не может расшифровать следующее сообщение и сервер отвергает его отправку; новое устройство входит внешним коммитом; чужой (не участник) внешний коммит → 403; два коммита в одну эпоху → один 409; без права на коммит KeyPackage не выдаётся; в базе нет открытого текста после `e2ee_since` (запрос по `body <> ''` у `mls`); Выкл — старые группы работают как раньше.
- Приложение: два устройства одного человека + веб, смена эпохи в фоне, переустановка (resync), копия и восстановление, история 25 сообщений, опрос и подсчёт, правка и удаление у всех.
- Нагрузка: группа 1024 человек × 5 устройств (5120 листьев) — время коммита и входа на iPhone среднего класса и в вебе, размер GroupInfo, нагрузка сервера при одновременном выходе 100 человек. Пороги — в настройках, не в коде.
- Проверка на проде за выключателем: включить для одной тестовой группы владельца, пройти сценарии на его телефонах, потом Авто.

## 10. Риски

1. **Большие группы в вебе**: `ts-mls` на JS медленнее Rust; вход в группу на 5120 листьев (проверка дерева O(n)) может занимать секунды. Мера: замер в G5; если плохо — сервер ведёт дерево (4.3 шаг 2), телефоны грузят только нужное.
2. **Размер GroupInfo** после каждого коммита в большой группе (до ~1,5 МБ, оценка). Мера: gzip, хранение в файлах, шаг 2 из 4.3.
3. **Совместимость двух библиотек** (OpenMLS и ts-mls) на редких путях (внешний коммит с resync, удаление нескольких листов). Мера: перекрёстные тесты, векторы IETF, закреплённые версии.
4. **Гонки коммитов** в активной группе: право на коммит снижает 409, но при плохой сети устройство может держать право до конца срока. Мера: короткий срок (настройка), повтор с догоном.
5. **Потеря сообщений при сбое состояния** (устройство не может применить коммит): resync внешним коммитом; сообщения той эпохи, которые оно не расшифровало, для него потеряны (как у Wire). Строка «Не удалось расшифровать сообщение» как у WhatsApp «Ожидание сообщения».
6. **Пуш без ключа эпохи на iPhone** после смены состава, пока приложение не открывали: «Новое сообщение в {группа}» вместо текста — приемлемо, у WhatsApp тоже бывает.
7. **Открытые метаданные**: кто в группе, кто когда пишет, `mention_ids`, `topic_id`, название группы и тем — сервер видит (у WhatsApp тоже видит состав и время). Шифрование названия группы и списка (как Signal zkgroup) — вне этой работы.
8. **Старое приложение у участников** в режиме Вкл не прочитает новые сообщения. Поэтому основной режим — Авто.
9. **Параллельная работа**: путь отправки медиа групп сейчас меняет другой помощник; G3 начинаем только после его PR.

## 11. Что не входит

Каналы, сообщества (решение владельца 17.11 — следующее обновление), звонки групп (закреплены), шифрование названий групп и состава, Key Transparency (план 25.11, «позже»), жалоба на сообщения групп (её сейчас нет; новую функцию не вводим без слова владельца).
