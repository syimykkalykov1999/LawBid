# Групповые звонки через Cloudflare Realtime SFU

Статус: дизайн + серверная часть (PR 1, 2 и серверная часть PR 5) реализованы в API; мобильное приложение не тронуто. Дата: 2026-10-24.

ВАЖНО: решения владельца от 2026-10-24 (раздел 11) заменяют разделы 5 и 10 там, где они расходятся: звонок никогда не отклоняется из-за сбоя Cloudflare, максимум людей задаётся настройкой (по умолчанию 20), внешний вид приложения не меняется.

## Краткое резюме для владельца (простыми словами)

Сейчас в групповом звонке каждый телефон отправляет своё видео каждому другому («сетка», mesh). На 9 людях телефон шлёт 8 копий видео сразу, греется и ест трафик. Поэтому потолок 9 человек.

Предлагаем: телефон шлёт видео один раз в Cloudflare, а Cloudflare раздаёт его остальным (это и есть SFU). Тогда телефон нагружен почти как в звонке на двоих, а участников можно 20-50.

- Цена: $0.05 за ГБ, что Cloudflare отправил участникам. Первые 1000 ГБ в месяц бесплатно (общие для SFU и TURN). Исходящее от телефона в Cloudflare бесплатно. Ориентир: видеозвонок 5 человек, у каждого входящий поток примерно 4 видео по ~0.5 Мбит/с, это ~0.9 ГБ в час на человека; 1000 ГБ хватит примерно на 1000 человеко-часов группового видео в месяц. Аудио почти ничего не весит.
- Рекомендация: брать «чистый» SFU (не готовый комплект RealtimeKit), потому что у RealtimeKit нет Flutter-SDK, а наши экраны, CallKit, «Идёт сейчас» и вызов участников уже написаны и должны остаться своими.
- Если Cloudflare недоступен: для 2-4 человек автоматически падаем назад на текущую сетку; для большего числа звонок честно не стартует с понятным сообщением.
- Работа: около 6-7 недель одного разработчика, делится на 8 небольших PR. Включаем настройкой в админке (`calls.video_provider` = `cloudflare`), откат одной настройкой за секунды.
- Нужно от вас: завести приложение Realtime SFU в Cloudflare и внести App ID и App Secret в админку (раздел Интеграции), см. вопросы внизу.

## 2. Факты Cloudflare SFU (из документации)

- База API: `https://rtc.live.cloudflare.com/v1`, заголовок `Authorization: Bearer <APP_SECRET>`. Секрет только на сервере.
- Эндпоинты: `POST /apps/{appId}/sessions/new`; `POST .../sessions/{sid}/tracks/new` (publish `location:"local"`, pull `location:"remote"` с `sessionId` издателя и `trackName`; local и remote в одном запросе смешивать нельзя); `PUT .../renegotiate` (ответ клиента на offer SFU); `PUT .../tracks/update` (смена simulcast-слоя `preferredRid`); `PUT .../tracks/close`; `GET .../sessions/{sid}`.
- Сессия = одно PeerConnection одного устройства. Один PC отправляет и принимает много треков (сколько угодно «mid»).
- Лимиты: 50 запросов/с на сессию; до 64 треков на запрос; число треков на сессию жёстко не ограничено; трек без пакетов 30 с будет удалён; потеря связи сессии: окно повторного использования 30 с; кодеки: video H.264/H.265/VP8/VP9/AV1, audio Opus. Число сессий и битрейт в документации не заданы (уточнить у поддержки).
- Регионы: приложение не выбирает регион, Cloudflare сам (anycast). Каскадирование между ЦОД в документации не описано, уточнить.
- Simulcast: издатель делает 3 кодировки `rid` f/h/q (полное/1/2/1/4); подписчик указывает `preferredRid`, `priorityOrdering`, `ridNotAvailable`. Это даёт экономию трафика и адаптацию на плитках.
- DataChannels: есть на SFU (выделяются через API), но для нас не нужны: состояние mute/camera идёт через наш сокет.
- Цена: $0.05/ГБ egress, 1000 ГБ/мес бесплатно, общий пул с TURN.
- Не проверено (404 при чтении страницы): подробная схема тел запросов/ответов `tracks/new` и `renegotiate`. Брать из OpenAPI `realtime-api-2024-05-21.yaml` на шаге PR 1.

## 3. Точная схема работы

Роли: телефон (flutter_webrtc), наш API (NestJS, держит секрет), Cloudflare SFU. Телефон никогда не ходит в Cloudflare напрямую по HTTP: всё через API. Медиа (DTLS-SRTP) идёт прямо телефон - Cloudflare.

Хранилище состояния: на `CallParticipant` добавить `cf_session_id` и `cf_tracks` (JSON: `{audio: "mic", video: "cam"}`, `mid`-ы подписок) либо Redis по ключу `call:{id}:cf`. Рекомендуется Redis с TTL, так как состояние эфемерное и пересоздаётся при реконнекте.

### 3.1 Вход в звонок
1. Участник принимает вызов/присоединяется обычным путём (`accept` / `joinCall`, кольцо, push, CallKit без изменений).
2. Телефон вызывает `POST /calls/:id/sfu/session` (новый). API проверяет, что пользователь joined в этом звонке и провайдер `cloudflare`, вызывает `sessions/new`, сохраняет `sessionId` на участнике, возвращает `{ sessionId, iceServers }` (ICE: Cloudflare STUN `stun.cloudflare.com:3478`; публикация идёт на публичные адреса Cloudflare, TURN нужен только за жёсткими сетями, выдаём через уже существующий `iceServers()`).
3. Телефон создаёт `RTCPeerConnection`, добавляет локальные микрофон и камеру как transceiver sendonly (для видео с simulcast rid f/h/q, см. 3.5), делает offer.
4. `POST /calls/:id/sfu/publish { sdp, tracks:[{mid,trackName:"mic"},{mid,trackName:"cam"}] }`. API проверяет, что `trackName` из белого списка (`mic`, `cam`), и шлёт в Cloudflare `tracks/new` local с `sessionDescription` offer. Ответ Cloudflare с answer SDP возвращается телефону, он делает `setRemoteDescription`. Статус `mic`/`cam` сохраняется.
5. API рассылает через сокет `call:participants` (уже есть `broadcastParticipants`) обновлённый состав; в элементе участника новое поле `sfuReady: true`.

### 3.2 Подписка на остальных (pull)
1. Когда телефон получил состав (или событие `call:sfu_tracks`), он запрашивает `POST /calls/:id/sfu/subscribe { userIds? }` (пусто = все).
2. API проверяет авторизацию (см. раздел 6), строит список `remote` треков: для каждого joined участника с `cf_session_id`, кроме самого запрашивающего, `{location:"remote", sessionId: чужойSid, trackName:"mic"|"cam"}`; для видео с `simulcast.preferredRid` (по умолчанию `h`, для крупной плитки `f`, для маленьких `q`). Батчи до 64 треков.
3. Cloudflare возвращает `requiresImmediateRenegotiation` и SFU-offer; API отдаёт offer телефону, телефон делает `setRemoteDescription`, `createAnswer`, шлёт `POST /calls/:id/sfu/answer { sdp }`, API вызывает `renegotiate`. Ответ API содержит соответствие `userId -> mid`, чтобы привязать входящие потоки к плиткам.
4. Все мутации одной сессии сериализуем на API (очередь на `sessionId`), потому что Cloudflare требует завершить обмен SDP до следующей мутации.

### 3.3 Кто-то вошёл / вышел
- Вошёл: новый участник сам делает 3.1-3.2 (подписывается на всех). Остальные получают `call:participants` с новым `sfuReady`, вызывают `subscribe { userIds:[новый] }`.
- Вышел или отключён (leave, kick, `sweepSilentMembers`, сокет упал): API вызывает `tracks/close` для его треков на всех подписчиках, при необходимости закрывает его сессию, чистит состояние и рассылает `call:participants`. Подписчики убирают плитку и `removePeer`.
- Конец звонка (`finish`): закрыть все сессии (best effort), очистить состояние.

### 3.4 Mute и камера
- Микрофон: `track.enabled = false` локально (Cloudflare не обязательно извещать, пакеты идут тишиной/не идут, 30-секундный GC трека не страшен, так как пока включён mute мы держим трек). Состояние отправляется как сейчас: `PUT /calls/:id/mute` (`setMuteState`), все видят значок. Хост-мьют (`muteParticipant`) остаётся: сервер ставит `muted_by_host`, клиент жертвы сам выключает трек; принудительность обеспечивает SFU-сторона через `tracks/close` аудиотрека жертвы у подписчиков при нарушении (опционально).
- Камера: выключение = `enabled=false` + флаг `video_off` в составе; плитка показывает аватар. Длительное выключение (более ~20 с) = `tracks/close` для `cam` (экономия), включение = `publish` нового cam-трека и подписчики подтягивают его по событию. Это тот же путь, что `enableVideo/disableVideo` сейчас.
- Громкий динамик, переключение камеры (`switchCamera`) локальные.

### 3.5 Simulcast и качество
Публикуем 3 слоя (f/h/q). Плитки: активный говорящий и крупная плитка = `f` или `h`, сетка 3x3 = `q`/`h`. Смена слоя: `tracks/update` через `POST /calls/:id/sfu/layer`. Существующая адаптация `_applyTier` по результатам `getStats` переиспользуется для верхнего потолка отправки.

### 3.6 Реконнект и фон
- Обрыв сети до 30 с: Cloudflare держит окно повторного использования сессии; клиент делает ICE restart (аналог `restartIce`), без новой сессии. Дольше или 410 `session_error`: клиент вызывает `/sfu/session` заново, потом publish и subscribe (полное пересоздание, плитки мигают, но звонок жив).
- Фон: аудио сохраняется существующим механизмом (`call_foreground`, audio background mode iOS, foreground service Android); он не зависит от того, куда идёт PeerConnection.
- CallKit/ConnectionService и кольцо, push, «Идёт сейчас» (`live_calls`, `call:ongoing`) не меняются: они про состояние звонка, а не про транспорт.
- Демонстрации экрана в текущем коде звонков нет (поиск `getDisplayMedia` пуст), в объём не входит; позже добавляется как третий трек `screen`.

## 4. Интеграция в админку и настройки

Секреты (Admin → Интеграции), новый провайдер в `provider-registry.ts`:
- id `cloudflare_sfu`, поля: `appId` (не секретное, паттерн `^[0-9a-f]{32}$`), `appToken` (секретное, App Secret; env `CLOUDFLARE_SFU_APP_ID`, `CLOUDFLARE_SFU_APP_TOKEN`).
- Класс `CloudflareSfuProvider implements VideoCallProvider` (name `cloudflare`), `isConfigured()` = оба поля заданы. Тип `name` расширить: `'webrtc' | 'livekit' | 'cloudflare'`.
- Настройка `calls.video_provider`: паттерн `^(p2p|livekit|cloudflare)$`; проверка при сохранении (как для livekit в `admin-config.service.ts`): `cloudflare` нельзя включить без ключей. Описание поправить (сейчас «до 9 человек»).
- Правило ёмкости: при `cloudflare` потолок `calls.max_participants` не режется до 9 (верхняя граница настройки сейчас 50, рекомендуем стартовать с 20); при `p2p` остаётся 9.
- Кнопка «Проверить» в админке: `sessions/new` + закрыть; показывает зелёный/красный.
- Метрики: счётчик байт на звонок брать из `getStats` клиента (приблизительно) и сверять с счётом Cloudflare; админский алерт при 70% бесплатных 1000 ГБ (общих с TURN).

## 5. Запасной вариант при падении Cloudflare

- Проверка здоровья: `sessions/new` в `/calls/video` (кэш 30 с) и счётчик ошибок за минуту.
- Звонок из 2-4 человек (по числу при старте; потолок fallback `calls.sfu_fallback_max` = 4, на 4 mesh ещё терпим): автоматически стартует в mesh. Клиент узнаёт из ответа `provider: "p2p"` в данных звонка.
- 5 и больше: старт отказывает с сообщением «Групповой видеозвонок временно недоступен, попробуйте аудио» (аудио в mesh на 9 человек выдерживается; предложить аудио-fallback до 9).
- Уже идущий звонок при сбое SFU: клиент показывает «Связь нестабильна», пробует переподключиться 3 раза (раздел 3.6); если не удаётся и участников не больше 4, звонок переключается на mesh на лету через существующий `call:signal` (`addPeer`/`createOfferFor`); иначе завершается штатно.
- Провайдер записывается в строку звонка (`Call.media_provider`), чтобы вход позже и история знали, в каком режиме звонок.

## 6. Безопасность

- `appToken` (App Secret) только на сервере: хранится зашифрованным в `SecretsService`, в клиент, логи и ответы API не попадает; маскируется в админке.
- Клиент получает только `sessionId` и SDP; SDP от клиента проверяется по размеру и типу, `trackName` из белого списка.
- Шифрование: DTLS-SRTP между телефоном и Cloudflare (не end-to-end: Cloudflare SFU видит медиа, как любой SFU; упомянуть в политике приватности, если звонки юридические/конфиденциальные. Вопрос владельцу).
- Авторизация на нашей стороне (все `/calls/:id/sfu/*` за JWT и теми же проверками, что `livekitToken`: звонок живой, пользователь joined, провайдер включён):
  - publish: только в свой `cf_session_id`, только `mic`/`cam`; в канальном звонке слушатель (не хост/админ) публиковать не может (как роль `listener` в LiveKit);
  - subscribe: только на сессии joined участников этого же звонка, `sessionId` издателя берётся из нашей БД/Redis, а не из тела запроса (клиент не может подписаться на чужой звонок);
  - kick/удалённый/заблокированный: треки закрываются, сессия закрывается, повторный `session` отклоняется;
  - rate limit на `/sfu/*` (50 запросов/с на сессию это лимит Cloudflare; у нас 10/с на пользователя).
- Аудит: события сессии пишутся в лог звонка без SDP.
- Права хоста: мьют, кик, голосование остаются на нашей стороне.

## 8. План тестирования

- Unit (API): провайдер (маппинг ответов, ошибки по трекам при HTTP 200), очередь мутаций, авторизация (чужой звонок, не-участник, listener публикует, kicked подписывается), белый список треков, валидация настройки. Мок Cloudflare через `nock`/fake fetch.
- Unit (Flutter): парсинг ответов, сопоставление mid и userId, конечный автомат реконнекта, выбор слоя simulcast по размеру плитки.
- E2E (API + сокет): звонок на 4 клиентах с мок-SFU: вход, выход, kick, мьют, конец; проверка, что закрытые треки не остаются; fallback при 5xx от Cloudflare.
- На устройствах: минимум 3 телефона (iOS + Android, разные сети: Wi-Fi, LTE, за корпоративным NAT) и 6+ через эмуляторы: вход и выход по очереди, mute/камера, переключение сети Wi-Fi/LTE, блокировка экрана 5 минут (звук идёт), входящий GSM-вызов, CallKit, «Идёт сейчас», 30-секундный обрыв и 60-секундный обрыв.
- Нагрузка: скрипт на headless-клиентах (Node + werift или Chrome headless) создаёт K звонков по N участников, шлёт синтетическое видео 500 кбит/с; метрики: время до первого кадра, потери, rate лимиты 50 rps, фактический egress против расчёта. Прогон на 20 участников x 5 звонков, затем 50 x 1. Контролируем стоимость: пробный прогон 100 ГБ = $0 (в бесплатной квоте), но ограничить квотой.

## 11. Решения владельца 2026-10-24 и API для мобильного разработчика

### 11.1 Решения (заменяют разделы 5 и 10 при расхождении)

- Выпускаем до релиза. Только звонки 1 на 1 остаются P2P с TURN; групповые идут через Cloudflare SFU.
- Максимум людей в SFU-звонке: настройка `calls.sfu_max_participants`, по умолчанию 20. `calls.max_participants` (9) остаётся для обычной сетки (mesh).
- Cloudflare не настроен или недоступен (только тогда): звонок НИКОГДА не отклоняется и не обрезается ниже обычного лимита. До `calls.sfu_fallback_mesh_max` человек (по умолчанию 4) идут напрямую (mesh) с видео; если людей больше, у всех только аудио, тоже mesh. Это относится и к тем, кто подключается к идущему звонку: когда в звонке становится больше порога, сервер сам переводит звонок в «только аудио» (`video=false`). Когда Cloudflare снова здоров, НОВЫЕ звонки идут через SFU (идущий звонок свой транспорт не меняет).
- Сквозное шифрование (insertable streams / FrameCryptor) позже. Сейчас не делаем. В API места для него: ключ звонка раздаётся рядом с сессией (`POST /sfu/session` может вернуть поле с ключом), SDP-поток от этого не зависит.
- Звонок, начатый как 1 на 1 и ставший групповым через «добавить человека», остаётся mesh (транспорт не меняется на лету). Это ограничение первого релиза; вопрос владельцу, нужно ли переносить такие звонки на SFU.

### 11.2 ЖЁСТКОЕ ПРАВИЛО ДЛЯ МОБИЛЬНОЙ ЧАСТИ: внешний вид не меняется

Менять нельзя ничего видимого: расположение, кнопки, цвета, размеры, экраны звонка и все существующие элементы управления остаются как сейчас. Меняется только транспорт медиа под ними (одно PeerConnection вместо сетки). Единственное разрешённое видимое добавление: короткое сообщение при сбое (11.5).

### 11.3 Как работает серверная часть

- Тип транспорта записан в звонок при старте: `CallDto.mediaProvider` = `cloudflare` | `p2p` (не меняется до конца звонка; колонка `calls.media_provider`). `p2p` = как сейчас (mesh/1:1).
- Роуты `/sfu/*` работают только для `mediaProvider = cloudflare`, только для участника со статусом `joined` (иначе 404; завершённый звонок 409). `sessionId` издателя всегда берётся из состояния на сервере (Redis `sfu:call:{id}`), никогда из тела запроса.
- Одна мутация за раз на сессию (очередь на сервере). Незавершённый offer блокирует следующую мутацию (409 `CALL_STATE_CONFLICT`, подождите/ответьте и повторите; зависший offer снимается через 15 с).
- Выход, кик, тишина (sweep), голосование, конец звонка: сервер сам закрывает треки человека в Cloudflare и рассылает `call:participants`. Клиенту достаточно убрать плитку и закрыть свои подписки на ушедшего (`/sfu/close { userIds }`).
- Лимит 10 запросов/с на пользователя на `/sfu/*`.
- Ошибки: 503 `CALL_MEDIA_UNAVAILABLE` (Cloudflare не отвечает), 409 `CALL_STATE_CONFLICT`, 403 (слушатель канального звонка пытается публиковать), 400 (неверный SDP/трек), 404.

### 11.4 Эндпоинты (все POST, JWT, ответ в обычной обёртке `{data: ...}`)

1. `POST /calls/:id/sfu/session` -> `{ sessionId, iceServers:[{urls:["stun:stun.cloudflare.com:3478"]}] }`. Для сетей за NAT TURN берите, как сейчас, из `GET /calls/ice-servers`. Повторный вызов (реконнект дольше 30 с) заменяет старую сессию.
2. `POST /calls/:id/sfu/publish` `{ sdp, tracks:[{mid, trackName:"mic"|"cam"}] }` (sdp = offer с sendonly transceiver, mid из этого offer) -> `{ type:"answer", sdp, tracks:[{mid,trackName}], failed:[{trackName,errorCode}] }`. Примените answer через setRemoteDescription. Сервер рассылает `call:participants`.
3. `POST /calls/:id/sfu/subscribe` `{ userIds?, trackNames?, rid? }` (пусто = все; `rid` f|h|q, по умолчанию h для видео) -> `{ requiresAnswer, type:"offer"|null, sdp|null, subscriptions:[{userId,trackName,mid}], skipped:[{userId,trackName,reason}] }`. Если `requiresAnswer`: setRemoteDescription(offer), createAnswer, затем `/sfu/answer`. `subscriptions` связывает ваш mid с человеком (для плитки). `skipped.reason`: `not_in_call`, `not_published`, `already_pulled`, `batch_limit` (больше 64 треков: повторить после answer) или код Cloudflare.
4. `POST /calls/:id/sfu/answer` `{ sdp }` -> `{ ok:true }`.
5. `POST /calls/:id/sfu/close` `{ trackNames?:["mic"|"cam"], userIds?, sdp? }`: свои треки (выключили камеру надолго) или подписки на ушедших. Для подписок остановите transceiver, сделайте offer и пришлите в `sdp`: ответ `{closed:[mids], type:"answer", sdp}` примените; без `sdp` треки закрываются принудительно. Для своих треков (`trackNames`) сервер рассылает `call:participants`.
6. `POST /calls/:id/sfu/layer` `{ userId, rid:"f"|"h"|"q" }` -> `{ ok:true }` (слой simulcast подписанной камеры). Форма вызова `tracks/update` в OpenAPI Cloudflare не описана примером; проверить на устройстве.

### 11.5 События и поля, которые читает приложение

- `call:participants` (существующее событие) теперь содержит: `mediaProvider`, `video` (актуальное, может стать `false` при переходе в аудио), `mediaFallback`, а у каждого участника `sfuReady` (публикует хотя бы один трек) и `sfuTracks` (`["mic","cam"]`). Когда у человека появились `sfuTracks`, которых вы ещё не тянули: `subscribe {userIds:[он]}`. Когда пропали: закройте подписку.
- `CallDto` (GET /calls/:id и все ответы со звонком) содержит `mediaProvider` и `mediaFallback`.
- `mediaFallback` (только у групповых звонков): `{ active, reason: "sfu_unavailable"|null, videoBlocked, videoMaxParticipants }`. `active` = Cloudflare выбран админом, но звонок идёт mesh из-за сбоя/отсутствия ключей. `videoBlocked` = людей больше порога, камеру включать нельзя.
- ЕДИНСТВЕННОЕ разрешённое видимое добавление: если `mediaFallback.videoBlocked` и человек нажимает кнопку видеозвонка или камеры, камера НЕ включается, показывается короткое сообщение (тот же снекбар/тост, что уже используется в приложении) с текстом «На сервере идут работы. Видео можно будет включить примерно через час.» Ключ перевода добавить во все 85 языков через `scripts/i18n-add.mjs` на мобильном шаге. Звонок при этом продолжается с аудио у всех.

### 11.6 Последовательность (клиент, SFU-звонок)

1. Принять/войти обычным путём (accept/join, кольцо, push, CallKit без изменений). Если `mediaProvider = cloudflare`:
2. `/sfu/session` -> создать RTCPeerConnection (один на звонок) -> добавить sendonly mic (и cam) -> offer -> `/sfu/publish` -> setRemoteDescription(answer).
3. Получив `call:participants`: для каждого нового человека с `sfuTracks` -> `/sfu/subscribe` -> (если `requiresAnswer`) setRemoteDescription(offer), createAnswer -> `/sfu/answer`. Запросы одной сессии выполнять строго по очереди и на клиенте.
4. Mute/камера/хост-мьют/кик/голосование остаются существующими запросами; камера выключена надолго -> `/sfu/close {trackNames:["cam"]}`, снова включили -> `/sfu/publish` новым cam.
5. Выход: обычный leave; сервер закроет треки. Конец звонка: сервер закрывает всё.
6. Реконнект: до 30 с ICE restart на том же PC; иначе `/sfu/session` заново, затем publish и subscribe.
7. `mediaProvider = p2p`: ничего не менять, работает существующий mesh-код (в том числе в режиме сбоя).

### 11.7 Что подтверждено по OpenAPI Cloudflare (calls-api-2024-05-21.yaml)

База `https://rtc.live.cloudflare.com/v1`; `sessions/new` -> 201 `{sessionId}`; `tracks/new` тело `{sessionDescription?, tracks:[{location:local|remote, mid, sessionId, trackName, simulcast:{preferredRid, priorityOrdering, ridNotAvailable}}], autoDiscover?}`, ответ `{requiresImmediateRenegotiation, sessionDescription, tracks[+errorCode,errorDescription], errorCode}`; `renegotiate` тело `{sessionDescription}`; `tracks/close` тело `{tracks:[{mid}] (обязательно, минимум 1), force (обязательно), sessionDescription?}`, закрытие идёт по `mid`, а не по trackName; `tracks/update` `{tracks, sessionDescription}`; `GET sessions/{id}` -> `{tracks[+status], dataChannels}`. Код сервера: `apps/api/src/modules/calls/cloudflare-sfu.client.ts` (единственное место, знающее формат Cloudflare).
