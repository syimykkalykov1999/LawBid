# Защита админки и приватного контента (2026-10-28)

Что сделано и что вам нужно сделать самому. Всё выключено или работает как раньше, пока вы не включите.

## 1. Чтение приватного (привилегия адвокат-клиент)

- Единственное место: админка → Модерация → «Приватные чаты и файлы».
- Любое чтение (переписка, звонки, список файлов кейса, сам файл, текст сообщения) требует **код причины** (4 штуки: жалоба, непосредственный вред, юридический запрос, техпроблема с согласия) и **пояснение** от 10 символов. Это касается и вас как владельца.
- Запись в журнал аудита делается **до** показа. Если записать не получилось, ничего не показывается (ошибка 503 AUDIT_UNAVAILABLE).
- В списке переписки текста нет. Текст одного сообщения и ссылка на файл открываются кодом из приложения-аутентификатора, введённым не раньше чем `admin.private_stepup_seconds` секунд назад (по умолчанию 120). Второй админ не нужен.
- Страница «политика приватного контента»: Система → «Право и жалобы» → «Тексты и контакты» → поле «Приватный контент: политика» (en и ru). Тексты по умолчанию уже есть. Покажите их юристу, прежде чем публиковать.
- Месячный отчёт: страница «Приватные чаты и файлы» (внизу) и письмо владельцу 1-го числа в 07:15 UTC. Выключатель: `admin.access_report_enabled`.

## 2. Журнал аудита с цепочкой хешей

- Каждая строка журнала хранит хеш предыдущей (в базе, триггер `audit_log_chain`). Подмена или удаление строки ломает цепочку.
- Проверка: админка → API `GET /admin/audit-log/verify-chain` (только владелец); то же делает ночная выгрузка и пишет в лог `audit_log hash chain is BROKEN`, если цепочка сломана.
- Старые строки (до 2026-10-28) без хеша; цепочка начинается с первой новой строки.
- Нагрузка: запись в журнал идёт по одной (общая блокировка на время транзакции). Админских действий мало, это не заметно.

## 3. Ежедневная выгрузка журнала в S3 (делаете вы)

Копия журнала уходит в бакет аудита каждую ночь (01:30 UTC), файлами `admin-audit/ГГГГ/ММ/ДД/audit-<от>-<до>.jsonl`. Ничего не делается, пока бакет не включён.

1. В Terraform (папка `infra/envs/prod`) поставьте `audit_logs_enabled = true` и `admin_audit_export_enabled = true`.
2. Для копии, которую никто не перепишет, нужен S3 **Object Lock** (`audit_logs_object_lock = true`). Внимание: включается только при создании бакета, и с ним перестаёт доставляться S3 access log документов (см. предупреждение у переменной). Если бакет уже создан без Object Lock, политика бакета всё равно запрещает удаление через IAM, а версионирование хранит историю.
3. `terraform plan`, посмотрите, `terraform apply` (вы сами).
4. Выкатите API. Проверка: на следующее утро в бакете появится папка `admin-audit/`. Переключатель в приложении: `admin.audit_export_enabled` (Настройки).

## 4. Список разрешённых адресов (IP allowlist)

По умолчанию выключен. Настройки (все меняются с кодом 2FA):

- `admin.ip_allowlist` — адреса: `203.0.113.7` или диапазон `203.0.113.0/24` (IPv4), для IPv6 только точные адреса.
- `admin.ip_allowlist_enabled` — включить. Система **не даст включить**, если вашего текущего адреса нет в списке.

Защита работает на входе и на каждом запросе админки. Запрещённый адрес получает ошибку `ADMIN_IP_NOT_ALLOWED`; в журнал пишется `admin.ip_denied`.

### Аварийный обход (если вы заперли себя)

Выберите один способ.

**A. Через переменную окружения (быстрее всего).**
1. AWS Console → ECS → кластер → сервис API (`api`) → Update service → создайте новую ревизию Task definition с переменной `ADMIN_IP_ALLOWLIST_BYPASS` = `1` (или добавьте её в Terraform, `api_env`, и сделайте `apply`).
2. Дождитесь, пока новые задачи станут healthy. Зайдите в админку, исправьте список или выключите `admin.ip_allowlist_enabled`.
3. **Уберите переменную** и перевыкатите, иначе список не действует.

**B. Через базу.** Подключитесь к базе (как в `docs/runbooks/DEPLOY_PROD.md`) и выполните:

```sql
UPDATE app_config SET value = 'false'::jsonb WHERE key = 'admin.ip_allowlist_enabled';
```

Настройки кэшируются на минуту: подождите 1–2 минуты. Это изменение попадёт в логи базы, но не в журнал аудита, поэтому потом запишите его вручную в инцидентный журнал.

## 5. Оповещение о входе с нового устройства или адреса

Включено по умолчанию (`admin.login_alert_enabled`). Когда админ входит с браузера/системы или IP, которых у него раньше не было, владельцу (всем super_admin) уходит письмо. Первый вход аккаунта не считается. В строке журнала `admin.login` появляются поля `newIp` / `newDevice`. Письма идут через ваш SES; если почта не настроена, вход всё равно проходит.

## 6. Лимит одновременных сессий

`admin.max_concurrent_sessions` (по умолчанию 0 = без лимита, меняется с кодом 2FA). Например, 2: третий вход закрывает самую старую сессию, в журнал пишется `admin.session_evicted`.

## 7. Отказ при сбое журнала (fail closed)

Для чувствительных разделов (деньги, зарплаты, ключи, админы, сессии, запросы госорганов, выгрузки, журнал) и всех приватных чтений строка журнала пишется **до** действия. Не записалась — действие не выполняется, ответ 503 `AUDIT_UNAVAILABLE`. Просмотр денежных страниц тоже. В остальных разделах поведение прежнее: сбой записи логируется, действие не отменяется.

## Источники

- ABA Model Rule 1.6(c) и Formal Opinion 477R (разумные меры защиты клиентской информации в сети), см. `docs/legal/LEGAL_REGISTER.md` (ветка `claude/legal-register`, раздел C4).
- AWS S3 Object Lock, режимы Governance/Compliance: https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock.html
- NIST SP 800-92 (защита журналов от подмены) и RFC 6962-стиль цепочки хешей (идея «каждая запись хранит хеш предыдущей»).
