# NAT: трафик и когда выгодны VPC-эндпоинты

> **Для владельца:** весь выход серверов в интернет идёт через один NAT
> (`nat_per_az = false`). NAT берёт **$0,045 за каждый ГБ** (+ $0,045 в час,
> ≈ $33/мес). Тревога `lawbid-prod-nat-bytes-0` пишет письмом, если за сутки
> через NAT прошло больше `nat_traffic_alarm_gb_per_day` ГБ (по умолчанию
> 20 ГБ ≈ $0,9 в сутки). Это не авария: приложение работает. Что делать:
> открыть этот файл и проверить, что именно качает сервер.

## Цены (us-east-1, на 2026-10-24)

- NAT Gateway: $0,045/час и $0,045/ГБ ([AWS VPC pricing](https://aws.amazon.com/vpc/pricing/);
  в примере страницы указан регион Ohio, у N. Virginia та же цена).
- Interface-эндпоинт: $0,01/час за каждую зону (AZ) и $0,01/ГБ
  ([AWS PrivateLink pricing](https://aws.amazon.com/privatelink/pricing/)).
- Gateway-эндпоинт (S3, DynamoDB): бесплатно. S3 у нас уже включён.

## Точка безубыточности

Эндпоинт на одну зону: $0,01 × 730 ч ≈ **$7,3/мес**. Каждый ГБ через
эндпоинт вместо NAT экономит $0,045 − $0,01 = **$0,035**.

| Эндпоинт в | Фиксированная цена | Выгоден, если через него идёт больше |
|---|---|---|
| 1 зоне (как у нас) | ≈ $7,3/мес | **≈ 210 ГБ/мес** |
| 2 зонах | ≈ $14,6/мес | **≈ 420 ГБ/мес** |

Сейчас стоят 4 эндпоинта в одной зоне (`ecr.api, ecr.dkr, logs,
secretsmanager`) ≈ $29/мес. Они окупаются, только если суммарно экономят
больше $29: то есть через них идёт больше ≈ 840 ГБ/мес (≈ 210 ГБ на
каждый). Для ECR (`ecr.dkr` + S3) это образы: 0,5 ГБ × число запусков
задач. Если трафик мал, лишний эндпоинт можно убрать из
`interface_endpoints` (но проверить по цифрам ниже, не наугад).

Большая часть исходящего трафика (Twilio, Stripe, Cloudflare, Bunny, Firebase)
уходит в интернет и **через эндпоинт идти не может** — NAT тут нужен всегда.

## Как измерить (прежде чем менять)

1. Метрики NAT: CloudWatch → `AWS/NATGateway`, `BytesOutToDestination` +
   `BytesInFromDestination` (сумма = то, за что платим), по `NatGatewayId`.

   ```sh
   aws cloudwatch get-metric-statistics --namespace AWS/NATGateway --metric-name BytesOutToDestination \
     --dimensions Name=NatGatewayId,Value=<nat-id> --start-time $(date -u -v-7d +%FT%TZ) --end-time $(date -u +%FT%TZ) \
     --period 86400 --statistics Sum --output table
   ```

2. Кто именно качает: Cost Explorer → фильтр Usage type `NatGateway-Bytes`,
   либо VPC Flow Logs (включаются `audit_logs_enabled = true`, лежат в
   журнальном бакете), либо Logs Insights по логам потоков.
3. Решение: если один AWS-сервис (ECR, CloudWatch Logs, Secrets Manager,
   SQS и т. п.) даёт > 210 ГБ/мес — добавить для него interface-эндпоинт в
   `interface_endpoints`. Если трафик к Twilio/Stripe/Cloudflare/Bunny —
   эндпоинт не поможет; тогда смотреть, нет ли лишних скачиваний (фото,
   видео, обновления), и писать Claude «NAT много трафика».

## Что даёт код

- Тревога `lawbid-prod-nat-bytes-<n>` (`infra/modules/monitoring`, сумма
  in + out за 24 часа, письмо). Выключить: `nat_traffic_alarm_gb_per_day = 0`.
- Откат: удалить строку из tfvars (вернётся 20) или поставить 0.

## Принятый риск: одна зона (AZ) — и как отключить его одной строкой

Сейчас (запуск, экономия ≈ $62/мес): один NAT, все interface-эндпоинты
(ECR, логи, секреты) и по одной задаче API стоят в **одной** зоне. Если эта
зона AWS упадёт, в живой зоне уже работающие задачи продолжают отвечать, но
**новые** задачи не смогут скачать образ, прочитать секреты и выйти к
Stripe/FCM/SES. То есть авария зоны = частичная или полная недоступность на
минуты — часы. Мы это принимаем, пока людей мало (аудит 2026-10-25, S4-2).

Когда пользователей станет достаточно, включается **одной правкой tfvars**
(`infra/envs/prod/launch.tfvars.example`, блок «Multi-AZ egress»):

```hcl
nat_per_az             = true  # по NAT в каждой зоне, +$33/мес
interface_endpoint_azs = 2     # эндпоинты в двух зонах, +$29/мес
api_min_tasks          = 2     # по задаче API в каждой зоне, ≈ +$18/мес
```

Дальше `terraform plan` (проверить, что новых ресурсов NAT/эндпоинтов, а
не удалений) и `apply`, ≈ 10 минут, без простоя. Ручное аварийное
восстановление при падении зоны: поставить те же три строки и применить.
Альтернатива в будущем — Regional NAT Gateway
([AWS VPC docs](https://docs.aws.amazon.com/vpc/latest/userguide/nat-gateways-regional.html)).

## Тревоги порта и лимита (аудит S4-4)

`lawbid-prod-nat-port-alloc-<n>`: у NAT кончились порты — новые исходящие

## Автоматика эндпоинтов (S9-6, 2026-10-25)

На старте четыре платных VPC-эндпоинта (ecr.api, ecr.dkr, logs, secretsmanager; около 29 $ в месяц в одной зоне) НЕ создаются: они выгодны только при трафике через NAT больше примерно 830 ГБ в месяц. Маленькая функция AWS Lambda (`<name>-endpoints-autoscale`, модуль `infra/modules/endpoints-autoscale`) раз в час смотрит трафик NAT:

- трафик больше 20 ГБ в сутки (по последнему часу) — создаёт недостающие эндпоинты и пишет вам письмо;
- 7 спокойных суток подряд (NAT + эндпоинты меньше 10 ГБ в сутки) — удаляет их и пишет письмо;
- между двумя изменениями проходит минимум сутки.

Главный выбор владельца — в админке, «Настройки», ключ `scale.endpoints.mode`: **auto** (по умолчанию: решает трафик), **on** (эндпоинты всегда включены), **off** (никогда; уже созданные удаляются). Ключ `scale.endpoints.ceiling` — сколько эндпоинтов можно держать (0-4). Задание «Экономика» раз в 5 минут копирует их в файл `ops/scale-controls.json` в бакете documents, Lambda читает его раз в час (поэтому изменение применяется в течение часа; ручной выбор не ждёт суточной паузы).

Аварийный выключатель и потолок лежат в AWS Systems Manager → Parameter Store (ключи начинаются с `/<name>/endpoints-autoscale/`):

- `mode`: `on` (работает), `dry-run` (только пишет, что сделал бы), `off` (ничего не делает);
- `ceiling`: сколько эндпоинтов можно держать (0 — ни одного, 4 — все).

Трогает только эндпоинты с меткой `ManagedBy=<name>-endpoints-autoscale`. Если эндпоинт заведён в Terraform (`interface_endpoints`), Lambda его не касается. Если Lambda сама ломается три раза за три часа — тревога `<name>-endpoints-autoscale-errors` на почту. Стоимость самой автоматики: центы.
