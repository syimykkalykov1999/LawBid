# Публичные страницы для поисковиков: переключатели и порядок включения

Пакет «Продвижение», задача «статический генератор» (план: `docs/architecture/PSEO_ASO_PACKAGE_PLAN_2026-10-27.md`, разделы 2.2-2.8). Код: `scripts/seo/*`, workflow `.github/workflows/seo-deploy.yml`. Terraform не менялся.

Что нужно знать: без единой настройки ничего во внешнем виде сайта не меняется, кроме двух правок «на безопасность»: из разметки адвоката убран `aggregateRating` (рейтинг-звёзды без видимых отзывов Google считает нарушением), а `lastmod` в sitemap теперь настоящая дата изменения, а не дата сборки. Остальное включается переключателями (Settings → Secrets and variables → Actions → **Variables** в GitHub). Пока переменной нет, работает по-старому.

## Переключатели (Variables)

| Переменная | Что делает |
|---|---|
| `SEO_SITEMAP_INDEX=true` | `/sitemap.xml` становится индексом, страницы лежат в `/sitemaps/lawyers-1.xml`, `attorneys-1.xml`, `practice-areas-1.xml`, `site-1.xml`. В каждом файле до 10 000 адресов (потолок формата 50 000). Только индексируемые страницы. |
| `SEO_ROBOTS_AI=true` | robots.txt: пускает поисковых и «по запросу пользователя» ботов (Googlebot, Bingbot, OAI-SearchBot, ChatGPT-User, Claude-SearchBot, Claude-User, PerplexityBot, Perplexity-User); обучающих (GPTBot, ClaudeBot, anthropic-ai, Google-Extended, CCBot, Applebot-Extended, Meta-ExternalAgent) закрывает. Закрыты для всех `/api/ /auth/ /qr/ /q/ /g/ /r/ /internal/`, `?utm_`. Чтобы пустить обучающих: переменная `SEO_AI_TRAINING=allow` (в workflow она не пробрасывается намеренно: менять только осознанно, правкой файла). |
| `SEO_LLMS=true` | `/llms.txt` (короткий список хабов, без имён адвокатов) и `/llms-full.txt` (только гиды по практикам). Пользы для ранжирования пока никто не доказал, файл почти бесплатный. |
| `SEO_QUALITY_GATE=true` | Слабые страницы получают `noindex,follow` и уходят из sitemap. Пороги: страница штата/практики от 300 слов; «штат × практика» от 3 адвокатов; профиль от 150 символов био и без слов «best», «#1», «guaranteed», «top-rated». Подстройка: `SEO_MIN_WORDS`, `SEO_MIN_ATTORNEYS`, `SEO_MIN_BIO_CHARS`. **Внимание:** сегодняшние тексты практик 170-260 слов, штатов 125; с порогом 300 они все станут noindex, пока тексты не расширят (следующая задача пакета). Перед включением сделайте dry run и посмотрите цифры. |
| `SEO_RAMP_PER_DAY=200` | В индекс заходит не больше N новых страниц в сутки. Первый запуск «усыновляет» всё, что уже опубликовано (ничего не пропадает); дальше новые страницы идут очередью, лучшие первыми. Счётчик живёт в `seo-manifest.json`. |
| `SEO_INCREMENTAL=true` | В S3 заливаются только изменившиеся файлы (по хешу), удалённые страницы удаляются, а кэш CloudFront сбрасывается только для изменившихся путей: не больше 30 путей в сутки, никогда `/*`. Манифест `seo-manifest.json` лежит в корне бакета и загружается последним. |

Без `SEO_INCREMENTAL` старый путь (каждая папка заменяется целиком) остался, но сброс кэша теперь не `/*`, а до 30 путей по папкам (`/lawyers/*`, `/attorneys/*`, ...). Приложение больше не сбрасывается при каждой ночной сборке.

## Порядок включения (рекомендую)

1. Запустить вручную workflow **SEO pages** с галкой `dry_run`: в логе будут план загрузки и первые строки sitemap и robots. Ничего не публикуется.
2. Включить `SEO_INCREMENTAL=true`. Первый запуск зальёт всё (манифеста ещё нет), дальше только изменения.
3. `SEO_SITEMAP_INDEX=true`, затем в Google Search Console и Bing Webmaster Tools переотправить `https://<сайт>/sitemap.xml` (адрес прежний).
4. `SEO_ROBOTS_AI=true`, `SEO_LLMS=true`.
5. Когда тексты страниц расширены: `SEO_QUALITY_GATE=true` и `SEO_RAMP_PER_DAY=200`.

## Предохранители

- Если план хочет удалить больше 30 % опубликованных файлов (и больше 100), шаг «Plan the publish» падает с кодом 3 и ничего не заливает. Так пустой ответ API не стирает сайт. Если удаление настоящее, запустить workflow с галкой `allow_mass_delete`.
- Ограничение сбросов: 30 путей в сутки на все запуски дня (счётчик в манифесте). Что не влезло, обновится само за час (`max-age=3600`). Приоритет: удалённые страницы, robots.txt, sitemap.xml, остальное; при переполнении страницы одной папки сливаются в один `/<папка>/*`.
- Файлы `_next/` (сайт компании, имена с хешем) никогда не удаляются инкрементальным путём: у кэшированной страницы могут быть ссылки на старые куски.

## Что нужно владельцу

- Terraform не требуется: функция CloudFront `seo_index` уже отдаёт файлы с расширением из корня бакета (`/llms.txt`, `/sitemaps/*.xml`, `/seo-manifest.json` проходят без правок). Список `ROOT_FILES` в `infra/modules/web/main.tf` трогать не нужно.
- IAM-роль деплоя (`AWS_DEPLOY_ROLE_PROD`) должна уметь: чтение и запись в бакет (было), `s3:DeleteObject` (было для `sync --delete`), `cloudfront:CreateInvalidation` (было). Новых прав нет.
- Файл `seo-manifest.json` публичен (пути и хеши страниц, никаких данных людей); в robots.txt он закрыт.
- Размер манифеста растёт с числом страниц (около 300 байт на страницу: 100 тыс. страниц примерно 30 МБ). Для миллиона страниц генератор переедет в очередь BullMQ (задача 2 плана), там состояние будет в БД.

## Технически

- `scripts/seo/lib/discovery.mjs`: sitemap-индекс, robots, llms (чистые функции). `lib/gate.mjs`: проверки качества и очередь выкладки. `lib/manifest.mjs`: хеши, план загрузки, выбор путей для сброса. `publish-plan.mjs`: CLI плана (`--dry-run`, `--allow-mass-delete`). `build.mjs --dry-run`: решает всё и печатает сводку, файлы не пишет.
- `lastmod`: `updatedAt` сущности, если API его отдаёт (сейчас публичный каталог поле не отдаёт; когда добавят, подхватится само), иначе дата, когда содержимое страницы последний раз менялось (по хешу из прошлого манифеста), иначе день сборки.
- Тесты: `node --test scripts/seo/test/*.test.mjs` (их же гоняет workflow перед публикацией).
