# Публичные страницы для поисковиков: переключатели и порядок включения

Пакет «Продвижение», задача «статический генератор» (план: `docs/architecture/PSEO_ASO_PACKAGE_PLAN_2026-10-27.md`, разделы 2.2-2.8). Код: `scripts/seo/*`, workflow `.github/workflows/seo-deploy.yml`. Terraform не менялся.

Что нужно знать: без единой настройки ничего во внешнем виде сайта не меняется, кроме двух правок «на безопасность»: из разметки адвоката убран `aggregateRating` (рейтинг-звёзды без видимых отзывов Google считает нарушением), а `lastmod` в sitemap теперь настоящая дата изменения, а не дата сборки. Остальное включается переключателями (Settings → Secrets and variables → Actions → **Variables** в GitHub). Пока переменной нет, работает по-старому.

## Где включать: админка «Продвижение: SEO и сторы»

С 2026-10-27 те же переключатели есть в админке (**Контент и модерация → Продвижение: SEO и сторы**, право `promotion`; у владельца всегда, остальным включает владелец). Там же: кнопка пробного запуска, цифры последней сборки из `seo-manifest.json` (читается с сайта, кэш 10 минут) и чек-лист каналов (Google Search Console, Bing, магазины приложений и так далее) с галочками «Сделано».

Как это работает: workflow в шаге «Resolve the switches» читает `GET /api/v1/public/seo-settings` (публичный, только чтение, шесть значений, без данных людей). Значение из админки главнее. Пока тумблер не трогали (в ответе `null`) или API недоступен, действует репозиторная переменная ниже; если нет и её, выключено. Ключи в настройках: `seo.incremental_enabled`, `seo.sitemap_index_enabled`, `seo.robots_ai_enabled`, `seo.llms_enabled`, `seo.quality_gate_enabled`, `seo.ramp_per_day`; галочки чек-листа: `seo.checklist.<канал>`. Код: `scripts/seo/resolve-switches.mjs`, `apps/api/src/modules/admin-promotion/`. Инструкция для владельца: «Продвижение: страницы для поиска, Google Search Console и Bing» в разделе «Инструкции».

Пробный запуск из админки стартует `seo-deploy.yml` с `dry_run=true` через то же GitHub-приложение, что и «Инфраструктура из админки» (если оно подключено; иначе страница показывает команду `gh workflow run seo-deploy.yml -f dry_run=true`).

## Переключатели (Variables)

| Переменная | Что делает |
|---|---|
| `SEO_SITEMAP_INDEX=true` | `/sitemap.xml` становится индексом, страницы лежат в `/sitemaps/lawyers-1.xml`, `attorneys-1.xml`, `practice-areas-1.xml`, `site-1.xml`. В каждом файле до 10 000 адресов (потолок формата 50 000). Только индексируемые страницы. |
| `SEO_ROBOTS_AI=true` | robots.txt: пускает поисковых и «по запросу пользователя» ботов (Googlebot, Bingbot, OAI-SearchBot, ChatGPT-User, Claude-SearchBot, Claude-User, PerplexityBot, Perplexity-User); обучающих (GPTBot, ClaudeBot, anthropic-ai, Google-Extended, CCBot, Applebot-Extended, Meta-ExternalAgent) закрывает. Закрыты для всех `/api/ /auth/ /qr/ /q/ /g/ /r/ /internal/`, `?utm_`. Чтобы пустить обучающих: переменная `SEO_AI_TRAINING=allow` (в workflow она не пробрасывается намеренно: менять только осознанно, правкой файла). |
| `SEO_LLMS=true` | `/llms.txt` (короткий список хабов, без имён адвокатов) и `/llms-full.txt` (только гиды по практикам). Пользы для ранжирования пока никто не доказал, файл почти бесплатный. |
| `SEO_QUALITY_GATE=true` | Слабые страницы получают `noindex,follow` и уходят из sitemap. Пороги: страница штата/практики от 300 слов; «штат × практика» от 3 адвокатов; профиль от 150 символов био и без слов «best», «#1», «guaranteed», «top-rated». Подстройка: `SEO_MIN_WORDS`, `SEO_MIN_ATTORNEYS`, `SEO_MIN_BIO_CHARS`. **Внимание:** сегодняшние тексты практик 170-260 слов, штатов 125; с порогом 300 они все станут noindex, пока тексты не расширят (следующая задача пакета). Перед включением сделайте dry run и посмотрите цифры. |
| `SEO_RAMP_PER_DAY=200` | В индекс заходит не больше N новых страниц в сутки. Первый запуск «усыновляет» всё, что уже опубликовано (ничего не пропадает); дальше новые страницы идут очередью, лучшие первыми. Счётчик живёт в `seo-manifest.json`. |
| `SEO_INCREMENTAL=true` | В S3 заливаются только изменившиеся файлы (по хешу), удалённые страницы удаляются, а кэш CloudFront сбрасывается только для изменившихся путей: не больше 30 путей в сутки, никогда `/*`. Манифест `seo-manifest.json` лежит в корне бакета и загружается последним. |

Без `SEO_INCREMENTAL` старый путь (каждая папка заменяется целиком) остался, но сброс кэша теперь не `/*`, а до 30 путей по папкам (`/lawyers/*`, `/attorneys/*`, ...). Приложение больше не сбрасывается при каждой ночной сборке.

## Порядок включения (рекомендую)

1. Запустить вручную workflow **SEO pages** с галкой `dry_run`: в логе будут план загрузки и первые строки sitemap и robots. Ничего не публикуется.
2. Включить `SEO_INCREMENTAL=true`. Первый запуск зальёт всё (манифеста ещё нет), дальше только изменения.
3. `SEO_SITEMAP_INDEX=true`, затем в Google Search Console и Bing Webmaster Tools переотправить `https://<сайт>/sitemap.xml` (адрес прежний).
4. `SEO_ROBOTS_AI=true`, `SEO_LLMS=true`.
5. Когда тексты страниц расширены: `SEO_QUALITY_GATE=true` и `SEO_RAMP_PER_DAY=200`.

## Предохранители

- Если план хочет удалить больше 30 % опубликованных файлов (и больше 100), шаг «Plan the publish» падает с кодом 3 и ничего не заливает. Так пустой ответ API не стирает сайт. Если удаление настоящее, запустить workflow с галкой `allow_mass_delete`.
- Ограничение сбросов: 30 путей в сутки на все запуски дня (счётчик в манифесте). Что не влезло, обновится само за час (`max-age=3600`). Приоритет: удалённые страницы, robots.txt, sitemap.xml, остальное; при переполнении страницы одной папки сливаются в один `/<папка>/*`.
- Файлы `_next/` (сайт компании, имена с хешем) никогда не удаляются инкрементальным путём: у кэшированной страницы могут быть ссылки на старые куски.

## Что нужно владельцу

- Terraform не требуется: функция CloudFront `seo_index` уже отдаёт файлы с расширением из корня бакета (`/llms.txt`, `/sitemaps/*.xml`, `/seo-manifest.json` проходят без правок). Список `ROOT_FILES` в `infra/modules/web/main.tf` трогать не нужно.
- IAM-роль деплоя (`AWS_DEPLOY_ROLE_PROD`) должна уметь: чтение и запись в бакет (было), `s3:DeleteObject` (было для `sync --delete`), `cloudfront:CreateInvalidation` (было). Новых прав нет.
- Файл `seo-manifest.json` публичен (пути и хеши страниц, никаких данных людей); в robots.txt он закрыт.
- Размер манифеста растёт с числом страниц (около 300 байт на страницу: 100 тыс. страниц примерно 30 МБ). Для миллиона страниц генератор переедет в очередь BullMQ (задача 2 плана), там состояние будет в БД.

## Технически

- `scripts/seo/lib/discovery.mjs`: sitemap-индекс, robots, llms (чистые функции). `lib/gate.mjs`: проверки качества и очередь выкладки. `lib/manifest.mjs`: хеши, план загрузки, выбор путей для сброса. `publish-plan.mjs`: CLI плана (`--dry-run`, `--allow-mass-delete`). `build.mjs --dry-run`: решает всё и печатает сводку, файлы не пишет.
- `lastmod`: `updatedAt` сущности. Публичный каталог (`GET /public/directory/attorneys`) теперь отдаёт `updatedAt` каждого адвоката (поле `updated_at` профиля, уже было в БД, схема не менялась), и `lastmod` в sitemap равен дню изменения профиля, а не дню сборки. Если поля нет (старый API), берётся дата, когда содержимое страницы последний раз менялось (по хешу из прошлого манифеста), иначе день сборки.
- `scripts/seo/lib/render.mjs`: чистая функция `renderSite(attorneys, options)`: данные на входе, файлы на выходе, ни сети, ни диска. `build.mjs` (CLI и workflow) и задача API `seo.generate` вызывают одну и ту же функцию, поэтому страницы не расходятся. `lib/manifest.mjs: planPublish` делает то же решение «что залить, что удалить, какие пути сбросить» по картам хешей в памяти.
- Тесты: `node --test scripts/seo/test/*.test.mjs` (их же гоняет workflow перед публикацией).

## Генератор в API: задача `seo.generate` (BullMQ)

Страницы можно собирать не только в GitHub Actions, но и самим API: задача читает каталог из БД (реплика, по 100 строк за чтение, три запроса на страницу, без запросов на каждого адвоката), рисует страницы той же `renderSite` и заливает в S3 только изменившиеся (по хешу). HTTP-запросов к собственному API нет, при заходе посетителя API и БД не нагружаются.

**Выключено по умолчанию.** Переключатель в админке: Система → Настройки, ключ `seo.generator_mode`:

| Значение | Что происходит |
|---|---|
| `off` (по умолчанию) | Ничего. Задача по расписанию просыпается, видит `off` и сразу выходит; события не ставятся в очередь; БД, Redis и S3 не трогаются. |
| `nightly` | Раз в сутки в 05:10 UTC (после ночных снимков: `storage.snapshot` в 04:55). |
| `nightly+events` | Ночью и ещё: когда юриста подтвердили, скрыли (приостановка), вернули, удалили аккаунт или он поменял профиль, в очередь `cron-heavy` ставится одна отложенная задача (через 60 секунд, не чаще чем раз в 10 минут). Все события за это время дают одну сборку (одинаковый id задачи). Событие, пришедшее во время сборки, даёт ещё одну сборку после неё. Ночная сборка подхватывает всё, что события пропустили (смена фото, лицензий, рейтинга). |

Нужны переменные окружения задачи в ECS (если их нет, задача пишет «skipped» и ничего не делает, даже при `nightly`):

| Переменная | Значение |
|---|---|
| `SEO_WEB_BUCKET` | Имя бакета сайта (тот же, что `WEB_BUCKET` в GitHub). |
| `SEO_SITE_URL` | `https://<сайт>` без пути (для canonical и og:url). |
| `SEO_WEB_DISTRIBUTION_ID` | Необязательно: номер раздачи CloudFront для точечного сброса кэша. Без него страницы обновятся сами за час (`max-age=3600`). |
| `SEO_QUALITY_GATE`, `SEO_RAMP_PER_DAY`, `SEO_MIN_WORDS`, `SEO_MIN_ATTORNEYS`, `SEO_MIN_BIO_CHARS`, `SEO_RAMP_BASELINE`, `SEO_INDEX_EMPTY` | Те же переключатели и с тем же смыслом, что для `build.mjs` (раздел выше), все выключены, пока не заданы. Значения должны совпадать с переменными GitHub, иначе страница «мигает» между двумя сборщиками. |

Права: роли задачи в ECS нужны `s3:GetObject`, `s3:PutObject`, `s3:DeleteObject` на бакет сайта (только префиксы `lawyers/`, `practice-areas/`, `attorneys/`, `seo-gen-manifest.json`) и `cloudfront:CreateInvalidation`. Это Terraform, шаг владельца; пока прав нет, `nightly` запишет ошибку и страницы останутся как были.

Что публикует задача и чего нет: только HTML-страницы `/lawyers/**`, `/practice-areas/**`, `/attorneys/**` и свой манифест `seo-gen-manifest.json`. `sitemap.xml`, `robots.txt`, `llms.txt`, `/sitemaps/*`, страницы сайта компании и `.well-known` по-прежнему делает ночной workflow **SEO pages**: он склеивает их с сайтом компании, а сайта компании у API нет. Состояние разгона (`SEO_RAMP_PER_DAY`) и даты `lastmod` задача читает из `seo-manifest.json` workflow, только на чтение. Если включаете оба сборщика, workflow оставьте ночным запасным: он перезальёт то же самое, и гонки нет, потому что оба рисуют одной функцией из одних данных.

Ограничения и предохранители (все в админке, Система → Настройки):

- `seo.generator_max_attorneys` (5000): сколько юристов собирать за раз. Все страницы одного прогона лежат в памяти (около 30 КБ на профиль: 5000 юристов примерно 150 МБ). Если юристов больше, сборка отказывается, пишет тревогу `seo_generator_too_many` и ничего не меняет (неполный набор стёр бы страницы). Больше 5000 включать вместе с потоковой отрисовкой (следующая задача).
- `seo.generator_max_uploads_per_run` (2000): файлов за сборку; остальное доедет со следующей. Первая сборка 100 тыс. страниц растянется на несколько дней вместо одного взрыва PUT.
- `seo.max_invalidation_paths_per_day` (30): путей сброса CloudFront в сутки, никогда не `/*`; первые 1000 в месяц бесплатны.
- `seo.generator_debounce_seconds` (60), `seo.generator_min_interval_minutes` (10): окно слияния событий и минимальный промежуток между сборками по событиям.
- Если сборка хочет удалить больше 30 % опубликованных страниц (и больше 100), она не пишет ничего и пишет тревогу `seo_generator_mass_delete` (так пустой ответ БД не стирает сайт).
- Манифест `seo-gen-manifest.json` записывается последним, поэтому упавшая сборка просто планируется заново. Задача не запускается при паузе тяжёлых задач (она в списке `HEAVY_CRON_JOBS`). Один запуск за раз (замок Redis `cron:seo.generate`).

Стоимость (S3 Standard, PUT $0.005 за 1000, цены из плана, раздел 2.4): состояние в покое ничего не стоит. Одна сборка читает ceil(N/100) страниц из БД (реплика) и делает PUT только для изменившихся файлов: при 5% изменений в сутки на 10 тыс. страниц это около 500 PUT, меньше $0.003 в сутки. Первая заливка 10 тыс. страниц: $0.05. Хранение 0.4 ГБ: около $0.01 в месяц. Сброс CDN: до 30 путей в сутки (около 900 в месяц, бесплатно). Нагрузка на БД: 5000 юристов это 50 чтений по 100 строк раз в сутки и по одной сборке на всплеск событий (не чаще раза в 10 минут). Тревоги в логах: `seo_generator_too_many`, `seo_generator_mass_delete`, метрика `seo_generate` (только числа, без имён и текстов).

Порядок включения: 1) завести три переменные в ECS и права в Terraform; 2) `seo.generator_mode = nightly`; на следующий день посмотреть в логах `seo_generate` (сколько страниц залито); 3) `nightly+events`. Откат: `off`; уже залитые страницы остаются, как были.

Проверка (smoke): `seo.generator_mode = nightly`, запустить задачу руками из очереди `cron-heavy` (имя `seo.generate`), в логе `seo pages generated`, в бакете появился `seo-gen-manifest.json`; повторный запуск: `uploaded: 0`.

Тесты: `apps/api/src/jobs/handlers/seo-generate.job.spec.ts` (выкл не читает ничего, первая и повторная сборка, лимиты, отказ при массовом удалении), `apps/api/src/common/seo/seo-generator.trigger.spec.ts` (очередь, слияние событий, интервал), `scripts/seo/test/render.test.mjs` (чистая функция и план по хешам в памяти).

## Новые типы страниц: посты адвокатов, хабы «город × практика», вопросы юристам (2026-10-27)

План: `docs/architecture/PSEO_ASO_PACKAGE_PLAN_2026-10-27.md`, разделы 2.1, 2.3, 2.8, 6. Код: `scripts/seo/lib/render.mjs` (`renderSite`), `gate.mjs`, `discovery.mjs`; в API: `PublicDirectoryService.seoPosts()` / `seoQuestions()` и задача `seo.generate`. **Всё выключено по умолчанию**; пока переключатели не заданы, все страницы и все файлы (sitemap, llms.txt, манифест) побайтово такие же, как раньше (это проверяет тест «all three switches OFF»).

### Что строится

| Тип | Адрес | Что на странице | Разметка |
|---|---|---|---|
| Пост адвоката | `/attorneys/<username>/posts/<slug>/` | Только текстовый пост: заголовок, автор (ссылка на профиль), дата, текст, тема (ссылка на практику), блок «not legal advice» | `Article` (автор `Person`, издатель `Organization`), `BreadcrumbList`, `og:type=article`, canonical на себя |
| Хаб города | `/lawyers/<штат>/<город>/<практика>/` и страница города `/lawyers/<штат>/<город>/` | До 20 адвокатов с этой практикой в городе, ситуации, как это работает, FAQ практики; ссылки штат ↔ город ↔ практика (страницы штата и «штат × практика» получают разделы «Cities»/«by city») | `CollectionPage` + `ItemList` из `Attorney` (подтип `LegalService`), `FAQPage`, `BreadcrumbList`. Сама площадка `LegalService` не помечается (план 2.8) |
| Вопрос юристам | `/legal-questions/<slug>/` и список `/legal-questions/` | Вопрос, проверенный ответ верифицированного адвоката (с именем и ссылкой), «General information, not legal advice», ссылки на практику/штат | `FAQPage` (Question + acceptedAnswer), `BreadcrumbList` |

Адрес страницы поста и вопроса: «читаемая часть из заголовка (до 60 знаков) + первые 8 знаков id». Id держит адрес уникальным и стабильным; если заголовок поменяли, адрес меняется, старая страница удаляется (404). Адреса, как и у остальных страниц, заканчиваются на `/`.

### Переключатели (все выключены, пока не заданы)

| Переменная | Что делает |
|---|---|
| `SEO_PAGES_POSTS=1` | Страницы постов. Задача читает посты из БД только при этом переключателе; `build.mjs` читает ключ `posts` из файла `--offline`. |
| `SEO_PAGES_CITIES=1` | Хабы «город × практика» и страницы городов. Хаб создаётся только если в городе не менее `SEO_MIN_CITY_ATTORNEYS` (по умолчанию 3) адвокатов с такой практикой; иначе страницы нет вовсе (не noindex, а нет файла). |
| `SEO_PAGES_QA=1` | Вопросы юристам и список. Задача читает вопросы из БД только при этом переключателе. |
| `SEO_AD_LABEL=off` | Убирает блок «Attorney Advertising. Prior results do not guarantee a similar outcome.» По умолчанию он показан на новых страницах, где адвокат лицензирован в Нью-Йорке (план, раздел 6; текст показать юристу в NY до включения). На старых типах страниц (профиль) блок пока не добавлен: отдельная задача. |
| `SEO_MIN_POST_CHARS` (300), `SEO_MIN_QA_CHARS` (300), `SEO_MIN_CITY_ATTORNEYS` (3) | Пороги. `SEO_MAX_POSTS`, `SEO_MAX_QUESTIONS` (по 20000): потолок строк за прогон в задаче API; если больше, прогон отказывается и пишет тревогу `seo_generator_too_many` (неполный набор стёр бы страницы). |

### Проверки качества (всегда включены для этих трёх типов)

Новые типы проверяются даже при выключенном `SEO_QUALITY_GATE`: у них нет «старого поведения», которое надо сохранить, а кнопка «выключить» это сам переключатель типа.

- Пост: текст короче `SEO_MIN_POST_CHARS` → `noindex,follow` и вне sitemap (причина `thin-post`); слова «best», «#1», «guaranteed», «top-rated» в заголовке или тексте → `noindex` (`unverified-claim`). Фраза «best interests» (стандарт семейного права) не считается хвастовством.
- Вопрос: самый длинный проверенный ответ короче `SEO_MIN_QA_CHARS` → `noindex` (`thin-answer`); та же проверка слов. Вопрос без проверенного ответа страницы не получает вообще.
- Хаб города: меньше порога адвокатов → страницы нет.
- Контактные данные (e-mail, телефон с разделителями, SSN) в посте, вопросе или ответе: страницы нет вовсе (не noindex, потому что noindex-страница всё равно публична). Счётчики в логе: `skipped` (`post-contact-info`, `qa-contact-info` ...), без текстов.
- Тот же разгон `SEO_RAMP_PER_DAY` и тот же манифест хешей: новые страницы входят в индекс не быстрее N в сутки (первый запуск с разгоном «усыновляет» всё, что уже есть). Пока включён `SEO_QUALITY_GATE`, остальные типы проверяются как раньше.
- Sitemap: отдельные файлы `sitemaps/posts-<n>.xml`, `cities-<n>.xml`, `legal-questions-<n>.xml` (при `SEO_SITEMAP_INDEX`); в `/llms.txt` добавляются разделы «Cities» и «Legal questions» (только когда есть что перечислять; имён адвокатов и постов там нет).

### Откуда данные и какие пробелы (схема БД не менялась)

Посты: только опубликованные, не удалённые и не в архиве, без видео, фото и файлов, тема «legal» (`content_class`), автор в каталоге. Но каталог эти поля не заполняет, поэтому **на боевых данных хабов пока не будет**, пока не добавят поле «город офиса» (схема + экран профиля, отдельная задача) и не пропишут его в `PublicDirectoryService.attorneys`. |

У самого вопроса `safety_flags` тоже пустые. Автор вопроса (даже не анонимный) на странице не показывается и не читается из БД. |

**Важно для двух сборщиков.** Страницы постов лежат внутри папки `/attorneys/`, страницы вопросов в новой папке `/legal-questions/`. Ночной workflow без `SEO_INCREMENTAL` заменяет папку целиком (`sync --delete`) и сотрёт то, что залила задача API, потому что постов и вопросов у него нет. Поэтому, если включаете посты или вопросы в задаче API, держите workflow в режиме `SEO_INCREMENTAL=true` (он удаляет только то, что значится в его собственном манифесте).
