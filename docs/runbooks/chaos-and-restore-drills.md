Делаем как Netflix и AWS Well-Architected (надёжность):

  описать «нормальное состояние» цифрами, потом сломать одну вещь, сравнить,
  держать «радиус поражения» малым, автоматически останавливать опыт, как только
  людям стало плохо.
- **AWS Well-Architected, надёжность:** REL12-BP04/BP05 — учения на отказ
  (AWS FIS, GameDay); REL09-BP04 — копия базы считается рабочей только после
  восстановления; REL13 — план на случай аварии проверяется.
- **Шаблоны не свои:** действия и права взяты из руководства AWS FIS
  (`ecs-task-actions.html`, справочник действий) и из библиотеки сценариев FIS

  проверка восстановления — по образцу AWS Backup «Restore testing validation»
  (`restore-testing-validation.html`). Всё прочитано 25.11.2026.

Учения только на **staging** (`lawbid-staging`). Боевой (prod) модуль не примет:
имя с `prod` отклоняется ещё на `terraform plan`, и спутник SSM для задержки на
задаче prod тоже отклоняется.

## Часть 1. Учения FIS на staging

### Что есть (Terraform: `infra/modules/fis-gameday`, подключён в `infra/envs/staging`)

| Шаблон (тег Name) | Что ломает | Что должно быть («хорошо») |
|---|---|---|
| `lawbid-staging-api-stop-tasks` | `aws:ecs:stop-task` — останавливает 50 % задач API | ECS поднимает новые за 1–2 мин, балансировщик уводит трафик; 5xx почти нет (меньше 1 %), сайт открывается |
| `lawbid-staging-api-latency` | `aws:ecs:task-network-latency` +200 мс (±10) на 50 % задач API, 5 мин | p95 растёт примерно на 200 мс, но запросы не падают по таймауту; повторы не устраивают «шторм»; после конца — сразу как было |
| `lawbid-staging-redis-failover` | `aws:elasticache:replicationgroup-interrupt-az-power`, 3 мин | реплика Valkey становится главной за ≤ 1 мин, сокеты переподключаются сами, вход и чаты работают |
| `lawbid-staging-rds-failover` | `aws:rds:reboot-db-instances forceFailover=true` | переключение базы на резервную в другой зоне за ~1–2 мин. **Есть только при `database_multi_az = true`** |
| `lawbid-staging-az-power` | сценарий «AZ Availability: Power Interruption»: на 2 мин режет сеть всех подсетей одной зоны, на 30 мин гасит узлы Valkey в этой зоне, переключает базу (если Multi-AZ) | всё живое уходит во вторую зону: сайт и вход работают, 5xx < 1 % после первых 2–3 минут, через 30 мин всё само возвращается |

Остановка опыта (stop conditions) — у каждого шаблона три сигнала CloudWatch:

1. «нет ни одной здоровой задачи API» 2 минуты (свой сигнал модуля);
2. «больше половины запросов с ошибкой» 3 минуты (свой сигнал модуля);
3. **существующий** сигнал «Приложение выдаёт ошибки (больше 1 %)» —
   `lawbid-staging-api-5xx-ratio` (модуль monitoring).

Сработал любой — FIS сразу прекращает опыт и откатывает действие (сеть
возвращается, задержка снимается). Это и есть «стоп, людям плохо».

Журнал каждого опыта (FIS, схема журнала 2) — в CloudWatch Logs
`/aws/fis/lawbid-staging` (у шаблонов задержки и зоны).

### Как запускать (человек с входом в AWS на staging; ничего не запускается само)

1. Нормальное состояние: открыть CloudWatch → Alarms — все сигналы `lawbid-staging-*`
   в OK. Записать p95 и долю 5xx за последний час (дашборд `lawbid-staging`).
2. Взять номер шаблона:
   ```sh
   cd infra/envs/staging && terraform output -json gameday_templates
   ```
3. Запустить один опыт (по одному, не параллельно):
   ```sh
   aws fis start-experiment --experiment-template-id <ID> --tags Drill=$(date +%F)
   ```
4. Во время опыта: каждые 2 с дёргать `https://api.staging.lawbid.app/health/live`
   (например, `loadtest/scripts/gameday.sh` или `watch -n2 curl -s -o /dev/null -w '%{http_code}\n' …`),
   смотреть дашборд.
5. Конец: `aws fis get-experiment --id <EXP>` → `state.status` = `completed`
   (прошёл) или `stopped` (сработал сигнал — это результат, а не поломка учения).
6. Через 5 минут после конца — все сигналы снова OK. Нет — это находка, разбирать.
7. Записать строку в таблицу ниже (одна строка на опыт).

Порядок (от маленького к большому, как у Netflix): stop-tasks → latency →
redis-failover → rds-failover (если Multi-AZ) → az-power. Раз в квартал полный
круг; после крупного изменения инфраструктуры — тот шаблон, который его касается.

### Что значит «плохо» и что делать

- `stopped` по сигналу 5xx на stop-tasks или redis-failover — приложение не
  переживает потерю одной задачи / главного узла: смотреть `api-5xx.md`,
  `db-redis-unavailable.md`, исправлять код или настройки, повторить.
- Задержка 200 мс даёт таймауты — где-то слишком короткий таймаут или нет
  повтора с паузой: найти по журналам API, исправить.
- AZ: после 3 минут всё ещё ошибки — что-то живёт только в одной зоне
  (одна задача, одна NAT, база без Multi-AZ). Записать и чинить.

## Часть 2. Ежемесячная проверка восстановления базы (AWS Backup restore testing)

### Как устроено (Terraform: `infra/modules/backup`)

1. **1-го числа в 14:00 UTC** AWS Backup сам берёт самую свежую копию базы
   (не старше 7 дней) и поднимает из неё **временную** базу
   `awsbackup-restore-test-…` (`db.t4g.micro`, одна зона, не публичная, в той же
   сети и с теми же группами доступа, что и настоящая). Живая база не трогается.
2. Когда копия поднялась (событие `Restore Job State Change` = `COMPLETED`),
   EventBridge запускает функцию `lawbid-<env>-restore-validate`.
3. Функция запускает разовую задачу из определения `lawbid-<env>-migrate`
   (тот же образ и тот же вход в базу, что и у миграций; адрес базы заменён на
   временную копию) и выполняет **проверочные запросы**:
   - копия открыта на запись (`pg_is_in_recovery()` = false);
   - есть применённые миграции (`_prisma_migrations`);
   - таблица `users` читается, людей не меньше порога (prod 1, staging 0);
   - печатает число миграций, людей и время самого нового пользователя (это RPO).
4. Итог отправляется в AWS Backup (`PutRestoreValidationResult`):
   `SUCCESSFUL` или `FAILED` с причиной.
5. **Уборка:** AWS Backup сам удаляет временную базу через 1 час
   (`restore_test_validation_hours`). Наших ручных шагов нет.

Тревоги:

- копия не поднялась — звонок на критический канал (было и раньше);
- копия поднялась, но проверочный запрос не прошёл — сигнал
  `lawbid-<env>-restore-validation-failed` на критический канал.

### Как посмотреть результат

AWS Backup → Jobs → **Restore jobs** → строка за 1-е число: `Status` = Completed,
`Validation status` = Successful. Подробности — журнал
`/aws/lambda/lawbid-<env>-restore-validate` (строка `restore_check` с цифрами)
и журнал задачи migrate (`restore_check: {...}`). Время от начала до
`Completed` — это наш RTO.

### Если FAILED

1. Прочитать причину в `Validation status message`.
2. `task did not start` — нет мест в подсетях / права: смотреть ECS → Tasks → Stopped.
3. `exit 1` — не подключилась к копии: группы доступа базы и задач, TLS.
4. `exit 3/4/5` — копия поднялась, но данные не те (только чтение, нет миграций,
   нет людей): **копия негодная**, сразу ручное восстановление по
   `restore-drill.md` (`scripts/ops/restore-drill.sh`), разбор, запись в
   `KNOWN_ERRORS.md`.
