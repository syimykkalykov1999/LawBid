# База данных: уборка, таймауты, реплика (DB-ops hardening, 2026-10-25)

Что добавлено в пакете `claude/db-ops-hardening` и что с этим делать. Всё по умолчанию безопасно: поведение приложения не меняется, пока вы сами ничего не включите.

## 1. Уборка «мёртвых» строк (autovacuum)

- Группа параметров RDS (`infra/modules/postgres`) теперь пишет в лог долгие уборки (`log_autovacuum_min_duration` = 1 с), ожидания блокировок (`log_lock_waits`, `deadlock_timeout` = 1 с), время ввода-вывода (`track_io_timing`) и временные файлы больше 10 МБ (`log_temp_files`).
- База убирает мусор раньше: `autovacuum_vacuum_scale_factor` 0,05 (было 0,2), `autovacuum_analyze_scale_factor` 0,02 (было 0,1). Значения меняются через переменные модуля.
- Миграция `20261101300000_autovacuum_hot_tables` ставит ещё более строгие настройки (1 %, лимит работы 2000, пауза 2 мс) на таблицы, которые растут и теряют строки быстрее всех: `messages`, `notifications`, `sessions`, `post_view_events`, `cross_family_outbox`, `cross_family_inbox`, `search_outbox`. Это только параметры хранения: перезаписи данных нет.
- Раз в сутки (04:35 UTC) воркер запускает `db.health` и пишет в лог:
  `db_dead_tuple_ratio` (доля мёртвых строк, таблицы от 10 тысяч строк), `db_table_size` (самые большие таблицы), `db_txid_age` (расстояние до переполнения счётчика транзакций).
  Жёлтый сигнал (`alert: db_table_large` / `db_table_bloat`) идёт при 20 ГБ или 20 % мёртвых строк. Включатель с тремя состояниями (**Настройки → `db.health_mode`**: off / on / auto, по умолчанию auto: раз в сутки, но пропускается, пока тяжёлые задачи на паузе). Пороги меняются в админке: **Настройки → `db.health_table_size_gb`, `db.health_dead_ratio_percent`** (0 = не проверять).
- Тревоги CloudWatch (`infra/modules/monitoring/db-health.tf`): `db-dead-tuple-ratio` (20 %), `db-txid-age` (1 млрд, это срочное письмо), `db-table-health`, `outbox-oldest-pending` (30 минут), `scatter-partial-failure`.

### Что делать при тревоге
- `db-dead-tuple-ratio` пришла один раз: ничего, база чистит сама. Несколько дней подряд: напишите Claude «раздутие таблицы».
- `db-txid-age`: срочно напишите Claude «txid wraparound». Обычно ищут зависшую транзакцию и делают ручной `VACUUM FREEZE`.

## 2. Таймауты миграций

- Миграция `20261101310000_migrator_role_timeouts` ставит роли `lawbid_migrator`: ждать блокировку не дольше 5 секунд (`lock_timeout`) и не выполнять один запрос дольше 10 минут (`statement_timeout`). Действует на новые подключения. Тот же текст в `infra/postgres/role-settings.sql` (для базы, где миграция ещё не ходила).
- `scripts/deploy/run-migrations.sh`: если миграция не получила блокировку (SQLSTATE 55P03, в логе «lock timeout»), задача запускается ещё один раз через 20 секунд. Миграция идёт одной транзакцией, поэтому неудачная попытка ничего не меняет. Любая другая ошибка останавливает выкладку сразу.
- Большая правка таблицы (долгий backfill) должна идти порциями, а не одним запросом дольше 10 минут.

## 3. Очистка служебных событий между частями базы

В ночной задаче `storage.retention` добавлены:
- `cross_family_outbox` со статусом `done` старше 7 дней (**Настройки → `storage.retention_outbox_done_days`**, 0 = хранить всегда). Строки `pending` и `dead` не трогаются.
- `cross_family_inbox` старше 30 дней (**`storage.retention_inbox_days`**). Для этого добавлен индекс по `applied_at` (миграция `20261101330000_...`).
- Каждую минуту реле (`outbox.sweep`) пишет возраст самого старого ожидающего события (`cross_family_outbox_oldest_pending`). Пока частей базы одна, строк нет и строка не пишется.

## 4. Реплика для чтения: отставание

Включатель с тремя состояниями: **Настройки → `db.replica_reads`** (off — только главная база; on — реплика всегда; auto — по умолчанию, реплика пока отставание ниже порога **`db.replica_max_lag_ms`**, 5000 мс). Пока `DATABASE_REPLICA_URL` пуст, это ни на что не влияет.

`PrismaReadService` (когда задан `DATABASE_REPLICA_URL`) каждые 5 секунд замеряет отставание реплики. Если отставание больше `DB_REPLICA_MAX_LAG_MS` (по умолчанию 5000), все чтения идут на главную базу, и сообщение `replica_lag_state` пишется в лог один раз при смене состояния. Код, которому нужно свежее (или терпимее), вызывает `readDb({ maxStalenessMs })`.

На реплику переведены: публичный каталог юристов, строка публичного профиля юриста (профиль самого смотрящего, его подписки и блокировки читаются с главной), гостевая лента, списки комментариев (свои комментарии за последние 30 секунд дочитываются с главной), подсказки поиска и популярное (они уже читали реплику через поиск).

- Пока таблицы разнесены по нескольким физическим базам (шардинг включён), реплика не используется: у неё нет маршрутизации по шардам.
- `DB_REPLICA_POOLER_HOST` направляет подключение реплики через PgBouncer. Это должен быть ОТДЕЛЬНЫЙ PgBouncer, чей `DATABASE_URL` указывает на реплику. Не `DB_POOLER_HOST`: тот пулер ведёт на главную базу, и «реплика» молча читала бы главную.

## 5. Уровень изоляции транзакций

`withTxRetry(prisma, fn, { isolation: 'readCommitted', op: 'имя' })`. По умолчанию остаётся Serializable (деньги, ставки, принятие). Отправка обычного сообщения в чате использует read committed (строка беседы уже блокируется `FOR UPDATE`; подарок со звёздами остаётся Serializable). Лайки и подписки не используют `withTxRetry`, это одиночные запросы, они уже в read committed. В журнале повторов теперь есть поле `op` (метка места вызова) и `isolation`; при read committed повторяется и взаимная блокировка (40P01).

## 6. Прочее

- PgBouncer: `query_wait_timeout` по умолчанию 10 секунд (было 30), как `pool_timeout` приложения.
- Тест `apps/api/src/prisma/pooler-safe-sql.spec.ts` падает, если в SQL появился `pg_advisory_lock(`, `LISTEN` или `SET` без `LOCAL`: такие вещи ломаются только за пулером.
- Массовая запись по нескольким базам (`updateMany` / `deleteMany`) при отказе одной базы бросает `ScatterPartialFailureError` с именами баз и пишет `scatter_partial_failure` (тревога).
- SQL-функция `new_sharded_id(shard)` даёт идентификатор, упорядоченный по времени (как в приложении). Для новых таблиц: `id UUID PRIMARY KEY DEFAULT new_sharded_id()`. Доля случайных (v4) идентификаторов среди новых строк пишется раз в минуту как `shard_id_v4_share`.
- Prisma: `binaryTargets` для Alpine x64/ARM64 и glibc arm64 (лишние файлы движка не скачиваются во время работы).

## Что делать вам (владельцу)

См. инструкцию в админке **Инструкции → «RDS: параметры базы и перезагрузка»** (`apps/admin/content/guides/aws-rds-parameter-group.md`). Коротко: параметры группы (кроме `rds.logical_replication`) применяются сразу; `rds.logical_replication` и перезагрузка делаются в воскресное окно вместе с Multi-AZ.
