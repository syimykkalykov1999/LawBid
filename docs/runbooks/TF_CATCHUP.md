# Подтянуть настройки сервера (Terraform) до кода: три команды

Для владельца. Terraform (описание сервера) отстал от кода: около 94 файлов и 15 новых модулей, а на сервере пока нет прав для SEO-страниц, двух тревог и увеличенного пула соединений воркера. Здесь всё делается тремя командами; скрипт ничего не применяет сам.

Когда: **до** выкладки кода (Deploy → Approve), один раз. Причина в `docs/dev/DEPLOY_SAFETY_AUDIT_2026-10-27.md` (находки 8 и 9).

## Команды (в Терминале Mac, по порядку)

1. Войти в AWS. Откроется браузер, войдите в аккаунт AWS:
   ```sh
   aws login
   ```
2. Посчитать план. Ничего не меняется, 2-10 минут:
   ```sh
   cd /Users/sima/Desktop/LawBid && git pull && bash scripts/dev/tf-catchup.sh plan
   ```
   Прочитайте русскую сводку: сколько добавится, изменится, заменится, удалится.
   - **Зелёное «Опасных удалений и замен нет»** — можно дальше.
   - **Красный СТОП** — ничего не применяйте, скопируйте вывод и напишите Claude. Скрипт такой план всё равно не примет.
3. Применить ровно этот план. Скрипт ещё раз спросит, напишите `ДА`:
   ```sh
   bash scripts/dev/tf-catchup.sh apply
   ```

После этого: выкладка кода (Deploy → Approve) как обычно.

## Что делает скрипт

- Без входа в AWS (`aws sts get-caller-identity` не прошёл) отказывается: «сначала aws login».
- `plan`: берёт настоящие настройки прода из Secrets Manager (`lawbid-prod/terraform-tfvars`), подставляет **текущую** версию кода с сервера (`scripts/deploy/current-tag.sh`, иначе apply откатил бы выкладку), считает план в файл `tfplan` и пропускает его через `scripts/deploy/plan-guard.sh` (база, секреты, ключи KMS, Redis, S3, копии не удаляются).
- Красный СТОП: любое удаление или замена (`-/+`), кроме новых версий описания задач ECS и тревог CloudWatch (в тревоге нет данных, её удаление безвредно; такие строки показываются жёлтым); отдельно и сразу для `aws_ecs_service`, `aws_db_instance`, `aws_elasticache_*`.
- `apply`: принимает только сохранённый `tfplan` (не старше 2 часов, тот же аккаунт, файл не менялся, версия кода на сервере не сменилась с момента плана), заново проверяет СТОП, спрашивает `ДА`. Автоматически не применяется никогда.
- Секреты (`terraform.tfvars`, план) лежат в `~/.lawbid-tf-catchup` (права 700) и удаляются после успешного apply. В git и на экран не попадают.
- Вход в AWS: ключи из сессии `aws login` **не** замораживаются в окружении (они живут ~15 минут и истекали посреди плана). Terraform и `aws` получают их через `credential_process` и сами обновляют. Кеш плагинов Terraform у скрипта свой (`~/.lawbid-tf-catchup/plugin-cache`), общий `~/.terraform.d/plugin-cache` с символическими ссылками ему не мешает; первый запуск скачивает провайдеры (несколько минут).
- Проверка правил без AWS: `bash scripts/deploy/plan-guard.test.sh` (маленькие планы-примеры: тревоги проходят, база/секреты/KMS/Redis/S3 — нет).

## Что изменится на сервере (PR `claude/tf-catchup-2026-10-27`)

Только добавления:

1. Права воркера для SEO-страниц (`modules/stack`): чтение, запись и удаление в бакете сайта **только** в папках `lawyers/`, `practice-areas/`, `attorneys/`, `legal-questions/` и файле `seo-gen-manifest.json`, чтение `seo-manifest.json`, список бакета (чтобы отсутствующий файл был «нет», а не «нельзя»), `cloudfront:CreateInvalidation` и `ListInvalidations` только на раздачу сайта. Приложение (`releases/`), `robots.txt`, sitemap не затрагиваются. Настройки среды: `SEO_WEB_BUCKET`, `SEO_WEB_DISTRIBUTION_ID`, `SEO_SITE_URL` (из `web_host`). Сама генерация по-прежнему выключена: включается в админке «Продвижение: SEO и сторы» (`docs/runbooks/SEO_STATIC_PAGES.md`).
2. Две тревоги (`modules/monitoring/deploy-alarms.tf`), письма на тот же адрес, что остальные:
   - `cron-job-failing`: регулярная фоновая задача падала минимум в двух из последних трёх часов;
   - `migrate-failed`: задача миграций остановилась с ошибкой или не стартовала (письмо на русском; новая версия при этом не запускается).
3. Пул соединений воркера с базой: `worker_db_pool_size` (по умолчанию 6, было 3). Воркер крутит до пяти задач одновременно. Считается в проверке бюджета соединений базы; при включённом pooler не действует.
4. Починка двух ошибок слияния, из-за которых `terraform validate` на main не проходил: дубль `output "media_distribution_id"` в `modules/s3` и лишний аргумент `vpc_id` у `module "ecs"`.

Остальное в плане (около 94 файлов отставания) — то, что уже лежит в main и просто не применено.

## Что ещё в плане, кроме «трёх вещей» (репетиция 2026-10-27)

План на репетиции (`docs/dev/PROD_REHEARSAL_2026-10-27.md`, раздел 3) был шире, чем три пункта выше. Это всё код, который уже лежит в `main`, но на сервер ещё не попал. Что это и почему не страшно:

- **77 новых тревог CloudWatch** (+ ~20 изменяемых, 10 сводных) и **45 счётчиков из журналов** — только мониторинг: письма на тот же адрес, что остальные. Данных не трогают, денег почти не стоят (тревога $0.10 в месяц, счётчики бесплатны).
- **Правила ключей KMS (2 шт., только `policy`)** — кто может пользоваться ключом шифрования базы/секретов. Сам ключ не меняется и не пересоздаётся, данные не перешифровываются. Прочтите в плане, что строки только добавляются (новые роли ECS/Lambda).
- **CloudFront**: кэш-поведение сайта (`ordered_cache_behavior`), заголовки безопасности для app и site, две функции (`app_noindex`, `seo_index`), версия HTTP у раздачи медиа. Применяется без остановки сайта, но раздача обновляется 5-15 минут.
- **Права ролей ECS (2: `task` и `execution_secrets`)** — воркер получает доступ к бакету SEO-страниц и к новым секретам. Только расширение.
- **Старая тревога `lawbid-prod-db-cpu` удаляется** — её дубль с правильным порогом (85 %) живёт в `modules/monitoring`. Удаление тревоги безвредно, скрипт теперь показывает такие удаления жёлтым и не считает их СТОПом.

Что было исправлено, чтобы план стал зелёным (PR `claude/tf-plan-green-2026-10-27`): класс двух групп логов базы закреплён `STANDARD` (как на сервере; иначе план их пересоздавал и терял 30 дней логов базы), две функции GuardDuty не пересоздаются: `RUNTIME_MONITORING` описана ровно как в AWS (все три подпункта агентов), а у `RDS_LOGIN_EVENTS` подпункт `RDS_DATA_RISK` (его включил сам AWS; провайдер Terraform 5.100 такого имени ещё не знает) оставлен как есть через `ignore_changes`.

### Про пользователя миграций (не чинить!)

Миграции базы на проде идут под пользователем **`lawbid_admin`** (он в секрете `MIGRATOR_DATABASE_URL` и владеет всеми таблицами), а не `lawbid_migrator`, как написано в старых документах. Это нормально и менять **не нужно**: если «исправить» секрет на `lawbid_migrator`, первая же миграция упадёт с «must be owner of table» (проверено на копии прода 2026-10-27). Следствие: миграция `20261101310000_migrator_role_timeouts` на проде ничего не делает (её таймауты прилипают к роли, которой никто не пользуется) — это безвредно, код править не нужно.

## Откат

Откат здесь не `terraform apply` прежнего состояния: старый apply сам по себе ничего не вернёт, а в плане с «возвратом» легко оказываются удаления.

Все изменения PR добавляющие: права, две тревоги, одна переменная. Они ничего не ломают, если оставить. Убрать их — отдельный план: Claude правит код (убирает ресурсы), вы снова делаете `plan`, читаете сводку и `apply`. Если выкладка кода пошла плохо — это не Terraform, а «Rollback production» в GitHub Actions (`docs/runbooks/DEPLOY_SAFETY.md`).

## Если что-то пошло не так

- «Вы не вошли в AWS» или «Вход в AWS истёк» (в том числе `ExpiredToken` посреди плана) — `aws login --remote` (откроется ссылка, войдите в аккаунт), потом команду заново.
- «Terraform init не прошёл» — скрипт теперь печатает саму ошибку. Если в ней слово `symlink`, удалите папку `~/.lawbid-tf-catchup/plugin-cache` и запустите снова.
- «У вас старая версия кода» — `cd /Users/sima/Desktop/LawBid && git pull`.
- «За это время на сервере сменилась версия кода» — прошла выкладка; `plan` заново.
- Ошибка посреди `apply` — не запускайте ничего руками, Terraform записал, что успел; пришлите вывод Claude, он покажет безопасный следующий план.
