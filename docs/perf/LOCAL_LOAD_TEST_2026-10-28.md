# Локальный нагрузочный тест на ноутбуке (2026-10-28)

## Коротко для владельца

- **Что сделали.** На Linux-ноутбуке подняли копию сервера как в проде (база, пулер соединений, Redis, API, воркер) и залили **1 миллион пользователей** (100 тыс. юристов, 3 млн постов, 500 тыс. дел, 1,5 млн ставок, 500 тыс. чатов, 10 млн сообщений, 10 млн уведомлений). Потом пускали «людей»: 100, 1 000 и 5 000 одновременно.
- **Что ломается первым — лента дел для юриста.** Один запрос «какие дела мне видны» просматривает все открытые дела (250 тыс.) каждый раз. Он один съедает всю базу уже при **100 людях онлайн**: ответы медленные (1–4 с), при **~500 людях** всё приложение встаёт (ответы 15–30 с). Если дать базе в 4 раза больше процессора, это почти не помогает.
- **Второе — поиск юристов по имени**: 0,6–3,4 с в среднем, иногда 25–30 с и ошибка.
- **Если эти два места убрать** (тест без них), всё остальное держится хорошо: **1 000 человек — без ошибок, 95 % ответов быстрее 0,08 с**, чат доставляет сообщение за 0,1 с. Дальше упирается уже в процессор серверов API: один сервер (1 ядро) тянет примерно **125–175 человек онлайн**; на 16 серверах предел был около **2 800 человек**, база при этом справлялась.
- **Что чинить (по порядку):** 1) ленту дел для юриста (индекс + переписать запрос + кэш); 2) поиск по имени; 3) `/me/session` (8 одинаковых запросов о подписке на каждый старт приложения); 4) короче держать блокировку при отправке сообщения в чат. После этого — короткий прогон в AWS (≈ $7–10 за профиль m1).
- **10 млн пользователей** не заливали: оценка 2–4 часа и ~210 ГБ, правило было «больше 3 часов — не начинать». **1 млрд** на одной базе невозможен (≈ 21 ТБ) — нужен шардинг; расчёт ниже.
- **Ноутбук:** пик температуры 97 °C на долю секунды во время заливки (при тестах 72–91 °C), памяти оставалось ≥ 41 ГБ, диска 1,67 ТБ. Пауз по перегреву не было. Режим питания остался «power-saver» — сменить без пароля нельзя (см. «Не сделано»).

## Стенд

| Часть | Как | Как в проде |
|---|---|---|
| Postgres 16 | Docker, 2 CPU / 16 ГБ (как db.r7g.large), один прогон 8 CPU; `pg_stat_statements`, `log_min_duration_statement=500` | RDS |
| PgBouncer | образ из `infra/pgbouncer`, transaction pooling, пул 40 + 5 | свой PgBouncer |
| Redis 7 | 1 CPU, без TLS | ElastiCache (TLS) |
| API | образ `apps/api/Dockerfile`, 1 vCPU / 2 ГБ на задачу (как `api_cpu=1024`), `DB_POOL_SIZE=10`, 1 / 8 / 16 задач за nginx (вместо ALB) | ECS |
| Worker | тот же образ, `dist/src/worker.js`, 0.5 vCPU / 1 ГБ, джобы включены | ECS |
| Генератор | k6 2.0.0 в Docker на том же ноутбуке, 6–8 CPU | EC2 |

Отличия от прода: `NODE_ENV=development` (production требует TLS к Redis/БД и боевые Stripe/SMS-ключи; dev-режиму нужен `pino-pretty`, он добавлен слоем `Dockerfile.dev`), все платные интеграции выключены (SMS/e-mail mock, без Stripe/Bunny/S3/FCM). Процессор ноутбука (i9-14900HX, режим power-saver) — не Graviton; абсолютные цифры на AWS будут другими, соотношения — те же.

Модель нагрузки (`loadtest/k6/vus.js`): каждый виртуальный человек делает одно действие из стандартного набора `lib/mix.js` (старт приложения, лента, рилсы, профиль юриста, пост, поиск, чаты, отправка сообщения, уведомления, дела и ставки) и думает 1–3 с. 100 человек ≈ 50 запросов/с. Плюс открытые Socket.IO-сокеты, через которые меряется доставка сообщения. Админ-действия исключены: у одного админа одна сессия, а нагрузка от персонала ничтожна.

## Данные (профиль «1M»)

Генераторы репозитория `scripts/ops/admin-load-gen.sql` + `user-load-gen.sql`, умноженные на 10 (`loadtest/local-docker/scale_sql.py`), в 8 параллельных потоков (`par_seed.py`), плюс `loadtest/sql/loadtest-extra.sql` и `licenses.sql` (лицензия и 2 практики каждому юристу — без них лента дел была пустой).

Для засева триггер выключался; в проде важно не писать аудит пачками в одной транзакции.

## Результаты

Все прогоны — на базе 1M; рамп 1–2 мин, удержание 3–4 мин; правило остановки k6: p95 > 2 с или ошибок > 5 % в течение 60 с.

| b8full-pg8-1000 | 8 | **8** | 1 000 (+200) | стоп на 66 с | 129 | 12 / 3 157 / 7 872 | 0,04 % | Postgres 791 % (лента дел 2,8 с в среднем) |

\* без действий `cases`, `bids`, `search` (`SKIP_ACTIONS`) — чтобы увидеть, что ломается вторым.

Сокеты: подключение p95 33 мс (b8-1000), доставка сообщения через REST → БД → Redis → сокет p50 29 / p95 115 / p99 218 мс; 100 % доставленных. В больших прогонах `ws_connected` 55–60 %: часть сокетов прерывалась при остановке/конце теста до `realtime:ready`; причину до конца не разобрал — проверить на AWS-смоуке.

Калибровка одной задачи API (1 vCPU), 50 параллельных запросов без пауз: `/config/bootstrap` 1 702 req/s; `/me/session` **155 req/s** при 104 % CPU API и 11 % CPU базы — упор в процессор Node.

Ресурсы (пики): API 450–720 МБ на задачу; Postgres 5,4–6,8 ГБ; Redis до 75 МБ, до 26 900 оп/с (b16-5000: ~38 команд Redis на запрос, больше всего `HMGET` — 3,6 млн); PgBouncer до 48 % CPU; k6 до 3 CPU. Ноутбук: пакет CPU 72–91 °C во время k6 (выборка 10 с), пик 97 °C один раз при заливке; RAM свободно ≥ 41 ГБ.

|---|---|---|---|---|

В нынешнем виде m1/m10 упрутся в API и в ленту дел, деньги уйдут на подтверждение уже известного. Порядок: исправить №1–4 → локально повторить `b8full-1000` (должен пройти) → AWS `smoke` ($2) → `m1` с `api_cpu = 1024` и `api_max_tasks ≈ 24` ($7–10) → `m10` только после m1 в бюджете.

## Не сделано и почему

- **10M** — оценка > 3 ч (выше).
- **Режим питания `performance`** — `powerprofilesctl set` требует авторизации polkit (нет sudo по ssh). Владельцу: `powerprofilesctl set performance` в сессии на ноутбуке перед следующими прогонами, после — `balanced`. Все цифры сняты в power-saver.
- **NODE_ENV=production** — нужен TLS к Redis/Postgres и боевые ключи Stripe/SMS; использован development (см. «Стенд»).
- **Звонки, CDN-статика, админ-нагрузка** — не мерялись (нет TURN/LiveKit/CloudFront локально; у админа одна сессия).
- Причина `ws_connected` 55–60 % в больших прогонах не разобрана.

## Как повторить

Скрипты: `loadtest/local-docker/` (стек, засев, прогоны, сторож температуры), сценарий `loadtest/k6/vus.js`, `SKIP_ACTIONS` в `loadtest/k6/lib/mix.js`. На ноутбуке засеянный том `lawbid-lt-pgdata` сохранён (базы `lawbid_lt` = 1M и `lawbid_lt_empty` = пустая с миграциями), сырые результаты — `~/loadtest/results/<прогон>/` (summary.json, k6.log, pgss_top.txt, stats.log).

```sh
cd loadtest/local-docker && ./make-env.sh && docker compose up -d   # образы — см. шапку compose.yml
./seed.sh 10 lawbid_lt 8 && docker exec -i lawbid-lt-postgres-1 psql -U root -d lawbid_lt < licenses.sql
./prepare.sh ~/loadtest/results/fx-1m 6000 1500 0
./run.sh b8-1000 ~/loadtest/results/fx-1m VUS=1000 WS=200 HOLD=4m SKIP_ACTIONS=cases,bids,search
python3 summarize.py ~/loadtest/results/b8-1000
```
