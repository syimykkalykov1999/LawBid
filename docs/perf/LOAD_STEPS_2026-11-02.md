# Ступени «меньше людей, больше нажатий» на ноутбуке (2026-11-02)

Вопрос владельца: раз 10M проверено у нас, почему не проверить ещё жёстче: меньше «людей», но больше одновременных нажатий. Ответ: можно, и это бесплатно (ноутбук, AWS не трогается). Не прогонялось: ноутбук выключен, в облаке такого стенда нет (база 10M весит 205 ГБ).

## Что добавлено
Открытая модель нагрузки в `loadtest/k6/vus.js`: `RPS=<n>` включает `ramping-arrival-rate`, то есть фиксированное число запросов в секунду, пока сервер успевает; `VUS` тогда только потолок рабочих (`maxVUs`). Смесь действий та же, что в m1/m10 (`lib/mix.js`, среднее 1,31 запроса на действие). Аккаунты берутся случайно из файла токенов, поэтому лимит «100 запросов в минуту на человека» размазан по всем аккаунтам (5000 rps = 300 000 запросов/мин, нужно ≥ 3 000 аккаунтов, в `prepare.sh` их 12 000).
Если сервер не успевает, k6 пишет `dropped_iterations` (не молчит) и срабатывает стоп-кран: ошибки > 5 % или p95 > 2 с за 60 с.

## Ступени (`ladder.sh`)
| Ступень | Запросов/с | Сокетов держим | API | Время |
|---|---|---|---|---|
| q500 | 500 | 1000 | 8 | 1 мин разгон + 4 мин |
| q1k | 1000 | 2000 | 16 | 2 + 4 мин |
| q2k | 2000 | 4000 | 16 | 2 + 4 мин |
| q5k | 5000 | 8000 | 16 | 3 + 4 мин |

Дальше до потолка железа: `q10k`, `q20k`, `q50k` (16 API, 10 000 сокетов) и `qmax`: сам поднимается 500 → 1000 → 2000 → 5000 → 10 000 → 20 000 → 50 000 → 100 000 и останавливается на первой ступени, которую не удержали. После каждой ступени `saturation.py` пишет строку `ceiling = N rps, bottleneck: X`, где X один из: CPU ноутбука целиком, генератор k6, CPU БД, CPU Redis, все API заняты, или «не CPU» (блокировки, пул соединений, очередь; смотреть `pg.log`, `pg-slow.log`, `health.log`).
База выбирается параметром `DB=<имя базы>` (меньшая, 1M или 100k, может дать больше запросов в секунду, чем 10M). Команда: `DB=lawbid_lt loadtest/local-docker/ladder.sh <fixtures> qmax`.

**Честно:** выше потолка железа ноутбука цифры ничего не говорят о проде: если упёрся CPU ноутбука или генератор k6, то вина не кода, это предел самой машины (сервер и генератор делят одни 4 ядра). Ценность ноутбучных ступеней в другом: найти, ЧТО ломается первым (запрос, блокировка, пул), и починить. На AWS после этого идём дёшево: smoke → m1 → m10.

Команда (на ноутбуке, стенд поднят по `loadtest/local-docker/compose.yml`, база засеяна, аккаунты сделаны `prepare.sh <fixtures> 12000 3000 0`):
`loadtest/local-docker/ladder.sh <fixtures> q500 q1k q2k q5k`
Ступени идут по очереди и останавливаются на первой упавшей. Она и есть потолок ноутбука.

## Критерии и что смотреть
Зелёная ступень: ошибок < 1 %, p95 < 800 мс, `dropped_iterations` = 0 (иначе сервер не вытянул заданный темп), сокеты подключились ≥ 95 %, чат доходит ≥ 98 % за ≤ 2 с. По каждой ступени записать p95/p99, % ошибок и где упёрлось: `stats.log` (CPU контейнеров: API, Postgres, Redis, k6), `pg.log` (активные/всего соединений), `redis.log`, `pgss_top.txt` (самые тяжёлые запросы), `seqscans.txt`.
Как читать: CPU k6 ≥ 90 % = упёрся генератор (цифры занижены, не код); CPU Postgres у потолка при малой загрузке API = база/запрос; все API на 100 % = нужны ещё задачи (не код); соединения БД у `max` = пул/PgBouncer; рост p99 при ровном CPU = блокировка или очередь (искать в `pg-slow.log`).
Ограничение: 4 ядра на всё сразу у ноутбука; потолок ноутбука не равен потолку AWS, он только указывает КУДА чинить.
