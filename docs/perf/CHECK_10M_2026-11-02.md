# Проверка базы 10M одной командой

2026-11-02. После засева 10M (users 10M, posts 30M, messages 100M, notifications 100M, 205 ГБ) нужна повторяемая проверка горячих чтений, которая не зависит от памяти человека.

```
cd loadtest/local-docker
./check-10m.sh                       # счётчики + EXPLAIN горячих запросов
RUN_R1K=1 ./check-10m.sh <fx dir>    # то же + ступень r1k и счётчики Seq Scan после неё
```

Результат: `~/loadtest/results/check-10m-<дата>/` (`explain.txt`, `explain.json`, при r1k — `r1k.txt`, `seqscans.txt`). Код выхода: 0 — зелёное, 1 — есть находки, 2 — стенда 10M нет.

## Что считается находкой
| Проверка | Порог |
|---|---|
| Строк в таблице | меньше 95 % профиля (users 10M, posts 30M, messages 100M, notifications 100M) |
| Seq Scan на `users`, `posts`, `messages`, `notifications` (и их партициях) | любой, даже быстрый: на 10M он станет минутами |
| Новая страница чата / уведомлений / ленты, посты автора | 50 / 50 / 100 / 50 мс |
| Поиск людей по слову (общее / редкое) | 300 / 100 мс |
| Чтение с диска на один запрос | больше 5 000 блоков (≈40 МБ) |
| После r1k: `seq_tup_read` по большим таблицам | больше 10 млн строк |

Запросы повторяют форму эндпоинтов (курсор, `LIMIT`); идентификаторы берутся из самих данных (`TABLESAMPLE`). Это проверка плана и времени на данных 10M, а не замена k6: полный путь запроса через API даёт r1k.

## Если стенда нет
Скрипт сам делает `docker start` для остановленных контейнеров. Если контейнера нет (тома удалены) — код 2. **Пересев 10M ≈ 8,5 ч и 205 ГБ диска, только с отдельным «да» владельца**; команда в шапке скрипта. Не делать `docker compose down -v` на этом стенде, пока находки не записаны в `docs/perf`: том — это и есть база 10M.
