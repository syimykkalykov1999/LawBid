## 1. Отвал Postgres на 40 с (1 000 человек + 200 сокетов, 8 API)

Сценарий `r1k` (`VUS=1000 WS=200 RAMP=1m HOLD=5m`), правило остановки k6 выключено (`NO_K6_ABORT=1`), чтобы прогон пережил отвал. На 150-й секунде `docker stop -t 5 lawbid-lt-postgres-1`, через 40 с `docker start`. Два прогона (`1102-fail-pg`, `1102-fail-pg2`), картина одинаковая; цифры второго (в первом не записался ряд по 10 с).

**Хронология** (контейнер остановлен 21:26:33,6 → 35,9; запущен 21:27:16,1):

| Фаза | Запросов | Ошибок | p95 (медиана 10-с окон) | p95 худшего окна |
|---|---|---|---|---|
| До (90 с до остановки) | 48 294 | **0** | 150 мс | 256 мс |
| Во время (остановка → старт + 20 с) | 40 989 | **30 009 (73 %)** | 10 мс (быстрые 500) | 355 мс |
| После (старт + 20 с … + 90 с) | 42 422 | **0** | 146 мс | 177 мс |
| Хвост (старт + 90 с … конец) | 51 242 | **0** | 139 мс | 180 мс |

- **Сколько ошибок.** 30 009 запросов за ~53 с (14,6 % за весь прогон из 205 388). Все — **HTTP 500** от API: `PrismaClientKnownRequestError P1017 «Server has closed the connection»` и `08P01 … FATAL: server login has been failing, cached error` (PgBouncer кэширует неудачный логин к серверу на `server_login_retry = 2 с`). Первые секунды отвала запросы висели до `query_wait_timeout` PgBouncer = **10 с** (max 10 340 мс), дальше отказ мгновенный (p50 5 мс) — пользователь видит ошибку сразу, а не крутилку.
- **`/health/ready`** (проверяет Postgres и Redis): 503 через ≤ 2 с после остановки; первый 200 через nginx — через **14 с** после `docker start` (в первом прогоне 7 с); все 8 задач — по логам ни одного 5xx начиная с 24-й секунды после старта. `/health/live` всё время 200 (ECS не стал бы перезапускать задачи, ALB вывел бы их из балансировки по `ready`).
- **Сами ли восстановились.** API — да: через ~24 с после старта базы первое чистое 10-с окно, p95 после (146–177 мс) равен p95 до. Соединения через PgBouncer пересозданы без рестарта задач. Worker — да: во время отвала 12 × `ERROR cron job failed`, после старта базы планировщики (`cron schedulers`) идут дальше, ошибок нет. Сокеты — **не пострадали вовсе**: 0 обрывов (`ws_unexpected_close`), 100 % подключений, вход в комнату 100 %; обмен по сокету не зависит от базы.
- **Что не восстановилось само.** Ничего из инфраструктуры. Потеряны данные тех действий, что пришлись на отвал: `chat_delivered` 84 % — 16 % сообщений были отправлены через REST в момент отвала, получили 500 и не доставлены (клиент должен повторить отправку сам; k6 этого не делает). Это ожидаемо и единственное последствие.

## 2. Отвал Redis на 40 с (1 000 человек + 200 сокетов, 8 API)

Тот же сценарий, на 150-й секунде `docker stop -t 5 lawbid-lt-redis-1`, через 40 с `docker start` (`1102-fail-redis`). Redis на стенде без персистентности, то есть после старта он **пустой**: кэши, лимиты, состояние адаптера Socket.IO, очереди BullMQ — всё с нуля.

**Хронология** (остановлен 21:33:44,2 → 44,5; запущен 21:34:24,7):

| Фаза | Запросов | Ошибок | p95 (медиана 10-с окон) | p95 худшего окна |
|---|---|---|---|---|
| До | 48 373 | **0** | 143 мс | 264 мс |
| Во время (остановка → старт + 20 с) | 23 005 | **7 223 (31 %)** | 5 101 мс | 5 723 мс |
| После (старт + 20 с … + 90 с) | 41 878 | **0** | 196 мс | 275 мс |
| Хвост | 51 159 | **0** | 175 мс | 219 мс |

- **Сколько ошибок.** 7 223 запросов (3,9 % за прогон из 186 402). Все — **HTTP 500**. В отличие от базы, отказ не мгновенный: каждый запрос висел **≈ 4 с** (ioredis `commandTimeout 2000` × `maxRetriesPerRequest 1` = две попытки по 2 с, `apps/api/src/redis/redis-connection.ts`), поэтому за 40 с через систему прошло втрое меньше запросов (150–185 за 10 с вместо 600) и p50 держался на 4 003 мс. Пользователь 4 секунды смотрит на крутилку и получает ошибку.
- **`/health/ready`**: 503 в течение всего отвала, **200 через 2 с** после `docker start` (все 8 задач). Первое чистое 10-с окно — через 6 с после старта. p95 первые 10 с после — 796 мс (холодные кэши), через 20 с — 257 мс, дальше 175–275 мс против 143 до (кэши прогреваются ещё пару минут).
- **Сами ли восстановились.** API — да, без рестарта задач; Redis-клиентов 111 до отвала и 111 после (все 8 задач + worker переподключились). Worker — да: во время отвала 48 × `cron worker error` и 40 × `push worker error` (BullMQ без Redis), после старта — **0 ошибок**, очереди (`queue depth`), планировщики и `trending tags rebuilt` идут штатно. Сокеты — **ни одного обрыва** (`ws_unexpected_close` 0, 399 сессий, вход в комнату 100 %): Socket.IO держит соединение с клиентом сам, Redis-адаптер переподключился; задержка доставки чата в первом окне после старта — p95 5,8 с, потом 2,4 с, через 20 с — норма (0,4 с).
- **Что не восстановилось само / потеряно.** (1) Сообщения, отправленные через REST во время отвала (`chat_delivered` 89,7 %, 285 не доставлены) — клиент должен повторить. (2) Всё содержимое Redis: на проде ElastiCache с репликой, так что это именно сценарий «потеря кэша», и приложение его переживает. (3) **Непонятное:** через 1 мин 45 с после старта Redis, когда k6 по расписанию (`WS_HOLD_SECONDS=300`) закрыл и заново открыл сокеты, **83 из ~200 новых подключений не удались** (`ws_fail` в окнах 03:36:10–03:36:30 UTC) — без единой записи WARN/ERROR ни в API, ни в nginx; в тесте с отвалом Postgres та же волна переподключений прошла 100 %. Клиентская сторона k6 считает подключение неудавшимся при `44/realtime` (отказ), `auth:error`, ошибке сокета или закрытии до `realtime:ready`. Гипотеза — тихий отказ при пустом Redis (проверка отзыва сессии / состояние присутствия); нужно повторить с логированием причины на стороне k6 (тег на `ws_connected`) и `LOG_LEVEL=debug` у одной задачи. В soak (переподключение каждые 10 мин без отвалов) видно, повторяется ли это без Redis-рестарта — см. раздел 3.

## 4. Засев 10M пользователей

Генераторы `scripts/ops/*load-gen.sql` расширять не пришлось: `scale_sql.py` умножает все «населённые» константы на S (S=100 → 10M пользователей, 1M юристов, 30M постов, 5M дел, 15M ставок, 5M чатов, 100M сообщений, 100M уведомлений, 60M просмотров). Проверка перед стартом: самый большой литерал 100 000 000 (int4 до 2,1 млрд), `g*10` до 300M, интервалы `now() - g seconds` до ~3 лет — всё в пределах типов; свободно 1,6 ТБ при ожидаемых ≈ 220 ГБ (1M заняла 22 ГБ). База `lawbid_lt_10m` создана и мигрирована во время soak (это ~1 мин лёгкой нагрузки, отмечено), сам засев стартовал в 23:43 после окончания soak, чтобы не мешать замерам: Postgres на время засева получил 16 CPU, 16 параллельных сессий `par_seed.py`, `synchronous_commit=off`.

**Что сломалось на масштабе 10M и как расширен засев.** Через 70 мин первая половина (`admin-load-gen.sql`: 10M пользователей, 30M постов, 5M дел, 15M ставок, 20M записей аудита) была готова (база 71 ГБ), а `user-load-gen.sql` встал на обновлении 3M постов видео-ассетами: планировщик выбрал **hash join по всем 31M постов** (seq scan 19 ГБ + хэш на диск при `work_mem` 16 МБ), 47 минут и 0 обновлённых строк (`IO/DataFileRead`). На 1M тот же запрос проходил за секунды. Запрос снят, `par_seed.py` расширен: (1) резидуальное разбиение ×16 теперь применяется и к `WITH … UPDATE`/`UPDATE` с большим `generate_series`, а не только к `INSERT`; (2) переменная `SEED_PGOPTIONS` добавляет параметры сервера на время засева (`-c enable_hashjoin=off -c work_mem=256MB`), чтобы обновления шли индексными пробами по первичному ключу. Засев продолжен с того же места (`user-load-gen.sql` со строки 17), без повторной заливки первой половины.

## Находки и что лечить (каждая — отдельным PR по правилу владельца)

### 1. Отвал Redis: зависание 4 с и 500 вместо быстрого отказа — PR #615

Класс: ioredis держит команды в офлайн-очереди до `commandTimeout` (2 с × 2 команды на запрос), и несколько мест пути запроса читают Redis без запасного варианта (`JwtAuthGuard` → проверка отзыва сессии, кэш `app_config`). Правка (PR #615, прошла `/code-review high`, `/security-review`, `/simplify`): штатные опции ioredis `enableOfflineQueue: false` + `socketTimeout` на основном клиенте (команда отклоняется мгновенно, пока соединение потеряно; замолчавший узел сбрасывается через 1 с), `503 SERVER_BUSY` + `Retry-After: 5` вместо 500 для инфраструктурных ошибок Redis, проверка отзыва сессии по таблице `sessions` при недоступном Redis (одна строка, memo 5 с), кэши `app_config` и feature-флагов через существующий `failSoftRedis`. Как у Facebook memcache / Netflix Hystrix: отказ кэша стоит латентность промаха, а не таймаута. Проверка на стенде (изолированная пара API + Redis, 50 человек, Redis выключен на 30 с, одна и та же база): в окне отвала было 100 % × 500 с p50 4,0 с, стало 503 мгновенно (p50 13–29 мс), аутентифицированные запросы проходят через таблицу сессий, `/health/ready` через 2 с. Таблица — в описании PR #615. Побочная находка для стенда: `mint.mjs` выпускает токены без строк в `sessions`, и новый fallback такие токены честно отвергает — добавлен `loadtest/local-docker/fixture-sessions.sh` (строки сессий для всех токенов фикстур), запускать после `prepare.sh`.

### 2. Отправка сообщения держит блокировку строки чата через 5 сетевых обращений — застои и P2028

Что видно: оба застоя soak и 500-е внутри них — `PrismaClientKnownRequestError P2028 «Unable to start a transaction in the given time»` (пул задачи из 10 соединений занят); в `pg_stat_activity` до 24 сессий `idle in transaction` с `UPDATE conversations / conversation_participants`, `INSERT messages`; `log_lock_waits` показал ожидания `ShareLock on transaction` по `SELECT … FROM conversations WHERE id = $1 FOR UPDATE` (`chat.service.ts:1276`) по 1 с; 22:06 — 14 `query_wait_timeout` в PgBouncer (пул 40 забит теми же транзакциями), `/health/ready` → 503 «database unreachable». Транзакция отправки (`chat.service.ts` 1269–1349) после PR #507 уже не делает подготовку под блокировкой, но внутри остаётся **5 round-trip'ов** (`FOR UPDATE` → `message.create` → `conversation.update` → `participant.updateMany` → `participant.update`); когда событийный цикл Node перегружен, каждый round-trip растягивается, блокировка держится ~1 с, а на горячих чатах выстраивается очередь, которая съедает пул соединений **всех** эндпоинтов задачи.

Как у больших: в WhatsApp/Telegram запись сообщения — одна атомарная операция хранилища, а счётчики непрочитанного и «последнее сообщение» обновляются асинхронно (fan-out), блокировок между отправителями нет. Правка (отдельный PR): одна SQL-команда с data-modifying CTE (проверка статуса + вставка + обновление `conversations` и участников в одном round-trip) или функция Postgres; обновление бейджей/участников вынести из транзакции в уже существующий `badges.messageArrived`. Побочно: `maxWait` интерактивных транзакций Prisma (по умолчанию 2 с) — при переполнении пула отвечать 503 с `Retry-After`, а не 500.

### 3. Воркер 0,5 vCPU даёт ~26 push-заданий/с — очередь push отстаёт

`bull:push:metrics:completed`: 1 500–1 700 заданий в минуту при воркере, упёртом в квоту 0,5 CPU все два часа (`docker stats` 51 % из 50 %); при 1 500 онлайн поток push больше, `prioritized` вырос до 40 689, самое старое задание ждало 22 мин (1 340 с) к концу soak. Отправителя push на стенде нет (`LoggingPushSender`, «no sender configured»), то есть ≈ 19 мс CPU уходит на одно задание **без** сети: `push-dispatcher.ts` делает до 8 чтений из базы на задание (пользователь, звонок, группа, участник, уведомление…; `User.findUnique took 300 ms` под нагрузкой). На проде спасает автоскейл воркеров по глубине очереди (`infra/modules/stack`, 50 ожидающих заданий на задачу), но платить за 8 чтений на пуш не нужно: кандидат на PR — читать настройки получателя одним запросом с коротким кэшем, батчить задания одного получателя, как у FCM-пайплайнов больших приложений (collapse keys уже есть).

### 4. Сокеты после рестарта Redis: 83 из 200 переподключений без следа в логах

См. §2. Нужен повтор с логированием причины на стороне k6 и `LOG_LEVEL=debug` у одной задачи — отдельный шаг.

### 5. Повтор REST-сообщений клиентом при потере

16 % и 10 % сообщений, отправленных во время отвалов, пропали для получателя: сервер ответил 500 (теперь — 503 с `Retry-After`, п. 1), k6 не повторяет. В приложении повтор по `Retry-After` уже есть для 503 (политика повторов читает заголовок) — после п. 1 это закрывает класс для 503; для 5xx без заголовка и обрыва сети — проверить в мобильном клиенте идемпотентный повтор `clientMessageId` (ключ уже передаётся). Отдельный шаг.

## Что не проверено

- Отвалы прогнаны по одному разу каждый (Postgres — дважды, картина совпала); отвал PgBouncer и nginx отдельно не делался.
- Причина 83 неудачных переподключений сокетов после рестарта Redis (нет серверных логов) — нужен повтор с логированием на стороне k6.
- Soak шёл выше комфортной ёмкости ноутбука (PSI CPU 40–47 %), поэтому латентность второго часа и часть застоев усилены самим стендом; класс проблемы (блокировка чата через round-trip'ы) от этого не зависит, но порог на проде другой.
- Два часа — мало для медленных утечек (десятки МБ/сутки): API +30 МБ за второй час, worker +10 МБ — в пределах шума, но стоит повторить на 12–24 ч на облачном стенде.
- Push-отправители (FCM/APNs) на стенде выключены: стоимость задания измерена без сети.
- 10M: SEED_NOT_CHECKED
