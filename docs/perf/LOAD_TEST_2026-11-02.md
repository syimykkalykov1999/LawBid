В `r1k` при базе 8 CPU медленные места по эндпоинтам: `chat_send` p95 1,46 с, `feed` 1,32 с, `chat_list` 620 мс, `session` 582 мс, `search_people` 564 мс (поиск людей упал с 2,4 с до 0,36 с на запрос — ему просто хватило процессора). База: лента постов 16 143 + 16 001 вызовов по 1–3,5 мс (73 с), поиск людей 40 вызовов по 359 мс (14 с). Все 8 задач API упёрлись в квоту 2 CPU — то есть 1 000 человек на этой смеси ≈ **16 CPU задач API**, вдвое больше оценки 28.10 (8 задач по 1 vCPU, но там без ленты дел и поиска).

В `r3k` (база 8 CPU) k6 остановил прогон на ≈1 800 человеках + 600 сокетах: ни одна часть не упёрлась по отдельности (API 132–173 % из 200 на задачу, база 312 % из 800, PgBouncer 79 %), но в сумме контейнеры заняли ≈ 33 ядра из 32 vCPU виртуальной машины (16 API ≈ 24, база 3, k6 5, Redis/PgBouncer/nginx ≈ 1,3). Это **потолок ноутбука**, а не сервера: дальше рост латентности идёт от нехватки процессора у всего стенда, включая генератор. Сокетов подключилось 40 % (см. находку 4). По базе на 3k тот же состав: лента постов 4 042 + 1 735 + 1 743 вызовов по ~7 мс (52 с), поиск людей 29 вызовов по 367 мс (10,6 с), запись сообщений 3 028 по 2,9 мс.

В `s10k` (2 000 человек + 10 000 сокетов, база 8 CPU, k6 8 CPU) картина та же, что на `r3k`: 2 000 действующих людей на 16 задачах — это снова потолок процессора всего стенда (API ×16 ≈ 25 ядер + база 3,2 + k6 6,8), p95 перевалил 2 с на 245-й секунде. А вот **10 000 сокетов проверить не удалось**: подключилось 482 (4,8 %), остальные отклонил сам API — лимит `realtime.max_connects_per_ip_per_minute` = 120 (по умолчанию), потому что все сокеты k6 приходят с одного адреса `172.18.0.1` (в логах задач API — тысячи `WARN ws connect limit`, метрика `ws_ip_limited`). Те 482, что подключились: вход в комнату 100 %, доставка 100 %, подключение p95 293 мс. Повторять `s10k` нужно с `realtime.max_connects_per_ip_per_minute = 0` в `app_config` на время прогона (как ступень `auth` делает с лимитами СМС) — в `ladder.sh` это ещё не добавлено.

## Находки

### 1. Поиск людей по имени читает всю таблицу users (код)

`apps/api/src/modules/search/postgres-search.provider.ts`, запрос `WITH cand AS (…)`, ветки по `users`:

```
->  Limit (actual rows=0)
      ->  Seq Scan on users (actual rows=0)
            Filter: (full_name_lower IS NOT NULL AND role = 'attorney'
                     AND (full_name_lower % 'carter' OR full_name_lower ~~ '%carter%'))
            Rows Removed by Filter: 1000001      Buffers: shared hit=24363
->  Limit (actual rows=0)
      ->  Seq Scan on users users_1 (actual rows=0)
            Filter: (… name_skel ~~ '%karter%' OR 'karter' <% name_skel OR name_cons ~~ '%krtr%' OR 'karter' % name_skel)
            Rows Removed by Filter: 1000001
Execution Time: 399 ms   (пустая база; под нагрузкой при 2 CPU — 2,4 с, максимум 5,7 с)
```

Почему: планировщик оценивает `full_name_lower % 'carter'` в ~20 000 строк (на деле 0), и с `LIMIT 1000` считает, что Seq Scan найдёт тысячу строк быстро — а читает все 24 363 страницы. Триграммные GIN-индексы (`users_full_name_trgm_idx`, `users_name_skel_col_trgm_idx` и др.) на месте и валидны, но даже с `enable_seqscan=off` индекс по `%` отдаёт **100 049 кандидатов** на перепроверку (порог похожести 0,3 на коротких именах), то есть индексный план тоже тяжёлый. Запросы k6 — обычные слова (`law`, `tax`, `visa`…), совпадений нет; у живых людей с опечатками будет так же.

Что делать (отдельный PR, в этом только замер): поиск по людям — сначала дешёвые ветки (`LIKE 'префикс%'` по btree `attorney_profiles.username_lower`, точное имя), триграммную ветку `%` включать только если дешёвые дали мало, и только по подмножеству юристов (частичный индекс `… WHERE role = 'attorney'`, их 100 тыс. вместо 1 млн), с порогом `set_limit`/`word_similarity` ≥ 0,5; либо убрать `LIMIT` из триграммных веток (он и провоцирует Seq Scan) и ограничивать уже после `UNION`. На 10M пользователей нынешний запрос — 10× дольше.

### 2. База 2 CPU — первая стена на 1 000 человек при 1M данных

С лентой дел и поиском (которых 28.10 не было в `b8-1000`) база db.r7g.large-размера держит **≈ 450–500 человек** этой смеси; при 8 CPU — 1 000 человек с запасом (310 % из 800). Основные едоки: лента постов (две формы запроса `posts`, ≈ 1,0–3,5 мс каждая, 32 тыс. вызовов за 5 мин), непрочитанные в чатах (`coalesce(sum(count(*) …))` по `messages`, 1 мс × 8,8 тыс.), поиск людей (п. 1). Для запуска это значит: либо RDS крупнее r7g.large на день запуска, либо реплика для чтения ленты, либо кэш ленты (28.10, п. 1 там же).

### 3. Задача API 1 vCPU в VM Docker Desktop (стенд, не код)

Подробно в «Стенд». Для расчётов «сколько задач API на 1 000 человек» использовать число из диагностического `r1k`: 8 задач по квоте 2 CPU — все в потолке; реальное потребление 1,1–1,3 CPU на задачу на простых путях и ~2 CPU на смеси. Проверить на Fargate можно только облачным `smoke`/`m1`.

### 4. Сокеты: лимит 120 подключений в минуту с одного адреса

`ws_connected` 60 % на `r1k` (200 сокетов за минуту), 40 % на `r3k` (1 000 за 3 мин), 4,8 % на `s10k` (10 000 за 4 мин) — это ровно `realtime.max_connects_per_ip_per_minute` = **120** (`app-settings.defaults.ts`, проверка в `realtime.gateway.ts`, ключ Redis `ws:connect:<ip>`): 200 − 120 = 80 отказов → 60 %; 4 мин × 120 = 480 ≈ 482 подключившихся. Так объясняется и «55–60 %» 28.10, причину которых тогда не нашли. Те, кто подключился, получают всё (`room_join_ok`, `chat_delivered` — 100 %).

Для стенда: на время `s10k` ставить ключ в 0 (как `auth` делает с лимитами СМС) — добавить в `ladder.sh`. Для прода это вопрос владельцу: мобильные операторы и офисы делят один адрес (сам текст подсказки в Админке так и говорит: «keep it generous»); в день запуска сотни людей за одним NAT упрутся в 120/мин и не получат чат в реальном времени (HTTP при этом работает). Значение задаётся в Админка → Настройки, `realtime.max_connects_per_ip_per_minute`; без команды владельца не трогаю.

### 5. Мелочи стенда, которых не было в инструкции

- База `lawbid_lt` не создаётся сама: нужно `CREATE DATABASE`, `npx prisma migrate deploy` + `node prisma/run-concurrent.mjs` из образа API, пароль роли `lawbid_app` (`lawbid_app_lt`), `CREATE EXTENSION pg_stat_statements` (без него `run.sh` не пишет `pgss_top.txt`).
- API при старте пытается создать `lawbid_lt_demo` и падает с `P1003` (роль не может `CREATE DATABASE`) — не фатально, но шумит; создана руками `OWNER lawbid_app`.
- Docker Desktop: VM по умолчанию 7,7 ГБ памяти — ставить ≥ 44 ГБ; после перезапуска Desktop поднимаются только `api`/`worker` (у остальных нет `restart`), нужен `docker compose up -d` заново.
- `watch.sh` читает `~/laptop-guard.log`, его пишет `~/laptop-guard.sh` — он не был запущен, запущен как `systemd-run --user --unit=laptop-guard`. Температура за ночь: 65–82 °C под нагрузкой, один всплеск 95 °C на первой `r100` сразу после пересоздания контейнеров; пауз и остановок сторожем не было.

## Стенд и почему он отличается от 28.10

Ноутбук тот же (i9-14900HX: 8 P-ядер + 16 E-ядер, 62 ГБ), режим питания `performance`. Но Docker сменился: 28.10 стенд работал на нативном Docker Engine, сейчас на ноутбуке стоит **Docker Desktop for Linux** — все контейнеры живут внутри виртуальной машины QEMU/KVM. Тома и образы 28.10 не сохранились (VM пустая), поэтому стенд собран заново: образы (`lawbid-lt-api:local` ≈ 3 мин), миграции (171 + 1 concurrent), засев 1M (`seed.sh 10`, 1 307 с, база 22 ГБ), `licenses.sql`, `prepare.sh … 12000 3000 0`. VM по умолчанию получила 7,7 ГБ памяти — поднято до 44 ГБ (`~/.docker/desktop/settings-store.json`, `MemoryMiB`).

Первая лестница (`API_CPUS=1`, как в compose по умолчанию) остановилась на `r1k` через 60 с ramp'а: ошибок 0 %, но p95 5,8 с при 149 req/s, все 8 задач API — 100 % CPU, Postgres 187 % из 200 %. Это в 3–4 раза хуже 28.10 (513 req/s, p95 77 мс на тех же 8 задачах). Разбор занял основную часть вечера, итог:

| Проверка | Результат | Вывод |
|---|---|---|
| Чистый CPU в VM против хоста (16 процессов node) | VM медленнее на 28 % | накладные расходы KVM умеренные |
| Сеть внутри VM: `redis-benchmark` по bridge | 210 тыс. оп/с, p50 0,12 мс | сеть не узкое место |
| Steal time в госте под нагрузкой | 0,08 ядра из 1,4 занятых | хост не отнимает CPU |
| Изменения API с 28.10 | 10 коммитов, путь `/config/bootstrap` и middleware не тронуты | регрессии кода на этом пути нет |
| Калибровка 1 задачи, `/config/bootstrap`, квота **1 CPU** | **511–647 req/s** при 100 % CPU (28.10: 1 702) | ↓ в 2,7 раза |
| То же, квота **2 CPU** | **1 532–1 960 req/s** при 114–118 % CPU | паритет с 28.10 |
| То же, без квоты | 1 799 req/s при 138 % | квота — причина |
| `/me/session`, квота 1 / 2 / без квоты | 34–59 / 49–54 / 95 req/s (28.10: 155) | движок Prisma без квоты заводит 32 потока tokio (по числу vCPU) и крутит их вхолостую — 8–10 ядер на 95 req/s |
| Привязка потоков qemu к P-ядрам (`taskset`) | bootstrap при квоте 2: 1 960; разброс между прогонами остаётся | гибридный процессор добавляет шум, но не объясняет ×3 |
| Отношение session/bootstrap | 1 : 11 (28.10 — 1 : 11) | профиль CPU `/me/session`: 39 % — сериализация запросов `@prisma/client`, 8 % GC, ~10 SQL на вызов, база тратит 1,2 мс на вызов; это не новая проблема |

Итог: **в VM Docker Desktop cgroup-квота в 1 CPU режет многопоточный процесс API (главный поток Node + GC + движок Prisma + libuv + поток pino-pretty) примерно втрое** по сравнению с тем же лимитом на нативном Docker 28.10. Поэтому ступени ниже шли с **`API_CPUS=2`** (квота 2 CPU на задачу, реальное потребление 1,1–1,3 CPU) — по пропускной способности bootstrap такая задача равна «задаче 1 vCPU» 28.10 и близка к задаче ECS `api_cpu=1024`. Сырые калибровки: `~/loadtest/results/calib-1102/`, сценарий `one.js` там же.

Что это значит для прода: на Fargate квота тоже cgroup (1 vCPU = 1024 CPU units), и движок Prisma видит ровно столько потоков, сколько даёт квота. Насколько там повторяется эффект VM — покажет только облачный `smoke` (`docs/runbooks/LOAD_TEST.md`); локально он не измерим.

## Что не проверено

- `r1kw` (публикация постов) и `auth` (вход по СМС-коду, 100 входов/с) — не запускались.
- Звонки (`callFlow`) — как и раньше, не гонялись.
- `r3k` и `s10k` — только в диагностической конфигурации (база 8 CPU); обе остановлены правилом на ≈1 800–2 000 человеках, это предел ноутбука, а не сервера.
- 10 000 одновременных сокетов — сняли лимит на адрес не успели, подключилось 482; нужен повтор `s10k` с `realtime.max_connects_per_ip_per_minute = 0`.
- Насколько эффект квоты 1 CPU в VM повторяется на Fargate — только облачный прогон.
