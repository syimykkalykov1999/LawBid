# Замеры скорости приложения на телефоне (2026-10-23)

## Для владельца (простыми словами)

Что это. Набор автоматических проверок, который сам «ходит» по приложению на
настоящем телефоне — как человек, но быстро и одинаково каждый раз — и
записывает цифры: как быстро приложение открывается, плавно ли крутится
лента, как быстро открываются чат и профиль, сколько оно ест памяти, как
быстро начинает играть видео. Так же измеряют скорость большие платформы
(Instagram, TikTok).

Что нужно, чтобы запустить. Телефон по кабелю к Маку, запущенный локальный
сервер LawBid и одна команда:

```
apps/mobile/tool/perf/run_device_perf.sh <номер-телефона-из-flutter-devices>
```

Свой аккаунт не нужен: используется тестовый юрист из учебных данных
(или демо-код, если задать `PERF_DEMO_CODE=...`).

Что получится. В конце печатается таблица и вердикт PASS (всё в норме) или
FAIL (что-то медленнее нормы, строки с FAIL — что именно). Файлы лежат в
`apps/mobile/build/perf/<метка>/`: `perf_result.md` (читать глазами) и
`perf_result.json` (для сравнения «до/после»).

Нормы (как у Instagram-класса приложений):

- Первый кадр после запуска — быстрее 2 секунд.
- Прокрутка: 99 из 100 кадров укладываются в 16,7 мс (телефоны с 60 Гц);
  на iPhone с 120 Гц — 90 из 100 кадров в 8,3 мс.
  Рывков длиннее 33 мс — не больше 1 % кадров.
- Открытие экрана по нажатию: вкладка и меню — до 150 мс, чат, профиль,
  рилс — до 250 мс.
- Память за весь прогон растёт не больше чем на 20 %; пик не больше 1,2 ГБ.
- Видео начинает двигаться: обычно до 0,5 секунды, 9 из 10 — до 1 секунды.

Важно знать. Замерять нужно на самой быстрой «профильной» сборке
(команда делает её сама), эмулятор и режим отладки цифры искажают. Если
сервер медленный или нет интернета, будут хуже «первая лента» и видео — это
не вина приложения; сравнивать лучше два прогона подряд на том же телефоне.
Запуск ставит на телефон приложение `dev` (свою копию), как обычная
разработка.

## Технически

### Состав

| Файл | Что делает |
| --- | --- |
| `integration_test/perf/perf_suite_test.dart` | Сценарии (один `testWidgets`), профиль-режим. |
| `integration_test/perf/perf_rig.dart` | Касания в реальном времени, запись `FrameTiming`, `watchPerformance`, «касание до кадра», память. |
| `integration_test/perf/perf_report.dart` | Чистый Dart: статистика кадров, бюджеты, JSON и Markdown (юнит-тест `test/perf_report_test.dart`). |
| `test_driver/perf_suite_driver.dart` | Сторона Мака: пишет `perf_result.json/.md` в `PERF_OUT`. |
| `tool/perf/run_device_perf.sh` | iOS (физический/симулятор) и Android (adb): холодный старт, сборка profile, прогон, итог. |
| `lib/core/diagnostics/perf_marks.dart` | Метки в приложении (`lb.main`, `lb.run_app`, `lb.first_frame`, `lb.first_feed_frame`, `lb.video_first_motion`) через `Timeline.instantSync`. В release-сборке каждая функция сразу выходит (`kReleaseMode`). |

Старый `integration_test/scroll_perf_test.dart` остался как быстрая проверка
одной прокрутки; в обычный `flutter test` ничего из `integration_test/` не
попадает (запуск только через `flutter drive`).

### Сценарии

1. Холодный старт. (а) Настоящий процесс: `flutter run --profile
   --trace-startup` `COLD_RUNS` раз (по умолчанию 3), берётся медиана
   `timeToFirstFrameRasterizedMicros` (от входа движка до первого кадра на
   экране; сам запуск процесса ОС до движка, 0,1–0,3 с, сюда не входит) и
   `timeToFrameworkInitMicros`. (б) Внутри приложения метки от входа
   `runLawBid`: `lb.first_frame` и `lb.first_feed_frame` (первый
   нарисованный `PostCard` — «первый осмысленный кадр» ленты).
2. Прокрутка (каждая под `watchPerformance`, плюс собственная статистика по
   `FrameTiming`): `feed_scroll`, `reels_swipe_10` (10 свайпов по роликам),
   `search_grid_scroll` (сетка постов с автоплеем превью), `chats_list_scroll`,
   `chat_history_scroll` (первый чат, 12 экранов вверх и вниз), `cases_list_scroll`
   (вкладка «Моё»).
   Для каждого: build и raster avg/p90/p99, доли кадров > 8,3 / 16,7 / 33 мс
   (кадр = более медленный из двух потоков), пропуски бюджета экрана
   (`1000/Гц`).
3. Задержка нажатия до кадра нового экрана (`timeToFrame`, 3 повтора, берётся
   медиана): `open_chat` (тап по строке), `open_profile`, `open_reel_from_grid`
   (тап по видео-плитке поиска), `tab_switch_search/feed/mine` (тап по нижней
   панели), `theme_picker_open`. Конец измерения = конец кадра, в котором
   экран уже построен и нарисован; растеризация этого кадра (пара мс) в
   замер не входит.
4. Память: RSS (`ProcessInfo.currentRss`), куча Dart после `gc`
   (`vm_service.getAllocationProfile(gc: true)`), размер и число элементов
   `imageCache` — после каждого блока и после финальной паузы 5 с.
   Рост = последняя точка против первой (после прогрева ленты).
5. Видео: `PerfMarks.videoStarted` из `ReelVideo` — время от «проигрывай»
   (`active` стал true) до движущейся картинки (`_rendered`). Отдельно для
   ленты, рилс и сетки поиска (постер → движение).

### Бюджеты и допущения

Это цели класса Instagram/TikTok, не опубликованные цифры компаний:

- Холодный старт < 2 с — ориентир Google/Apple и общая практика крупных
  приложений (Android vitals считает «медленным» холодный старт > 5 с,
  хорошим принято < 2 с). Лента (< 3 с) зависит от сети; бюджет для
  локального API.
- Кадры: 60 Гц — 16,7 мс; 120 Гц (iPhone ProMotion, S25 Ultra) — 8,3 мс на
  кадр, но один пропущенный кадр допускается (p99 ≤ 16,7 мс). Android vitals
  называет медленным кадр > 16 мс и зависшим > 700 мс; наш порог рывка 33 мс
  строже: не больше 1 % кадров.
- Отклик: правило RAIL (Google) — ответ на касание в пределах 100 мс; экраны,
  которые строят длинный список, получили 250 мс.
- Память: рост ≤ 20 % за прогон (утечка), пик ≤ 1,2 ГБ (запас до
  убийства процесса на iPhone/Android).
- Видео: медиана ≤ 0,5 с (цель из `VIDEO_START_2026-10-23.md`), p90 ≤ 1 с.

Все числа в `PerfBudgets` (`perf_report.dart`); менять только там и здесь.
Частота экрана берётся у устройства: при > 75 Гц применяются бюджеты 120 Гц.

### Данные и сервер

Нужен запущенный API (`apps/api`). Пользователь — тестовый юрист из seed
(`+12125550101`, пароль из seed; `PERF_PHONE`, `PERF_PASSWORD` меняют) либо
демо-мир: `PERF_DEMO_CODE=<код блогера>` (`/demo/invites/redeem`, затем
вход как в `DemoCodeSheet`). Скрипт сам подбирает адрес API для телефона:
эмулятор Android `10.0.2.2`, физический Android — `adb reverse` на
`127.0.0.1`, iPhone — адрес Мака в локальной сети, симулятор `127.0.0.1`.
`API_BASE_URL` переопределяет. Конфиг собирается в `build/perf/<метка>/perf.json`
из `config/dev.json` (или `dev.example.json`), в git не попадает.

### Запуск

```
cd apps/mobile
tool/perf/run_device_perf.sh <device-id> [метка]    # iPhone 17 Pro Max / Samsung S25 Ultra
COLD_RUNS=5 PERF_DEMO_CODE=ABCD1234 tool/perf/run_device_perf.sh <id> demo
PERF_NO_FAIL=1 ...                                   # не падать на FAIL
```

Выход: `build/perf/<метка>/perf_result.{json,md}`, `drive.log`,
`cold_N.log`, `start_up_info_N.json`; для физического iPhone ещё копия
файлов с телефона (`Documents/lb_perf`, через `xcrun devicectl ... copy
from`) в `on_device/`. На Android release-подобная profile-сборка не
`debuggable`, `run-as` недоступен, поэтому основной путь доставки результата
— драйвер (`binding.reportData`); файл на телефоне пишется как резервный.
Код возврата: 0 — все бюджеты в норме, 1 — есть FAIL, 2/3 — нет устройства
или API.

### Ограничения

- Профиль-режим не работает на симуляторе iOS и даёт искажённые цифры на
  эмуляторе Android; на них проверяется только, что набор запускается.
- Нижняя панель нажимается по долям ширины (4 вкладки + «+» по центру); если
  дизайн панели изменится, поправить `PerfRig.tapNav`.
- `Posts` в поиске — третья вкладка у юриста и вторая у клиента.
- Реальный запуск на телефонах не делался автором (см. отчёт); эталонные
  цифры появятся после первого прогона координатора.
