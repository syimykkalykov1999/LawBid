## Полный проход «1M онлайн + 10M строк, все сценарии» и цена повтора
«Миллион пользователей в секунду» понимаю как **1 млн человек онлайн ≈ 480 тыс. запросов/с** на пике + 10M людей в базе.
| Статья | Оценка за один полный проход (3 ч стенда, 1 ч пика) |
|---|---|
| API Fargate: 7 500–16 000 vCPU (30–64 запроса/с на vCPU), Spot $0,0148/vCPU-ч | $330–710 |
| База: ≈ 3 200 vCPU при 150 запросов/с на vCPU → ≈ 50 × `db.r7g.16xlarge` (вывод $8,83/ч) — только если уже шардирована | $1 300 |
| Redis cluster, OpenSearch, ALB (≈ 8 600 LCU × $0,008), NAT | $250–400 |
| Генераторы k6: ≈ 1 000 × `c7g.xlarge` Spot | $175 |
| WAF (≈ 1,7 млрд запросов × $0,6/млн) + CloudFront | $1 000–1 200 |
| Засев 10M на каждом новом стенде (час на создание/заполнение) | +$50–100 |
| **Итого** | **≈ $3 000–4 000 за проход**, ±50 % |
Цена повторной попытки при красном — **почти столько же** (стенд пересоздаётся; ускорить можно снимком базы с 10M: хранение ≈ $25/мес, повтор без засева экономит ≈ $100 и час).
**Квоты (честно):** нужно ≈ 16 000 vCPU Fargate + 4 000 vCPU EC2 Spot + десятки RDS; сейчас 32/16/40, запросы поданы на 256/64. Новому аккаунту такие квоты не одобрят без истории расходов и обращения к менеджеру AWS; реалистично получить сотни, не тысячи. Значит, **прямой проход на 1M онлайн сейчас невыполним**, даже если деньги есть. Кроме того, текущий код пишет в **одну** базу-лидер: 3 200 vCPU одной базой не бывает — нужен шардинг, а он в коде только подготовлен.

## «Ячейка × N» вместо полного прохода
Идея, как у больших: проверить одну ячейку (ее API + база + Redis + поиск) на пределе и доказать, что ячейки независимы, а общие части (ALB, WAF, CDN, DNS, Redis-ключи) держат N ячеек.
| Шаг | Что | Цена |
|---|---|---|
| 1 | Одна ячейка = вариант Б (100 тыс. онлайн) с 10M строк в её базе | $200–300 (+$120 с WAF/CDN) |
| 2 | Две ячейки одновременно + общий слой (ALB, WAF, CDN, глобальные ключи Redis) под суммарной нагрузкой 200 тыс. | $500–700 |
| 3 | Расчёт: 10 ячеек = 1M онлайн; общий слой проверен до 200 тыс., дальше — по запасу и расчёту (не измерено, так и писать) | $0 |
| **Итого** | | **≈ $700–1 000** против $3 000–4 000, и квоты (≈ 1 700 vCPU на шаг 2) реальны |
Повтор при красном — шаг 1 заново, **≈ $250**. Честная оговорка: «10 ячеек» подтверждается только шардированием в коде; пока его нет, N=1, и потолок продукта — одна ячейка.

## Стоп по сумме (этот PR)
`loadtest/scripts/cost-guard.py` запускается в фоне в job `run` до создания стенда. Каждую минуту суммирует реальные $/час того, что работает у этого запуска (Fargate, RDS, Redis, генераторы, ALB, NAT — цены `loadtest/prices.json`, общие с калькулятором), плюс разовые статьи (CloudFront, WAF, трафик) по времени. На 80 % `confirm_cost` — предупреждение; на 100 % — `gh run cancel`, и шаги `always()` сносят стенд (тот же путь, что при любом падении); сторож раз в час — вторая сетка. Если AWS недоступен 3 раза подряд — считает по оценке профиля ×1,5. **Лимит — параметр кнопки (`confirm_cost`)**; это жёсткий потолок: кнопка пускает, если верхняя граница оценки (×1,5) ≤ лимита, а страж режет по факту на 100 % лимита (с запасом +10 % на неучтённые статьи). Если цены AWS выше расчёта более чем на ±30 %, нормальный прогон может быть остановлен — впишите лимит с запасом. Страж падает «закрыто»: если он умер или не смог отменить — отмена повторяется 10 раз, при старте проверяется, что процесс жив, а перед `terraform destroy` он останавливается, чтобы не прервать снос. Не проверено на реальном AWS (проверка — первый `smoke`); отмена через `gh run cancel` рассчитывает на то, что `always()` отработает при отмене (так задокументировано GitHub).

## Что переносим на ноутбук бесплатно уже сейчас
- 10M строк в БД: `EXPLAIN` поиска, ленты, чатов, r1k на БД 2 CPU, «человек на vCPU» на 10M (идёт у ноутбучной сессии).
- Kill-тесты БД/Redis под нагрузкой и soak 2–4 ч (идут).
- Сокеты 10k с отключённым лимитом адреса, шторм входа по СМС (`auth`), сигналы звонков (медиа и Cloudflare — нет).
- **OpenSearch в Docker** (флаг `search.engine`) на 10M людей: скорость и память против Postgres-поиска — не требует AWS.
- Реплика чтения Postgres в Docker: проверить, что код читает с реплики и откатывается на основную при отказе.
- Не переносится на ноут: Fargate-производительность, RDS Multi-AZ/EBS, CloudFront/WAF, ALB, межзонный трафик, 100k+ сокетов — только облако.

2. **Но стенд `m10` занижен.** Он собран по замеру 28.10 (до ленты и поиска): 40 задач API × 0,5 vCPU = 20 vCPU и база `db.r7g.2xlarge` (8 vCPU) на 5 000 запросов/с. Такой «стенд» стоил бы тысячи долларов за час и проверял бы заведомо известное. Большие компании так не тестируют: они проверяют одну «ячейку» (shard + её API) на пределе и умножают ячейки.
