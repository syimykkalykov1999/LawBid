## Админка (apps/admin): что уже было

- Кэш запросов 30 с, повторы 1/2/4 с с разбросом, 4xx не повторяются (`src/app/providers.tsx`, `src/lib/query-retry.ts`).
- Опрос раз в минуту, только пока вкладка видна, в 2 раза реже без фокуса, стоп через 15 мин простоя, откат при 429 (`src/lib/live.ts`). Тяжёлые сводки без таймеров (revalidate on focus).
- Списки на курсорах (`useInfiniteQuery`): 37 страниц и панелей. 63 из 253 GET-запросов несут limit/cursor, остальные — справочники и карточки.
- Записи в основном частичные: 40 PATCH против 53 PUT/POST (PUT — полные формы настроек).
- Анимации грузятся после первого кадра (`LazyMotion`), тяжёлые панели через `next/dynamic`.
- Прокси: стрим тела, лимит 25 МБ, понятные 502/504 (`src/app/api/proxy`).
- API: `/admin/counts` одним запросом с ETag, сводки в Redis (`AdminSummaryService`).

## Что нашёл и исправил (PR #562)

1. `/admin/system-health` (самая медленная ручка): общий Redis-кэш, старше 2 мин не показываем.
2. `/admin/counts`: общая сводка на 30 с вместо 4 запросов на каждый опрос каждого сотрудника.
3. Прокси терял ETag и If-None-Match: 304 не доходил до браузера. Исправлено.
4. Чтение ждало API 120 с × 3 повтора (до 8 мин «вечной загрузки»). Теперь 30 с (экспорты и проверка цепочки аудита — 120 с).
5. Sentry (130 КБ gzip) грузился сразу после гидратации и соревновался с данными страницы. Теперь грузится в простое (не позже чем через 4 с).
6. Каждый клик по ссылке шёл на сервер админки за пейлоадом (в Next 15 для динамических страниц кэш клиента по умолчанию 0 с). Включено `staleTimes: dynamic 30 с, static 180 с`: клики внутри 30 с открываются сразу, данные страницы всё равно обновляет TanStack Query.

## Админка: что НЕ сделано и почему

| Что | Почему / что нужно |
|---|---|
| CDN (CloudFront) перед админкой, brotli, кэш статики на краю | Сейчас статику отдаёт сама задача admin через ALB, gzip. Для медленного канала (1,3–2 Мбит/с) brotli даст около −15–20 % к JS; это изменение инфраструктуры (Terraform apply владельцем), в этом PR не делал. |
| Кэш профиля администратора в guard API | Каждый вызов `/admin/*` читает пользователя из БД (по замыслу «отключение админа действует сразу»). Кэш на 5 с сократит БД, но ослабит это правило: решение за владельцем, без профиля нагрузки не трогал. |
| launch, economy, partitions, spend/registry, infra, integrations | По 1–2 ответа 1,3–2,6 с за сутки; без профиля конкретной ручки оптимизировать вслепую нельзя. Нужна выгрузка из CloudWatch по этим путям за неделю. |
| 76 непроверенных `findMany` без `take` в admin-сервисах API | Выборочно проверил 10: справочники или `id in [...]`, ограничены. Остальные не проверял. |
| Lighthouse / реальные замеры на телефоне | Нет прод-доступа из облака. |

## Веб (Flutter web, apps/mobile): что нашёл

Уже сделано ранее (docs/perf/WEB_PASS_2026-10-23.md, WEB_PERF_2026-10-25.md): wasm-сборка, версионированные неизменяемые файлы `v/<sha>/`, CloudFront с brotli и HTTP/3, предзагрузка движка с докачкой при обрыве (`boot_head.js`), логотип встроен в HTML (первый кадр без запроса), иконочные шрифты обрезаны (16 и 40 КБ вместо 450–500), предсоединение к API.

Почему логотип висит 3–5 с и на медленной сети «не открывается»: это вес самого Flutter-приложения. На Chrome/Edge грузится wasm-приложение 3,7 МБ + движок 2,3 МБ, на Safari/Firefox JS-сборка + CanvasKit. На 1,3–2 Мбит/с это 25–40 с только на скачивание, и этого не сократить настройками кэша: первый заход всегда тяжёлый, повторные берутся из кэша браузера.

Что реально уменьшит первый заход (не сделано, решения нужны):
- Flutter 3.50+ с `--enable-wasm-deferred-loading` (S17-4): разбиение на части. Блокер: закреплён 3.47.5.
- Лёгкая публичная страница на обычном HTML для входа на сайт (посадочная, юристы по штатам) — она уже есть в SEO-блоке `index.html`, но интерактивная часть всё равно Flutter.
- Измерить реальный размер брotli-пакетов на проде (`curl -sI` с `accept-encoding: br`): я не мог.

Сайт `LawBidSite` (Next.js, отдельный репозиторий) в этом аудите НЕ смотрел.
