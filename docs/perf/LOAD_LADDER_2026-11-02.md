# Лестница нагрузки на мощном ноутбуке (2026-11-02)

Цель владельца: сломать и починить всё **до** живых пользователей, чтобы первые люди не получили плохой отзыв. Интернет владельца 1,3–2 Мбит/с, поэтому нагрузка идёт **не по сети на прод**, а целиком на ноутбуке: весь сервер (API, воркер, Postgres, Redis, PgBouncer) в Docker и генератор k6 там же. Прод в этом не участвует (k6 сам отказывается идти на боевые адреса).

Состояние: ступени `r100`, `r1k`, `r3k`, `s10k` **прогнаны 2 ноября** — результаты и находки в `LOAD_TEST_2026-11-02.md` (`r1k` остановилась по правилу: база 2 CPU и поиск людей по имени; `r1kw` и `auth` ещё не гонялись). Ниже — исходная инструкция. Всё, что ниже названо «проверено», относится к прогону 28.10 (`LOCAL_LOAD_TEST_2026-10-28.md`); новое помечено «не прогонялось».

## Что добавлено в этом шаге (не прогонялось)

1. **Вход по СМС-коду** — `loadtest/k6/auth.js`: поток новых входов в секунду (запрос кода + проверка кода, каждый раз новый номер = регистрация). СМС не уходит: провайдер `mock`, код фиксированный `000000`, API разрешает такой код только в режиме разработки. Лимиты «на один адрес» подняты в отдельном файле `api-auth.env` (`AUTH_TEST=1 ./make-env.sh`, ключи те же, что в `api.env`), потому что все тестовые входы идут с одного адреса. Лимиты СМС (суточный бюджет, защита по префиксу номера, потолок регистраций) лежат в БД: ступень `auth` ставит их на время прогона и **удаляет после, даже если упала**. Номера идут по разным префиксам, чтобы защита от накрутки СМС не сработала на сам тест.
2. **Публикация постов** — действие `post_create` в смеси людей; включается `WRITES=1`, по умолчанию выключено. Ступень `r1kw` зелёная, только если больше половины публикаций реально создали пост (метрика `post_created`); иначе 403 «нет прав» выглядело бы как успех. Из-за новой доли в смеси `r1kw` с `r1k` напрямую не сравнивать.
3. **Скрипт ступеней** — `loadtest/local-docker/ladder.sh`: гонит ступени по очереди, на первой упавшей останавливается.

## Ступени и пороги

Остановка прогона (правило владельца): ошибок > 5 % или p95 > 2 с в течение 60 с. Цели ниже — это «зелёное».

| Ступень | Что идёт | API | Зелёное, если | Зачем |
|---|---|---|---|---|
| `r100` | 100 человек + 50 сокетов | 2 | ошибок < 1 %, p95 < 1,5 с | вся цепочка вообще работает |
| `r1k` | **1 000 человек** + 200 сокетов, все действия (с лентой дел и поиском) | 8 | ошибок < 1 %, p95 < 800 мс, чат доходит ≥ 98 % за ≤ 2 с | проверка исправлений #507 |
| `r1kw` | то же + публикация постов | 8 | то же | запись в БД |
| `r3k` | **3 000 человек** + 1 000 сокетов | 16 | ошибок < 1 %, p95 < 1,5 с | потолок ноутбука |
| `s10k` | 2 000 человек + **10 000 удерживаемых сокетов** | 16 | сокетов подключилось ≥ 95 %, p95 подключения < 3 с, чат ≥ 98 % | рассылка реального времени |
| `auth` | вход по СМС-коду, 1 → **100 входов/с** (`LOGIN_RATE`) | 4 | успешных ≥ 99 %, p95 < 3 с; стоп, если 60 с подряд < 95 % или p95 > 4 с | регистрация в день запуска |

Звонки: сигналинг (`callFlow`) сейчас запускается только `main.js`; на ноутбуке его можно включить профилем `local` (`calls_per_s`), но этот путь не проверялся. Первый шаг на ноутбуке — `r100`, потом решить, добавлять ли звонки (см. ниже «Не прогонялось»).

## Честно про «10 000 и 100 000»

- **10 000 человек, которые одновременно что-то делают (а не просто онлайн)** на ноутбуке не поместятся вместе с базой и генератором: по замеру 28.10 это ≈ 65–80 vCPU серверов API. Поэтому «10k» на ноутбуке = **10 000 открытых сокетов + 2 000 действующих людей** (`s10k`), а полные 5 000 запросов/с — это облачный профиль `m10` (≈ $20, оценка ±30 %).
- **100 000 человек** с ноутбука проверить нельзя: при паузе 1–3 с это ≈ 50 000 запросов/с, ≈ 600–800 vCPU API (по замеру до исправлений). Для 100k считаем расчётом по замеренной цене «сколько vCPU API на 1 000 человек», а не обещанием. Также у одного компьютера ~28 000 портов на один адрес, поэтому больше ~25 000 сокетов с одного генератора без отдельной настройки не откроется.
- «1M в базе» (данные) и «N человек онлайн» — разные вещи: база 1M уже есть, ступени меняют только число людей.

## Инструкция для владельца (после того как скажете, что ноутбук включён)

Прогон идёт через Remote Control: я запускаю команды сам, вам ничего вводить не нужно. Если захотите руками, вот что и зачем.

**Один раз поставить.** Нужны: Docker (с Docker Compose), Node 20+, Python 3, git. k6 ставить **не нужно** — он запускается внутри Docker. Если ноутбук на Windows, нужен WSL2 с Ubuntu (скрипты — для Linux; на Mac часть замеров температуры не работает).

**Запуск по одной команде, всё из папки репозитория `loadtest/local-docker`:**

```sh
# 1. собрать образы и поднять стенд (команды docker build — в шапке compose.yml)
./make-env.sh && AUTH_TEST=1 ./make-env.sh && docker compose up -d   # make-env.sh не затирает готовый api.env (FORCE=1 — затереть, тогда заново prepare.sh)
# 1а. база с нуля (если тома lawbid-lt-pgdata нет): создать, прогнать миграции образом API, пароль роли, статистика запросов, демо-база
docker exec -i lawbid-lt-postgres-1 psql -U root -d postgres -c "CREATE DATABASE lawbid_lt" -c "CREATE DATABASE lawbid_lt_demo"
docker run --rm --network lawbid-lt_default -e DATABASE_URL=postgresql://root:lawbid@postgres:5432/lawbid_lt lawbid-lt-api-dev:local sh -c "npx prisma migrate deploy && node prisma/run-concurrent.mjs"
docker exec -i lawbid-lt-postgres-1 psql -U root -d lawbid_lt -c "ALTER ROLE lawbid_app WITH LOGIN PASSWORD 'lawbid_app_lt'" -c "CREATE EXTENSION IF NOT EXISTS pg_stat_statements" -c "ALTER DATABASE lawbid_lt_demo OWNER TO lawbid_app"
# 2. залить данные (если том lawbid-lt-pgdata уже есть — пропустить); ~10–22 мин (на время засева базе можно дать 8 CPU: docker update --cpus 8 lawbid-lt-postgres-1, после — вернуть 2)
./seed.sh 10 lawbid_lt 8 && docker exec -i lawbid-lt-postgres-1 psql -U root -d lawbid_lt < licenses.sql
# 3. завести тестовые аккаунты (больше, чем людей: у каждого лимит 100 запросов в минуту)
./prepare.sh ~/loadtest/results/fx-1m 12000 3000 0
# 4. сторож температуры (останавливает нагрузку при перегреве)
systemd-run --user --unit=lt-watch -E WATCH_PG=1 bash watch.sh
# 5. по ступеням; на первой упавшей остановится
./ladder.sh ~/loadtest/results/fx-1m r100 r1k
./ladder.sh ~/loadtest/results/fx-1m r1kw r3k s10k
./ladder.sh ~/loadtest/results/fx-1m auth
```

**Если Docker — это Docker Desktop (виртуальная машина), а не нативный Docker Engine:** дать VM память (`~/.docker/desktop/settings-store.json`: `"MemoryMiB": 45056`, `"Cpus": 32`, затем `systemctl --user restart docker-desktop`) и гонять ступени с `API_CPUS=2 ./ladder.sh …` — в VM cgroup-квота в 1 CPU режет задачу API втрое, с квотой 2 CPU задача равна задаче 28.10 (замер и разбор: `LOAD_TEST_2026-11-02.md`, «Стенд»). После перезапуска Desktop поднимаются только `api`/`worker`, остальное — `docker compose up -d` заново.

**Куда смотреть.** После каждой ступени скрипт печатает таблицу (запросов/с, ошибки %, p50/p95/p99, самые медленные места). Сырое — `~/loadtest/results/<дата-ступень>/`: `summary.json`, `k6.log`, `pgss_top.txt` (самые тяжёлые запросы к базе), `stats.log` (процессор и память контейнеров), `temp.log`. «Зелёное» — по таблице выше; красное — строка `rung … FAILED`, там же путь к результатам.

**Перед прогоном:** режим питания ноутбука `performance` (`powerprofilesctl set performance`, после прогона `balanced`). Все цифры 28.10 сняты в `power-saver`, то есть реальный запас больше.

**Деньги:** 0 $. AWS не трогается. В прод ничего не уходит.

## Находка для запуска (не про ноутбук)

На проде по умолчанию стоят предохранители от СМС-накрутки: 300 кодов в сутки (режим `auto` сам растёт до ×3 от лучшего дня за неделю, но не больше ×10 = 3 000), потолок регистраций `sms.signup_daily_cap`, защита по префиксу номера. Это правильно против мошенников, но в день запуска всплеск из тысяч настоящих регистраций упрётся в них, и люди получат «не удалось отправить код» — тот самый плохой отзыв. Ступень `auth` покажет, что и как отвечает, а значения для запуска владельцу надо выставить заранее в Админка → Настройки (поиск `sms.` и `budget.sms`). Без команды владельца я их не трогаю.

## Что на ноутбуке проверить нельзя и как закрыть дёшево

| Что | Почему не на ноутбуке | Чем закрыть |
|---|---|---|
| Cloudflare (звонки SFU, CDN, защита) | нет ключей/аккаунта в стенде, это внешний сервис | после вставки ключей в Админка → Интеграции: маленькая проба `calls-smoke` и ручной звонок с двух телефонов; нагрузку на сам Cloudflare считает он, нужна проверка лимитов тарифа |
| TURN (coturn) | локально нет; на проде сервер выключен «до нужды» | облачный `calls-smoke` ($1,4 по оценке) — 20 каналов по минуте; запуск TURN по требованию проверить отдельно (включился ли сам при звонке) |
| Пуши FCM / APNs | нужны боевые ключи Google/Apple и реальные телефоны | только на телефонах в финальном раунде; нагрузкой не проверяется |
| ALB, WAF (лимит тела 8 КБ, правила) | в стенде вместо ALB обычный nginx | облачный `smoke` ($1,3) покажет ALB и WAF вживую; WAF-правила нагрузкой не «ломать» |
| Реальная сеть и телефоны (3G, потери) | на ноутбуке всё по localhost | ручные проверки на телефонах + профили сети в симуляторе |
| СМС, Stripe, Bunny, S3 | платные, в стенде выключены | отдельными ручными проверками в тестовых режимах |
| Процессор AWS (Graviton) и RDS | ноутбук другой | соотношения те же, абсолютные цифры нужны из облачного прогона |

**Дешёвый часовой облачный прогон (позже, после зелёных r1k/r3k).** По `docs/runbooks/LOAD_TEST.md`: кнопка в GitHub с вашим подтверждением суммы, стенд сам удаляется, сторож добивает забытое. Порядок: `smoke` (≈ $1,3, верхняя граница $2) → `calls-smoke` (≈ $1,4) → `m1` (≈ $7–10). Перед `m1` по предупреждению в `LOCAL_LOAD_TEST_2026-10-28.md` поднять в `infra/envs/loadtest/profiles/m1.tfvars` размер задачи API до 1 vCPU и потолок до ≈ 24 — иначе деньги уйдут на уже известное. Terraform этого стенда ещё ни разу не применялся — первый запуск `smoke` и есть его проверка.

## Что не прогонялось (так и называем)

- Все новые ступени и `auth.js`: синтаксис проверен, сам k6 и Docker в среде, где писался шаг, не запускались. Номера телефонов проверены через ту же библиотеку, что и в API (20 тыс. выбранных — все валидны, 200 тыс. подряд — без повторов). Ограничения входа найдены чтением кода (лимиты на адрес и номер, бюджет СМС 300/сутки, защита по префиксу, потолок регистраций) и сняты для теста; не найденные станут видны на `auth`: счётчик `login_fail` в итоге показывает шаг и код ответа (429/403/503/401).

- Повторный замер после PR #507 (четыре узких места) — это и есть ступень `r1k`.
- Звонки на ноутбуке не гонялись ни в 28.10, ни здесь.
