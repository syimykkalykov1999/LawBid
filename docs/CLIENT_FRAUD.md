# Повторные аккаунты мошенников и балл риска клиента (owner 2026-10-05)

Сценарий владельца: клиент-мошенник обманывает адвокатов, собирает жалобы, его блокируют, а он регистрируется снова тем же телефоном, почтой, Apple/Google-аккаунтом или с того же телефона и продолжает. Защита работает сама (принцип автоматизации, `docs/AUTOMATION_PRINCIPLE.md`); сотрудник только смотрит очередь. Платных сервисов нет: бесплатные идентификаторы устройства и наши собственные данные.

Код: `apps/api/src/modules/client-fraud/` (`ClientFraudService` — глобальный `ClientFraudCoreModule`; админка — `ClientFraudModule`, `/admin/fraud/*`). Чистая логика решения — `fraud-decision.ts`; тесты — `fraud-decision.spec.ts`, `client-fraud.service.spec.ts`. Миграция `20261005200000_owner_client_fraud`.

## 1. Отпечатки (только хэши)

Таблица `identity_fingerprints` (`user_id`, `kind`, `hash`, `first_seen_at`, `last_seen_at`, `banned_at`). Значение никогда не хранится: `HMAC-SHA256(AUTH_EVENT_PEPPER, "fraud-fp:v1:<kind>:<нормализованное значение>")` (`fingerprint.util.ts`). Смена `AUTH_EVENT_PEPPER` обнуляет все совпадения.

| kind | откуда | сила |
|---|---|---|
| `phone` | телефон аккаунта / запроса кода | сильный |
| `email` | почта (Gmail: без точек и `+тега`, googlemail = gmail) | сильный |
| `apple`, `google` | `sub` из id_token Sign in with Apple / Google | сильный |
| `card` | `subscriptions.card_fingerprint` (Stripe, аккаунт платформы) | сильный |
| `device` | заголовок `X-Device-Key`: Android `ANDROID_ID`, iOS — случайный id в Keychain (переживает переустановку) | устройство (своя настройка) |
| `ip` | IP входа, 30 дней | только показ сотруднику (общий IP у незнакомых людей за NAT оператора) |
| `text` | нормализованный текст кейса ≥ 60 символов | слабый |

Карты клиентов не используются: оплаты адвокатам — direct charges на подключённых аккаунтах Stripe, а fingerprint карты в Stripe свой у каждого аккаунта. `X-Device-Id` (сессии, лимиты) не меняется; `X-Device-Key` — отдельный заголовок только для этого.

Пишутся при каждом входе (`AuthService.issueLogin`, `SocialAuthService.login`) и при публикации кейса.

## 2. Блокировка повторного входа

«Заблокированный» владелец отпечатка: `users.status = suspended`, или активный бан `account_bans(kind=user)`, или `identity_fingerprints.banned_at` (аккаунт удалён, будучи заблокированным: `AccountAnonymizationService` замораживает хэши).

Проверка (`assertSignInAllowed`) — до отправки кода (`requestOtp`, экономит SMS), до создания аккаунта (соц-вход) и перед выдачей сессии (`issueLogin`):

| совпадение | `fraud.match_action` / `fraud.device_action` | результат |
|---|---|---|
| сильный отпечаток | `block` (по умолчанию) | 403 `ACCOUNT_SUSPENDED` без причины, событие `sign_in_blocked` |
| устройство | `review` (по умолчанию) | вход разрешён, аккаунт сразу `restricted` и в очереди |
| любое | `off` | ничего |

При `fraud.auto = false` любое `block` превращается в `review`. Сотрудники админки не проверяются.

## 3. Балл риска (только клиенты)

`ClientFraudService.signalsOf` за окно `fraud.window_days` (180):

| сигнал | баллы |
|---|---|
| `fraud_reports` — адвокаты, **имевшие дело** с клиентом (ставка на его кейс или чат), пожаловались `fraud`/`impersonation` на клиента или его кейс | `fraud.weight_fraud_report` (25) за адвоката |
| `other_reports` — другие жалобы тех же адвокатов | `fraud.weight_report` (8) за адвоката |
| `contact_issues` — подтверждённые фальшивые контакты | 15 |
| `chargebacks` — оспоренные через банк оплаты | `fraud.weight_chargeback` (30) |
| `cancelled_after_bids` — закрытые без выбора кейсы со ставками сверх двух | 5 |
| `shared_with_blocked` — сильный отпечаток/устройство общие с заблокированным | 100 (только для показа и сортировки; статус даёт правило §2) |
| `weak_shared_with_blocked` — тот же текст кейса, что у заблокированного | 15 |
| `many_accounts_on_device` — больше 2 аккаунтов на устройстве | 10 за лишний |
| `duplicate_text` — тот же текст кейса у другого аккаунта (считаются не больше 2 аккаунтов: шаблон сам по себе не ограничивает; блокировка не распространяется по тексту и сети) | 10 |

Жалобы посторонних не считаются (нельзя «завалить» клиента жалобами). Пороги: `fraud.review_score` 30 → очередь, `fraud.restrict_score` 60 → ограничен, `fraud.ban_score` 100 → блокировка (4 адвоката с жалобой на мошенничество).

Пересчёт: вход, кейс, жалоба (`ReportsService`), блокировка любого аккаунта (`AdminUsersService.suspend`, `AdminSanctionsService.blockUser`, автоматическая), кнопки в админке, ночной job `fraud.sweep` (03:55 UTC: очередь, свежие блокировки за 2 дня, удаление старых хэшей).

## 4. Статусы и решения (`decideStatus`)

`client_fraud_profiles.status`: `ok` → `review` (работает как обычно, в очереди) → `restricted` (403 `ACCOUNT_RESTRICTED` на публикацию кейса и сообщения в чатах; поддержка открыта) → `banned` (`users.status = suspended`, сессии завершены, открытые кейсы клиента в архиве).

- статус = максимум из правила связи (§2) и балла;
- после «Снять» сотрудника автоматика молчит, пока балл не вырастет выше зафиксированного (`cleared_score`); восстановление в «Люди» считается тем же «Снять»;
- блокировку снимает только человек; решение сотрудника автоматика не понижает (только повышает);
- блокировка аккаунта пересчитывает все аккаунты с общими отпечатками (до 200), так падают и уже созданные запасные аккаунты.

История — `client_fraud_events` (только добавление): `sign_in_blocked`, `linked_match`, `auto_*`, `staff_*`, `linked_banned`, кто, когда, балл, заметка. Аудит админских действий — `fraud.*`.

## 5. Админка

Галочки → «Борьба с мошенниками» → вкладка «Клиенты» (`/verification/trust`, область `verification`, роли verifier + super_admin): KPI, очередь, карточка `/verification/trust/clients/<id>` (сигналы, связанные аккаунты с видом общего отпечатка — без значений, история), «Снять» / «Ограничить» / «Заблокировать» (+ «и все связанные»), «Пересчитать», правила с пресетами. Дашборд: `fraudQueue`, `fraudBlocked7d`. Письмо проверяющим (или супер-админу) о новой блокировке/очереди, не чаще раза в 30 минут на человека (`fraud.notify_staff`).

| пресет | сильное совпадение | устройство | пороги review / restrict / ban |
|---|---|---|---|
| Мягко | review | review | 50 / 90 / 150 |
| Стандарт (по умолчанию) | block | review | 30 / 60 / 100 |
| Строго | block | block | 20 / 40 / 70 |
| Выключить | `fraud.enabled = false`: ничего не пишется и не проверяется | | |

## 6. Приложение

`X-Device-Key` (`lib/core/network/device_key.dart`, канал `lawbid/device_key` в `MainActivity.kt`). На `ACCOUNT_RESTRICTED` — карточка «Аккаунт ограничен» с «Написать в поддержку» (`AccountRestrictedHost`). Отказ во входе — существующий экран блокировки без причины. Тексты не называют совпавший признак.

## 7. Приватность и хранение

Только хэши. Хэши обычных аккаунтов удаляются через `fraud.fingerprint_retention_days` (365) без использования и сразу после удаления аккаунта; хэши заблокированных хранятся `fraud.blocked_retention_days` (1095). Описание для владельца и юриста: `/mnt/project-files/legal/client-fraud.md`.
