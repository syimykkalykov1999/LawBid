## 1. Общая логика

- Лента LawBid — **только юридический образовательный контент**: адвокаты публикуют обучающие посты (законы, права людей, практические советы), чтобы продвигать свой профиль, как в других соцсетях. Клиенты читают, лайкают, сохраняют, комментируют, подписываются на адвокатов.
- Публиковать посты могут **только верифицированные адвокаты** (файл 3, раздел 6.4). Клиенты посты не публикуют.
- Формат постов на старте: **текст + фото**. Видео в приложении пока не публикуются, архитектура закладывается сейчас, включение флагом `video_posts` позже (раздел 3.6).
- Механика лайков, комментариев, сохранений, подписок и уведомлений повторяет Instagram.
- Профили клиентов закрыты (файл 3): клиент не имеет публичного профиля, его нельзя искать и на него нельзя подписаться.

Навигация (файл 1, раздел 3): нижнее меню **Лента | Поиск | + | Моё | Профиль**. Справа сверху в Ленте иконка **Чатов** с общим бейджем; внутри экрана чатов два раздела **Чаты | Уведомления**.

## 2. Вкладка «Лента»

### 2.1 Состав
- **Клиент:** один поток постов, вкладок нет.
- **Адвокат:** две вкладки сверху: **Лента** (посты) и **Кейсы** (файл 4). Переключение сохраняет позицию прокрутки каждой вкладки.
- Верхняя панель: слева логотип LawBid, справа иконка Чатов (бейдж = непрочитанные сообщения + непрочитанные уведомления, раздел 11.3).

### 2.2 Как формируется поток
Единый интерфейс `FeedProvider` (позже к нему подключается продвижение профилей, флаг `profile_promotion`, сейчас выключен и слот не создаётся).

1. **Посты подписок:** посты адвокатов, на которых подписан пользователь (и собственные посты адвоката), от новых к старым.
2. **Рекомендации:** посты адвокатов, на которых пользователь не подписан, опубликованные за последние 14 дней. Скоринг: `score = (likes + 2*comments + 2*saves) / (возраст_в_часах + 2)^1.5`. Воркер каждые 10 минут пересчитывает топ-N в Redis (`ZSET feed:reco`).
3. **Смешивание:** если у пользователя есть подписки, каждый 4-й элемент страницы берётся из рекомендаций; если подписок нет, поток на 100% из рекомендаций. Когда посты подписок закончились, дальше идут рекомендации.
4. **Исключения:** посты со статусом не `published`, посты приостановленных адвокатов, уже показанные посты (в Redis хранится набор последних 500 просмотренных `post_id` на пользователя, TTL 3 дня).
5. **Курсор:** составной (последний `created_at,id` подписок + позиция рекомендаций), cursor-пагинация, `limit` 10-20. Никакого offset.
6. Первая страница кэшируется в Redis на 60 секунд, в приложении в drift для показа офлайн.

### 2.3 Пустые состояния
- Нет постов совсем: «Пока в ленте пусто» + блок «Рекомендуемые адвокаты» (раздел 6.3) с кнопками «Подписаться».
- Нет сети: показ кэша с баннером «Нет соединения».

### 2.4 Карточка поста
Сверху вниз: аватар адвоката, `@username` + синяя галочка, время («2 ч назад»), меню «⋯»; медиа (карусель фото, индикатор страниц); панель действий: лайк, комментарии, поделиться, справа «Сохранить»; счётчик лайков; текст (свернуть после 3 строк, «ещё»); хэштеги кликабельны (открывают страницу темы); «Посмотреть все комментарии (N)».
- **Двойной тап** по фото ставит лайк (анимация сердца).
- **Меню «⋯»:** у чужого поста: «Пожаловаться», «Копировать ссылку»; у своего: «Редактировать текст», «Удалить», «Копировать ссылку».
- Тап на автора открывает публичный профиль адвоката (файл 3).
- Посты без фото показываются как текстовые карточки. В сетке профиля (файл 3, вкладка «Посты») текстовый пост отображается плиткой с началом текста.
- На экране публикации и в детальном экране поста показывается строка: «Материалы носят информационный характер и не являются юридической консультацией».

## 3. Посты

### 3.1 Создание (адвокат, «+» → «Пост в ленту»)
- Поля: текст (обязателен, 1-2200 символов), фото (0-10 штук, порядок перетаскиванием).
- Из текста автоматически извлекаются хэштеги (`#dui`, `#divorce`): буквы, цифры, `_`, до 30 символов, максимум 10 на пост, нормализация в нижний регистр, сохраняются в `tags` и `post_tags`.
- Экран публикации предупреждает: «Публикуйте образовательные материалы. Не размещайте персональные данные клиентов и детали их дел».
- `POST /posts` (`Idempotency-Key`): проверки роли (`attorney`, `verified`, `active`), лимиты (раздел 13), проверка текста хуком модерации (раздел 12.3), создание `posts`, `post_media`, `tags`, `post_tags`, `attorney_profiles.posts_count + 1` (через агрегатор счётчиков).
- Для гейтов: неверифицированный адвокат видит экран «Пройдите верификацию» (файл 3); клиент пункта «Пост в ленту» в «+» не видит (у клиента в «+» только «Создать кейс», файл 1).

### 3.2 Фото
- JPEG, PNG, HEIC (конвертируется в JPEG на сервере), до 10 МБ на файл.
- Клиент сжимает до 2048 px по длинной стороне перед загрузкой; загрузка через pre-signed URL (файл 3, раздел 2.2), `file_purpose = post_image`.
- Воркер после загрузки создаёт варианты (превью 320 px, среднее 1080 px), фото отдаются через CDN (CloudFront), оригинал в приватном бакете.
- Файл со статусом скана не `clean` к посту прикрепить нельзя.

### 3.3 Редактирование и удаление
- Редактируется только текст (в течение всего времени), хэштеги пересчитываются, показывается пометка «Изменено» (`posts.edited_at`). Фото после публикации не заменяются.
- Удаление: soft delete (`deleted_at`), пост исчезает из всех выдач, счётчики корректируются.

### 3.4 Статусы контента
`published`, `hidden`, `removed` (`content_status`). `hidden`/`removed` выставляет модерация (файл 6); автор видит пометку «Пост скрыт модерацией» в своём профиле и причину в уведомлении `moderation_notice`.

### 3.5 Экран поста
Полная карточка + комментарии (раздел 5) + поле ввода. Открывается по тапу на пост, по deep link `lawbid.app/post/:id`, по уведомлению.

### 3.6 Видео (закладка на будущее)
- В БД уже есть `media_type = video`. В миграции добавляется `file_purpose = post_video` (раздел 14).
- Пока флаг `video_posts = false`: API отклоняет видео (`FEATURE_DISABLED`), в UI нет выбора видео.
- Когда флаг включён админом, включаются загрузка видео, транскодинг воркером и проигрыватель в карточке. Отдельного релиза серверной части не требуется; клиентский код видео-виджета подготавливается заранее и скрыт флагом.

## 4. Лайки и сохранения

- **Лайк поста:** `POST /posts/:id/like`, `DELETE /posts/:id/like`. Идемпотентно (PK `post_id + user_id`). Оптимистичное обновление в UI с откатом при ошибке. Лайкать могут клиенты и адвокаты.
- **Счётчики:** `like_count` обновляется агрегатором (Redis, сброс в БД воркером, файл 2, раздел 1.5), пользователю показывается значение из Redis + собственное действие.
- **Сохранение поста:** `POST/DELETE /saved-items` (`item_type = post`, механика из файла 4). Показывается в «Моё → Сохранённое». Сохранённый пост, который позже удалён/скрыт, отображается как «Пост недоступен».
- **Поделиться:** системное меню шаринга со ссылкой `lawbid.app/post/:id`.
- **Пожаловаться на пост:** `POST /reports` (`target_type = post`, причина из `report_reason`); повторная жалоба того же пользователя на тот же объект игнорируется. Обработка в файле 6.

## 5. Комментарии

### 5.1 Правила
- Комментировать могут клиенты и адвокаты (клиенты задают вопросы, адвокаты отвечают, это основной канал знакомства).
- Длина 1-1000 символов. Редактирования нет (как в Instagram), только удаление.
- **Ответы:** один уровень вложенности. Ответ на ответ привязывается к родительскому комментарию верхнего уровня (с подставленным `@username` адресата в тексте).
- **Лайки комментариев:** `POST/DELETE /comments/:id/like`, идемпотентно.
- **Удаление:** автор комментария удаляет свой; автор поста может удалить любой комментарий под своим постом. Soft delete (`deleted_at`), при удалении родителя ответы скрываются вместе с ним.
- **Жалоба:** `POST /reports` (`target_type = comment`).

### 5.2 Отображение автора комментария
- Адвокат: аватар, `@username` + галочка, тап открывает профиль.
- **Клиент:** формат «Имя + первая буква фамилии» (например «Anna K.»), стандартный аватар без фото, **тап ничего не открывает** (профили клиентов закрыты).
- Поле ввода у клиента подсказывает: «Не публикуйте личные данные и детали дела. Опишите общий вопрос».

### 5.3 Списки
- `GET /posts/:id/comments?cursor=` (сначала новые), по 20 штук, у каждого показано число ответов и «Показать ответы» (подгрузка `GET /comments/:id/replies?cursor=`).
- Счётчики `comment_count` и `reply_count`: агрегатор, как у лайков.
- Уведомления: автору поста о новом комментарии (`post_comment`), автору комментария об ответе (`comment_reply`) и лайке (`comment_like`).

## 6. Подписки

### 6.1 Правила
- Подписаться можно только на **адвокатов** (`follows.followee_id` — адвокат, проверка в сервисе). Подписчиками могут быть клиенты и адвокаты. Нельзя подписаться на себя.
- `POST /attorneys/:id/follow`, `DELETE /attorneys/:id/follow`, идемпотентно. Подписки без подтверждения (профили адвокатов публичные).
- Счётчики `followers_count`, `following_count`: агрегатор.
- Уведомление адвокату о новом подписчике (`new_follower`): если подписчиков за короткое время много, агрегируется (раздел 11.4).

### 6.2 Списки и приватность
- **Подписчики адвоката** (`GET /attorneys/:id/followers`): в списке показываются **только адвокаты**; клиенты-подписчики учитываются в счётчике, но по имени не показываются (приватность клиентов).
- **Подписки адвоката** (`GET /attorneys/:id/following`): публичный список адвокатов, на которых он подписан.
- **Подписки клиента:** видит только сам клиент («Профиль → Подписки»).
- Кнопка «Подписаться»/«Вы подписаны» на профиле и в результатах поиска.

### 6.3 Рекомендуемые адвокаты
`GET /suggestions/attorneys?cursor=`: верифицированные адвокаты, на которых пользователь не подписан, сортировка по рейтингу и активности (посты за 30 дней); для клиента приоритет адвокатам из его штата. Показываются в пустой ленте и в состоянии поиска до ввода запроса.

## 7. Поиск (вкладка «Поиск»)

### 7.1 Структура
Вверху поле поиска, под ним переключатели-вкладки результатов; запрос общий для вкладок. Минимум 2 символа, задержка 300 мс, cursor-пагинация.

| Роль | Вкладки |
|---|---|
| Клиент | **Адвокаты**, **Посты**, **Темы** |
| Адвокат | **Люди** (только адвокаты), **Кейсы**, **Посты**, **Темы** |

Клиентов в поиске нет ни для кого.

### 7.2 Состояние до ввода
Последние запросы (хранятся локально, можно очистить), «Популярные темы» (топ хэштегов за 7 дней, из Redis, обновляется воркером), «Рекомендуемые адвокаты» (раздел 6.3).

### 7.3 Адвокаты / Люди
- Поиск по имени и фамилии, `@username`, практике (название специализации/категории), штату.
- Фильтры: практика, штат, минимальный рейтинг, язык общения.
- Результат: аватар, имя, `@username` + галочка, рейтинг и число отзывов, первые практики, штаты, кнопка «Подписаться».
- Видимость по статусу адвоката: как в файле 3 (раздел 6.1): `verified` показываются, `unverified/pending/rejected` без галочки, `suspended` скрыты. Ранжирование: точное совпадение `@username`, затем префикс, затем сходство (trigram), при равенстве выше `verified`, затем по рейтингу.

### 7.4 Кейсы (только адвокат)
- Поиск по тексту заголовка и описания среди кейсов, **доступных этому адвокату по правилам файла 4 (раздел 4.1)**: чужие штаты и практики не возвращаются никогда.
- Фильтры: практика, штат, дата публикации (за 24 часа, 7 дней, 30 дней, все).
- Результат выводится теми же карточками, что и вкладка «Кейсы» (файл 4, раздел 4.2).

### 7.5 Посты и Темы
- Посты: полнотекстовый поиск по тексту постов (только `published`), сортировка: релевантность, затем дата.
- Темы: поиск хэштегов по префиксу; тап открывает страницу темы `#dui` (`GET /tags/:tag/posts`): вкладки «Топ» (по скорингу) и «Новые».

### 7.6 Техническая реализация
- Интерфейс `SearchProvider` (`searchAttorneys`, `searchCases`, `searchPosts`, `searchTags`); реализация на старте `CockroachSearchProvider` на индексах файла 2 (раздел 5.3: trigram, tsvector, GIN). Позже заменяется внешним поисковиком без изменения API.
- Rate limit на поиск (раздел 13). Поисковые запросы не логируются вместе с идентификатором пользователя в открытом виде.
- Результаты `SearchProvider` для кейсов **всегда** проходят через тот же `CaseAccessPolicy`, что и список кейсов (единая точка проверки), отдельной логики доступа в поиске нет.

## 8. Чаты

### 8.1 Раздел «Чаты» (внутри экрана иконки чатов, вкладка 1 из 2)
- Список бесед, сортировка по `last_message_at` (новые сверху), cursor-пагинация.
- Строка: аватар собеседника, имя, предпросмотр последнего сообщения, время, число непрочитанных, чип кейса (заголовок кейса), иконка «без звука».
- **Отображение собеседника:** для адвоката, пока `contacts_unlocked = false`, клиент показан как «Клиент по кейсу «заголовок»» со стандартным аватаром; после принятия бида имя и фото клиента (если есть). Для клиента адвокат виден всегда (профиль публичный).
- Чаты создаются только из кейса (файл 4, раздел 9): нет кнопки «Новое сообщение». Пустое состояние: у клиента «Чаты появятся, когда адвокат напишет вам по кейсу или вы примете предложение»; у адвоката «Откройте кейс и нажмите «Написать клиенту»».

### 8.2 Экран беседы
- Шапка: собеседник, ниже заголовок кейса (тап открывает кейс), меню «⋯»: «Без звука», «Пожаловаться».
- Сообщения: пузыри, разделители по дням, время, статусы своих сообщений: отправляется / отправлено / прочитано (`Seen`, по `last_read_message_id` собеседника). Индикатор «печатает…» (ephemeral, через realtime).
- Поле ввода: только текст, до 2000 символов. Вложений (фото, файлы) в этом ТЗ нет.
- Системные сообщения (`type = system`, локализуемые): «Предложение принято, контакты открыты», «Стороны не договорились», «Кейс закрыт», «Кейс принят другим адвокатом. Чат доступен только для чтения».
- Если беседа `closed`: сверху баннер «Чат закрыт», ввод отключён.

### 8.3 Маскировка контактов (файл 4, раздел 9)
Пока `contacts_unlocked = false`, сервер при сохранении находит в тексте телефоны (включая записанные словами и с разделителями), email и ссылки, заменяет на `[контакт скрыт]` в `body_display`, оригинал хранится в `body_original`, `contact_masked = true`. Обе стороны видят `body_display`. Отправителю показывается разовая подсказка «Контакты скрываются до принятия предложения». После разблокировки новые сообщения не маскируются, старые остаются в исходном виде маскировки.

### 8.4 Отправка и доставка
- `POST /conversations/:id/messages` `{clientMessageId, body}`: идемпотентно (UQ `conversation_id + sender_id + client_message_id`). Приложение генерирует `clientMessageId` (UUID), сообщение сразу показывается в списке со статусом «отправляется» (outbox в drift), при отсутствии сети остаётся в очереди и отправляется автоматически при появлении соединения с повтором.
- Права: участник беседы, беседа не `closed`, для адвоката инициирование беседы и отправка требуют активной подписки/триала (файл 4, раздел 2); если подписка неактивна, ввод заменён на «Продлите подписку, чтобы писать» (файл 6).
- После сохранения: `conversations.last_message_at/last_message_id`, публикация события `message:new` в realtime получателю и отправителю, push получателю, если он не в этой беседе (раздел 11.5).
- **Прочитано:** `POST /conversations/:id/read` `{lastReadMessageId}` вызывается, когда сообщения показаны на экране; обновляет `conversation_participants.last_read_message_id`, событие `message:read` отправителю, пересчёт бейджа.
- **Без звука:** `PATCH /conversations/:id/mute` `{until}` (`muted_until`): push от этой беседы отключён, сообщения продолжают приходить.
- **Жалоба:** `POST /reports` (`target_type = message` или `user`).

### 8.5 Realtime (Socket.IO)
- Подключение `/realtime` с access-токеном (проверка при handshake, повторная проверка при обновлении токена), комнаты `user:{id}` и `conversation:{id}` (вход только для участников).
- Масштабирование: Socket.IO Redis adapter, стики-сессии не требуются (транспорт WebSocket с fallback).
- События сервера: `message:new`, `message:read`, `typing` (отправляется клиентом `typing:start/stop`, не сохраняется, TTL 5 секунд), `notification:new`, `badge:update`, `conversation:update`.
- Клиент: автоматическое переподключение с экспоненциальной задержкой; после переподключения запрашивает пропущенное (`GET /conversations?updatedSince=`, сообщения текущей беседы после последнего известного `id`), а не полагается на доставку событий.
- Realtime только доставляет; источник правды всегда БД и REST. Потеря сокета не приводит к потере сообщений.

## 9. Уведомления (раздел 2 из 2 внутри экрана иконки чатов)

### 9.1 Список
- Вкладка **Уведомления**: записи из `notifications`, новые сверху, cursor-пагинация, группы «Сегодня», «На этой неделе», «Раньше».
- Строка: иконка по типу, текст (локализованный шаблон `notif.<type>` с параметрами из `payload`, например имя адвоката), время, синяя точка у непрочитанного.
- Тап открывает целевой экран (таблица 9.2) и помечает уведомление прочитанным. Кнопка «Отметить все как прочитанные» (`POST /notifications/read {all:true}`).
- Пустое состояние: «Пока нет уведомлений».

### 9.2 Типы и переходы
Типы и категории берутся из enum файла 2. Целевые экраны:

| Тип | Категория | Открывает |
|---|---|---|
| `bid_received`, `offer_countered`, `offer_accepted`, `bid_accepted`, `bid_rejected`, `negotiation_failed` | bids | детали бида |
| `case_updated`, `case_stale_prompt`, `case_archived`, `completion_requested`, `completion_reminder`, `case_closed`, `contact_issue_update` | cases | детали кейса |
| `review_requested` | cases | форма отзыва (файл 3) |
| `review_received` | cases | вкладка «Отзывы» своего профиля |
| `new_follower` | social | профиль подписчика-адвоката (если подписчик клиент, открывает свой список подписчиков без перехода в профиль) |
| `post_like`, `post_comment`, `comment_reply`, `comment_like` | social | пост (с прокруткой к комментарию) |
| `verification_update` | system | экран статуса верификации (файл 3) |
| `subscription_trial_ending`, `subscription_payment_failed`, `subscription_status` | system | экран подписки (файл 6) |
| `security_new_device` | system | «Активные устройства» (файл 1) |
| `moderation_notice` | system | экран с текстом решения/предупреждения |
| `new_message` | messages | **не хранится в списке уведомлений**, используется только для push; открывает беседу |

Тип `new_message` в таблицу `notifications` **не записывается**: непрочитанные сообщения считаются через чаты, поэтому в бейдже нет двойного счёта.

### 9.3 Создание уведомлений: единая точка
Все модули создают уведомления только через `NotificationsService.emit({type, recipientId, payload, dedupeKey?})`. Сервис:
1. проверяет настройки получателя по категории (раздел 9.5);
2. записывает `notifications` (если тип не `new_message`);
3. публикует `notification:new` и `badge:update` в realtime;
4. ставит push в очередь (BullMQ) с учётом тихих часов и «без звука» беседы;
5. для события `system`-категории, требующего письма, ставит email в очередь (раздел 9.5).
Прямая запись в `notifications` из других модулей запрещена (правило для Cursor).

### 9.4 Агрегация
Уведомления `post_like`, `comment_like` и `new_follower` агрегируются: для одного получателя и одного объекта за окно 1 час создаётся одна запись (`dedupe_key`, `aggregate_count`), текст «Sarah и ещё 5 отметили ваш пост». Для остальных типов агрегации нет.

### 9.5 Push, email и настройки
- **Push (FCM):** токены в `push_tokens` (привязаны к сессии), регистрация `POST /push-tokens`, удаление при выходе и при ошибке `UNREGISTERED`. Текст push локализуется на сервере по `users.ui_language`. В payload только идентификаторы и deep link, без чувствительных данных (тексты сообщений маскированы как `body_display`). Повторная отправка при временной ошибке (3 попытки, экспоненциальная задержка).
- **Push по умолчанию:** включены для bids, cases, messages, system; в social только `post_comment`, `comment_reply`, `new_follower` (агрегированный); лайки (`post_like`, `comment_like`) без push, только в списке; marketing выключен, пока нет согласия `marketing_push`.
- **Email:** только для категории `system` (`verification_update`, `subscription_*`, `security_new_device`, `moderation_notice`). Другие категории по email не отправляются.
- **Настройки (Настройки → Уведомления):** для каждой категории переключатели «Push» и «Email» (`notification_settings`); для `system` push и email отключить нельзя; «Тихие часы» (начало, конец, часовой пояс, `notification_quiet_hours`): push в это время откладываются до конца тихих часов (кроме `security_new_device`).

## 10. Бейджи

- `GET /badges` → `{chatsUnread, notificationsUnread, total}`.
- **Бейдж иконки чатов = `total` = непрочитанные сообщения (сумма по беседам, с учётом `last_read_message_id`, беседы «без звука» тоже считаются) + непрочитанные уведомления (без `new_message`).** Внутри экрана у вкладок «Чаты» и «Уведомления» отдельные бейджи.
- Значения хранятся в Redis-счётчиках на пользователя, обновляются при событиях и раз в сутки сверяются с БД; изменение доставляется событием `badge:update`.
- Число на иконке приложения (iOS) = `total`.
