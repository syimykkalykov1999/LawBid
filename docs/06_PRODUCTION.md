## 1. Подписка адвоката (Stripe)

### 1.1 Условия (зафиксированы)
- Цена **$399 в месяц**, валюта USD, единственный тариф.
- **Триал 7 дней с обязательной привязкой карты**, автосписание в конце триала, напоминание за 2 дня до окончания.
- Триал доступен только **после одобрения верификации** (файл 3) и только один раз на адвоката и один раз на карту (`subscriptions.card_fingerprint`, проверка уникальности среди использованных триалов).
- Если триал недоступен (карта уже использовалась в триале), приложение честно показывает «Пробный период недоступен, будет списано $399 сейчас», и подписка создаётся без триала после явного подтверждения.
- Без активной подписки/триала адвокат видит кейсы, но не видит контакты клиентов и не может отправлять биды и писать клиентам (файл 4, раздел 2).
- Комиссий с гонораров нет. Платёж клиенту-адвокату вне приложения.

### 1.2 Определение «подписка активна» (единый сервис)
`SubscriptionAccessService.isActive(userId)` возвращает `true`, если:
- `status IN ('trialing','active')`, **или**
- `status = 'past_due'` и `now() < grace_ends_at` (льготный период, по умолчанию **3 дня**, `app_config: subscription.past_due_grace_days`).
Результат кэшируется в Redis на 60 секунд и сбрасывается при обработке вебхука. Это единственное место проверки; файл 4 и файл 5 используют только этот сервис.

### 1.3 Статусы (`subscription_status`) и переходы
| Статус | Смысл | Доступ |
|---|---|---|
| `incomplete` | подписка создана, карта не подтверждена | нет |
| `trialing` | идёт триал | да |
| `active` | оплачено | да |
| `past_due` | последний платёж не прошёл | да, пока действует льготный период |
| `canceled` | отменена, период закончился | нет |
| `expired` | триал закончился без успешного списания | нет |

Отмена пользователем: `cancel_at_period_end = true`, доступ сохраняется до конца оплаченного периода (или до конца триала без списания).

### 1.4 Потоки
**Старт триала** (экран «Подписка», доступен после `verified`):
1. `POST /subscriptions/start` → сервер создаёт `Stripe Customer` (если нет), `SetupIntent`, возвращает `clientSecret` и признак `trialEligible`.
2. Flutter (`flutter_stripe`, PaymentSheet) подтверждает карту (включая 3D Secure).
3. `POST /subscriptions/confirm` → сервер создаёт Stripe Subscription (цена `STRIPE_PRICE_ID`, `trial_period_days = 7` если eligible, `payment_settings` с сохранением карты), записывает `subscriptions`, `card_fingerprint`.
4. Финальное состояние приходит вебхуком; приложение опрашивает `GET /subscriptions/me` до подтверждения статуса.

**Управление:** «Управление подпиской» открывает Stripe Customer Portal во встроенном браузере (`POST /subscriptions/portal-session`: смена карты, счета, отмена). Список платежей в приложении из `payments` (`GET /subscriptions/payments`).
**Отмена и повторная подписка:** после `canceled/expired` новая подписка создаётся тем же потоком, но без триала.

### 1.5 Вебхуки Stripe
- Эндпоинт `POST /webhooks/stripe`: проверка подписи (`STRIPE_WEBHOOK_SECRET`), сырое тело, немедленный ответ 200 после записи события в `stripe_webhook_events` (идемпотентность по `stripe_event_id`), обработка в очереди BullMQ с повторами.
- Обрабатываемые события: `customer.subscription.created/updated/deleted`, `invoice.paid`, `invoice.payment_failed`, `invoice.payment_action_required`, `setup_intent.succeeded`, `charge.refunded`.
- События могут приходить не по порядку: обработчик **всегда перечитывает актуальную подписку из Stripe API** и синхронизирует `subscriptions`, а не применяет событие «вслепую».
- Действия при смене доступа:
  - **активна → неактивна:** вызов `BidsService.withdrawActiveBidsForAttorney()` (файл 4), уведомление `subscription_status`, сброс кэша доступа.
  - **`invoice.payment_failed`:** `status = past_due`, `grace_ends_at = now() + grace`, уведомление `subscription_payment_failed` (push + email).
  - **неактивна → активна:** уведомление, контакты по принятым бидам открываются (файл 4, раздел 8.3).
- Напоминание об окончании триала: задача BullMQ на `trial_ends_at - 2 дня`: уведомление `subscription_trial_ending` (push + email) с датой и суммой списания; при отмене подписки задача пропускается.
- Ошибки вебхуков: 5 повторов с backoff, затем запись в dead-letter очередь и алерт.

### 1.6 Админ-действия по подписке (роль `finance`, аудит обязателен)
Просмотр подписки и платежей адвоката, ссылка на объект в Stripe Dashboard, **«Продлить подписку на N дней»** (компенсация при подтверждённой жалобе на контакт, файл 4, раздел 8.4; реализуется через `stripe.subscriptions.update` с переносом `trial_end`/периода, причина обязательна). Возвраты выполняются в Stripe Dashboard, результат приходит вебхуком.

### 1.7 Экраны Flutter (feature `subscription`)
1. «Подписка»: карточка тарифа ($399/мес), «7 дней бесплатно, затем $399/мес, отмена в любой момент», кнопка «Начать бесплатный период» (до верификации кнопка неактивна с пояснением).
2. Текущий статус: дата окончания триала/следующего списания, состояние, кнопки «Управление» и «Отменить».
3. Paywall-экраны для гейтов («Сделать бид», «Написать клиенту», «Контакты клиента»): краткое описание и переход на экран «Подписка».
4. История платежей.
5. Состояния: loading/empty/error/offline; ошибка оплаты с понятным текстом и действием «Обновить карту».

### 1.8 Расширение под будущие платные услуги
Платёжный слой строится на интерфейсе `PaymentProvider` (сейчас `StripePaymentProvider`). Продвижение профиля и видео включаются флагами `profile_promotion`, `video_posts` (файл 1), но **в этом ТЗ не реализуются**: таблицы и экраны для них добавляются отдельным ТЗ, когда появится бюджет.
Примечание к релизу: правила Apple/Google могут требовать встроенных покупок для цифровых подписок. Способ оплаты решается перед подачей в магазины (раздел 11.4), архитектура `PaymentProvider` позволяет добавить реализацию без переписывания бизнес-логики.

## 2. Админ-панель

### 2.1 Технологии и доступ
- Отдельное веб-приложение `apps/admin`: **Next.js (App Router) + TypeScript + Tailwind + shadcn/ui + TanStack Query**, клиент API генерируется из OpenAPI.
- Домен `admin.lawbid.app`, за CloudFront + WAF, опциональный allowlist IP (флаг).
- Серверные эндпоинты `/admin/*` с отдельным JWT (`aud = admin`), guard `AdminAuthGuard` и декоратор `@Roles()`. Токены мобильного приложения на `/admin/*` не принимаются и наоборот.
- **Вход администратора:** email + код на почту + **обязательная 2FA (TOTP)**; при первом входе привязка приложения-аутентификатора и выдача recovery-кодов (`admin_credentials`). Сессия 8 часов, простой 30 минут. Регистрации админов нет: аккаунт создаёт `super_admin` в разделе «Администраторы».
- Просмотр чувствительных данных (контакты клиента, тексты сообщений, документы верификации, содержимое кейса вне очереди) требует ввода **причины просмотра** (минимум 10 символов), которая пишется в `audit_log.justification`.
- Все действия администраторов пишутся в `audit_log` (кто, что, объект, до/после, IP, причина).

Проверка прав только на сервере, «deny by default».

### 2.3 Разделы и функции
1. **Дашборд:** новые пользователи (клиенты/адвокаты) за 24 ч и 7 дней; очередь верификации (размер, возраст самой старой заявки); подписки `trialing/active/past_due`, оценка выручки (число `active` × цена); открытые кейсы; биды за сутки; открытые жалобы, споры и обращения «Не могу связаться».
2. **Верификация:** интерфейс поверх API из файла 3 (очередь, карточка, документы по подписанным ссылкам с вводом причины, решения по лицензиям, запрос информации, отказ, `recheck`, `suspend/restore`).
3. **Пользователи:** поиск по имени, email, телефону, `@username`, id; карточка (роль, статус, профиль, сессии, устройства, кейсы и биды списком, подписка); действия: отозвать сессии, предупредить (`moderation_notice`), приостановить/восстановить (правила 3.4).
4. **Модерация:** раздел 3.
5. **Кейсы:** очередь **споров** (`case_disputes`): просмотр хронологии из `case_journal` и заявленных причин, решение «Закрыть кейс» или «Вернуть в работу» с комментарием (уведомления обеим сторонам, событие `dispute_resolved`); очередь **«Не могу связаться»** (`contact_issue_reports`): решение `confirmed/rejected` с комментарием, счётчик подтверждённых обращений клиента, автоприостановка по порогу (файл 4, раздел 8.4).
6. **Подписки и платежи:** раздел 1.6.
7. **Флаги функций:** список из `feature_flags` с переключателями и процентом раскрытия; для платных сервисов (`stripe_identity`, `persona_verification`, `profile_promotion`, `video_posts`, `auto_bar_check`) перед включением показывается предупреждение «Функция использует платный сервис», а сервер проверяет наличие ключей провайдера и не даёт включить без них. Изменения применяются без релиза (кэш флагов сбрасывается) и пишутся в аудит.
8. **Конфигурация:** редактор значений `app_config` (лимиты, минимальные версии приложения, льготный период, пороги) с валидацией схемой.
9. **Локализация:** список языков, включение/выключение, импорт xlsx/csv (`dry-run` с отчётом: новые/изменённые ключи, ошибки плейсхолдеров, дубли; затем `apply`), экспорт в xlsx (файл 1, раздел 9).
10. **Юридические документы:** версии `terms`, `privacy`, `disclaimer`, `client_contact_sharing` по языкам, публикация новой версии (при смене обязательной версии пользователи при следующем входе подтверждают заново).
11. **Запросы госорганов:** реестр `data_access_requests` (тип, номер, орган, дата, объём), кнопка «Подготовить пакет данных» в рамках объёма запроса, каждая выгрузка пишется в `data_access_log`. Прямого доступа для госорганов в приложение нет (файл 4, раздел 12).
12. **Журнал аудита:** фильтры по администратору, действию, объекту, датам.
13. **Администраторы:** создание, назначение роли, отключение (только `super_admin`), сброс 2FA.

## 3. Модерация

### 3.1 Что модерируется
Посты, комментарии, сообщения (по жалобе), пользователи, кейсы, отзывы (жалобы на отзывы адвокатов, файл 3). Жалобы приходят через `POST /reports` (файл 5).

### 3.2 Очередь жалоб
- Раздел «Модерация» (роль `moderator`): очередь `reports` со статусом `open`, сортировка по давности, группировка по объекту (много жалоб на один объект показываются одной строкой со счётчиком).
- Карточка: объект и его контекст, причина(ы), автор, история нарушений автора.
- Действия (`moderation_actions`): **скрыть** (`hidden`), **удалить** (`removed`), **предупредить автора** (`moderation_notice`), **приостановить пользователя**, **восстановить**, **отклонить жалобу** (`dismissed`). Каждое действие обязательно с причиной, фиксируется в аудите, автор получает уведомление `moderation_notice` (кроме `dismissed`).
- Скрытые/удалённые посты и комментарии исчезают из всех выдач (лента, поиск, профиль); отзыв в статусе `hidden/removed` исключается из рейтинга с пересчётом (файл 3, раздел 7.5).

### 3.3 Автоматическая проверка (реализация `ContentModerationHook`)
Правила (список слов и порогов хранится в `app_config: moderation.*`, редактируется в админке):
- Стоп-слова и спам-шаблоны: `block` (публикация отклоняется) или `hold` (уходит в очередь модератора, автору показывается «Пост на проверке»).
- Повторяющийся текст и массовые ссылки от одного автора: `hold`.
- Порог: 3 подтверждённых жалобы на один объект автоматически ставят его в `hidden` до решения модератора.
Никаких внешних AI-сервисов на этом этапе не подключается.

### 3.4 Санкции к пользователю
- **Предупреждение:** уведомление `moderation_notice`.
- **Приостановка** (`users.status = suspended`, `suspended_reason`): все сессии отзываются, вход блокируется (`ACCOUNT_SUSPENDED`), контент скрывается из выдач. Для адвоката дополнительно действия файла 3 (раздел 2.5). Для клиента: его `open` кейсы переводятся в `archived`, активные биды `rejected_auto`; кейсы `in_progress` остаются.
- **Восстановление:** статус `active`; кейсы клиента остаются в архиве (клиент возвращает сам).
- Апелляций в приложении нет; обращения идут в поддержку по email.

## 4. Безопасность

### 4.1 Транспорт и API
- TLS 1.2+ везде, HSTS, HTTP→HTTPS редирект. **Certificate pinning** в мобильном приложении с резервным ключом и механизмом ротации.
- Заголовки безопасности (`helmet`), CORS только для домена админки, отдельные политики для API.
- Глобальный `ValidationPipe` (`whitelist`, `forbidNonWhitelisted`), ограничение размера тела запроса, таймауты.
- Rate limiting (файл 1, 5) + защита от перебора на всех аутентифицирующих эндпоинтах.
- Защита от SMS-pumping (файл 1, раздел 10.6): лимиты по номеру/IP/устройству, блок подозрительных префиксов, алерт на всплеск стоимости SMS.
- Обязательная проверка целостности приложения (Play Integrity / App Attest) в релизной сборке включается флагом.

### 4.2 Авторизация и доступ к данным
- **Deny by default:** каждый эндпоинт имеет явный guard роли и policy на объект (владелец/участник/доступ по лицензии). Единые политики: `CaseAccessPolicy`, `BidAccessPolicy`, `ConversationAccessPolicy`, `ProfileAccessPolicy`.
- Защита от IDOR: все выборки по `:id` проверяют принадлежность объекта пользователю в самом запросе.
- Клиентские данные (имя, телефон, email) отдаются адвокату **только** через `GET /cases/:id/contacts` с проверкой принятого бида и активной подписки.
- Разделение JWT мобильного приложения и админки (раздел 2.1).

### 4.3 Данные
- Шифрование: диски и бэкапы кластера БД (управляемый CockroachDB Cloud), S3 SSE-KMS, Redis in-transit (TLS) и at-rest, секреты в AWS Secrets Manager (не в репозитории, не в образах).
- Документы верификации: приватный бакет, доступ только по подписанным ссылкам (5 минут), просмотр логируется (файл 3).
- Логи: `pino` с редактированием (redact) полей `phone`, `email`, `authorization`, `refreshToken`, `code`, `body`, `idToken`; Sentry с очисткой персональных данных; в логи не попадает содержимое сообщений и кейсов.
- Пароли не используются (беспарольный вход), OTP хранятся только как HMAC.

### 4.4 Приложение и цепочка поставки
- Flutter release: `--obfuscate --split-debug-info`, отключённая отладка, секреты не в коде (`--dart-define` для публичных ключей).
- Автоматические проверки в CI: `npm audit`, `dart pub outdated`/аудит зависимостей, Dependabot, gitleaks (поиск секретов), CodeQL (SAST), Trivy (сканирование контейнеров). Критические находки блокируют слияние.
- Закреплённые версии зависимостей (lock-файлы), обновления через PR.

### 4.5 Перед запуском
Внешний пентест (API, мобильное приложение, админка), исправление критических и высоких находок, повторная проверка. Юридическая проверка юристом: Terms of Service, Privacy Policy, дисклеймеры, модель подписки в контексте правил рекламы и вознаграждения адвокатов штатов.

## 5. Приватность и жизненный цикл данных

### 5.1 Удаление аккаунта (реализует файл 1, раздел 10.7)
Ежедневная задача находит пользователей с `deletion_requested_at < now() - 14 дней` и выполняет **анонимизацию** в одной транзакции по сущностям + очистку файлов:
- `users`: имя `Deleted`, фамилия `User`, `email`/`phone_e164` = null, `user_identifiers` удаляются, сессии и push-токены отзываются/удаляются, `status = deleted`, `anonymized_at = now()`.
- Файлы: аватар и документы верификации удаляются из S3, `files.deleted_at`.
- Адвокат: `username` заменяется на `deleted_<короткий id>`, био/фирма очищаются, профиль скрыт, подписка Stripe отменяется немедленно (записи `payments` остаются как финансовые).
- Контент: посты адвоката → `removed`, комментарии → автор «Deleted user».
- Чаты: тексты сообщений удалённого пользователя заменяются на `[deleted]` (`body_original`, `body_display`).
- Кейсы: открытые кейсы клиента закрываются, биды отклоняются (`rejected_auto`); кейсы в работе закрываются с событием журнала, контрагент уведомляется.
- `case_journal`, `contact_disclosures`, `auth_events`, `user_consents`, `audit_log` **не удаляются** (хранение 5 лет), ссылаются на обезличенного пользователя.

### 5.2 Выгрузка данных пользователя
«Скачать мои данные» (Настройки, повторная аутентификация): `POST /users/me/data-export` → запись `data_export_jobs` (`type = user_data`), фоновая задача собирает JSON+ZIP (профиль, кейсы, биды, посты, комментарии, лайки, собственные сообщения, согласия, устройства), кладёт в приватный S3, уведомление и письмо со ссылкой (действует 24 часа). Тот же механизм используется для PDF «Истории кейсов» (`type = case_history_pdf`, файл 4, раздел 12, ссылка 10 минут).

### 5.3 Хранение и целостность журнала
- **Ежемесячная задача** удаления записей `case_journal` с `retain_until < now()` под ролью БД `lawbid_retention` (файл 2, раздел 6.3).
- **Ежедневная проверка цепочки хэшей** `case_journal` (по кейсам, изменённым за сутки, и выборочно по остальным); нарушение = критический алерт.
- **Очистка:** истёкшие сессии, OTP, старые уведомления (файл 5, `notifications.retention_days`), просроченные экспорт-файлы.

### 5.4 Запросы госорганов
Процесс: `super_admin` регистрирует запрос в разделе «Запросы госорганов» (тип, номер, орган, объём), готовит пакет данных строго в объёме запроса, каждый доступ фиксируется в `data_access_log`. Данные выдаются вне приложения по официальному каналу. Тексты процесса согласуются с юристом.

### 5.5 Согласия
Учёт согласий в `user_consents` (файл 1, раздел 10.2 H, файл 4, раздел 3.1). Смена версии юридического документа требует повторного принятия при следующем входе. Маркетинговые push/email отправляются только при согласии.

## 6. Инфраструктура

### 6.1 Состав (AWS, управляемые сервисы)
| Компонент | Решение |
|---|---|
| БД | **CockroachDB Cloud** (dedicated, 3+ ноды, multi-AZ), автоматические бэкапы и PITR |
| Кэш, очереди, rate-limit, realtime adapter | Amazon ElastiCache for Redis (кластер, multi-AZ, TLS) |
| Приложение | **ECS Fargate**: сервис `api` (REST + Socket.IO) и сервис `worker` (BullMQ, cron-задачи) из одного Docker-образа, разные команды запуска |
| Балансировка | Application Load Balancer (WebSocket-совместимые таймауты) + AWS WAF |
| Файлы | S3: приватный бакет документов, бакет медиа постов (private + CloudFront), SSE-KMS, версионирование, cross-region replication для документов |
| CDN | CloudFront для медиа и админки |
| Email | Amazon SES (домен с SPF, DKIM, DMARC) |
| SMS | Twilio Verify |
| Push | Firebase Cloud Messaging |
| Секреты | AWS Secrets Manager + KMS |
| IaC | **Terraform** (`infra/`), состояние в S3 + блокировка |
| Логи/метрики/трассировка | CloudWatch Logs и Metrics, OpenTelemetry Collector, Sentry (ошибки), Grafana (дашборды) |

### 6.2 Окружения
`dev` (локально docker-compose), `staging` (отдельный AWS-аккаунт, уменьшенный размер, тестовые ключи Stripe/Twilio), `prod` (отдельный AWS-аккаунт). Данные prod никогда не копируются в staging без анонимизации. Конфигурация только через env/Secrets Manager, схема валидируется при старте (файл 1).

### 6.3 Масштабирование (цели файла 1: 5M+ регистраций, 500k DAU, 5k RPS пик)
- `api` и `worker` масштабируются автоматически: цель по CPU 60%, минимум 2 задачи на сервис в 2 зонах, максимум задаётся в Terraform; отдельные очереди BullMQ (`push`, `email`, `moderation`, `search-index`, `counters`, `cron`) с независимой конкурентностью.
- Stateless API (файл 1), Socket.IO через Redis adapter, счётчики и горячие данные в Redis.
- Пул подключений к БД ограничен на инстанс; транзакции с `withTxRetry` (файл 2).
- Нагрузочное тестирование (раздел 9.4) обязательно до запуска.

### 6.4 Бэкапы и восстановление
- CockroachDB: полный бэкап ежедневно, инкрементальный каждый час, PITR; хранение 30 дней (для ежедневных).
- S3: версионирование, репликация документов в другой регион.
- Redis не является источником правды (потеря допустима, данные восстанавливаются из БД).
- Целевые показатели: **RPO ≤ 1 час, RTO ≤ 4 часа**. Тест восстановления **раз в квартал** с записью результата в `docs/runbooks/restore-drill.md`.
- Перед каждой продовой миграцией схемы проверяется, что свежий бэкап создан.

## 9. Тестирование

### 9.1 Уровни
| Уровень | Инструмент | Требование |
|---|---|---|
| Unit (бэкенд) | Jest | покрытие бизнес-логики ≥ 80% |
| Интеграционные/e2e (бэкенд) | Jest + Supertest + testcontainers | все критические потоки раздела 9.2 |
| Контрактные | OpenAPI + сгенерированный Dart-клиент | сборка падает при расхождении |
| Flutter unit/widget | `flutter_test`, `mocktail` | вся бизнес-логика провайдеров и ключевые виджеты |
| Golden | `flutter_test` | ключевые экраны в светлой и тёмной темах |
| Интеграционные Flutter | `integration_test` | критические пользовательские сценарии |
| Нагрузочные | k6 | раздел 9.4 |
| Безопасность | автотесты + пентест | раздел 9.3 |

### 9.2 Критические потоки (обязательные e2e)
1. Регистрация по телефону/email/Apple/Google, refresh-ротация, «Выйти везде».
2. Онбординг клиента с обязательными подтверждёнными контактами; онбординг адвоката.
3. Верификация адвоката (подача → проверка → одобрение/отказ/докрутка).
4. Создание кейса, показ только адвокатам с нужной лицензией и практикой.
5. Бид → торг (5 раундов) → «Стороны не договорились»; бид → принятие: автоотклонение остальных, выдача контактов, открытие чата; конкурентное принятие.
6. Гейты подписки: без подписки нет бидов, нет контактов; триал → списание → отмена; неуспешный платёж → льготный период → потеря доступа и автоотзыв бидов.
7. Жизненный цикл кейса: напоминание, архив, «Выполнено», автозакрытие, спор.
8. Пост → лайк → комментарий → подписка → уведомления → push.
9. Чат: маскировка контактов до принятия бида, идемпотентность, realtime между двумя инстансами.
10. «История кейсов» с reauth, PDF-экспорт; неизменяемость журнала.
11. Удаление аккаунта: grace period и анонимизация; выгрузка данных.

### 9.3 Тесты безопасности (автоматические)
- Матрица авторизации: для каждого эндпоинта проверка ролей и чужих объектов (IDOR): клиент/адвокат/админ/аноним.
- **Тесты утечки контактов клиента:** ни один ответ API адвокату (кейсы, биды, чаты, поиск, уведомления, история) до принятия бида и активной подписки не содержит имя/телефон/email клиента.
- Тесты маскировки телефонов/email/ссылок (цифры, слова, пробелы, обфускация).
- Токены: истёкший, отозванный, повтор refresh, токен мобильного приложения на `/admin`.
- Загрузка файлов: неверный MIME, подмена расширения, слишком большой файл, вредоносный файл (EICAR).
- Rate limits и защита от перебора OTP.

### 9.4 Нагрузочные тесты (k6, staging с production-размером)
Сценарии: лента, поиск, список кейсов адвоката, отправка бида, чат (сообщения + WebSocket), логин по OTP, вебхуки. Цели: 5k RPS пик, p95 чтения < 300 мс, записи < 600 мс, ошибки < 0.5%, стабильность 1 час. Результаты в `docs/perf/`.

### 9.5 Политика качества
PR не сливается при падении любого теста; flaky-тест исправляется или удаляется в течение спринта; ручные чек-листы приёмки этапов (файлы 1-5) проходятся на реальных устройствах iOS и Android.

- **Приёмка:** токен мобильного приложения не работает на `/admin/*` и наоборот; без 2FA вход невозможен; роль без права получает 403; каждое действие есть в `audit_log`.

### Этап 6.3: Админ: верификация и пользователи
- Интерфейс верификации над API файла 3, раздел «Пользователи» (поиск, карточка, отзыв сессий, предупреждение, приостановка/восстановление по правилам 3.4).
- **Приёмка:** верификатор проходит заявку от очереди до одобрения; просмотр документа требует причины и пишется в аудит; приостановка клиента отзывает сессии и архивирует его открытые кейсы.

### Этап 6.4: Модерация

- **Приёмка:** объект с 3 подтверждёнными жалобами скрывается; скрытый пост пропадает из ленты, поиска и профиля; отзыв со статусом `hidden` пересчитывает рейтинг.

- Очереди и решения раздела 2.3 (п. 5, 11, 12) поверх API файла 4.

### Этап 6.6: Админ: флаги, конфиг, локализации, юридические документы
- Раздел 2.3 (п. 7-10): переключатели с проверкой ключей провайдера, редактор `app_config`, импорт/экспорт переводов (`dry-run/apply`), версии документов с повторным принятием.
- **Приёмка:** включение флага применяется в приложении без релиза; платный флаг нельзя включить без ключей; импорт xlsx с новой колонкой языка добавляет язык; новая версия ToS требует принятия при следующем входе.

### Этап 6.7: Stripe: бэкенд подписки
- Раздел 1.1-1.6: клиенты и подписки Stripe, `start/confirm`, триал 7 дней с картой, `SubscriptionAccessService` (кэш и сброс), вебхуки (проверка подписи, идемпотентность, очередь, перечитывание из Stripe), льготный период, автоотзыв бидов, напоминание за 2 дня, портал, продление подписки админом, защита триала по `card_fingerprint`.

### Этап 6.8: Flutter: подписка и гейты

- **Приёмка (ручной чек-лист):**
  1. Неверифицированный адвокат не может начать триал
  2. Старт триала с тестовой картой, включая 3D Secure
  3. Без подписки: бид, «Написать клиенту» и контакты ведут на экран подписки
  4. Отмена: доступ до конца периода; повторная подписка без триала
  5. Все 5 состояний есть на каждом экране, нет hardcode-строк и цветов
