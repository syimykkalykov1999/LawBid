# «Авто» на «Масштабе» — что почему стоит (14.11, проверено)

Прод на 14.11 ~18:20 по Неваде: людей ноль, а счёт идёт как под нагрузкой (≈ $25/день с 11.11 вместо ≈ $12). Ниже по каждому пункту: причина с доказательством, что исправлено в коде (PR `claude/auto-finish`), что заработает само после выката, и что остаётся владельцу.

## 1. Redis cache.r7g.large не уменьшается (≈ $320/мес)
- **Причина (доказано журналом решений, Logs Insights):** у Redis один узел без копии (`AutomaticFailover disabled`, 1 участник). Каждый 5-минутный проход отвечает `no_failover`: днём менять размер одиночного узла нельзя. Уменьшать можно было только в одном ночном проходе в 03:30 по Чикаго, а 14.11 в 09:30 UTC он попал на выкат (`deploying`). Следующая попытка была только через сутки. 11–12.11 размер не менялся, потому что Redis был занят изменением (`not_available`).
- **Исправлено в коде (в том же `decision.py`, без переписывания):** в ночном окне (01:00–06:00 по Чикаго = 23:00–04:00 по Неваде) каждый 5-минутный проход тоже пробует уменьшить по ночным правилам. Остальные защиты остаются (выкат, разовые задачи, изменение в процессе). Одиночный узел проход по-прежнему никогда не увеличивает. Выкат больше не отнимает целые сутки: через 5 минут будет новая попытка.
- **Пауза при уменьшении:** несколько секунд, до минуты. Очереди и сокеты переподключатся сами.

## 2. База db.t4g.large не уменьшается (≈ $188/мес)
- **Причина (доказано журналом):** каждый проход отвечает `not_multi_az`: днём одиночную базу (без Multi-AZ) не трогают. Единственной попыткой оставался ночной проход в 03:30. Последнее уменьшение было 13.11 в 01:30 PST, после этого — ничего.
- **Исправлено так же:** в ночном окне каждый проход пробует уменьшить по ночным правилам (6 спокойных часов, 6 ч после последнего изменения, все остальные защиты).
- **Пауза:** при смене размера одиночной базы она **недоступна несколько минут**. Поэтому только ночью.
- По сегодняшним цифрам (за 6 ч: соединений до 34, свободно 4,96 ГБ, процессор до 5,25 %) расчёт выбирает **db.t4g.medium**.

## 5. «Свой пул соединений базы (PgBouncer на Fargate) — Не получилось»
- **Что это за запись:** запрос `f758b39f` (Авто: `aws.pgbouncer` вкл → выкл, 13.11 21:33 UTC, запуск 43511676199). Это тот самый сбой 13.11. Применение оборвалось на полпути:
  - `Error: deleting Security Group (sg-09bf3a8b15352b73b) … DependencyViolation` — группу безопасности пула нельзя было удалить, пока на ней висели сетевые карты задач или правило группы базы;
  - `Error: resetting RDS DB Parameter Group (lawbid-prod-postgres16) … ResetDBParameterGroup … 403` — у роли выката нет этого права.
- Сам отчёт о результате получил `401 «Not the infra-apply workflow.»`: база лежала, API не смог прочитать ключи GitHub App и решил, что зовёт «не тот». Скрипт считает 4xx окончательным и повторять не стал, поэтому запрос так и остался «Не получилось».
- **Исправлено в коде:** если ключи не читаются или ключи GitHub недоступны, это теперь ответ **503** («повторите»), а не 401. `scripts/infra/api.sh` повторяет 503 до 15 минут, и запрос закроется. Поддельный или чужой токен по-прежнему 401.
- **Сейчас:** сервис `pgbouncer` работает, 2 из 2 задач (события ECS 14.11 17:18–17:19 CST).
- **Защита от выключения под нагрузкой уже есть и покрывает этот путь** (#1026/#1053):
  - пока у API задан `DB_POOLER_HOST`, «Авто» держит пул включённым (`KEEP_ON … poolerLive`);
  - выключение пула — только с кодом 2FA владельца (`OWNER_CONFIRM_OFF`);
  - автоматический план, который задевает что-то кроме модуля пула и группы базы, отклоняется (`AUTO_SCOPE`).
- **Включение — где риск остаётся (не исправлял: решение владельца по пулу ещё не принято):** у сервиса пула нет `wait_for_steady_state`, а проверка здоровья API (`/health/live`) базу не проверяет. Если пул поднимется, но до базы не достанет, откат выката ECS не сработает. Предложение: `wait_for_steady_state = true` в `infra/modules/pgbouncer` и проверка «пул отвечает SELECT 1» до переключения API.
- **#1027 (минимум 2 сервера API):** слит, менял только `growth.auto.tfvars.json`. Ему нужен только выкат облака (то же применение из админки).

## 6. Тревога `alarm:queue-backlog` «Проблема»
- **Какая очередь:** `cron`. Возраст самой старой задачи был 300 / 3599 / 599 / 599 / 300 с, у `cron-fast` постоянно 59 с. Это ровно периоды расписаний (5 мин, 1 ч, 10 мин, 1 мин), а не настоящее ожидание. Тревога моргала: 17:18, 18:13, 18:18 CST — сработала → прошла.
- **Причина (доказано кодом BullMQ 6.3.9):** когда отложенная задача становится готовой, BullMQ обнуляет ей `delay` (`commands/includes/promoteDelayedJobs.lua:39: HSET jobKey delay 0`). Поэтому наш `waitingAgeSeconds` считал возраст от прошлого запуска. Это же число раздувало сигнал автомасштаба фонового сервера.
- **Исправлено в коде** (`ops-metrics.job.ts`, на месте): берётся большая из двух задержек (`delay` / `opts.delay`) плюс момент запуска из id задачи расписания (`repeat:<имя>:<время>`). Тест: было 3602 → стало 2.

## 8. CloudWatch и ECR при нуле людей (по типам расходов, 13.11)
- **ECR:** `DataTransfer-Out-Bytes` $1,55/день, хранение $0,03/день. Деньги уходят не на хранение, а на скачивание образов **из AWS наружу**. Скорее всего, это проверки при каждом выкате: шаг Trivy и генерация SBOM в `deploy.yml` скачивают оба образа (api и admin) на машину GitHub. Это оценка по устройству процесса, не по журналу скачиваний. Правило очистки образов уже есть и работает (последняя проверка 14.11 04:42): неподписанные — 2 дня, всего 60 последних. **Не менял:** сначала сверить по CloudTrail, кто скачивает.
- **CloudWatch:** $1,66/день = метрики $0,72 + тревоги $0,66 + составные тревоги $0,27. Приём журналов ≈ 0. Хранение журналов 14–30 дней — настроено. Это цена самих тревог и метрик очередей (по 2–3 метрики на каждую из ~20 очередей), а не ошибка.
- SES — по решению владельца не нужен, не трогал.

## Как проверить сразу, не дожидаясь ночи
После выката облака с этим PR (одно применение из админки с 2FA несёт и новый код Lambda) запустить:

```
aws lambda invoke --function-name lawbid-prod-redis-autoscale --cli-binary-format raw-in-base64-out --payload '{"mode":"night","night_now":true}' /tmp/redis.json && cat /tmp/redis.json
aws lambda invoke --function-name lawbid-prod-db-autoscale --cli-binary-format raw-in-base64-out --payload '{"mode":"night","night_now":true}' /tmp/db.json && cat /tmp/db.json
```

- Успех — ответ `{"result": "down", "to": "cache.t4g.micro"}` (база: `"to": "db.t4g.medium"`), строка журнала `"event": "decision", "mode": "night", "action": "down"` и письмо «Redis уменьшен …».
- Флаг `night_now` действует только при ручном запуске; расписания его не шлют. Все остальные защиты и окна спокойствия (Redis 1 ч, база 6 ч — это уже настройки Terraform `*_autoscale_tuning`) остаются.

1. **Масштаб → любой переключатель → «Применить» → код 2FA.** Это одно применение облака: оно выкатывает #1064 (копия базы, OpenSearch), #1027 (2 сервера API) и новый код Lambda из этого PR. Проверить: Масштаб → строки 8 и 9 «Выкл», а у Lambda новая дата изменения.
2. **IAM (только вы):** дать роли `lawbid-prod-github-deploy` право `rds:ResetDBParameterGroup`, иначе любой план, сбрасывающий параметр базы, падает с 403, как 13.11.
3. **PgBouncer «Вкл»:** Масштаб → «Свой пул соединений базы (PgBouncer на Fargate)» → «Вкл» → «Применить» → код 2FA. Что проверить потом:
   - на «Масштабе» строка «Включено», без «Не получилось»;
   - Здоровье системы → «База» зелёная;
   - у сервиса `pgbouncer` 2 задачи;
   - на прод-сайте вход и лента открываются.
   - До этого шага лучше выкатить предложение из пункта 5 (ожидание пула до переключения API).
4. **Ручная проверка «Авто» (кто-то с правом `lambda:InvokeFunction`):** две команды выше. Ожидаемая пауза: Redis — секунды, база — несколько минут.
