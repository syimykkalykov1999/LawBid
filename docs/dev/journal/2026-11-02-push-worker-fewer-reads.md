# 2026-11-02 · push-воркер: на 1:1-сообщение на 2 чтения БД меньше (находка тестера 2)

PR и SHA слияния: допишутся после слияния.

Было (`docs/perf/LOAD_RESILIENCE_2026-11-02.md` §3): воркер 0,5 vCPU разбирал ~26 заданий/с, задание делало до 8 чтений БД (пользователь, участник, сообщение, переключатель «Сообщения», тихие часы, отправитель, файл аватара + его видимость).

Стало (`push-dispatcher.ts`):
- Тихие часы приходят в том же чтении пользователя (`quiet_hours` в `select`, связь внутри одной семьи таблиц, guard `cross-family-include` зелёный) для 1:1, группы и уведомления; отдельный `quietUntil` удалён.
- Переключатель категории (`pushAllowed`) идёт через `BadgesService.mutedCategories`: тот же Redis-кэш настроек, который в этом же задании уже читают значок и переключатели тем (сбрасывается `settingsChanged`). Единый источник правды вместо второго чтения таблицы; звонки получили то же.
- Итог на горячем пути 1:1: −2 чтения БД на задание. Остаются пользователь, участник, сообщение, отправитель, файл аватара + видимость (аватар зависит от зрителя, кэшировать его между получателями небезопасно — не трогали).

Тесты: `push-dispatcher.reads.spec.ts` (нет чтения таблиц настроек/тихих часов; «Сообщения» выкл. из кэша; тихие часы 1:1 и группы откладывают push), существующие 658 тестов notifications+sharding зелёные.

Не проверено: замер заданий/с на стенде. При недоступном Redis `BadgesService.prefs` читает из БД двумя запросами (≈ +1 запрос против прежнего одного), на здоровом пути −2.
