# 2026-11-02 · поиск юристов по имени: частичные индексы только по юристам

Находка прогона на ноутбуке (1000 человек, Postgres 2 CPU): p95 поиска людей ≈ 2,4 с. Причина: запрос кандидатов `users WHERE role='attorney' AND <имя совпало> LIMIT 1000` — планировщик перемножает «10 % юристов» и «N % совпало со словом», ждёт ~20 тыс. строк, считает, что 1000 наберутся быстро, и выбирает seq scan всей таблицы; если слово встречается у клиентов, а у юристов нет («carter» в сидах), скан не останавливается (в GIN-плане — 100 тыс. строк кучи и отброс по роли).
Воспроизведено локально: PostgreSQL 16, 1M users (10 % юристов, имена как в `scripts/ops/admin-load-gen.sql`), те же индексы и те же выражения, что в `nameSql`. EXPLAIN ANALYZE, одна сессия, кэш тёплый:
- «carter»: 375 ms (Seq Scan, 1M строк отброшено) → 0,21 ms; «kim»: 405 ms → 0,19 ms.
- «sofia» (есть и у юристов): 27 ms → 26 ms; «hernandez» (у 100 % юристов — синтетика): 10 ms → 127 ms (Bitmap без раннего останова; на реальных данных имя у ~1 % юристов).
- Несуществующее слово («zorbax»): индекс и раньше, 0,35 ms.
Исправление: `prisma/concurrent/20261110100000_attorney_name_partial_indexes.sql` — три частичных GIN (`full_name_lower`, `name_skel`, `name_cons`) `WHERE role='attorney'`; ~10 % строк, ~+13 % к размеру имён-индексов, существующие индексы остаются. Код запроса не менялся.
Не закрыто: ветка КЛИЕНТОВ того же запроса (`role='client'`) страдает зеркально — слово, которое есть у юристов и нет у клиентов, «hernandez» = 3,1 с на сидах. Частичные индексы по клиентам удвоили бы индексы (90 % строк); в сидах имя жёстко связано с ролью (`g%10`), в проде такой связи нет, поэтому не делаем без реальных данных. Сиды лучше сделать независимыми от роли (имя по `g/10`) — отдельным шагом, чтобы не менять идущий прогон. НЕ проверено: на AWS RDS и под нагрузкой k6 (сначала повторить ступень r1k на 2-CPU Postgres после применения индексов). Squawk локально не ставился (check-migrations прошёл).
