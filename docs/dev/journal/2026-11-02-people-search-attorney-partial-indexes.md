# 2026-11-02 · поиск людей по имени: причина медленных ответов в нагрузочном прогоне — сиды, не индексы

Находка прогона на ноутбуке (1000 человек, Postgres 2 CPU): p95 поиска людей ≈ 2,4 с. Запрос кандидатов `users WHERE role='attorney' AND <имя совпало> LIMIT 1000`: планировщик ждёт ~20 тыс. строк, выбирает seq scan, а совпадений среди юристов нет.
Воспроизведено локально (PostgreSQL 16, 1M users, выражения из `nameSql`): «carter» 375 мс, «kim» 405 мс (Seq Scan). Причина в СИДАХ: в `scripts/ops/admin-load-gen.sql` и `search-load-gen.sql` фамилия бралась как `[1+g%10]`, а юристы — это `g%10=0`, то есть ВСЕ юристы «Hernandez», все остальные имена были только у клиентов (и наоборот для ветки клиентов, там 3,1 с). В проде имя от роли не зависит.
Сиды исправлены: фамилия `[1+(g/10)%10]`, имя `[1+(g/7)%12]` — каждое имя есть у 10 % юристов и 10 % клиентов. Те же замеры на новом распределении (1M, EXPLAIN ANALYZE): юристы 30–37 мс, клиенты 23–28 мс на любое слово, несуществующее слово 0,4 мс; Seq Scan не выбирается.
Пробовали: три частичных GIN `WHERE role='attorney'` (-13 % к индексам) дают на этих данных 13–22 мс вместо 30–37 мс (×2) — не оправдывает три индекса и запись при регистрации; в PR не включены.
НЕ проверено: сам k6 на ноутбуке после смены сидов (ступень `r1k` на Postgres 2 CPU надо повторить; 1M-база должна быть засеяна заново скриптами из репозитория), RDS. Лимит 1000 кандидатов на ветку при частых словах остаётся (~25–35 мс на запрос в одной сессии; под 1000 человек на 2 CPU это может быть всё ещё заметно — смотреть `pgss_top.txt`).
