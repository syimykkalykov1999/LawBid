# 2026-11-02 · поиск людей по имени: два дефекта запроса + честные сиды

Находка прогона на ноутбуке (PR #578): `GET /search/people` читает всю таблицу `users`, p95 ≈ 2,4 с на Postgres 2 CPU. Воспроизведено локально, PostgreSQL 16, 1M users, выражения из `nameSql`; сиды сначала делали имя зависимым от роли (`g%10`), это исправлено, и дефекты остались — значит это продукт, а не сиды.

**Дефект 1 — арм «весь текст ~ всё имя» (`% name_skel`) для ОДНОГО слова.** На коротком слове («will», «visa») GIN при пороге 0,3 отдаёт ~100 тыс. кандидатов на перепроверку: 250–410 мс на запрос, 0,4 мс без арма. Для одного слова арм ничего не добавляет к word_similarity (она не меньше similarity). Для нескольких слов арм остаётся. `name-match.sql.ts` + тест.

**Дефект 2 — LIMIT внутри ветки.** Ветки кандидатов были `SELECT id FROM users WHERE role=X AND <имя> LIMIT 1000`. Планировщик перемножает долю роли на плоскую оценку триграммы (~20 тыс. строк), решает, что 1000 наберутся быстро, и читает всю таблицу, если слова нет: «emily carter» 196 мс Seq Scan → 65 мс (индекс), «sofia zorbax»/«will smith» 0,2–0,4 мс. Ветки теперь `MATERIALIZED` CTE (планируются без LIMIT, LIMIT применяется к результату), `postgres-search.provider.ts`. Цена: слово, которое есть у 10 % пользователей (синтетика), считает все 100 тыс. совпадений (~120 мс вместо раннего останова 25 мс); у реальных имён доля на порядок меньше.

**Сиды** `scripts/ops/admin-load-gen.sql`, `search-load-gen.sql`: имя больше не привязано к роли (`[1+(g/10)%10]`, `[1+(g/7)%12]`). Раньше слово, которого нет у юристов, но есть у клиентов (и наоборот), давало искусственный худший случай.

Как у больших: Instagram/Telegram ищут людей отдельным индексом (префиксы/n-граммы, нормализованные имена, поиск по подписанным/контактам сначала), а не триграммным сканом базы. У нас такой слой есть — `search.engine` (OpenSearch за `SearchProvider`, выключен до роста); Postgres-путь остаётся запасным и должен быть дешёвым, поэтому правим его, а не переписываем.
НЕ проверено: k6 на ноутбуке после этих правок (повторить `r1k` на Postgres 2 CPU, база пересоздана новыми сидами), RDS, интеграционный запуск `people()` на настоящей схеме (проверен эквивалентный SQL на PG16 и юнит-тесты; tsc и jest search зелёные).
