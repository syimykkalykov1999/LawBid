# 2026-11-02 — сигнал «пора готовить вторую базу» (без автопереноса)
- Новая карточка «Рост базы данных» (`shard_growth`) в «Здоровье системы»: размер основной базы и оценка строк больших таблиц пользователей против двух порогов в настройках (`growth.shard_db_gb` = 400 ГБ, `growth.shard_rows` = 1 млрд). Жёлтая с 80 %, красная со 100 % любого из двух. В карточке готовый план «перенести верхнюю половину логических частей»: сколько частей, строк, минут.
- Дёшево: три чтения каталога (`pg_database_size`, оценки `pg_class.reltuples`, `GROUP BY` по `shard_map` на 256 строк), без `COUNT(*)`. Здоровье и так кэшируется общей сводкой.
- Автоперенос НАМЕРЕННО не включён: целевой базы нет (`DATABASE_URL_SHARDS` пуст, это Terraform и секреты), а перенос живых данных людей между физическими базами необратим для владельца. Перенос остаётся кнопкой «Шарды» под step-up; поле `autoMove` всегда `false` и закреплено тестом.
- Что искали: `sharding/move/shard-move.service.ts` (`splitPlan`) — готовый план есть, но он считает `COUNT(*)` по каждой таблице (на большой базе тяжело), поэтому сторож считает ту же оценку по `reltuples` с теми же константами скорости; `partition.growthSignal` и `tableGrowth` в `system-health.service.ts` — образец сигнала, расширен, не дублирован.
- Не проверено: на реальной RDS (порог 400 ГБ подобран по практике одной базы PostgreSQL, не замерен на нашей нагрузке); `packages/api-contract/generate.sh` локально не запускался (нет Dart), значение enum добавлено в `openapi.json`, Dart-клиент и `oasdiff-err-ignore.txt` вручную по образцу `table_growth`, проверит CI.
