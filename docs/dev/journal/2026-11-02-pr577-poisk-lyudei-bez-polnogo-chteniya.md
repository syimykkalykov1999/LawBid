# 2026-11-02 · PR #577 · поиск людей по имени: два дефекта запроса + честные сиды

SHA слияния: допишется после слияния.

Находка прогона на ноутбуке (PR #578, отчёт ноутбучной сессии): `GET /search/people` читает всю таблицу `users`, p95 ≈ 2,4 с на Postgres 2 CPU. Воспроизведено локально, PostgreSQL 16, 1M users, выражения из `nameSql`; сиды сначала делали имя зависимым от роли (`g%10`), это исправлено, и дефекты остались — значит это продукт, а не сиды.

**Дефект 1 — арм «весь текст ~ всё имя» (`% name_skel`) для ОДНОГО короткого слова.** На слове из 4–5 триграмм («will», «visa») GIN при пороге 0,3 отдаёт ~100 тыс. кандидатов на перепроверку: 250–410 мс на запрос, 0,4 мс без арма. Для нескольких слов и для одного слова от 6 букв арм остаётся (там он избирателен, и он ловит опечатки с similarity 0,45–0,6, которые word_similarity при пороге 0,6 пропустит). Цена: для короткого одного слова пары с similarity 0,45–0,6 больше не находятся. `name-match.sql.ts` + тест.

**Дефект 2 — LIMIT внутри ветки.** Ветки кандидатов были `SELECT id FROM users WHERE role=X AND <имя> LIMIT 1000`. Планировщик перемножает долю роли на плоскую оценку триграммы (~20 тыс. строк), решает, что 1000 наберутся быстро, и читает всю таблицу, если слова нет. Теперь одна ветка на роль — `MATERIALIZED` CTE (`nameCandidateCtes`), планируется без LIMIT и использует индексы, внутри потолок `NAME_SCAN_CAP` = 20 000 строк (двухбуквенный префикс «ma» не материализует десятки тысяч: 15 мс против 2 мс у ранней версии с LIMIT; без потолка был бы весь набор). Роль, которая всё равно отфильтруется (`f.role = 'client'` убирает юристов), даёт пустой CTE и не читает таблицу. Замеры на 1M (PG16, сиды из этого PR): «emily carter» 196–413 мс Seq Scan → 65–69 мс (индекс), «sofia zorbax»/«will smith» 36–42 → 0,2–0,5 мс. Слово у 10 % пользователей (синтетика) упирается в потолок 20 000 вместо раннего останова.

**Сиды** `scripts/ops/admin-load-gen.sql`, `search-load-gen.sql`: имя больше не привязано к роли (`[1+(g/10)%10]`, `[1+(g/7)%12]`). Раньше слово, которого нет у юристов, но есть у клиентов (и наоборот), давало искусственный худший случай.

Как у больших: Instagram/Telegram ищут людей отдельным индексом (префиксы/n-граммы, нормализованные имена, поиск по подписанным/контактам сначала), а не триграммным сканом базы. У нас такой слой есть — `search.engine` (OpenSearch за `SearchProvider`, выключен до роста); Postgres-путь остаётся запасным и должен быть дешёвым, поэтому правим его, а не переписываем.
Базовые («до») замеры сняты на тех же новых сидах тем же запросом без правок, поэтому сравнение честное; сами сиды сравнивать со старыми нельзя.
НЕ проверено: k6 на ноутбуке после этих правок (повторить `r1k` на Postgres 2 CPU, база пересоздана новыми сидами), RDS, интеграционный запуск `people()` на настоящей схеме (проверен эквивалентный SQL на PG16 и юнит-тесты; tsc и jest search зелёные).
