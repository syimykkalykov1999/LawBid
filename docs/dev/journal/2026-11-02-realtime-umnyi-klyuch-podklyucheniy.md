# 2026-11-02 · лимит подключений сокетов: считаем человека, не адрес

SHA слияния: допишется после слияния. PR: допишется.

Было: `realtime.max_connects_per_ip_per_minute` считал все новые сокеты с одного адреса. За одним адресом (мобильный оператор CGNAT, офис, суд) живут тысячи людей — один шумный клиент мог отрезать остальных; 10k сокетов с ноутбука упирались в лимит (тест нагрузки 2026-11-02, #578).

Стало (`realtime.gateway.ts`, `overConnectLimits`):
- Токен валиден → считаем человека: `realtime.max_connects_per_user_per_minute` (по умолчанию 60, 0 = выкл.), метрика `ws_user_limited`. Цикл переподключений одного клиента режется на нём.
- Адрес для вошедших — только широкая сетка безопасности: 10 × `max_connects_per_ip_per_minute`, метрика `ws_ip_limited`.
- Токена нет или он негодный — как раньше, по адресу (`max_connects_per_ip_per_minute`).
- Проверка по-прежнему не ждёт рукопожатие и при сбое Redis/настроек пропускает (fail-open).

Как у больших: Telegram, WhatsApp, Instagram считают аккаунт и устройство; адрес защищает только то, у чего нет аккаунта (анонимное рукопожатие).

Не проверено: на реальной нагрузке (s10k на ноуте без снятия лимита адреса теперь должен проходить, если токены разных людей; прогон — у ноутбучной сессии). Устройство пока не отдельный ключ (в токене нет device id): человек считается целиком.
После деплоя: Админка → Настройки → `realtime.max_connects_per_user_per_minute` (сохранённое значение перекрывает умолчание).

Ревью (code-review) нашло и поправлено: ключи Redis разведены (`ws:connect:ip:<адрес>` и `ws:connect:u:<id>`), адрес берётся в ключ только если это настоящий IP (`net.isIP`), иначе подделанный X-Forwarded-For мог бы «выбрать» счётчик чужого человека; демо-сессии считаются по адресу (у демо один аккаунт на многих посетителей); обе настройки читаются одним запросом; описание в Админке. Следствие: при умолчании 120 сетка для вошедших = 1200/мин с адреса (6000 при 600). Счётчик старого вида `ws:connect:<ip>` после деплоя просто истекает за минуту.
