# Боевой тест на AWS — план (пункт 59 владельца, 13.11.2026)

Короткий настоящий тест в AWS, **не больше $50**, который проверяет то, что ноутбук проверить не мог:
серверы Graviton (ARM64) на Fargate Spot, рост **и уменьшение** под нагрузкой (API, фоновые задачи,
PgBouncer, лямбды db-autoscale и redis-autoscale), запасной путь при нехватке Spot, путь
CloudFront / ALB / WAF, настоящие p95 и доля ошибок, и что всё **само вернулось вниз** после.

Статус: **только подготовлено**. Ничего в AWS не создавалось, нагрузка не запускалась.

## 1. Что берём готовое (правило №1)

Не изобретаем: в репозитории уже есть весь конвейер нагрузочных тестов — кнопка GitHub
`Load test` (`.github/workflows/load-test.yml`), отдельная одноразовая копия системы
(`infra/envs/loadtest`, тот же модуль `infra/modules/stack`, что и прод), генераторы k6
(`loadtest/k6`, k6 — Grafana, AGPL-3.0, запускается как готовая программа, код не копируется),
сторож денег (`loadtest/scripts/cost-guard.py`), правило остановки (`loadtest/scripts/guard.py`),
GameDay на AWS FIS (`loadtest/scripts/gameday.sh`), удаление «всегда» и часовой сторож
(`load-test-watchdog.yml`). Боевой тест — это **новый профиль `combat`** этого конвейера плюс
два небольших скрипта (наблюдатель и учения). Отдельной папки `apps/api/k6` в репозитории нет:
всё нагрузочное живёт в `loadtest/`, поэтому новые файлы там же (`loadtest/combat/`).

**Тестовые аккаунты:** только люди, которых скрипт `loadtest/scripts/box/seed.sh` создаёт в базе
**этой одноразовой копии** (≈ 100 000 выдуманных), токены подписывает `loadtest/scripts/mint.mjs`
случайным ключом этой копии. Настоящих пользователей в этой базе нет. Прод не нагружается: k6,
скрипт генератора и workflow трижды отказываются от адреса без `loadtest` в имени.

## 3. Что нужно от владельца ДО запуска (по порядку)

1. **Обновить права тестовой роли** (Terraform/IAM — только владелец): `cd infra/bootstrap-loadtest && terraform apply`.
   Проверено сейчас (только чтение): у роли `lawbid-loadtest-github` подключено **6** политик из 8 —
   нет `fis` и `dns`, и совсем нет прав на **Lambda / EventBridge / Scheduler**. А копия системы с 12.11
   сама создаёт лямбды (запасной путь Spot, VPC endpoints) — без новых прав создание остановится на
   `AccessDenied` **даже у smoke**. Этот PR добавляет политику `lawbid-loadtest-lambdas` (только имена
   `lawbid-loadtest-*`, прод и staging запрещены тем же Deny). Будет 9 политик на роль (предел AWS 10).
2. **Один зелёный `smoke`** (≈ $1.3): кнопка сама не пустит `combat` без зелёного smoke за 3 дня
   (правило ступеней). Smoke ни разу не проходил: последние запуски 02.11 упали на проверке образов
   (теперь образы `lawbid-pgbouncer:1.24.0-3` и `lawbid-clamav:1.4-debian` в ECR есть — проверено).
3. **Решение про общий показатель сокетов** (влияет на прод, см. п. 8): принять, что прод на ≈ 30 минут
   добавит 1–2 сервера API (≈ $0.05), **или** сначала отдельным маленьким PR добавить показателю
   `OpenSockets` / `HeapUsedMb` измерение окружения.
4. **Квоты AWS** (Service Quotas, us-east-1): Fargate On-Demand vCPU и Fargate Spot vCPU — по ≥ 12
   **сверх** того, что занимает прод; EC2 Spot ≥ 8 vCPU. Если не хватит — создание остановится, деньги
   почти не потратятся, сторож всё уберёт.
5. Время запуска: днём по Неваде (например 10:00–16:00), не в ночное окно базы (01:30 по Неваде).

Секреты GitHub уже есть (проверены только имена): окружение `load-test` — `AWS_LOADTEST_ROLE`,
`LOADTEST_CERTIFICATE_ARN`; репозиторий — `AWS_LOADTEST_WATCHDOG_ROLE`, `AWS_REGION`, `ECR_REGISTRY`.

## 4. Как устроен стенд `combat` (как прод, но маленький)

`infra/envs/loadtest/profiles/combat.tfvars`, сверено с `infra/envs/prod/growth.auto.tfvars.json`:

- **ARM64 (Graviton)**, API / фоновые задачи / PgBouncer на **Spot 4:1 + 1 обычный** — как прод;
  лямбда запасного пути Spot включена (`on`).
- Пороги роста API **как на проде**: CPU 60 %, 3 000 запросов в минуту на сервер, 2 500 сокетов на
  сервер; пауза перед ростом 3 мин, перед уменьшением 10 мин; потолок 10 серверов (у прода 100).
- Фоновые задачи: CPU 60 % или очередь; **порог очереди 5 на сервер вместо 50**, чтобы короткий тест
  успел показать «очередь → больше серверов → меньше». Потолок 4.
- PgBouncer: CPU 50 %, 2 … 4 сервера (у прода до 100).
- База: **db.t4g.medium Multi-AZ** (лямбда растит базу днём только Multi-AZ), лямбда db-autoscale
  **включена (`on`)**, потолок для теста db.t4g.large; рост после 2 × 5 мин ≥ 70 % (у прода 3 × 5).
- Redis: **cache.t4g.small** + запасной узел, лямбда redis-autoscale `on`, потолок cache.t4g.medium;
  уменьшение после 15 спокойных минут (у прода 1 час), чтобы спуск был виден внутри теста.
- Возврат со «запасного пути» на Spot через 10 мин (у прода 30).
- WAF на ALB и на CloudFront **включены** (лимит «запросов с одного адреса» поднят, иначе WAF
  заблокировал бы сами генераторы — так было и раньше во всех профилях).

## 5. Сценарий по минутам (нагрузка 66 мин, весь прогон ≤ 2 ч)

Создание ≈ 25 мин (Multi-AZ база), миграции и запуск ≈ 10, заполнение данными ≈ 15, нагрузка 66,
удаление ≈ 15. Жёсткий потолок 2 часа на всё — в `loadtest/profiles.json`.

| Минута | Нагрузка | Что должно случиться | Что это доказывает |
|---|---|---|---|
| 0–6 | 20 зап/с; сокеты растут до 9 000 (2 × 4 500) | — | сокеты держатся через ALB на ARM |
| 6–14 | 20 зап/с; 9 000 сокетов | API +1…2 сервера **по сокетам** (> 2 500 на сервер) | правило сокетов работает само |
| 14–22 | разгон до 450 зап/с | API растёт **по запросам и CPU** (≈ 50 зап/с на сервер → 8–10) | правило запросов и CPU; новые серверы в основном на Spot |
| 22–37 | 450 зап/с | фоновые задачи растут по очереди; PgBouncer по CPU, если дойдёт | очередь и пул |
| 24 | GameDay `ecs`: AWS FIS останавливает половину API | ECS сразу заменяет; ошибок < 1 % | **прерывание Spot** (тот же сигнал SIGTERM) не роняет сервис |
| 26 | учение: redis-autoscale `force` → cache.t4g.medium | смена размера Redis онлайн через переключение на запасной узел | рост Redis под нагрузкой без простоя |
| 30 | учение: лямбде Spot отдаём **точное событие AWS** «нет места на Spot» для API | API переходит на обычный Fargate (плавная замена, под нагрузкой) | **запасной путь Spot** |
| ≈ 40–45 | — | сама же лямбда (тик 5 мин) возвращает API на Spot | путь обратно на Spot |
| 37–39 | падение до 10 зап/с, сокеты закрываются | — | — |
| 40 | учение: db-autoscale `force` → db.t4g.large | Multi-AZ: сначала запасная копия, потом переключение ≈ 1 мин | рост базы и цена этой минуты в ошибках |
| 39–66 | 10 зап/с (хвост) | API, фоновые задачи, PgBouncer **уменьшаются до минимума**; Redis **сам** уменьшается обратно до cache.t4g.small | **спуск вниз** |
| 62 | статусы лямбд + ночная проверка базы | ответ базы «не ночь» | правило владельца: база уменьшается только ночью после 6 спокойных часов |

Если база сама наберёт ≥ 70 % CPU 10 минут на 450 зап/с — она вырастет **сама** раньше учения, тогда
учение ответит «уже растёт / пауза» — это тоже результат. Довести базу до 70 % специально, большими
размерами, не планируем: цель — доказать механизм, а не размер (размеры — профили u1k/u10k).

## 7. Жёсткие правила остановки

| Правило | Кто следит | Что делает |
|---|---|---|
| Ошибок > **1 %** за последние 60 с (не меньше 200 запросов) | `guard.py` на каждом генераторе + порог k6 | останавливает нагрузку |
| p95 > 2 с за последние 60 с | `guard.py` + k6 | останавливает нагрузку |
| 5xx на ALB > **1 %** за 2 мин (не меньше 500 запросов) | `combat-watch.py` (CloudWatch) | отменяет прогон → стенд удаляется |
| База или Redis теста удаляются / пропали / сломаны | `combat-watch.py` | отменяет прогон → стенд удаляется |
| Потрачено ≥ **$40** (живой подсчёт того, что запущено) | `cost-guard.py`, `confirm_cost=40` | отменяет прогон → стенд удаляется |
| 2 часа на весь прогон | workflow + генераторы | нагрузка не стартует / останавливается |
| Любая данные-часть **прода** | IAM: явный Deny на всё с тегом `Project=lawbid` (rds, elasticache, ecs, lambda, …) | роль физически не может тронуть прод |

После любой остановки: `terraform destroy` три попытки → удаление по тегу → проверка «ничего не
осталось» → часовой сторож удаляет всё старше 4 часов.

## 8. Важная находка: общий показатель с продом

Правила роста по сокетам и по очереди читают показатели `LawBid/Runtime OpenSockets {Service=api}`
и `HeapUsedMb {Service=worker}` **без измерения окружения** (комментарий в `infra/modules/ecs/main.tf`
это признаёт). Значит, пока идёт тест:
- 9 000 сокетов теста поднимут **среднее** по серверам прода + теста → прод может добавить 1–2
  сервера API на ≈ 30 минут (≈ $0.05) и потом сам их убрать;
- среднее на сервер в тесте будет ниже (прод «разбавляет») — поэтому сокетов 9 000, а не 6 000;
- для фоновых задач прод увидит «больше серверов» → может только уменьшиться (у прода минимум 1).
Наблюдатель записывает действия автомасштабирования прода (только чтение), отчёт их покажет.
Починка (отдельно, не в этом PR): добавить к этим показателям измерение `Env`.

## 9. Как подтверждаем спуск вниз

- `combat-watch.py` каждые 30 с пишет таблицу: сколько серверов API / фоновых / PgBouncer
  (сколько из них на Spot, какая стратегия), размер базы и Redis, доля 5xx. В конце в отчёт запуска
  (Summary) добавляется таблица: **старт → пик (когда) → конец, вырос ли, вернулся ли (когда)**,
  смена Spot → обычный → Spot.
- Ждём: API, фоновые и PgBouncer вернулись к минимуму к минуте ≈ 60–66 (15 мин «тишины» у AWS +
  10–15 мин паузы); API снова на Spot к ≈ 45; Redis снова cache.t4g.small к ≈ 60.
- База **не** уменьшится в тесте — так задумано владельцем (только ночью, 6 спокойных часов); отчёт
  покажет ответ лямбды «не ночь». Стенд удаляется вместе с базой.
- После удаления: шаг «PROOF — nothing tagged lawbid-loadtest is left»; вручную:
  `loadtest/combat/teardown.sh` (только чтение) и `loadtest/combat/teardown.sh --prod-check`
  (действия автомасштабирования прода за 3 часа).
- Через сутки: Cost Explorer по тегу `Project = lawbid-loadtest`.

## 10. Чего этот тест честно НЕ докажет

- Настоящую нехватку Spot у AWS заказать нельзя — даём лямбде **ровно то событие**, которое шлёт AWS
  (`SERVICE_TASK_PLACEMENT_FAILURE` на `FARGATE_SPOT`; проверено настоящим разборщиком лямбды).
- Прерывание Spot: FIS останавливает задачи сигналом SIGTERM, как Spot, но без 2-минутного
  предупреждения.
- Уменьшение базы (ночь + 6 часов) — только ответ лямбды.
- API через CloudFront (прокси веб-версии) — нужен настоящий DNS; тест идёт в ALB напрямую,
  CloudFront проверяется на файлах веб-версии.
- Автовключение WAF при атаке и рост до 100 серверов — не в этом тесте.

## 11. Как запустить (когда п. 3 выполнен)

```
loadtest/combat/run.sh            # бесплатная проверка на Маке, в AWS ничего
loadtest/combat/run.sh --start    # просит GitHub запустить combat, $40, gameday=ecs
```
Дальше на странице запуска: таблица цены → **Review deployments → load-test → Approve and deploy**.
Через ≈ 2 часа: отчёт в Summary и в Artifacts. Если что-то осталось:
`loadtest/combat/teardown.sh --sweep <RunId>`.
