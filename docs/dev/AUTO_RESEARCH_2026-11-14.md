# Как крупные площадки меняют размер базы и кэша (исследование 14.11)

Вопрос владельца: как сделать, чтобы «Авто» само росло и уменьшалось, дёшево сейчас (0 людей) и надёжно потом. Ниже — четыре подхода, сравнение с нашим и что из них взять. Цены — us-east-1, по открытым страницам AWS и обзорам 2025–2026 годов (ссылки внизу). Перед покупкой их стоит сверить с калькулятором AWS.

## Четыре подхода

| | Как растёт и уменьшается | Простой при смене | Цена при 0 людей | Цена потом |
|---|---|---|---|---|
| **A. Наш: своя автоматика размера** (Lambda + лесенка размеров, `decision.py`) | Вертикально: размер узла, по метрикам, с окнами спокойствия и защитами | Redis: секунды. База без Multi-AZ: несколько минут, поэтому ночью | Redis t4g.micro ≈ $12 + база t4g.micro ≈ $12 (без копий) | Растёт по лесенке до потолка денег |
| **B. AWS Application Auto Scaling** (ElastiCache: шарды и реплики; Aurora: реплики для чтения) | Горизонтально: число реплик или шардов по целевой метрике (target tracking). **Размер узла сам не меняет** | Нет: добавляется или убирается копия | Нужен минимум 1 узел и, для реплик, Multi-AZ, то есть ≥ 2 узла | Хорошо при большой равномерной нагрузке |
| **C. Aurora Serverless v2** (база) | Ёмкость в ACU меняется сама, за секунды, без простоя; с конца 2024 умеет 0 ACU (автопауза) | Нет. После паузы первое соединение ждёт секунды (в обзорах до ~15 с) | Пауза — $0 за вычисления. Но наш API, задания по расписанию и проверки ходят в базу каждую минуту, поэтому пауза почти не наступит; держит ≥ 0,5 ACU ≈ $44/мес | ≈ $0,12 за ACU-час; при росте дороже обычного узла того же размера |
| **D. ElastiCache Serverless (Valkey)** (кэш) | Сам, без размеров и без простоя | Нет | Пол ≈ $6/мес (100 МБ) + оплата за каждую команду (ECPU) | Очереди BullMQ шлют много мелких команд; при нагрузке может выйти дороже узла |

## Что делают крупные
- **Нагрузку растят горизонтально, а не размером:** реплики для чтения, шарды. Так делают AWS Application Auto Scaling, Aurora replica auto scaling, Netflix (EVCache — много узлов) и GitHub (MySQL с репликами и шардами).
- **Размер узла меняют редко и при запасе:** с Multi-AZ или копией, переключение на копию (failover) за секунды. Stripe и GitHub пишут о заранее спланированной ёмкости и плавном переключении, а не о ночном уменьшении. Это из их открытых инженерных статей; точных порогов они не публикуют.
- **Уменьшают осторожно (scale-in protection):** AWS ElastiCache сжимается, только когда метрика ниже 75 % цели, по одному шагу, с паузой 15 минут по умолчанию (на рост — 10 минут). Растут быстро, сжимаются медленно.
- **Запланированное масштабирование (scheduled scaling):** известный тихий час заранее — это то же, что наше ночное окно.

## Сравнение с нашим
- **Наш подход A похож на AWS там, где это важно:** цель с запасом (target tracking: идём сразу к самому маленькому размеру, где пик помещается с запасом), паузы между изменениями (cooldown), рост быстрый, уменьшение медленное, ночное окно.
- **Чего у AWS нет, а у нас есть:** смена размера одного узла. При 0 людей это самое дешёвое: один маленький узел без копии.
- **Где мы слабее:** простой базы без Multi-AZ на несколько минут при смене размера. Поэтому уменьшение и рост одиночного узла — с высоким порогом и в окне, где людей нет.

## Рекомендация
1. **Сейчас (0 людей) оставить наш подход A.** Один маленький узел Redis и одна маленькая база — самое дешёвое (≈ $24/мес на двоих против ≈ $50 и больше у C+D), и он теперь сам уменьшается и растёт.
2. **Взять у AWS:**
   - сжатие только при запасе и по одному решению за паузу (у нас есть: окно спокойствия и `down_cooldown_h`);
   - рост быстрее, чем сжатие (есть; для одиночного узла рост после 30 минут перегрузки — PR #1097);
   - запланированное окно (есть; теперь часы окна — настройка, см. ниже).
3. **Когда придут люди** (база выросла до t4g.large или дольше 1–2 ч в день держится выше 50 % процессора):
   - включить Multi-AZ базе и копию Redis — тогда смена размера проходит за секунды, днём;
   - для чтения — реплики (они уже есть, «Авто» их добавляет и убирает).
4. **Aurora Serverless v2 и ElastiCache Serverless — не сейчас.** Пересмотреть при неровной нагрузке (резкие всплески днём, пусто ночью), когда оплата за ACU или ECPU выйдет дешевле лесенки. Переход — отдельная работа (новый кластер, перенос данных).

## Окно для проверки сразу, без ожидания ночи
- Часы окна стали частью той же настройки Terraform `redis_autoscale_tuning` / `db_autoscale_tuning`: `night_start_h`, `night_end_h` (часы `NIGHT_TZ`, по умолчанию America/Chicago; конец не входит в окно; окно может переходить через полночь).
- Для проверки, например, в 19:00 по Чикаго: `{"night_start_h": 19, "night_end_h": 21}` в обоих tuning, потом применение. Через ≤ 5 минут проход пробует уменьшить.
- После проверки вернуть `{"night_start_h": 1, "night_end_h": 6}` (или убрать ключи) тем же применением.
- Выключатель роста одиночного узла в tuning задаётся числом: `{"single_node_up": 0}` (tuning — карта чисел).
