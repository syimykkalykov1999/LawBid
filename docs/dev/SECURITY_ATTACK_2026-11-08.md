## СРЕДНИЕ

### M1 — Нет блокировки аккаунта при переборе пароля + вход без App Check
**Что может злоумышленник:** имея много IP (ботнет, дешёвые прокси), перебирать
пароль одного аккаунта практически без потолка. Каждый IP получает 10 попыток в
час по этому аккаунту и 40 в час всего; счётчик «60 ошибок на аккаунт» тратится
ТОЛЬКО после неудачной проверки, поэтому правильный подбор в него никогда не
упирается. Вход `/auth/password/login` не помечен `@RequireAppCheck`, значит боту
не нужна аттестация приложения.
**Чем доказано:** `apps/api/src/modules/auth/password-auth.service.ts:109` (метод
`login`), счётчик `pwd-login-fail` тратится на строке 141 — внутри ветки
`if (!user || !ok)`, уже ПОСЛЕ `passwords.verify` (строка 134). Маршрут —
`apps/api/src/modules/auth/auth.controller.ts:507` (`@Post('password/login')`),
декоратора `@RequireAppCheck()` нет.
**Причина:** сознательный выбор («правильный вход владельца никогда не
блокируется»), но он убирает блокировку на уровне аккаунта.
**Что уже смягчает:** scrypt N=2^16, проверка пароля по списку частых и по базе
утечек (HIBP) при установке, минимум 8 символов, одинаковый тайминг для
несуществующего аккаунта.
**Минимальная починка (OWASP «Blocking Brute Force», device-cookie):** читать
счётчик неудач ДО проверки; после N неудач отказывать входам с незнакомых
устройств/IP (у которых нет прошлой успешной сессии на этом аккаунте — таблица
`Session`, `device_id`); знакомые устройства работают, владельца не запирает.
Плюс добавить `@RequireAppCheck()` на вход (эффект появится в режиме enforce, см. M5).
**Безопасно ли чинить до релиза:** да, серверно и маленько. Часть с App Check
даст эффект только после перевода App Check в enforce.

### M2 — Ассистент без обязанностей читает контакты клиента (ПОЧИНЕНО в ветке)
**Что может злоумышленник:** ассистент, чьё членство активно, но обязанностей
выдано ноль (или только «звонки»), вызывает `GET /cases/:id/contacts` и получает
имя, телефон (E.164), email и способ связи клиента по каждому выигранному
адвокатом делу.
**Чем доказано:** `apps/api/src/modules/cases/contacts/case-contacts.controller.ts`
— у контроллера не было ни `@RequiresDuty`, ни `@AttorneyOnly`.
`apps/api/src/modules/auth/guards/jwt-auth.guard.ts:192-237` подменяет ассистента
на личность адвоката и блокирует маршрут, только если на нём есть метка
`ATTORNEY_ONLY` или `REQUIRES_DUTY`; без метки маршрут разрешён.
**Причина:** защита в этом гварде — «разрешено, если нет метки» (fail-open для
недекорированных маршрутов).
**Починка:** навесил `@RequiresDuty('cases')` на весь контроллер + тест в
`assistant-gates.spec.ts`. Коммит `667c66ad7` в ветке `claude/security-fixes`
(НЕ запушено).
**Безопасно ли до релиза:** да. Чисто добавочная метка, как у остального
рабочего пространства дела.

### M3 — Подмена содержимого файла после всех проверок
**Что может злоумышленник:** загрузить безобидный PDF/DOCX/картинку, дождаться
прохождения confirm + антивируса, затем повторно использовать ту же ссылку
загрузки и перезаписать объект. Новые байты должны совпасть по размеру и
Content-Type, но внутри может быть что угодно (PDF с JS, DOCX с макросами,
вредонос). Вторая сторона дела/чата скачает это как «чистый» файл. Проходит мимо
проверки магических байт, `dangerousContent`, совпадения SHA-256 и ClamAV.
**Чем доказано:** `apps/api/src/modules/files/files.service.ts:517` (`confirm`)
хранит ключ загрузки как финальный (`s3_key: intent.key`, строка 599) — объект
остаётся по ключу, в который клиент ещё может писать, пока жива presigned-ссылка
(TTL, `modules/files/files.policy.ts`). Скан перечитывает объект один раз и не
сверяет повторно SHA-256, документы не переупаковываются, поэтому подмена после
скана больше не видна.
**Минимальная починка (OWASP File Upload Cheat Sheet — хранить под именем, которое
пользователь не контролирует):** в `confirm()` скопировать объект
`CopyObjectCommand` (AWS SDK, Apache-2.0) на серверный финальный ключ, записать
его в `s3_key`, удалить ключ загрузки, хэшировать и проверять уже скопированные
байты. Альтернатива (только для PUT): подписать `If-None-Match: *` в PUT и
срезать TTL до ~60 с; копия закрывает и POST-путь.
**Безопасно ли до релиза:** да, но это заметнее: правка в files.service + обёртке
хранилища, нужно обновить тесты confirm/scan. Готовить отдельно, с владельцем.

### M4 — Ассистент без обязанностей читает финансы адвоката
**Что может злоумышленник:** тот же ассистент без обязанностей читает
`GET /payments/history`, `/payments/summary`, `/payments/:id`,
`/payments/:id/receipt.pdf`, `/payments/export.csv` (вся история платежей
адвоката с именами клиентов), `/payout-account`, `/cases/:id/payments`,
`/cases/:id/payment-requests`; может `POST /payment-requests/:id/cancel` и создать
запрос на оплату.
**Чем доказано:** `apps/api/src/modules/case-payments/case-payments.controller.ts:70`
(`@Controller()` без метки обязанностей). Перевод денег уже защищён
(`assertNotAssistant` в `case-payments.service.ts`), но чтения — нет. Комментарий
`modules/auth/assistant/assistant-context.ts` прямо говорит, что ассистенты
«никогда не используют биллинг», то есть код расходится с задумкой.
**Минимальная починка:** навесить на класс `@AttorneyOnly()`. Если ассистент всё
же должен выставлять счета — тогда только маршруты payment-request пометить
`@RequiresDuty('cases')`. Это продуктовое решение (контроллер смешанный, в нём
есть и клиентские `payments/settings`, `payments/quote`), поэтому в ветку НЕ
закоммичено — нужно слово владельца.
**Безопасно ли до релиза:** да (добавочная метка), но подтвердить, что
приложение не ждёт от ассистента выставления счетов.

### M5 — App Check / Turnstile по умолчанию только логируют (конфиг)
**Что может злоумышленник:** пока режим — умолчательный `monitor`, скрипт зовёт
платные SMS-маршруты (`otp/request`, `password/reset/request`) и `phone/status`
без аттестации приложения — накрутка расходов/SMS-pumping.
**Чем доказано:** `apps/api/src/modules/auth/app-check/app-check.guard.ts:41-52,126`
— умолчание `'monitor'`, в этом режиме запрос всегда пропускается.
**Что ещё смягчает:** на номер 5/час и 10/день + кулдаун и дневной потолок; на IP
10/час; на устройство 10/час; гвард против SMS-pumping по префиксу; общий
бюджет расходов; только US-направления.
**Починка:** перевести `security.app_check.mode`/`security.turnstile.mode` в
enforce в админке, когда старые сборки уйдут. Решение владельца/админа.
Текущее прод-значение из кода не видно (настройка в БД).
**Безопасно ли до релиза:** да, это настройка.

## НИЗКИЕ

- **L1 — DoS на общей очереди хэширования.** Поток запросов на вход с многих IP
  забивает общую scrypt-очередь (конкуренция 4, потолок 200 на процесс), тогда и
  честные входы/сбросы получают 429. `apps/api/src/modules/auth/services/password.service.ts:71-110`;
  `password-auth.service.ts:134` (verify по dummy-хэшу и для несуществующих).
  Починка — та же, что M1 (App Check/Turnstile перед входом + бюджет на эндпоинт).
- **L2 — Прочие маршруты, открытые ассистенту без обязанностей.**
  `GET /bids/:id` (`modules/cases/case-bids/bid-detail.controller.ts:33`),
  `POST /cases/:id/conversation` (`modules/cases/mine/mine.controller.ts:107`),
  `GET /users/me/bids`, `/users/me/work`, saved-items, `GET /cases/:id/comments`
  и ответы/лайки/шеры (`case-comments.controller.ts`), `GET /invites/:id` +
  cancel, `GET /files/:id` и `/files/:id/views`. Починка — навесить
  `@RequiresDuty('cases')`/`@AttorneyOnly()`/`@RequiresDuty('chats')`. Коренная
  починка класса — сделать гвард «запрещено по умолчанию»: ассистенту открыты
  только явно помеченные обязанностью маршруты и `@AssistantSelf`. Это большее
  поведенческое изменение, трогает много контроллеров — сначала прогнать полный
  e2e, поэтому в ветку не вошло.
- **L3 — Контакты открываются через личный чат без принятой ставки (дизайн).**
  Клиент пишет `POST /conversations/direct` адвокату; после ответа
  `contacts_unlocked=true` (`modules/chat/chat.service.ts:1078-1125`), маски
  снимаются, можно слать файлы; в чатах дела голосовые всегда без маски
  (`chat.service.ts:1217`). Это выбор владельца (OQ-043 «запросы на сообщение»),
  но формально нарушает правило «контакты только после принятия ставки».
  Если правило строгое — для пары адвокат↔клиент держать `contacts_unlocked=false`
  без принятой ставки. Решение владельца.
- **L4 — Перебор телефонов адвокатов через синхронизацию контактов.**
  `POST /contacts/sync` принимает несолёные SHA-256 от номеров E.164; адвокаты
  всегда «находимы», ответ даёт userId/имя/username. Аккаунт с подтверждённым
  телефоном может проверять ~2×лимит новых номеров в день.
  `modules/contacts-sync/contacts-sync.service.ts:45-50`. Смягчено дневными
  HLL-потолками и алертом. Опц. починка: требовать подписку/возраст аккаунта,
  снизить дневной потолок.
- **L5 — Неподтверждённые публичные загрузки ненадолго доступны публично.**
  На публичном медиа-бакете R2 объект отдаётся по `publicBaseUrl/<key>` сразу
  после PUT — до confirm/скана/модерации (`modules/files/storage/s3-storage.service.ts`).
  Content-Type заблокирован на картинку/видео (не XSS). Починка — вместе с M3:
  грузить в приватный staging-префикс, копировать в публичный после скана.
- **L6 — DoS по памяти на confirm/scan.** `storage.read` грузит весь объект в
  память (до 100 МБ), зовётся из confirm и скана; много параллельных confirm с
  разных аккаунтов могут выесть память. Починка — стримить хэш/сниф первых байт
  или семафор. Смягчено лимитом presign на пользователя/час.
- **L7 — Пользователь может сам выбрать роль «assistant».**
  `modules/users/dto/profile.dto.ts` разрешает `'assistant'` в `@IsIn`. Влияния
  не найдено: без места (seat) гвард не даёт прав адвоката. Починка — убрать
  `'assistant'` из DTO (роль ставится кодом приглашения). Проверить приложение
  перед правкой.
- **L8 — SMS уходят в большем числе случаев, чем «регистрация + забыл пароль».**
  Кроме (a) регистрации и (b) сброса пароля, код шлётся при (c) переаутентификации
  по SMS на свой номер (`auth.service.ts`), (d) добавлении/смене телефона-контакта
  (`POST /users/me/contacts/request`), (e) привязке нового телефона как способа
  входа. Все — со своими лимитами. Нюанс: `callerId` в (c) берётся из
  `verifyAccessToken` без проверки блэклиста — отозванный токен младше 15 минут
  ещё может инициировать SMS на свой же номер (только расход). Решение владельца:
  либо принять (c)-(e) как часть правила, либо увести переаутентификацию на пароль/
  passkey. Код трогает экраны (UI заморожен) — нужно слово владельца.
- **L9 — Задачи/тайм-записи дела привязаны только к `case_id`.**
  `case-workspace.service.ts` (`taskOf`) и `case-billing.service.ts` (`openEntry`)
  скоупят строки по `case_id`, не по адвокату. Если дело когда-нибудь перейдёт
  новому адвокату, он сможет править задачи/записи прежнего. Починка — добавить
  `attorney_id` в where. Сейчас дела не переназначаются, поэтому низко.
- **L10 — Вебхук Bunny может принять токен-из-URL (конфиг).**
  `POST /webhooks/bunny/:token` принимается по токену в пути, если Read-Only-ключ
  Bunny не сохранён в админке (`modules/posts/bunny-webhook.controller.ts:104-113`).
  Токен попадает в логи ALB. Влияние малое (хэндлер только перечитывает видео из
  Bunny). Починка — операционная: сохранить ключ в проде, чтобы работала HMAC.

## Уже закрыто на `origin/main` (помощники читали отставшую копию 78c1d7e)

- **Гонка ротации refresh-токена.** На `origin/main` уже есть «один победитель»
  (S14-3): `tx.session.updateMany({ where:{ id, revoked_at: null }})`, и при
  `count !== 1` транзакция откатывается — два параллельных обновления одного живого
  токена больше не раздваивают цепочку. `apps/api/src/modules/auth/services/session.service.ts:302-329`.
- **Переклейка устройства при refresh.** `device_id` цепочки не переписывается
  вызывающим refresh (S14-4), там же.

Важно для координатора: три помощника анализировали рабочую копию
`/Users/sima/Desktop/LawBid` (SHA 78c1d7e), которая отстала от `origin/main`.
Я перепроверил ключевые находки прямо на `origin/main` (86d1cee1f): M1–M4 и M2
подтверждены на main; гонка ротации — нет, на main починено.

## Проверено и сделано верно

- **Подписи вебхуков:** Stripe (`stripe.webhooks.constructEvent` по сырому телу,
  секрет из SecretsService/env, идемпотентность по event id), LiveKit
  (`WebhookReceiver.receive`, JWT + SHA-256 тела), Bunny (HMAC-SHA256 по сырому
  телу, `timingSafeEqual`). Twilio — только исходящие SMS, входящего вебхука нет.
- **SSRF в превью ссылок закрыт** (`modules/link-preview/safe-fetch.ts`,
  `common/net/private-address.ts`): только https:443, запрет литеральных IP,
  `.local/.internal`, проверка КАЖДОГО разрешённого адреса (защита от DNS-rebinding),
  блок 169.254/10/172.16/192.168/127/CGNAT/IPv4-mapped/6to4/::1/fc../fe80/NAT64,
  перепроверка каждого редиректа, таймаут 5 с, потолок 1 МБ, только HTML.
- **SQL-инъекций нет:** все `$queryRawUnsafe`/`Prisma.raw` — на константах или
  проверенных идентификаторах, пользовательский текст всегда как параметр.
- **Загрузки валидируются серверно:** тип по allowlist на назначение, размер —
  `content-length-range` в политике S3 + проверка HeadObject, магические байты =
  заявленному типу, `dangerousContent`, ClamAV, переупаковка картинок; SVG/HTML
  запрещены; ключи строит только сервер (нет path traversal, нет IDOR по ключу).
- **OTP:** 6 цифр из `crypto.randomInt`, хранится только HMAC, TTL 600 с, 5 попыток
  атомарно (Lua), лестница блокировок, раздельные namespace по назначению. Перебор
  кода непрактичен.
- **Пароли:** scrypt N=2^16 с рехэшем, dummy-хэш для неизвестных (анти-энумерация),
  скрининг по утечкам/частым при установке; смена пароля рвёт прочие сессии.
- **Сессии/JWT:** refresh — 32 байта, хранится sha256, ротация с детекцией повтора
  (рвёт цепочку), лимиты на цепочку/IP. Access HS256 с issuer/audience/`typ`,
  TTL 900 с, блэклист отозванных в Redis. Reauth — своя аудитория, одноразовый
  (SET NX), привязан к sub+sid. Веб-cookie — HttpOnly/Secure/SameSite=Strict +
  проверка origin/заголовка от CSRF.
- **Admin:** отдельный JWT (`aud=lawbid-admin`), токен пользователя даёт 401; роли
  deny-by-default; TOTP одноразовый; тикет 5 попыток, расходуется атомарно.
- **Passkeys** (`@simplewebauthn/server`): челленджи одноразовые, origin из
  allowlist, счётчик подписи, привязка reauth к user+sid.
- **Настройки сервера:** helmet (HSTS в прод/стейдж, CSP строгая вне доков),
  строгий CORS с явными origin и credentials, `ValidationPipe` whitelist +
  forbidNonWhitelisted + transform, лимит тела 256 КБ (contacts/sync и вебхуки —
  свои), Swagger выключен в проде, `trust proxy` по числу хопов.
- **Секреты:** `npm audit` — 0 уязвимостей; gitleaks по исходникам — 10 срабатываний,
  все ложные (тестовые фикстуры в `*.spec.ts` + регэксп валидации
  `FCM_PRIVATE_KEY` в `config/env.schema.ts:481`). CI применяет `.gitleaksignore`,
  где они и погашены.

## Что НЕ проверялось и почему
