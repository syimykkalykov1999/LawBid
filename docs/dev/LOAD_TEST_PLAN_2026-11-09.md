# Нагрузочный тест на AWS — план и цена (пункт 11 владельца, 2026-11-09)

> **Цена до запуска:** вся лестница **smoke → u1k → u10k → u100k ≈ $33** (верхняя граница **$50**,
> оценка по прайсу AWS ±30 %). С запасом на один повтор любой ступени — **до $100**.
> Порог расходов **$450** трогать не обязательно, если в месяце осталось ≥ $150 запаса
> (`scripts/perf/loadtest-budget-brake.sh check`); если запаса меньше — поднять до $600 на время
> теста и **вернуть $450** сразу после (команды печатает тот же скрипт, применяет владелец).
> В этом PR ничего не создано и не запущено в AWS: только план, профили и скрипты.

## 1. Коротко

- Тест идёт **не на боевой системе**, а на **точной копии** (та же инфраструктура из Terraform,
  тот же образ API), которую кнопка в GitHub создаёт на 1–1,5 часа и **сама удаляет**. Так уже
  решено и построено 24.10 (`docs/runbooks/LOAD_TEST.md`): три независимых запрета грузить
  боевые адреса (workflow, скрипт генератора, сам k6). Причина простая: прод сейчас на
  `db.t4g.micro` / `cache.t4g.micro` (tfvars владельца) и на нём 10 000 человек онлайн
  положат базу вместе с живыми пользователями, а копию — не жалко.
- Три ступени по заказу владельца: **1 000 → 10 000 → 100 000 человек онлайн**, каждая
  **15 минут нагрузки**, следующая только после зелёной предыдущей (ворота в workflow).
- Цели (SLO): **p95 ответа API < 300 мс, 0 ошибок 5xx, ни одной тревоги**. Авто-стоп: ошибок
  > 5 % или p95 > 2 с в течение 60 с → нагрузка останавливается, отчёт собирается, копия
  удаляется. Денежный сторож: при достижении суммы `confirm_cost` запуск отменяется.
- Генераторы нагрузки — машины EC2 Spot **в той же сети** (трафик внутри региона $0.01/ГБ, а не
  $0.09 наружу), управляются через SSM, без SSH. Инструмент — бинарник **Grafana k6 2.3**
  (AGPL → используем как программу, не копируем код; сценарии наши), как и было.

## 3. Три ступени

«Человек онлайн» = 1 виртуальный пользователь k6: действие из смеси, пауза 1–3 с, своё
соединение сокета. По замерам на ноутбуке (28.10, 02.11) один человек онлайн ≈ **0,5 запроса/с**.

| Ступень | Людей онлайн | Запросов/с (пик) | Открытых сокетов | Разгон / пик / спуск | Копия: БД / Redis / API задач (0,5 vCPU) / генераторов | Ворота |
|---|---:|---:|---:|---|---|---|
| `smoke` (обязательная проверка сборки) | ~200 | 60 | 100 | 1 / 5 / 0,5 мин | db.t4g.medium / t4g.small ×2 / 2 / 1 | — |
| **`u1k`** | 1 000 | 500 | 1 000 | 3 / 10 / 2 мин | db.r7g.large / r7g.large ×2 / до 12 / 1 | зелёный `smoke` |
| **`u10k`** | 10 000 | 5 000 | 20 000 | 4 / 9 / 2 мин | db.r7g.2xlarge / r7g.xlarge ×2 / до 40 / 5 | зелёный `u1k` |
| **`u100k`** | 100 000 | 15 000 (см. ниже) | 100 000 | 5 / 8 / 2 мин | db.r7g.4xlarge / r7g.xlarge ×2 / до 48 / 6 | зелёный `u10k` |

Каждая ступень ≤ 15 минут нагрузки, копия живёт 1–1,5 ч (создание ≈ 25 мин, засев ≈ 10 мин,
нагрузка 15, удаление ≈ 15).

**Честно про 100 000.** 100 000 человек онлайн — это ≈ 50 000 запросов/с. Один PostgreSQL и
48 задач API по 0,5 vCPU (жёсткий потолок одного запуска, `loadtest/profiles.json limits`) этого не
дадут ни при каких индексах: по замерам задача 0,5 vCPU держит ≈ 30 запросов/с, 48 задач ≈ 1 500.
Поэтому ступень `u100k` — **поиск предела**: 6 генераторов просят 15 000 запросов/с и держат
100 000 сокетов; ожидаемый итог — **ABORTED или MISSED с точной цифрой, на скольких людях и где
упёрлось** (отчёт: *Per endpoint*, *Heaviest SQL*, CloudWatch). Это и есть ответ на вопрос «сколько
выдержим». Дальше — шардинг базы (в коде уже есть маршрутизация по шардам) и 1 vCPU на задачу
API; это отдельные решения владельца, не этот тест.

Что проверяется в каждой ступени (смесь `lib/mix.js`, доли итераций): старт приложения 8 %,
лента 16 %, рилсы 8 %, профиль юриста 8 %, пост 3 %, поиск 8 %, чаты 17 % (список / открыть /
отправить, доставка меряется по сокету), уведомления 5 %, дела и ставки 7 %, админка 5 % (списки,
поиск, один экспорт на ~300 действий), статика через CloudFront 10 %; плюс сокеты (держать,
комнаты, буря переподключений) и сигналы звонков (`u1k` 5/с, `u10k` 60/с, `u100k` 100/с), без
медиа-трафика TURN (звонки через Cloudflare, его не грузим).

**Пробел (честно):** в смеси нет загрузки медиа (`POST /files/presign` → PUT маленького файла →
`POST /files/:id/confirm`). Добавлять только после локального прогона (`loadtest/run-local.sh`):
непроверенный код k6 валит весь запуск на старте. Дизайн готов: действие `upload`, вес 2,
3 запроса, `purpose=post_image`, 4 КБ WebP, sha256 через `k6/crypto`, в копии хранилище — S3
копии (R2 в копии не подключён: `media.public_store = aws`, операций R2 = $0).

Регистрация/вход по СМС **не нагружаются**: в репозитории нет СМС-заглушки для копии, суите
запрещено трогать `/auth/otp` (`lib/http.js`), токены сидовых аккаунтов выписываются ключом JWT
копии (`mint.mjs`). Вход по паролю (без СМС) можно добавить тем же способом позже.

SLO-ворота для `u*` (в `profiles.json → budgets`): **p95 API < 300 мс**, доля ошибок < 0,2 %
(в k6 ошибкой считается и 4xx, поэтому не ровно 0; **5xx = 0** проверяется в отчёте по счётчику
ALB `HTTPCode_Target_5XX`), сокеты подключились ≥ 95 %, доставка в чат ≥ 98 % и p95 < 2 с,
звонки ≥ 95 %. Авто-стоп остаётся прежним (ошибок > 5 % или p95 > 2 с за 60 с).

## 4. Где выполняется и выключатель

- Копия и генераторы — Terraform `infra/envs/loadtest` (готов), одна команда workflow. Генераторы:
  `c7g.xlarge` Spot (4 vCPU, ≈ 1 500 зап/с на vCPU), в публичной подсети копии, с группой
  безопасности задач (видят RDS/Redis для засева), без входящих портов, команды через SSM.
- Запуск: `scripts/perf/run-loadtest.sh ladder --go` (или `start u1k --go`) → workflow печатает
  цену, **ждёт одобрения владельца** (окружение GitHub `load-test`), создаёт, грузит, удаляет.
  Без `--go` всё в режиме «показать, что будет».
- **Выключатель:** `scripts/perf/run-loadtest.sh kill --go` = отмена запуска в GitHub. Шаги
  `always()` workflow тогда **сразу удаляют копию** (3 попытки, потом зачистка по тегу); часовой
  сторож — вторая сеть; `scripts/perf/loadtest-cleanup.sh` — доказательство, что ничего не
  осталось (API тегов AWS). Ручного удаления на проде нет и не нужно.
- Жёсткие потолки одного запуска, которые нельзя превысить и по ошибке: 2 ч стены, 48 задач API,
  12 воркеров, 6 генераторов (Terraform `validation` + `check-profiles.mjs`), один запуск
  одновременно (`concurrency: load-test`).

по цене on-demand (Spot дешевле, не занижаем).

Пример строки (u10k): база `db.r7g.2xlarge` 1,5 ч × $1,104 + диск 50 ГБ gp3 за 1,5 ч = $1,67;
API 1,5 ч × в среднем 28 задач × $0,0247 (0,5 vCPU + 1 ГБ) = $1,04; WAF 2,65 млн запросов ×
$0,60/млн + 2 набора правил за 1,5 ч = $1,64; CloudFront 20 ГБ × $0,085 + 0,83 млн запросов ×
$0,0075/10k = $2,33. Полные таблицы печатает `scripts/perf/run-loadtest.sh price`.

Что ещё считать:
- **Автомасштабирование прода во время теста — $0:** прод в тесте не участвует, его ECS/RDS/Redis
  не растут. Копия сразу создаётся нужного размера (таблица §3); её автоскейл задач API внутри
  потолка профиля уже в строке «API+воркеры».
- **CloudWatch:** метрики копии стандартные (бесплатно), логи ≈ 1 ГБ × $0,50, в строке «ключи,
  логи»; Performance Insights 7 дней — бесплатный уровень.
- **R2:** в копии не используется — $0. **Трафик наружу:** генераторы в том же регионе — только
  $0,01/ГБ между ними и ALB (строка «Трафик»); отчёт в S3 и артефакты GitHub — копейки.
- **GitHub Actions:** раннер почти простаивает (нагрузку дают машины AWS) — в пределах лимита.
- Настоящую сумму покажет Cost Explorer через сутки по тегу `Project = lawbid-loadtest`.

## 7. Безопасность и что смотреть

- **Данные.** Сидовые люди, чаты, файлы, сообщения живут только в копии; `terraform destroy`
  удаляет базу, бакеты, Redis и генераторы вместе — «удалить тестовых пользователей одним
  скриптом» = `scripts/perf/loadtest-cleanup.sh` (доказательство по тегам; `--sweep` — зачистка
  по тегу как последняя мера). На проде ни одной тестовой записи не создаётся.
- **Лимиты и WAF.** На проде ничего не ослабляем. В копии WAF-лимиты на IP уже сняты
  (`waf_rate_limit_per_5m = 2 000 000 000` в `infra/envs/loadtest/main.tf`: 6 адресов генераторов
  иначе блокировали бы сами себя), лимит API «100 запросов/мин на человека» остаётся и
  тестируется; лимит сокетов на IP поднят SQL-вставкой (§6). Белый список для IP генераторов на
  проде не нужен — прод не трогаем.
- **Что смотреть во время запуска** (отчёт + CloudWatch копии): ALB 5xx и p95, здоровые задачи
  API vs потолок профиля (упёрлись в потолок = поднимать `api_max_tasks` в tfvars + profiles.json),
  CPU/подключения базы (< 80 %), Redis память/CPU, возраст очереди воркера, `dropped_iterations`
  (> 0 = не успевают генераторы, не сервер), доля подключённых сокетов, доставка в чат.
- **Авто-стоп:** ошибок > 5 % или p95 > 2 с за последние 60 с (каждые 5 с, ≥ 200 запросов в
  минуту) → стоп нагрузки, сбор, удаление, красный запуск с причиной. Денежный сторож — отмена при
  100 % `confirm_cost`. Стена 2 ч. Часовой сторож. Проверка «ничего не осталось» в конце.
- **Прод до/после:** `node scripts/ops/synthetic-check.mjs https://api.lawbid.dev` до и после
  каждого запуска — доказательство, что прод не задело (он и не должен был).

## 9. Что мешает сейчас (чинить до шага 5)

Все 8 запусков кнопки на AWS (24.10 ×6, 02.11 ×2) красные. Последние два — ещё до создания копии,
деньги не тратились:
1. `lawbid-pgbouncer:1.24.0-1 not in ECR` — образ пулера не был собран. **Уже собран** (отчёт
   09.11, `docs/dev/OWNER_ORDERS_2026-11-08.md`), `check` это проверяет.
2. Пустой тег образа API: `describe-images ... [-1].imageTags[0]` вернул `None` (у самого свежего
   образа нет тега) → `imageTag=None` → ошибка. Чинится передачей тега (`IMAGE_TAG=<sha> run-loadtest.sh
   start ...`) или правкой выбора тега на «самый свежий образ **с тегом**» — в следующем PR вместе
   с результатом локальной ступени (без прогона править workflow «на глаз» запрещено правилом
   одного пуша).
